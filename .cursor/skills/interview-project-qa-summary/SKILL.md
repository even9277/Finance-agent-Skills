# 项目 / 实习面试问题总结

把**简历上的项目点**写成面试官能听懂的「问题 + 回答」文档：先**锚定仓库里的实现位置**，再讲**原理、取舍、上线与突发**；与纯八股不同，**必须结合本仓库、简历表述与同文档里已有问答**，做到**前后统一、便于串讲**，并**如实标注已实现 / 未实现 / 建议补**。**产出文件路径、简历路径由用户在当轮调用中指明**（未指明时再问）。

## 何时启用

- 用户要整理**项目面、实习面**的深挖问答，或往 `interview-doc/*.md` 里**按编号追加**题目与回答。
- 用户提供**问题编号**（或主题），并希望你结合 **resume / 代码 / 设计文档** 写回答。
- 用户要求：**只给路径+行号不贴代码**、**大厂实践 + 本项目对照**、**与简历一致性说明**。

> 与 `interview-bagu-qa-summary` 分工：八股 skill 偏**通用后端理论与贯穿案例**；本 skill 偏**本项目实现与工程叙事**。

## 一、阅读文档（流程）

1. **读用户当轮约束（路径由用户在本轮指明）**  
   **产出 Markdown 路径**、**简历/项目描述文件路径**（如 `.tex` / `.md`）、题目编号规则（如继续 `### N`）、是否允许贴短代码（默认**不贴代码，只路径+行号**）、语言（默认简体中文）。用户通常在调用时一并给出；**若本轮未给出路径，先简短询问再写入**。

2. **读简历 / 项目描述（用户给出的路径）**  
   标出本轮问题对应的**成果点表述**，写作时与代码锚点**对齐**；末尾**简历↔代码**一致性段须可对照该文件中的原文措辞。

3. **读同文档已有问答（保证前后统一）**  
   除读尾部接编号外，须结合**同一产出文件**内已有内容，避免新题与旧题矛盾：  
   - **开篇总述 / 背景段**（若有）：业务边界、用户画像、技术栈叫法与后文保持一致。  
   - **相邻或主题相关的 `###` 题**：术语（如 category / 混合检索 / 工作流节点名）、口径（「已实现/规划中」）、举例型号或场景与前后题**统一**；必要时**简要呼应**前题结论（不重复粘贴全文）。  
   - 若新题与旧题表述冲突，**以代码事实为准**，并在本题 **「与简历&现状的一致性说明」** 中点明如何统一口径或建议改旧题措辞。

4. **读仓库（检索而非通读）**  
   用语义搜索/精确搜索定位：检索入口、配置、数据流、与问题强相关的模块。**禁止臆造路径**；找不到则明确写「当前仓库未检索到对应实现」，并给**建议落点**或**大厂常见做法**。

5. **读产出文件尾部（若追加）**  
   读用户指定 Markdown **最后约 80～120 行**，确认最后一个 `###` 编号，新题从 **N+1** 连续编号（除非用户要求另起一套编号）。

6. **读文件内注释型「需求说明」（若有）**  
   例如 `<!-- 需求复述 -->`：与 skill 冲突时**以用户当轮对话为准**，其次以该注释为准。

## 二、具体分析（流程与策略）

**1. 先锚定证据，再展开叙述**

- 在回答靠前位置给出 **「对应代码位置」**：`路径/文件.py` + **行号范围**（可多文件）；**不粘贴大段代码**（除非用户明确要求展示片段）。
- 再按 **Step1 / Step2 / Step3…** 展开；每一步可用 **加粗短语** 做小标题，**不用 `####` 及以下层级标题**。

**2. 叙事顺序（可合并段落，逻辑勿颠倒）**

- **业务与用户**：谁在用、解决什么痛点、典型 query 或场景（便于面试举例）。
- **问题定义**：面试官在问什么边界（必要时用「**这道题问的是：**」单独点明）。
- **设计与实现**：从 **0→1** 或 **数据流/调用链** 讲清；专业名词用 **（括号内一句人话解释）**。
- **工程取舍**：时间/成本/效果、技术债、可扩展点；**上线前如何测**、**线上突发如何降级/限流/重试**（若适用单独成 Step）。
- **大厂实践对照**：用**泛指**（不写虚构公司名），说明业界常见做法，再对照**本项目**是「一致 / 简化 / 未做」。

**3. 证据不足时的诚实策略**

- 代码没有、只有方案：写 **「当前项目未实现 / 仅部分实现」**，并给 **建议实现步骤或文件落点**。
- 与简历表述不一致：在回答**最后单独一段**写 **「与简历&现状的一致性说明」**，方便用户后续改简历或改代码。

**4. 三角对齐（代码 + 简历 + 同文档问答）**

- **代码**：路径+行号为事实来源；叙述不超出已锚定范围夸大。  
- **简历**：用词与量化表述尽量可对照；不一致时在末段说明。  
- **同文档其他题**：业务设定、模块命名、设计结论**一脉相承**；新题是前题的延伸时，用一句话承接（例如「承接第 3 题中的混合检索…」），方便面试官听懂整条故事线。

**5. 专业表达**

- 语言**凝练**、面向**完全不了解项目的面试官**也能跟上。
- **层次用 Step + 加粗**，与目标产出文件中已有题目排版**保持一致**。

## 三、输出要求（硬性）

| 项 | 规则 |
|----|------|
| 题号与标题 | **`### N、…`** 与 **`### N. …`** 均可；**与同文件已有小标题风格保持一致**；编号与目标文件已有题目**连续** |
| 代码引用 | **默认只写「文件路径 + 行号」**，不写长代码块 |
| 回答区标题 | **禁止** `####` 及以下；用 **`**加粗**`** 与 **Step1/2/3** |
| 名词 | 关键术语 **（括号补充）** |
| 前后统一 | 业务场景、模块/配置叫法、与前几题的结论**不打架**；必要时一句**承接前题** |
| **口述提示** | **默认每题回答末尾必含** **`**口述提示：**`**：用 **一至两句** 说明面试时**先答什么、再展开什么**（可与要点呼应，**勿重复粘贴正文**） |
| 结尾 | **「与简历&现状的一致性说明。」** 段建议保留（已实现 / 未实现 / 建议补；与简历是否一致） |
| 分隔 | 题与题之间可用 `---`（若用户文件已采用） |

**可选**：用户明确要求时，可附**极短**伪代码或接口名；默认仍以叙述 + 行号为主。用户或 `要求.md` 写明**关闭口述提示**时，省略 **口述提示** 块。

## 四、执行清单（每次任务）

```
- [ ] 用户已指明产出路径与简历路径（未指明则问）；读文件尾部与内联需求注释
- [ ] 读同文档开篇/相关题，术语与口径与前后问答统一
- [ ] 搜代码/配置，列出「路径 + 行号」锚点（无则注明并给建议）
- [ ] Step 叙事：场景 → 边界 → 实现 → 取舍 → 测试/突发（按需）→ 大厂对照
- [ ] 禁止 ####；专业词括注；末段「与简历&现状的一致性说明」
- [ ] 默认增加 **口述提示**（用户关闭则跳过）
```

## 五、用户可覆盖的默认

| 项 | 默认 |
|----|------|
| 产出路径 / 简历路径 | **以用户当轮调用中指明为准**；本轮未给则询问 |
| 题头格式 | `、` 与 `.` 均可，**跟随同文件已有题目** |
| 口述提示 | **默认开启**；用户或 `要求.md` 明确关闭则省略 |
| 代码展示 | 仅路径+行号 |
| 语言 | 简体中文 |
