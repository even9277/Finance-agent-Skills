# 简历 LaTeX 成果点优化

在用户编写或润色 **LaTeX 简历**（尤其是 `\item` 技术成果点）时，按 **阅读文档 → 具体分析 → 输出** 执行；与 **代码事实、用户当轮要求、面试问答文档** 三角对齐，**叙事可贯通、面试可讲清、真实可信** 即可。

## 用户既定偏好（默认遵守）

- **经历边界**：同一段实习下的 `\item` **允许混用** 公司实习与个人/横向项目中的工作；**以代码与用户当轮要求为准**，不强制拆段，但须 **前后逻辑贯通**（面试能一口气讲圆），**禁止** 为混写而虚构统一代码库或统一上线事实。
- **数字口径**：**不写** 明显失真、超出实习生日常职责范畴、或 **过于夸张** 的指标；延迟/QPS/准确率等 **仅在有文档、代码或可复述依据时写入**，否则用定性表述或删数字。
- **职责层级**：默认采用 **大厂实习生视角**——动词优先 **「实现 / 优化 / 落地 / 参与」**；**避免** 「设计」「主导」「架构（作动词）」等易被追问为 Owner 的表述，除非用户明确声称且可举证。
- **目标文件**：**不设仓库内默认路径**；每轮润色以 **用户指明的 `.tex` 路径** 为准；若有英文版同步需求，由用户当轮说明。

## 何时启用

- 用户要优化 `resume.tex` / `*.tex` 中的 **实习经历、项目经历** `\item`。
- 用户要把 **面试文档**（如 `interview-doc/*.md`）里的技术叙事 **压缩成简历一句话或多句 LaTeX**。
- 用户询问：成果点是否 **超出实习生工作量**、是否 **与代码一致**、如何写 **异步/记忆/多租户** 等表述。

## 一、阅读文档（流程）

按顺序完成；**缺路径时先向用户确认**。

1. **用户当轮约束**  
   **目标 `.tex` 路径（必指）**、语言（默认简体中文）、本轮要改的 `\item` 或主题；若混写多来源，用户可说明 **各点对应代码/仓库/文档**——未说明时以 **代码检索 + 用户补充** 对齐。**禁止** 替用户编造未出现的指标与职责。

2. **当前简历原文**  
   读出待改 `\item` 全文，标出 **技术名词、量化数字、动词层级**；将 **偏「设计/主导」** 的措辞标为待降级为 **实现/优化**（除非用户明确要求保留）。

3. **面试/备忘文档（若存在）**  
   读用户给出的 `interview-doc/*.md` 或与该 bullet **同主题** 的段落：问题背景、方案、**真实指标**（延迟、准确率、窗口大小等）。**数字与口径以文档+代码为准**，简历不得写文档未支撑的结论。

4. **代码库（当 bullet 声称具体实现时）**  
   用搜索定位相关模块，核对：**是否真有该机制**、**实现细节是否与简历动词匹配**（例如「并行」vs「线程池 offload」）。找不到实现则标为 **未验证**，建议改措辞或标「方案/预研」。

5. **写作风格样例**  
   同文件内 **相邻 `\item`**：保持 **加粗习惯**（`\textbf{}`）、**句式节奏**（先场景/问题，再技术，再效果）、**LaTeX 转义**（`_` → `\_`，`%` 等）。

## 二、具体分析（策略）

**1. 三角对齐（简历 ↔ 代码/事实 ↔ 面试文档）**

- 简历中的 **专有名词、架构角色、数字** 须在另外两角 **至少一角** 有依据。
- **冲突时以可验证事实为准**（代码路径、可复现指标、用户确认的实习范围），并 **给出建议改法**（降一级动词或移到正确项目）。

**2. 实习生视角与混写叙事**

- **默认动词**：**实现、优化、落地、参与、改造**；避免 **设计、主导、独立架构** 等除非用户书面确认且证据充分。
- **混写多来源**：允许落在同一段实习叙述中，但输出与面试口径需满足：**能说明各技术点分别对应哪类工作**（如「在业务系统中实现…；同期在验证性模块中…」），且 **不与代码事实矛盾**；若用户选择一条线串讲，代写 **一句承上启下的逻辑钩**（不编造项目组织关系）。
- **单段实习篇幅**：总 bullet 深度仍须像 **实习生贡献**；忌堆成「全栈 Owner 年报」。

**3. 技术表述精确性（常见坑）**

- **异步**：区分 **fire-and-forget**、**`run_in_executor`/`asyncio.to_thread`**、**原生 async I/O**；勿写 **「向量生成与写入并行」** 若代码实为 **串行准备数据 + 线程池写库**。
- **多租户/隔离**：**字段 filter** 勿夸大成 **DB 层 namespace/partition**，可写 **「按 user 字段过滤」** 或 **「用户级数据隔离」**。
- **记忆分层**：**短期**（会话内、内存/关系库）与 **长期**（跨会话、向量库）**分属不同存储是业界常态**；简历中若两点并列，需 **各自对应真实工作**，避免面试官追问时穿帮。

**4. 简历句式策略（与面试文档互证）**

- **前半**：场景/痛点 + 技术栈/模块 + 核心手段（加粗 2～4 个关键词）。
- **收尾（可选一句）**：**针对 {具体问题}，采用 {方案}，{可量化效果}** —— 数字须 **非夸张、属实习生可观测范围**，且有 **文档/代码/用户确认**；否则 **定性** 或 **不写数字**。

**5. 诚信与面试防御**

- 对每个 bullet 自问：**面试官让画架构/指代码时能否接住**？接不住则 **降级表述** 或 **移到真实项目**。

## 三、输出要求（硬性）

| 项 | 规则 |
|----|------|
| **格式** | 直接给出可粘贴的 LaTeX：`\item \textbf{小标题：} …` |
| **加粗** | 关键技术用 `\textbf{}`，与文件内其他 `\item` 一致 |
| **转义** | LaTeX 特殊字符：`%` `$` `&` `_` `#` 等按 TeX 规则转义（如 `asyncio.to_thread` → `asyncio.to\_thread`） |
| **数字** | 仅使用 **用户文档/代码/用户当轮确认** 的指标；无依据不写具体百分比/毫秒 |
| **篇幅** | 单条 `\item` 建议 **2～4 句** 或 **1 长句 + 1 效果句**，避免堆满五个技术点 |
| **交付物** | **润色后的完整 `\item` 文本**；必要时 **另起简短「一致性说明」**（简历 vs 代码 vs 文档差异及建议） |

## 四、可选：仍可向用户确认的情况

仅在 **无法从代码或已有文档判断** 时简短追问，例如：某指标是否 **允许对外写**、某句是否 **必须保留强动词**；**不重复追问** 已在本节「用户既定偏好」中写死的规则。
