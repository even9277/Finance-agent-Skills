# 观测与评估系统优化开发计划

> **写给谁看**：这份文档是给完全不懂技术的人写的。我们会尽量用生活中的比喻来解释。比如"会话"就像一次电话通话，"提示词"就像给员工下达的工作指令，"trace（追踪记录）"就像工厂流水线上每一步的操作日志。
>
> **文档用途**：这份计划是后续开发人员（包括 Codex AI）按步骤执行改造工作的"施工图纸"。每一步说清楚改哪些文件、怎么验收。

---

## 1. 背景与目标

### 1.1 为什么要做这件事

现在的系统已经能对话、能查数据、能给出投研建议，功能上跑通了。但有一个很大的问题：

> **我们根本不知道系统内部在每次对话时究竟发生了什么。**

打个比喻：就像你开了一家餐厅，菜做出来了，但你不知道厨师是怎么做菜的、哪道菜花了多长时间、哪个环节可能出了问题、客人为什么觉得味道不对。这样的话你永远无法提升菜品质量。

我们现在面临的具体问题：

1. **看不清过程**：用户发一条消息，系统经过"路由→实体解析→改写→规划→工具调用→总结"多个步骤才给出回答，但我们不知道哪一步出了问题、每步花了多少时间
2. **没有对话记录本**：每次对话结束后没有留下一份"人能读懂的复盘报告"，想回头分析很难
3. **提示词散落各处**：告诉AI怎么工作的"工作指令"（提示词）分散在十几个不同的代码文件里，想修改一条指令要找半天，改了之后也不知道效果有没有变化
4. **评测数据孤立**：已经有一些自动化测试（如路由测试、实体测试），但测试结果不和实际对话记录连在一起，无法追问"这次测试差的原因是什么"

### 1.2 我们想达到什么目标

完成这次改造后，要实现：

**（一）每次对话都有完整记录**
- 自动生成一份结构清晰的对话报告（Markdown 格式，人能读懂）
- 同时保留机器可以分析的 JSON 格式记录
- 按"会话"命名文件：比如一次连续聊天对应一个文件，里面包含这次所有对话轮次

**（二）看清楚每一步发生了什么**
- 路由（判断用户问什么类型的问题）有没有判对
- 实体解析（找出用户说的是哪只股票）准不准
- 查询改写（把用户的口语化问题变成精准的搜索语）有没有保留关键信息
- 工具调用（实际去查股票数据）成功了还是失败了
- 计划生成（规划要查哪些数据）质量怎么样
- 证据核验（检查数据是否支撑结论）过没过关
- 最终回答生成 有没有完整对应用户问题

**（三）提示词统一管理**
- 所有"工作指令"集中放在一个地方
- 每条指令都标明版本号（比如 v1.0），方便追踪"用哪条指令产生了这个效果"
- 修改指令前后效果对比有据可查

**（四）评测系统和实际对话打通**
- 已有的自动化测试能产出趋势图（今天比昨天好了还是差了）
- 发现问题的对话能方便地"标记为需要分析"

### 1.3 什么不做（范围边界）

以下内容**不在这次计划范围内**：

- 不修改任何对话逻辑、工具调用逻辑（核心功能不动）
- 不引入Redis缓存等性能优化
- 不做前端界面的观测展示
- 不做数据保留期限自动清理
- 不做坏案例（bad case）的完整标注体系（后续单独规划）
- 不强制立即启用\"文件+数据库双写\"（本期先保留数据库落库选项，默认关闭）

## 3. 验收标准

完成这次改造，必须满足以下条件才算验收通过：

### 验收项 A：观测总开关可以工作

- 在配置文件里把 `ENABLE_SKILL_TRACE=false` 改成 `false`，整个系统运行正常，不写任何日志
- 改成 `true`，恢复正常记录

### 验收项 B：会话 Markdown 报告自动生成

- 发送一条消息后，在 `Financial-MCP-Agent/logs/session_reports/` 目录下自动生成一个以会话ID命名的 `.md` 文件
- 文件里包含：对话时间、用户问题、最终回答、各阶段耗时汇总
- 同一会话的第二条消息，**追加**到同一个文件末尾（不是新建文件）

### 验收项 C：全链路 span 覆盖

发一条触发完整链路的问题（比如"帮我看看贵州茅台最近能不能买"），在 `chat_traces.jsonl` 里能找到以下所有阶段的记录条目：

| 阶段名 | 说明 |
|---|---|
| `route_stage1` | 第一层路由（是问数据还是闲聊） |
| `route_stage2` | 第二层路由（具体走哪条技能） |
| `entity_resolve` | 实体解析（找出"贵州茅台"对应代码） |
| `query_rewrite` | 查询改写（把问题规范化） |
| `plan_generate` | 计划生成（规划要查哪些工具） |
| `tool_execute` | 工具执行（实际查数据） |
| `evidence_verify` | 证据核验 |
| `synthesis` | 回答生成 |
| `stm_compress` | 短期记忆压缩（如触发） |
| `ltm_write` | 长期记忆写入（如触发） |
| `skill_executor` | 技能执行（如走技能路径） |

### 验收项 D：提示词集中管理

- `Financial-MCP-Agent/src/prompts/` 目录存在，里面有各模块对应的提示词文件
- 每个提示词文件有版本号常量（如 `PROMPT_VERSION = "v1.0"`）
- 原来代码文件里的提示词全部改为从 prompts 目录引用
- 现有功能测试（pytest）仍然通过

### 验收项 E：评测报告有趋势字段

运行 `python tests/evals/runner.py --target route --mode smoke` 后：
- 输出的 JSON 文件里有 `timestamp` 字段（记录本次运行时间）
- 运行两次，可以看到两份带时间戳的历史记录

### 验收项 F：数据库落库选项可用（默认关闭）

- 配置 `ENABLE_TRACE_DB_SINK=false` 时：系统只写文件（JSONL + Markdown），不访问数据库
- 配置 `ENABLE_TRACE_DB_SINK=true` 且数据库配置齐全时：新产生的 trace 能写入数据库观测表
- 任一模式下，对话主流程均不报错（数据库写入失败时不影响主回答）

## 7. 差距与风险

### 主要差距

1. **埋点覆盖率不足**：9个关键阶段中，只有 2 个有完整埋点（`skill_executor_node`、`query_rewriter`），其余 7 个没有
2. **没有总开关**：目前有 `ENABLE_LANGFUSE`、`ENABLE_TRACE_PROMPT_CAPTURE` 等分散开关，但没有一个可以控制全部的总开关
3. **没有人可读的报告**：只有机器用的 JSONL，没有人能方便阅读的 Markdown 会话报告
4. **提示词管理混乱**：17 个文件内嵌提示词，没有版本号，无法追踪"用了哪版指令产生了这个结果"
5. **评测孤岛**：测试在跑，但结果没有时间线，不知道好了还是差了

### 风险与应对

| 风险 | 可能影响 | 应对方法 |
|---|---|---|
| 加埋点引入代码错误 | 某个阶段异常 | 每加一个埋点就先运行功能测试验证 |
| 提示词迁移后引用出错 | 功能失效 | 迁移后每个模块单独运行测试验证 |
| 报告生成影响响应速度 | 用户体验下降 | 报告写入异步进行，不阻塞主流程 |
| 提示词文件格式不一致 | 后续维护困难 | 制定统一模板，先做一个，其他照抄 |

## 8. 本地优秀 Agent 实践参考

查看本地参考项目，找到以下值得借鉴的模式：

### 来自本仓库 OpenClaw 参考方向（SOLUTION_TRADEOFF.md 中提及）

- **trace 总开关模式**：用单一环境变量 `ENABLE_SKILL_TRACE=true/false` 控制全部，细粒度开关在总开关开启时才生效
- **提示词外置策略**：提示词独立成文件，版本号写在文件顶部常量里

### 现有代码的好范例（可直接复用）

- `mem0_prompts.py`：已经是"提示词独立文件"的正确做法，其他模块迁移时照此格式
- `skill_trace.py` 的 `_bool_env` 函数：已有环境变量读取工具函数，总开关复用此函数

## 9. 外部开源与官方实践参考

### Langfuse 官方实践（来自 SOLUTION_TRADEOFF.md 研究结论）

- **会话分组**：通过 `session_id` 把同一个用户会话的所有 trace 归到一组，方便回溯
- **分层 span**：外层是"一次对话轮次"的大 span，内层是"路由""工具调用"等子 span

**本项目映射**：`skill_trace_context` 已实现大 span，子 span 用 `trace_span` 包裹 → 缺口是部分阶段还没用 `trace_span`

### OpenTelemetry 通用实践

- **报告与追踪分离**：Trace（追踪记录）负责机器分析，Report（报告）负责人工复盘，两者独立生成，不互相依赖

**本项目映射**：JSONL 是 Trace，新增的 Markdown 是 Report，分别写入不同目录，互不干扰

### Promptfoo（提示词测试工具）模式

- 每个提示词版本是独立文件，文件名包含版本信息
- 变更提示词时创建新版本文件，旧版本保留供对比

**本项目映射**：采用更简单的方案 —— 文件内用版本常量（`PROMPT_VERSION = "v1.0"`），修改时更新版本号并在注释里写明修改原因

## 11. 目标架构与实现方案

### 11.1 整体架构图（文字版）

```
用户发一条消息
        ↓
【总开关检查】ENABLE_SKILL_TRACE=true?
        ↓ 是
【会话追踪开始】生成/延续 session_id
        ↓
┌─────────────────────────────────────────┐
│ 各阶段执行（每阶段用 trace_span 包裹）    │
│  路由 → 实体解析 → 改写 → 规划 →        │
│  工具调用 → 证据核验 → 回答生成          │
│  （同时：STM压缩 / LTM写入 异步进行）    │
└─────────────────────────────────────────┘
        ↓
【双路输出】
  ├── JSONL 追加写入（机器分析用）
  │     logs/chat_traces.jsonl
  └── Markdown 追加写入（人工复盘用）
        logs/session_reports/{session_id}.md
        ↓
【可选：Langfuse 上传】
  （如果 ENABLE_LANGFUSE=true，异步上传）
```

### 11.2 新增的会话 Markdown 报告格式

每个 `.md` 文件的内容格式如下（每次对话结束后**追加**一个"轮次"章节）：

```markdown
# 会话报告 · {session_id}

_首条消息时间：2026-05-28 21:30:00_

---

## 第 1 轮对话 · 2026-05-28 21:30:05

**用户提问：** 帮我看看贵州茅台最近能不能买

**系统回答：** （前200字摘要）...

**执行概览：**

| 阶段 | 耗时 | 结果 |
|------|------|------|
| 路由判断 | 120ms | tushare路径 |
| 实体解析 | 85ms | 贵州茅台 600519.SH |
```

## 13. 数据库与契约变更

本计划调整为：**默认继续文件落盘（JSONL + Markdown），同时保留数据库落库选项（默认关闭）。**

### 13.1 总体原则

1. **不动现有业务表**：不改会话、消息、用户画像等业务表结构  
2. **新增独立观测表**：trace 数据单独建表，避免污染业务库  
3. **默认关闭数据库写入**：先跑通文件方案，再按需开启数据库落库  
4. **不要求立即双写**：本期不强制\"文件+数据库同时写\"，先保留开关能力  

### 13.2 建议最小表结构（观测专用）

> 说明：下面是\"最小可用\"方案，便于后续查询与排障。

1. `trace_sessions`（会话级）
- `id`（主键）
- `session_id`（唯一）
- `user_id`
- `started_at`
- `updated_at`
- `meta_json`（jsonb）

2. `trace_spans`（阶段级）
- `id`（主键）
- `trace_id`
- `session_id`
- `span_id`
- `parent_span_id`
- `stage_name`
- `status`
- `started_at`
- `ended_at`
- `duration_ms`
- `data_json`（jsonb）
- `created_at`

### 13.3 索引建议

- `idx_trace_spans_session_created`：(`session_id`, `created_at` desc)
- `idx_trace_spans_trace_id`：(`trace_id`)
- `idx_trace_spans_stage_created`：(`stage_name`, `created_at` desc)

### 13.4 开关与回滚策略

- 新增开关：`ENABLE_TRACE_DB_SINK`（默认 `false`）
- 开启后写库失败：记录错误日志并降级为仅文件落盘，不中断主流程
- 回滚方式：关闭 `ENABLE_TRACE_DB_SINK` 即可快速回退到纯文件模式

```python
MODULE_NAME_PROMPT = """
```
