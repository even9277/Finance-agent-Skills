目前材料里有一个共同结论：**真正的大厂工程师不是每天只写代码，而是在“需求理解—方案设计—开发联调—上线监控—故障排查—复盘改进”的闭环里工作**。AI 让写代码更快了，但也把人的核心价值推向了 **问题定义、架构判断、验证与兜底**。

**我的判断是：你未来不要把自己定位成“会调 API 的 Agent 开发”，而要定位成“能把业务问题拆成工程链路，并用 Agent/RAG/后端系统稳定解决的人”。**  
现在 AI 确实会让“单纯写代码”变得越来越便宜，但大厂真正需要的人，**是能判断需求是否合理、方案是否可落地、系统哪里出问题、怎么验证修复效果、怎么让下一次不再出问题的人。**

****

一、真实的大厂程序员每天到底在做什么？

从经验帖看，大厂后端实习生或新人一开始不是马上写核心代码，而是先读业务文档、熟悉组内系统、看内部平台和开发规范；之后通常从改字段、查 bug、优化查询逻辑、新增后台接口这类小需求开始，逐渐参与“需求拆解—编码—联调—测试—上线”的完整闭环，还会处理上下游咨询、值班问题、写周报和串讲文档。也就是说，大厂日常并不是“每天激情写算法”，而是大量围绕业务系统做规范化交付。

如果是 Agent / 大模型应用开发，日常问题会更偏“工程化调优”：比如 RAG 分块策略怎么设计、Memory 如何管理长对话、工具参数怎么稳定抽取、模型幻觉怎么兜底、流式输出怎么和工具执行配合。牛客上一位从后端转 Agent 的工程师就提到，Agent 开发不是“LangChain 一把梭”，真正落地会遇到 Skills Embedding、RAG chunk、Memory、幻觉、流式输出等工程问题，面试和工作看重的是能否把后端架构能力迁移到 Agent 系统中。

再往上看，成熟工程师每天做的事情会越来越像“问题负责人”：看告警、查日志、定位链路、判断是不是依赖服务、数据库、缓存、模型、工具、上下文或数据源的问题。阿里云关于链路追踪的案例里就指出，微服务系统里一次请求会跨多个服务、DB、缓存和第三方依赖，因此需要 traceId（一次请求的全链路标识）把调用路径、耗时、状态和相关日志串起来，避免排查问题时到处翻日志。



 AI 让开发工作从“怎么写代码”转向“**写什么、为什么这样写、边界条件是什么、架构是否一致、交付质量是否稳定**”。他们也强调，未来 3–5 年更现实的主流不是全自动 AI 程序员，而是人机协作：AI 负责生成、探索、初稿，人负责需求表达、方案判断、架构设计和质量把关。



 当用户说“回答不准、报告太慢、工具调用错、上下文丢了、结果不可追溯”时，你能把问题定位到具体模块，并给出可验证的修复方案。  



**三、遇到问题时，你应该固定使用这套分析流程**

第一步，**先定义问题，不要立刻改代码**。  
你要问清楚：问题表现是什么？影响谁？发生频率是多少？有没有可复现输入？期望结果和实际结果差在哪里？影响指标是什么？比如“Agent 报告慢”不能直接等价于“模型太慢”，而要拆成：路由耗时、RAG 检索耗时、工具调用耗时、外部 API 等待、LLM 生成耗时、前端流式展示延迟。Google SRE 在故障处理中也强调，事故发生后首先关注的是用户影响和止血，而不是一上来就追根因。

第二步，**收集证据，而不是凭感觉猜**。  
后端系统看日志、指标、trace、数据库状态、缓存命中率、异常堆栈；Agent 系统还要看 prompt、上下文包、工具参数、工具返回、模型中间推理摘要、最终引用证据。Google Cloud 的 Gemini Cloud Assist Investigations 也是从错误信息、日志片段、资源配置、监控指标等上下文开始，构建相关资源拓扑，再生成排查观察结果。

第三步，**按层拆解假设**。  
对你来说，可以固定拆成八层：**输入层**（用户问题是否模糊）、**路由层**（是否选错 Skill/工具）、**上下文层**（短期记忆、长期记忆、RAG 是否混入噪声）、**检索层**（召回是否命中）、**工具层**（参数是否错、API 是否超时）、**模型层**（是否幻觉或格式不稳定）、**后端层**（DB/Redis/接口/并发是否异常）、**观测层**（日志是否足够定位）。CloudWeGo Eino 的 Agent 示例也强调 ReAct（思考—行动—观察循环）适合故障排查：先理清可能原因，再查监控数据，再根据证据继续缩小范围，而不是盲目操作。

第四步，**先止血，再根治**。  
线上真实场景里，用户正在受影响时，第一目标通常不是写出最优雅的长期方案，而是先降级、回滚、限流、切备用、关闭高风险功能、返回保守答案。Google SRE 的事故流程明确把 mitigation（缓解/止血）放在 root cause（根因分析）之前，因为降低用户损失比马上找出底层 bug 更紧急。

第五步，**最小修复 + 回归验证**。  
不要大改一片。你应该先做最小修改，然后用单元测试、接口测试、离线 golden set（固定评测样本集）、trace 回放、A/B 对比来验证。比如金融 Agent 工具误选，你不是简单“改 prompt”，而是要拿 50–100 条历史问题，比较修改前后路由准确率、工具成功率、无效调用率、回答可追溯率。

第六步，**复盘并沉淀为 SOP / Skill / Playbook**。  
Meta 的 DrP 根因分析平台就把事故排查步骤抽象成 analyzers（可执行的调查剧本），并集成到告警和事故管理工具中，帮助工程师自动化执行排查流程，Meta 称该平台被 300 多个团队使用、每天运行 5 万次分析，并降低 MTTR（平均修复时间）20%–80%。这给你的启发是：你未来做 Agent 工程，不只是“解决这一次问题”，还要把解决过程沉淀成可复用的工具链、评测集、日志规范和故障手册。



以后遇到问题时，不要问“我是不是又不会一个新技术”，而要问：**这个问题属于哪一层？有没有证据？影响指标是什么？最小止血方案是什么？长期修复方案是什么？怎么验证？怎么沉淀成下一次可复用的机制？**

你真正要练的不是“永远学完所有新东西”，而是这句话：**把模糊问题具体化，把具体问题链路化，把链路问题证据化，把修复动作指标化，把经验沉淀为系统能力。**


## Vibe Coding
我先把你说的 **“webcoding”理解为 AI 辅助编程 / vibe coding / agent coding**，也就是用 ChatGPT、Cursor、Claude Code、Codex 这类工具帮助自己完成真实项目开发。

你的这套流程整体方向是对的，已经不是“让 AI 直接写代码”的低级用法。你已经有了几个很好的意识：**先理解项目架构、先做方案沟通、让 AI 查优秀实践、让 AI 生成计划、执行后看 diff、最后做测试和验收**。这些都是专业程序员使用 AI 的核心动作。Cursor 官方也强调，使用 coding agent 时最重要的变化就是 **先计划再编码**，并且要给 agent 明确上下文、可验证目标、测试和 lint 等反馈信号。([Cursor](https://cursor.com/blog/agent-best-practices))

但你现在的问题也很明显：你的流程虽然长，但还没有形成真正稳定的**工程控制链路**。你现在更像是“把一个大任务交给 AI 分阶段做”，但还没有完全做到“人类工程师掌控需求、边界、验证、风险、回滚和沉淀”。也就是说，你现在是在用 AI 辅助开发，但还没有完全进入专业程序员的 **AI-assisted engineering（AI 辅助工程化开发）** 状态。Addy Osmani 在 2026 年的 AI coding workflow 里也强调，成熟用法不是把愿望丢给 LLM，而是先定义问题、补齐需求和边界，再形成清晰规格和分步计划，之后才写代码。([addyosmani.com](https://addyosmani.com/blog/ai-coding-workflow/))

**你当前 SOP 最大的优点**

你最大的优点是：**你没有一上来就让 AI 写代码**。你会先让 AI 理解项目架构、梳理数据流、分析模块分层，再开始改动。这一点非常重要，因为很多 AI 编程失败都是因为模型不知道当前项目的真实结构，最后写出一套“看起来合理、但和项目完全不兼容”的代码。Claude Code 官方工作流也建议，进入陌生代码库时要先让模型做 codebase overview（代码库总览）、分析架构模式、关键数据模型、认证流程、项目约定等内容，再深入具体模块。([Claude Code](https://code.claude.com/docs/en/common-workflows))

第二个优点是：你有**方案先行意识**。你会让 AI 复述问题、查优秀实践、给多个方案、分析优缺点和 tradeoff（权衡，指不同方案之间收益和代价的取舍）。这很接近专业开发中的设计评审流程。很多经验帖也反复提到，AI 编程不能从“帮我写代码”开始，而应该先写一个 mini PRD（小型需求文档，描述问题、用户旅程、预期结果），再让 AI 规划方案。([GitHub](https://github.com/mqyqingfeng/Blog/issues/436))

第三个优点是：你已经有**验收意识**。你会让 AI 给出验收标准，也会自己通读计划、看改动片段、跑测试、看日志。这说明你已经意识到：AI 写出来的代码不能天然相信，必须通过测试、日志、diff review（代码差异审查）来确认。Claude Code 官方把“给模型一种验证自己工作的方式”称为最高杠杆动作之一，比如测试、截图、预期输出、lint、构建命令等。([Claude Code](https://code.claude.com/docs/en/best-practices))

**你当前 SOP 最大的问题**

第一个问题是：**需求定义还不够工程化**。  
你现在会让 AI 分析“我要优化哪里”，但还缺少一个固定的需求入口文档。专业开发里，不能只写“我要优化工具调用”或者“我要改记忆模块”，而要明确：问题现象是什么、影响范围是什么、预期行为是什么、不做什么、边界条件是什么、成功标准是什么。否则 AI 后面生成的计划再详细，也可能是在解决一个没有定义清楚的问题。

你可以固定在每次开发前写一个 **mini PRD**：

“当前问题是：……  
用户场景是：……  
当前系统表现是：……  
期望行为是：……  
不做的范围是：……  
验收标准是：……  
风险点是：……”

这一步看似慢，但会极大减少后面返工。

第二个问题是：**上下文管理容易混乱**。  
你现在会让通用大模型分析问题、查资料、生成方案，再让 coding model 执行。但如果这些上下文没有沉淀成结构化文档，后面的执行模型很容易丢失关键约束。Anthropic 官方明确提醒，coding agent 的上下文窗口会很快被聊天、文件内容和命令输出填满，性能会随着上下文污染而下降；无关任务之间要 `/clear`，长任务要压缩和保留关键决策。([Claude Code](https://code.claude.com/docs/en/best-practices))

所以你不能只依赖“把前面聊天记录贴给另一个模型”。更规范的做法是沉淀四个文件：

**SPEC.md**：需求、边界、预期行为。  
**ARCH.md**：当前代码结构、数据流、关键模块。  
**PLAN.md**：实施计划、涉及文件、函数级改动。  
**TEST.md**：验收标准、测试用例、运行命令、预期输出。

这样你换模型、换会话、换工具时，核心上下文不会丢。

第三个问题是：**你现在的执行粒度可能太大**。  
你会让 AI 生成“比较完整的计划”，再交给便宜模型执行。这个思路可以，但风险是：计划太大时，执行模型容易一次改很多文件，最后你很难审查，也很难定位问题。Cursor 官方提到，如果 agent 做出来的东西不符合预期，不要在错误代码上反复补救，而是应该回到计划，修改计划后重新执行；它也建议把计划保存到工作区，方便恢复和复用。([Cursor](https://cursor.com/blog/agent-best-practices))

专业程序员会尽量把任务拆成 **小 PR / 小 commit / 小 diff**。也就是一次只改一个明确目标，例如：

“只改路由判断，不改工具执行器。”  
“只加参数校验，不改业务逻辑。”  
“只补测试，不改实现。”  
“只重构日志，不改变输出行为。”

这样 AI 写错了也容易回滚，你自己也更容易看懂。

第四个问题是：**测试责任不能主要交给 AI**。  
你自己已经意识到了：现在你更倾向于让大模型做三轮迭代测试，但这个地方本质上应该由你来主导。AI 可以帮你写测试、跑测试、解释日志，但**测试目标和判定标准必须由你定义**。Builder.io 的 Cursor 使用经验里也提到，复杂任务最好让 AI 先写测试，再写代码，再运行测试并迭代到通过；但是人仍然需要看它是否跑偏，必要时要及时停止和校准。([Builder.io](https://www.builder.io/blog/cursor-tips))

所以不要再用“让它自己迭代三轮”这种模糊说法。你应该改成：

“根据 TEST.md 中的测试矩阵，依次运行单元测试、集成测试、接口测试、关键功能手动验证。每次失败必须输出：失败命令、错误日志、根因假设、修改文件、验证结果。最多连续修复两次；如果仍失败，停止并输出人工排查报告。”

这才是工程化测试。

第五个问题是：**缺少风险分级和权限控制**。  
AI 不是所有代码都可以随便改。比如改 UI 样式、补注释、加测试、改小 bug，风险较低；但改数据库迁移、鉴权逻辑、支付/金融计算、并发锁、缓存一致性、删除文件、批量重构，就是高风险任务。Claude Code 官方也建议通过权限 allowlist（允许列表）、sandbox（沙箱，限制文件系统和网络访问）、auto mode 等方式控制 agent 可以执行哪些命令，降低重复确认成本的同时保持安全边界。([Claude Code](https://code.claude.com/docs/en/best-practices))

你后面应该给 AI 明确写：

“禁止删除文件，禁止修改数据库迁移，禁止改环境变量，禁止引入新依赖，除非 PLAN.md 明确允许。”  
“只能修改 PLAN.md 中列出的文件。”  
“所有新增依赖必须说明原因、替代方案和影响范围。”  
“所有涉及认证、权限、资金、隐私的改动必须暂停并等待人工确认。”

这就是专业开发中的安全边界。

第六个问题是：**代码审查还不够体系化**。  
你现在会逐个看修改片段，这是对的，但还可以更专业。AI 写完代码后，你最好用“写代码的模型”和“审代码的模型”分离。Anthropic 官方建议可以用多个 session（会话）或 writer/reviewer 模式：一个会话负责实现，另一个干净上下文的会话负责审查边界条件、竞态问题、风格一致性等。([Claude Code](https://code.claude.com/docs/en/best-practices))

Cloudflare 在 2026 年分享的大规模 AI code review 也说明，单个模型加通用提示词会产生很多模糊建议和幻觉；他们后来改成多个专业审查器，分别检查安全、性能、代码质量、文档、版本和合规，再由协调 agent 去重和判断严重程度。([The Cloudflare Blog](https://blog.cloudflare.com/zh-cn/ai-code-review/))

你作为初学者不需要搞这么复杂，但可以模仿这个思路，至少分成四类审查：

**功能审查**：是否真的解决需求。  
**影响范围审查**：是否误改无关模块。  
**稳定性审查**：异常、超时、空值、并发、回滚是否处理。  
**安全审查**：是否泄露密钥、是否绕过权限、是否引入危险命令。

第七个问题是：**上线和回滚意识还不够强**。  
你现在说“处理完就上线，看项目启动之后效果怎么样”，这在个人项目里可以，但如果要按大厂标准训练，你需要在上线前问：

“这次改动能否回滚？”  
“是否需要 feature flag（功能开关，用来控制新功能是否生效）？”  
“是否改了数据库结构？”  
“失败后用户看到什么？”  
“日志能不能定位？”  
“有没有保留旧逻辑兜底？”  
“上线后看哪些指标？”

大厂程序员和普通使用者的区别就在这里：普通人只关心“功能能不能跑”，专业工程师还关心“坏了能不能发现、能不能止血、能不能回滚、能不能复盘”。

**我建议你把 SOP 改成 10 步专业版**

**第一步：问题入口，不许直接写代码**

每次任务开始时，你先写清楚：

“我要解决的问题是什么？  
这个问题属于 bug、功能、重构、性能优化，还是工程治理？  
影响用户是谁？  
当前表现是什么？  
期望表现是什么？  
成功标准是什么？”

这一步对应你之前总结的通用思考体系里的 **先分类、再定性、找场景**。

比如你要优化 Agent 工具调用，就不能只写“优化工具调用”，而要写：

“当前金融 Agent 在用户询问股票行情时，偶尔错误选择基金工具，导致回答延迟增加且结果不准确。本次目标是优化工具路由和参数校验，使 100 条离线问题集中工具选择准确率提升，并减少无效工具调用。不改动底层 Tushare API 封装。”

这就是一个合格入口。

**第二步：代码库侦察，先理解再修改**

你现在已经在做这一步，但可以更规范。你要让 AI 输出：

“项目目录结构是什么？  
入口文件在哪里？  
请求从哪里进来？  
核心模块有哪些？  
数据流怎么走？  
我要改的功能涉及哪些文件？  
有没有已有类似实现可以复用？  
有哪些代码规范必须遵守？”

Claude Code 官方也建议在陌生代码库里先问架构、关键模型、认证、日志、边界 case 等问题，就像问一个资深工程师一样。([Claude Code](https://code.claude.com/docs/en/best-practices))

这一阶段只读代码，不改代码。输出物是 **ARCH.md**。

**第三步：需求澄清，让 AI 反问你**

你现在会让 AI 复述你的问题，这很好，但还可以升级成“让 AI 采访你”。Claude Code 官方建议，大功能可以先让 Claude interview you（采访你），让它追问技术实现、UI/UX、边界条件、tradeoff 等问题，直到形成完整 spec，再开新会话执行。([Claude Code](https://code.claude.com/docs/en/best-practices))

你可以固定用这个提示词：

“先不要写代码。请你作为资深后端工程师，围绕这个需求反问我 8 个关键问题，重点覆盖：业务目标、边界范围、数据输入输出、异常情况、是否兼容旧逻辑、测试标准、上线风险、回滚方案。”

这一步会帮你补齐很多初学者想不到的点。

**第四步：方案设计，必须给 2–3 个方案和权衡**

你现在已经会让 AI 查优秀实践和开源项目，这是对的。但要注意：不要让 AI 查完就直接给结论，而要让它形成对比表：

“方案 A：最小改动。  
方案 B：结构化重构。  
方案 C：长期治理方案。”

每个方案都要说明：

“改哪些模块？  
收益是什么？  
代价是什么？  
风险是什么？  
适合什么场景？  
为什么本次选它？”

你作为初学者，很多时候应该优先选 **最小可验证方案**，不要一上来选最复杂的架构升级。因为你现在训练的是工程闭环能力，而不是炫技。

**第五步：冻结计划，写到函数级但不要过度设计**

你现在会让 AI 写到“每个函数怎么改、输入输出是什么”，这很好，但要注意不要让计划变成 100 条细节，反而让执行模型迷失。计划应该包含：

“涉及文件清单。  
每个文件的修改目的。  
新增/修改函数的输入输出。  
不允许修改的范围。  
测试命令。  
验收标准。  
回滚方式。”

这一步输出 **PLAN.md**。  
计划一旦确认，执行阶段不要随意扩展范围。需要新增范围时，必须先回到计划修改。

**第六步：小步执行，不要一次全改**

执行时不要把整个 PLAN.md 一次性丢给模型。你应该拆成任务队列：

Task 1：只补测试。  
Task 2：只改路由逻辑。  
Task 3：只加参数校验。  
Task 4：只加日志。  
Task 5：只做文档和清理。

每完成一个 Task，都要：

“看 diff → 跑对应测试 → 记录结果 → commit。”

Cursor 官方提到，agent 可以克隆 repo、开分支、完成任务并提交 PR，但最后仍然需要人工 review 和 merge。([Cursor](https://cursor.com/blog/agent-best-practices)) 你个人项目也应该模拟这个流程，用 branch 和 commit 训练自己。

**第七步：测试先行，至少先有验收用例**

你现在测试意识还在形成期。以后建议你强制要求每个任务都有三类测试：

**最小单元测试**：验证一个函数或模块是否正确。  
**集成测试**：验证几个模块串起来是否正确。  
**手动验收样例**：模拟真实用户输入，看输出是否符合预期。

如果是 Agent/RAG 项目，还要加一类：

**离线评测集**：比如 30–100 条固定问题，记录期望工具、期望证据、期望回答边界。

不要只让 AI “帮我测试三轮”。你要给它明确测试矩阵。AI 可以跑，但测试靶子必须由你定义。

**第八步：独立审查，写代码和审代码分开**

AI 写完之后，你不要只问原模型“你检查一下有没有问题”。因为它刚写完，容易对自己的实现有路径依赖。更好的方式是开一个新上下文，让另一个模型只看 diff 和需求文档，做审查。

你可以让审查模型按这个模板：

“请基于 SPEC.md、PLAN.md 和 git diff 做代码审查。不要重写代码，只输出问题。重点检查：是否偏离需求、是否误改无关文件、是否破坏兼容性、是否缺少异常处理、是否有安全风险、是否缺少测试、是否有性能问题。”

七猫技术团队关于 AI Code Review 的文章也提到，AI 时代开发者会从以写代码为主转向以看代码为主，除了 AI Review，还必须保留人工 Code Review 和单元测试来保障交付质量。([七猫技术团队](https://tech.qimao.com/ai-shi-dai-de-code-review-zui-jia-shi-jian-2/))

**第九步：上线前检查，必须有回滚和观测**

上线前你要固定检查：

“是否能启动？  
测试是否全部通过？  
是否有新增依赖？  
是否有数据库变更？  
是否影响旧功能？  
日志是否能看出关键链路？  
错误时是否有降级？  
是否能一键回滚到旧版本？”

对于你的金融 Agent 项目，还要看：

“工具调用成功率有没有变化？  
平均延迟有没有变化？  
错误回答有没有增加？  
是否有无法追溯的回答？  
是否调用了不该调用的工具？”

这一步不是形式主义，而是让你从“会写功能”升级到“能负责功能”。

**第十步：复盘沉淀，把经验变成规则**

每次任务结束，你要写一个很短的复盘：

“本次改了什么？  
解决了什么问题？  
遇到什么坑？  
哪些提示词有效？  
哪些测试发现了问题？  
下次应该加入什么规则？  
是否需要沉淀到 Cursor Rules / CLAUDE.md / Skills / 项目开发规范？”

Claude Code 官方也提醒，不要一开始就过度优化规则；应该从简单开始，只有当 agent 反复犯同一种错误时，再添加规则或命令。([Cursor](https://cursor.com/blog/agent-best-practices))

这对你特别重要。你现在已经在整理 prompt 和 flow 词，但一定要注意：规则不是越多越好，而是**越短、越明确、越能阻止重复错误越好**。

**你的新 SOP 可以压缩成这条主线**

以后你可以记住这套流程：

**需求定义 → 代码侦察 → 需求澄清 → 方案权衡 → 计划冻结 → 小步执行 → 测试验证 → 独立审查 → 上线观测 → 复盘沉淀。**

再进一步压缩成一句话：

**先让 AI 帮你看清问题，再让 AI 帮你生成方案，最后让 AI 帮你执行和验证；但需求边界、技术取舍、测试标准、代码审查和上线责任必须由你掌控。**

**你作为初学者最容易踩的坑**

第一个坑是：**把“AI 能跑通”误以为“代码质量合格”**。  
能启动只是最低标准。你还要看边界条件、异常处理、日志、可维护性、是否符合项目原有风格。

第二个坑是：**计划写得很漂亮，但执行时失控**。  
所以一定要小步执行、限制文件范围、限制改动目标。

第三个坑是：**测试只是让 AI 自己跑，而不是自己设计测试**。  
AI 可以生成测试，但你要判断测试有没有覆盖真实场景。尤其是你的 Agent 项目，必须有固定问题集，不然每次都是凭感觉判断效果。

第四个坑是：**长会话越聊越乱**。  
如果一个模型连续修两次还修不好，就不要继续在同一个会话里纠缠。Claude Code 官方也建议，如果同一个问题纠正超过两次，说明上下文已经被失败路径污染，应该清空上下文，用更好的初始提示重新开始。([Claude Code](https://code.claude.com/docs/en/best-practices))

第五个坑是：**把便宜模型用于高风险复杂任务**。  
便宜模型可以做格式化、补注释、小范围重构、测试样例生成，但涉及架构、权限、数据库、并发、金融计算、工具执行链路时，最好用更强模型做计划和审查。便宜模型可以执行低风险子任务，但不能替你做最终判断。

**你后续学习 web coding / AI coding，应该重点练什么**

你现在不应该只学“怎么提示 AI 写代码”，而应该练五种能力。

第一，练**读代码能力**：看到一个项目，能说清入口、模块、数据流、状态存储、外部依赖。  
第二，练**写需求能力**：能把模糊想法变成 SPEC.md。  
第三，练**拆任务能力**：能把一个大功能拆成 5–8 个小 diff。  
第四，练**验收测试能力**：能设计输入、期望输出、边界 case 和评估指标。  
第五，练**代码审查能力**：能看懂 AI 改了什么、为什么改、有没有副作用。

这五个能力，比单纯记更多框架 API 更重要。AI 越强，越需要你做 **需求负责人、架构审查者、测试设计者、风险控制者**。

**你可以直接使用的专业 AI 编程提示词骨架**

以后每次开发前，你可以这样开头：

“你现在是我的资深后端/Agent 工程协作助手。先不要写代码。请先完成四件事：

1. 根据我的描述复述问题，判断这是 bug、功能、重构还是性能优化；
2. 阅读相关代码，输出当前架构、数据流、涉及文件和已有模式；
3. 反问我需求中不明确的地方，尤其是边界、异常、验收标准和风险；
4. 在确认需求后，给出 2–3 个方案，说明优缺点、风险、改动范围和推荐方案。”

方案确定后，再说：

“请根据确认后的方案生成 PLAN.md。要求包含：涉及文件、函数级改动、输入输出、禁止修改范围、测试命令、验收标准、回滚方式。不要写代码。”

执行时再说：

“请只执行 PLAN.md 中的 Task 1。不要修改其他文件。完成后输出：修改文件、核心逻辑、运行的测试命令、测试结果、是否需要继续。”

审查时再说：

“请作为独立 reviewer，只基于 SPEC.md、PLAN.md 和 git diff 审查，不要重写代码。重点检查需求偏离、兼容性、异常处理、安全风险、性能问题、测试缺口和无关改动。”

**最后给你一个最适合你的结论**

你现在的路线已经对了，但要从“会让 AI 帮我写代码”升级成“我能管理 AI 完成工程任务”。专业程序员使用 AI，不是比谁 prompt 写得花，而是比谁更能做到：

**需求清楚、边界明确、计划可审、执行可控、测试可验证、风险可回滚、问题可定位、经验可沉淀。**

你以后就按这句话训练自己。只要你每次开发都走完这个闭环，你的成长速度会比单纯看教程、背八股、堆面试题快很多。



### 开发规范
对于后端小白来说，不要一开始就纠结“我是不是要学完所有大厂规范”。你真正要建立的是一个工程习惯：**先分层，再命名，再定义模块边界，再写接口契约，再补测试，再加日志和 trace，最后把反复出现的流程沉淀成 Skill**。

一句话总结就是：**大厂开发规范 = 分层清楚 + 命名统一 + 模块边界明确 + 接口契约稳定 + 测试可验证 + 日志可排查 + Skills 可复用。**

**二、仓库里应该沉淀哪些规范文件？**

一个适合后端小白和编码 Agent 协作的项目，建议至少有这几类文件：

```plain
project-root/
├── README.md                 # 给人看的：项目介绍、启动方式、主要功能
├── AGENTS.md                 # 给编码 Agent 看的：项目规则、禁止事项、测试命令
├── DEVELOPMENT.md            # 给团队看的：开发规范、分层规则、命名规范
├── API_CONVENTION.md         # 接口规范：URL、入参、出参、错误码、分页
├── TESTING.md                # 测试规范：单测、集成测试、回归测试怎么写
├── OBSERVABILITY.md          # 日志、trace、指标、排障规范
├── .cursor/rules/*.mdc       # Cursor 项目规则
└── .agents/skills/
    ├── backend-feature-development/
    │   ├── SKILL.md
    │   ├── references/
    │   └── scripts/
    ├── api-design-review/
    │   ├── SKILL.md
    │   └── references/
    └── agent-tool-integration/
        ├── SKILL.md
        ├── tests/
        └── scripts/
```

`README.md` 是给人快速上手的，`AGENTS.md` 是给 Codex、Claude Code、Cursor Agent 这类编码 Agent 看的，里面写“怎么启动、怎么测试、哪些目录不能乱改、提交前必须跑什么命令”。AGENTS.md 官方社区把它定义为“给 coding agents 的 README”，用于放置构建命令、测试命令和代码规范等信息，避免把大量 Agent 专用细节塞进 README。

`Skills` 则是更细粒度的“可复用任务手册”。比如“新增一个后端接口”“接入一个 MCP 工具”“写一个数据库迁移”“排查 Agent 工具调用失败”，这些都可以做成一个 Skill。OpenAI Codex Skills 官方说明中，Skill 是一个目录，至少包含 `SKILL.md`，还可以带 `scripts/`、`references/`、`assets/`，并且会先用名称和描述做轻量匹配，真正命中后再加载完整说明，这叫**渐进式披露**（先看目录，真正需要时再打开详细文件，避免上下文过大）。

### **代码该怎么分层？**
**一个产业级 Agent 仓库，本质上不是“把 Agent 写在一个 Python 文件里”，而是把它拆成：接口入口、业务编排、Agent 运行时、工具能力、记忆/RAG、数据存储、异步任务、观测评测、安全治理、测试部署这几层。**  
我检索了几个比较适合参考的开源仓库：`agent-service-toolkit`、`fastapi-langgraph-agent-production-ready-template`、`DeerFlow`、`openai-agents-python` 和一个 FastAPI + Redis + Celery + LangGraph 的多 Agent 模板。它们共同体现的思路是：**Agent 只是核心执行链路的一部分，真正能上线的系统还必须有 API、状态、工具、数据库、日志、测试和部署。**

**一、先看几个值得参考的仓库**

**第一个是 **`**agent-service-toolkit**`**，适合作为小白理解“Agent 服务化”的入门模板。**  
它是一个基于 **LangGraph + FastAPI + Streamlit** 的 Agent 服务工具包，README 里明确说它包含 LangGraph agent、FastAPI service、client、Streamlit chat UI，并且使用 Pydantic 定义数据结构。它的 `src/` 目录被拆成 `agents/`、`schema/`、`core/`、`service/`、`client/`、`memory/` 等，非常适合理解“Agent 不是孤立脚本，而是一个服务”。([GitHub](https://github.com/JoshuaC215/agent-service-toolkit))

**第二个是 **`**fastapi-langgraph-agent-production-ready-template**`**，适合看产业级后端配套能力。**  
这个模板明确定位为 **FastAPI + LangGraph 的 production-ready agent backend**，包含状态化对话、长期记忆、工具调用、可观测性、限流、认证、Alembic 迁移、Redis/Valkey 缓存、结构化日志等能力。也就是说，它不是只写 Agent 逻辑，而是把“上线需要的周边工程能力”一起放进来了。([GitHub](https://github.com/wassim249/fastapi-langgraph-agent-production-ready-template))

**第三个是 ByteDance 的 **`**DeerFlow**`**，适合看 super agent harness 的分层。**  
DeerFlow 2.0 把自己定位为 **super agent harness**，不是单纯的研究 demo。它内置 filesystem、memory、skills、sandbox-aware execution，并支持规划和生成 sub-agents 来处理复杂多步任务。这里最值得你学习的是：产业级 Agent 需要一个 **Harness（运行支架）**，负责给 Agent 提供文件系统、记忆、技能、沙箱、子 Agent、工具执行等基础设施。([GitHub](https://github.com/bytedance/deer-flow))

**第四个是 **`**openai-agents-python**`**，适合看官方 SDK 仓库怎么组织。**  
它的 `AGENTS.md` 明确列出仓库结构：`src/agents/` 放核心库实现，`tests/` 放测试，`examples/` 放示例项目，`docs/` 放文档，并且用 `Makefile` 管理常用开发命令。这种结构对你写自己的 Agent 项目很有参考意义：核心代码、测试、示例、文档要分开。([GitHub](https://github.com/openai/openai-agents-python/blob/main/AGENTS.md))

**第五个是 **`**multi-agent-system-using-langgraph**`**，适合看异步任务和状态管理。**  
这个项目把技术栈列得很清楚：LangGraph 负责编排，FastAPI 提供 API 和 WebSocket，Celery 处理异步任务，PostgreSQL 存储任务和结果，Redis 作为高速 Agent workspace 和 broker。这种结构非常接近真实后端系统：用户请求进来后，不一定同步等 Agent 跑完，而是可以丢到异步任务里执行。([GitHub](https://github.com/AkhileshMalthi/multi-agent-system-using-langgraph))

**三、每一层到底负责什么？**

**1. 根目录层：项目入口和工程配置**

根目录放的是“项目怎么启动、怎么开发、怎么部署”。比如 `README.md` 给人看，`AGENTS.md` 给 AI 编码助手看，`.env.example` 告诉别人需要哪些环境变量，`docker-compose.yml` 启动 PostgreSQL、Redis、Kafka 等依赖，`pyproject.toml` 管 Python 依赖和工具配置。

小白可以理解为：**根目录是项目的说明书和工具箱**。  
不要把业务代码直接堆在根目录。

---

**2. core 层：全局基础设施**

`core/` 放全项目通用能力，比如配置、日志、安全、异常。这里不写具体业务。

例如：

```plain
core/config.py      # 读取环境变量
core/logging.py     # 统一日志格式
core/security.py    # JWT、权限校验
core/exceptions.py  # 全局异常类型
```

小白理解：**core 是地基，不是业务房间。**

---

**3. api 层：后端接口入口**

`api/` 或 `routers/` 负责接收 HTTP 请求，比如 `/chat`、`/agent-runs`、`/reports`。  
这一层只做三件事：**接收请求、调用 service、返回响应**。

不要在 API 层直接写 Agent 规划、数据库查询、工具调用。`agent-service-toolkit` 里就把 FastAPI service 和 agent 定义拆开，说明服务入口和 Agent 本体应该分层。([GitHub](https://github.com/JoshuaC215/agent-service-toolkit))

---

**4. services 层：业务流程编排**

`services/` 是后端业务大脑，负责把多个模块串起来。比如一次用户问答可能需要：

1. 校验用户身份；
2. 读取历史会话；
3. 调用 Agent；
4. 保存结果；
5. 返回响应。

这些逻辑应该放在 service，不应该放在 router。

小白理解：**router 是前台，service 是业务经理。**

---

**5. agents 层：Agent 运行时核心**

`agents/` 放 Agent 的核心逻辑，包括状态、执行图、规划器、执行器、Supervisor、多 Agent 协作等。  
比如：

```plain
agents/state.py      # AgentState，记录消息、意图、计划、工具结果
agents/graph.py      # LangGraph 工作流
agents/planner.py    # 规划下一步做什么
agents/executor.py   # 执行工具调用
agents/supervisor.py # 多 Agent 调度
```

DeerFlow 这类 harness 型项目强调 filesystem、memory、skills、sandbox、sub-agents，这说明产业级 Agent 运行时不只是“调用一次 LLM”，而是要管理任务状态、上下文、工具和多步执行。([GitHub](https://github.com/bytedance/deer-flow))

---

**6. tools 层：外部能力封装**

`tools/` 负责把外部 API、数据库查询、搜索、MCP Server、金融数据接口等能力包装成 Agent 可调用工具。

一个标准工具至少要有：

```plain
name
description
input_schema
output_schema
timeout
fallback
```

推荐做一个 `tools/registry.py`，所有工具都从这里注册，避免 Agent 裸调外部 API。

小白理解：**tools 是 Agent 的工具箱，registry 是工具清单。**

---

**7. memory / rag 层：记忆和知识库**

`memory/` 管短期记忆、长期记忆、上下文压缩、用户偏好。  
`rag/` 管文档解析、切块、向量检索、rerank、知识库问答。

`fastapi-langgraph-agent-production-ready-template` 就把长期记忆、工具调用、观测、认证、缓存等作为 production-ready agent backend 的关键能力。([GitHub](https://github.com/wassim249/fastapi-langgraph-agent-production-ready-template))

小白理解：**memory 解决“记住用户和对话”，RAG 解决“查知识库”。**

---

**8. repositories 层：数据库访问**

`repositories/` 专门访问 PostgreSQL。比如保存用户、会话、Agent 执行记录、工具调用记录。

不要让 `agents/`、`api/` 到处直接写 SQL。  
正确做法是：

```plain
service 调用 repository
repository 访问数据库
```

小白理解：**repository 是数据库管理员，其他模块不要越级查库。**

---

**9. workers 层：异步任务和消息队列**

如果 Agent 任务比较慢，比如深度报告、长文档分析、多 Agent 协作，就不应该让 HTTP 请求一直卡住。可以用 Celery、Kafka、Redis Queue 等放到后台执行。`multi-agent-system-using-langgraph` 就用 Celery 做异步任务，Redis 做状态/缓存和 broker，PostgreSQL 存任务结果。([GitHub](https://github.com/AkhileshMalthi/multi-agent-system-using-langgraph))

小白理解：**workers 是后台工人，专门处理耗时任务。**

---

**10. observability 层：日志、trace、指标、评测**

产业级 Agent 必须能回答一个问题：**这次 Agent 为什么答错了？**

所以要记录：

```plain
request_id
run_id
user_id
intent
plan
tool_calls
tool_latency
tool_error
evidence
final_answer
```

`agent-service-toolkit` 也强调包含测试、FastAPI service、agent、client 等完整工具链；`fastapi-langgraph-agent-production-ready-template` 更明确包含 Langfuse tracing、Prometheus metrics、Grafana dashboards、结构化日志。([GitHub](https://github.com/JoshuaC215/agent-service-toolkit))

小白理解：**observability 是行车记录仪，出错时靠它复盘。**

---

**11. guardrails 层：安全与边界控制**

`guardrails/` 负责输入检查、权限检查、输出检查、证据检查。  
尤其是 Agent 项目，不能让模型随便调用工具、随便编造实时数据、随便输出敏感信息。

建议至少有：

```plain
input_check.py        # 输入是否合法
permission_check.py   # 用户是否有权限
output_check.py       # 输出是否越界
evidence_check.py     # 是否有足够证据
```

小白理解：**guardrails 是护栏，防止 Agent 跑偏。**

---

**12. tests 层：测试**

产业级仓库一定要有测试。`openai-agents-python` 的仓库结构里就单独列出 `tests/`，`agent-service-toolkit` 也明确包含 unit 和 integration tests。([GitHub](https://github.com/openai/openai-agents-python/blob/main/AGENTS.md))

推荐分成：

```plain
tests/unit/          # 单个函数或模块测试
tests/integration/   # API + DB + 工具组合测试
tests/e2e/           # 模拟完整用户流程
```

小白理解：**测试不是额外工作，而是证明你没把项目改坏。**

---

你现在如果做 **FastAPI + PostgreSQL + Redis + Kafka + Agent/RAG + Vue**，不需要一开始完全照产业级大仓库做，可以先用这个版本：

│   │   ├── main.py
│   │   ├── core/

│   │   ├── services/

│   │   ├── tools/
│   │   ├── memory/
│   │   ├── rag/
│   │   ├── repositories/
│   │   ├── workers/

**你可以这样记忆：**

1. **api 接请求**：用户从这里进来。
2. **service 编业务**：决定这次请求怎么处理。
3. **agents 做推理**：负责规划、调用工具、生成结果。
4. **tools 接能力**：查数据库、查网页、调 MCP、调金融接口。
5. **memory/rag 给上下文**：记住用户、查知识库。
6. **repository 管数据**：只负责 PostgreSQL。
7. **worker 跑慢任务**：处理深度报告、长任务。
8. **observability 记录过程**：方便排查问题。
9. **guardrails 控风险**：防止越权、幻觉和危险操作。
10. **tests 保稳定**：证明改动没有破坏系统。

**一句话总结：标准产业级 Agent 仓库不是“一个 agent.py + 一个 prompt.txt”，而是一个后端工程系统：API 负责接入，Service 负责业务编排，Agents 负责智能执行，Tools 负责外部能力，Memory/RAG 负责上下文，Repository 负责数据，Workers 负责异步任务，Observability 和 Guardrails 负责可排查、可治理、可上线。**

### **命名规范怎么做？小白先按“看名字就知道用途”**
命名规范不是为了形式主义，而是为了降低理解成本。一个新人打开项目时，应该通过名字就知道文件和函数大概干什么。

Python 后端可以用这套规则：

```plain
文件/目录：snake_case
类名：PascalCase
函数/变量：snake_case
常量：UPPER_SNAKE_CASE
异常类：XxxError
数据库表：snake_case，通常用复数或业务统一约定
API路径：复数名词，例如 /users、/orders、/agent-runs
Skill名称：lowercase-hyphen，例如 agent-tool-debugging
```

Google Python Style Guide 中也强调常量使用全大写加下划线，异常类通常以 `Error` 结尾，并且应避免可变全局状态，因为全局状态会破坏封装，让数据库连接、全局注册表等在多环境下变得难控制。

接口命名建议遵循 Microsoft/Azure REST API 的思路：API 应围绕**资源**设计，路径尽量使用名词而不是动词。例如 `/orders` 比 `/create-order` 更合理，HTTP 方法本身已经表达了动作：`GET` 查询、`POST` 创建、`PUT/PATCH` 修改、`DELETE` 删除。

对于你的 Agent 项目，可以这样命名：

```plain
POST /agent-runs              # 创建一次Agent执行
GET  /agent-runs/{run_id}     # 查询一次执行结果
GET  /agent-runs/{run_id}/trace
POST /skills/{skill_name}/run
GET  /tools                   # 查看可用工具
```

不要这样写：

```plain
POST /runAgentNow
POST /doStockAnalysis
POST /getAnswerByLLM
```

因为这些名字会把“动作”写死在 URL 里，后期不好扩展，也不符合资源化接口风格。

### **每个功能模块怎么定义？用“五件套”定义清楚**
一个模块不是建个文件夹就完事了。每个模块都应该写清楚五件事：

```plain
1. 这个模块解决什么业务问题？
2. 它对外暴露哪些接口？
3. 它依赖哪些内部模块和外部服务？
4. 它的核心数据结构是什么？
5. 它失败时怎么降级、怎么记录日志、怎么测试？
```

比如“新闻分析模块”可以这样定义：

```plain
模块名：news_analysis

职责：
负责根据股票代码和时间范围获取相关新闻，完成新闻去重、情感分析、风险事件识别，并返回结构化新闻因子。

不负责：
不负责生成最终投资建议；
不负责用户画像读取；
不负责数据库权限校验；
不直接拼接最终回答。

输入：
stock_code、start_date、end_date、limit

输出：
NewsAnalysisResult，包括 sentiment_score、risk_level、key_events、evidence_list

依赖：
NewsSearchClient、LLMClient、NewsRepository、TraceLogger

失败处理：
新闻源超时则返回 degraded=true；
LLM 解析失败则降级为规则关键词识别；
证据不足时不输出强结论。
```

小白可以记一句话：**模块边界要写“不负责什么”，否则它会慢慢变成万能垃圾桶。**

### **Rules和skills的区别**
**你可以先把“全局规则”理解成给 AI 编程助手看的长期备忘录。**  
普通提示词是“这一次你要怎么做”，而规则文件是“以后每次进入这个项目都默认怎么做”。在 **Cursor** 里，它主要对应 **User Rules、Project Rules、AGENTS.md、Skills**；在 **Codex** 里，它主要对应 `**~/.codex/AGENTS.md**`**、项目根目录 **`**AGENTS.md**`**、**`**.agents/skills/**`。Cursor 官方文档说明它支持 Project、Team、User Rules 和 AGENTS.md 这几类持久指令；Codex 官方文档也说明，Codex 会在开始工作前读取 `AGENTS.md`，并把全局规则、项目规则和更近目录里的规则串起来使用。([Cursor](https://cursor.com/docs/rules?utm_source=chatgpt.com))

**一、先区分三种东西：全局规则、项目规则、Skill**

**全局规则**适合放你个人长期不变的偏好，比如“回答中文”“改代码前先阅读项目结构”“不要一次性大重构”“提交前说明测试结果”。它会影响你打开的多个项目，所以不要写太具体的项目目录或业务逻辑。

**项目规则**适合放当前项目必须遵守的规范，比如你的金融 Agent 项目采用 FastAPI、PostgreSQL、LangGraph、MCP、Skills，那么可以规定 `router.py` 不写复杂业务、`service.py` 负责业务编排、`repository.py` 负责数据库访问、Agent 工具必须通过 registry 注册。

**Skill**适合放可重复执行的开发流程，比如“新增一个后端接口”“接入一个 Agent 工具”“排查工具调用失败”。Codex 官方明确把 Skills 定义为可复用工作流：一个 Skill 是目录结构，至少包含 `SKILL.md`，还可以带 `scripts/`、`references/`、`assets/`；Codex 会先看 Skill 的名称和描述，只有判断任务匹配时才读取完整 `SKILL.md`。([OpenAI开发者](https://developers.openai.com/codex/skills))

所以你不要把所有东西都塞进一个超长规则里，推荐结构是：

```plain
个人长期偏好        → 全局规则
项目固定约束        → 项目 AGENTS.md / .cursor/rules/*.mdc
复杂重复任务流程    → skills/*/SKILL.md
详细解释文档        → docs/development/*.md
真正强制检查        → lint / pytest / pre-commit / CI
```

**二、在 Cursor 里怎么注入全局规则？**

在 Cursor 中，你可以分三层做。

第一层是 **User Rules**，也就是你个人所有项目都通用的规则。你可以在 Cursor 里进入 **Settings → Rules**，找到 User Rules，然后写入非常短的个人偏好。这里不建议写太长，因为它会影响所有项目。Cursor 官方文档说明 Rules 用来配置持久指令，并支持 User、Project、Team Rules 与 AGENTS.md。([Cursor](https://cursor.com/docs/rules?utm_source=chatgpt.com))

你可以放这种内容：

```markdown
你是我的后端开发与 Agent 工程辅助助手。

通用要求：
- 默认使用中文解释。
- 修改代码前，先阅读相关目录结构和已有实现。
- 优先做最小必要改动，不做无关重构。
- 新增功能时必须考虑分层、测试、错误处理和日志。
- 如果涉及安全、权限、密钥、数据库迁移，必须显式提醒风险。
- 最终回答必须说明修改了哪些文件、为什么这样改、是否运行测试。
```

第二层是 **Project Rules**，也就是放在项目里的 `.cursor/rules/*.mdc`。这类规则最适合你的个人项目，因为它可以跟着 Git 仓库走，之后你换电脑、换模型、换会话，规则仍然在项目里。社区和官方生态里现在更推荐使用 `.cursor/rules` 下的 `.mdc` 规则文件，而不是旧的单个 `.cursorrules` 文件；NVIDIA NeMo Agent Toolkit 的开发者文档也把 Cursor Rules 按 `general.mdc`、模块子目录、工作流子目录等方式组织，说明这种“规则分层”更利于维护。([NVIDIA Docs](https://docs.nvidia.com/nemo/agent-toolkit/1.2/extend/cursor-rules-developer-guide.html?utm_source=chatgpt.com))

你的项目里可以这样建：

```plain
.cursor/
└── rules/
    ├── 00-project-core.mdc
    ├── 10-python-fastapi-backend.mdc
    ├── 20-api-contract.mdc
    ├── 30-database-repository.mdc
    ├── 40-testing-quality.mdc
    ├── 50-security-observability.mdc
    └── 70-agent-runtime.mdc
```

比如 `10-python-fastapi-backend.mdc` 可以先写成：

```markdown
---
description: FastAPI 后端分层开发规则，适用于 app/**/*.py、modules/**/*.py
globs:
  - "**/*.py"
alwaysApply: false
---

# FastAPI Backend Layering Rules

- router.py 只负责接收请求、依赖注入和返回响应，不写复杂业务逻辑。
- schemas.py 只定义请求和响应模型。
- service.py 负责业务流程编排。
- repository.py 只负责数据库读写。
- clients/ 只封装外部 API 调用。
- 新增接口必须同时考虑 schema、service、测试、错误处理和日志。
- 禁止在业务代码中硬编码 API Key、数据库密码或 token。
```

第三层是 **AGENTS.md**。如果你希望 Cursor、Codex、GitHub Copilot 等多个工具都能读同一份项目规则，那么建议在项目根目录放一个 `AGENTS.md`。AGENTS.md 官方定位就是“给 coding agents 的 README”，适合写项目启动、测试、代码风格和 PR 指令；Cursor 也支持 AGENTS.md。([GitHub](https://github.com/sanjeed5/awesome-cursor-rules-mdc/blob/main/cursor-rules-reference.md?utm_source=chatgpt.com))

项目根目录可以这样放：

```plain
your-project/
├── AGENTS.md
├── .cursor/rules/
├── app/
├── tests/
└── docs/
```

`AGENTS.md` 可以写成：

```markdown
# AGENTS.md

## Project Overview
本项目是一个 Python/FastAPI + Agent/RAG 项目，主要包含后端 API、Agent runtime、工具调用、数据库和可观测性模块。

## Working Rules
- 修改前先阅读 README.md、docs/development/DEVELOPMENT.md 和相关模块代码。
- 一次只完成一个明确任务，不做无关重构。
- 新增后端功能必须遵守 router / schema / service / repository 分层。
- 新增 Agent 工具必须通过 tools/registry.py 注册，并定义 input_schema、output_schema、timeout、fallback。
- 修改业务逻辑必须补充或更新测试。
- 最终回答必须列出修改文件、测试结果和剩余风险。

## Commands
- Format: ruff format .
- Lint: ruff check .
- Test: pytest
```

**三、在 Codex 里怎么注入全局规则？**

Codex 的全局规则最核心的是 `~/.codex/AGENTS.md`。官方文档明确说明：你可以在 Codex home 目录创建全局 `AGENTS.md`，让每个仓库继承你的工作习惯；同时也可以在仓库根目录添加项目级 `AGENTS.md`，让项目规则覆盖或补充全局规则。([OpenAI开发者](https://developers.openai.com/codex/guides/agents-md))

在 Linux、macOS、WSL 里，你可以这样做：

```bash
mkdir -p ~/.codex
nano ~/.codex/AGENTS.md
```

如果你是在 Windows PowerShell 里，可以大致这样做：

```powershell
mkdir $HOME\.codex
notepad $HOME\.codex\AGENTS.md
```

里面写你的个人通用规则：

```markdown
# Global Codex Instructions

## Working Agreements
- 默认使用中文解释代码修改。
- 修改代码前先阅读项目结构，不要凭空猜测。
- 优先做最小必要改动，避免无关重构。
- 新增依赖前必须说明原因和风险。
- 涉及数据库、权限、密钥、安全逻辑时必须额外提醒。
- 完成后说明修改文件、测试命令、测试结果和潜在风险。
```

然后在每个具体项目根目录再放一个项目级 `AGENTS.md`：

```bash
cd your-project
touch AGENTS.md
```

项目级规则写项目自己的内容：

```markdown
# Repository Instructions

## Stack
- Backend: FastAPI
- Database: PostgreSQL
- Cache: Redis
- Agent Runtime: LangGraph
- Tests: pytest
- Lint/Format: ruff

## Architecture Rules
- API 入口放在 router.py。
- 请求和响应模型放在 schemas.py。
- 业务流程放在 service.py。
- 数据库访问放在 repository.py。
- 外部 API 调用放在 clients/ 或 tools/。

Before finishing:
- Run ruff check .
- Run pytest for related tests.
- Report changed files and test results.
```

Codex 官方还说明，Codex 会从全局目录和项目目录读取指导文件，并且更靠近当前工作目录的文件优先生效；如果你有特殊模块，比如 `services/payments/`，可以在子目录放 `AGENTS.override.md` 做更具体的规则。([OpenAI开发者](https://developers.openai.com/codex/guides/agents-md))

你可以用这个命令检查是否生效：

```bash

```

官方文档也建议用类似方式让 Codex 汇总当前加载的指令来源，确认全局和项目规则是否被读到。([OpenAI开发者](https://developers.openai.com/codex/guides/agents-md))

**四、Codex 里怎么放 Skills？**

如果你发现有一类任务会反复出现，比如“新增后端接口”“接入 MCP 工具”“排查 Agent 工具调用失败”，不要每次都写长提示词，可以做成 Skill。Codex 官方说明，个人 Skills 可以放在 `$HOME/.agents/skills`，共享团队 Skills 可以放在项目里的 `.agents/skills`；Skills 是可复用工作流，比单纯的全局规则更适合多步骤任务。([OpenAI开发者](https://developers.openai.com/codex/learn/best-practices))

例如你可以建：

```plain
your-project/
└── .agents/
    └── skills/
        ├── backend-feature-development/
        │   └── SKILL.md
        └── agent-tool-integration/
            └── SKILL.md
```

`backend-feature-development/SKILL.md` 可以写：

```markdown
---
name: backend-feature-development
description: 新增或修改 FastAPI 后端功能时使用，要求遵守分层架构、schema 校验、测试、日志和最小改动原则。
---

# Backend Feature Development Skill

## Workflow
1. 阅读 AGENTS.md、README.md、相关模块代码。
2. 判断影响层次：router、schema、service、repository、client、tests。
3. 先定义或更新 Pydantic schema。
4. 保持 router 简单，不写复杂业务逻辑。
5. 将业务编排放入 service。
6. 将数据库读写放入 repository。
7. 增加错误处理、日志和必要测试。
8. 运行 ruff check 和 pytest。
9. 总结修改文件、测试结果和风险。
```

你在 Codex 里可以显式说：

```plain
请使用 backend-feature-development skill，帮我新增一个用户画像查询接口。
```

Codex 也可以根据 Skill 的 `description` 自动判断是否使用，所以 `description` 一定要写清楚触发场景。Codex 官方明确说明 Skill 可通过显式调用或根据 description 隐式调用，description 是匹配的关键。([OpenAI开发者](https://developers.openai.com/codex/skills))

**五、怎么复用别人整理好的安全 rules？**

你可以复用，但不要直接“无脑复制到全局规则”。正确做法是：**先看来源 → 再裁剪 → 再改成你的技术栈 → 先放项目规则 → 小范围测试 → 再沉淀为通用规则**。

我推荐你先看 GitHub Awesome Copilot 里的 **Security and OWASP Instructions**。它是社区维护的 Copilot 指令集合，其中安全规则覆盖 Web 安全、OWASP、反模式、检测方式、修复示例，还包含现代后端框架和 AI/LLM 安全相关内容；它适合作为你提取安全规则的原材料，而不是整篇原样塞进 Cursor User Rules。([GitHub](https://github.com/github/awesome-copilot/blob/main/instructions/security-and-owasp.instructions.md?utm_source=chatgpt.com))

你可以这样复用：

第一步，先把别人的安全规则保存到项目文档里，而不是直接作为全局规则：

```plain
docs/development/security-rules-source.md
```

第二步，提取和你项目有关的内容，比如 FastAPI、数据库、密钥、日志、Agent 工具调用。不要把 Java、Rails、前端 React 专属规则全部放进来。

第三步，整理成你自己的 `.cursor/rules/50-security-observability.mdc`：

```markdown
---
description: 后端与 Agent 项目的安全、密钥、权限、日志和工具调用规则
globs:
  - "**/*.py"
  - "**/*.env*"
  - "**/*.yml"
  - "**/*.yaml"
alwaysApply: false
---

# Security and Observability Rules

- 禁止硬编码 API Key、数据库密码、Token、Cookie。
- 禁止提交 .env、私钥、证书和真实生产配置。
- 所有外部输入必须经过 Pydantic/schema 校验。
- 数据库查询必须使用 ORM 或参数化查询，禁止字符串拼接 SQL。
- 日志中禁止打印手机号、身份证、银行卡号、完整 token。
- 权限判断必须在 service 或 dependency 层显式完成。
- Agent 工具调用必须经过工具白名单和参数 schema 校验。
- 高风险动作必须设计二次确认或 human approval。
- 发现安全风险时，优先解释影响，再给出最小修复方案。
```

第四步，把关键安全规则同步到 `AGENTS.md`，但只放最核心的几条：

```markdown
## Security Rules
- Never hardcode secrets.
- Never log sensitive data.
- Validate all external inputs.
- Use parameterized queries or ORM.
- Agent tools must be registered and schema-validated.
```

这样 Cursor 和 Codex 都能看到。

**六、哪些规则适合放全局，哪些不适合？**

适合放全局的规则是长期不变、所有项目都适用的规则，比如：

```markdown
- 修改前先理解现有代码，不要凭空新建重复模块。
- 优先最小改动，不做无关重构。
- 不硬编码密钥。
- 修改后说明测试结果。
- 涉及安全、数据库、权限、部署时提醒风险。
```

不适合放全局的规则包括：

```markdown
- 本项目使用 FastAPI 的 app/modules 目录结构。
- 股票工具必须调用 Tushare。
- LangGraph 状态字段必须包含 active_entity。
- 某个数据库表叫 user_profiles。
```

这些应该放到项目 `AGENTS.md` 或 `.cursor/rules/*.mdc` 里。否则你以后打开另一个项目，AI 会把金融 Agent 的规则错误套用到别的项目上。

**七、一个最小可用的落地方案**

你现在可以直接按这个顺序做，不需要一次搞得很复杂。

第一步，在 Cursor 的 User Rules 里写个人通用规则：

```markdown
默认使用中文。修改代码前先阅读项目结构和相关文件。优先最小必要改动，不做无关重构。新增功能必须考虑分层、测试、错误处理、日志和安全。涉及密钥、权限、数据库迁移、外部工具调用时必须提醒风险。完成后说明改了哪些文件、运行了哪些测试、还有什么风险。
```

第二步，在每个项目根目录放 `AGENTS.md`：

```markdown
# AGENTS.md

## Project Rules
- This is a FastAPI + Agent/RAG backend project.
- Keep API layer thin.
- Put business logic in service.py.
- Put database access in repository.py.
- Put external API calls in clients/ or tools/.
- Register all Agent tools through tools/registry.py.
- Add or update tests when changing behavior.

## Commands
- Lint: ruff check .
- Format: ruff format .
- Test: pytest
```

第三步，在项目里建 Cursor rules：

```plain
.cursor/rules/
├── 00-project-core.mdc
├── 10-python-fastapi-backend.mdc
├── 50-security-observability.mdc
└── 70-agent-runtime.mdc
```

第四步，在 Codex 里建全局规则：

```bash
mkdir -p ~/.codex
nano ~/.codex/AGENTS.md
```

第五步，把重复任务做成 Skill：

```plain
.agents/skills/backend-feature-development/SKILL.md
.agents/skills/agent-tool-integration/SKILL.md
```

**八、怎么验证规则真的生效？**

在 Cursor 里，你可以新开一个 Chat，然后问：

```plain
请列出你当前能看到的项目规则、AGENTS.md 指令，以及你准备如何遵守它们。
```

在 Codex 里，你可以运行：

```bash
codex --ask-for-approval never "Summarize the current instructions and list instruction sources."
```

如果它能说出你的全局规则、项目 `AGENTS.md`、后端分层规则，就说明基本生效。Codex 官方也建议用类似方式验证当前加载了哪些指导文件。([OpenAI开发者](https://developers.openai.com/codex/guides/agents-md))

**九、最重要的安全提醒**

复用别人 rules 时，要把它当成“代码”一样审查，而不是当成普通文本。尤其要注意三类风险：第一，里面是否偷偷要求上传密钥、关闭测试、跳过安全检查；第二，里面是否包含你项目不适用的技术栈规则；第三，里面是否过长，导致真正重要的规则被上下文挤掉。Codex 官方也强调，`AGENTS.md` 应保持小而关键，复杂重复流程更适合放进 Skill，并配合 linters、type checkers、pre-commit 等工具强制执行。([OpenAI开发者](https://developers.openai.com/codex/concepts/customization))

**一句话总结：Cursor 里用 User Rules 管个人习惯、**`**.cursor/rules/*.mdc**`** 管项目和模块规则；Codex 里用 **`**~/.codex/AGENTS.md**`** 管个人全局规则、项目 **`**AGENTS.md**`** 管仓库规则、**`**.agents/skills**`** 管重复开发流程。复用别人安全 rules 时，不要整篇全局导入，而是先裁剪成适合你项目的安全规则，再放进项目规则和 AGENTS.md 中测试。**

**三、我建议你的 User Rules 不要写太技术栈细节**

User Rules 是“你个人所有项目都默认遵守的习惯”，所以它应该短而稳定。比如你可以在 Cursor User Rules 或 `~/.codex/AGENTS.md` 中写：

```markdown
你是我的 Python 后端、Agent 工程和全栈开发助手。

通用工作规则：
- 默认使用中文解释思路和修改结果。
- 修改代码前，先阅读项目结构、README、AGENTS.md 和相关模块代码。
- 优先做最小必要改动，不做无关重构。
- 遇到不确定的项目约定，先搜索仓库中已有实现，优先复用已有模式。
- 新增功能必须考虑分层、参数校验、错误处理、日志、测试和安全。

**五、怎么安全复用别人的 rules**

你可以直接复用别人开源 rules，但不要无脑复制。建议按这 5 步：

**第一步：只从可信来源挑规则。**  
优先顺序是：官方文档 > 大型社区集合 > 明确说明来源的个人仓库 > 随机 Gist。比如 Cursor 官方 Rules、Codex AGENTS.md、GitHub awesome-copilot、fastapi-best-practices、awesome-cursorrules 这些优先级更高。

**第二步：不要直接执行安装脚本。**  
比如有些仓库提供 `curl ... | bash` 一键安装，我建议你不要直接运行。先打开脚本内容，看它会复制哪些文件、是否会改你的 shell 配置、是否会覆盖已有 rules。

**第三步：先复制到临时目录审查。**

```bash
mkdir -p rules-review
# 把你下载的 .mdc 或 .cursorrules 先放这里

### AGENT.md
**先说明一下：你说的 AgentMD，通常指的是 **`**AGENTS.md**`**。**  
它可以理解成：**专门写给 AI 编码助手看的 README**。普通 `README.md` 主要给人看，告诉人怎么启动项目、项目是什么；而 `AGENTS.md` 是给 Cursor、Codex、Copilot 这类 coding agent 看，告诉它：**这个项目怎么开发、代码怎么分层、测试怎么跑、哪些事情不能乱做**。AGENTS.md 官方也把它定义为一种简单开放格式，核心定位就是“README for agents”。([AGENTS](https://agents.md/?utm_source=chatgpt.com))

**为什么要使用 AGENTS.md？**

最直接的原因是：**AI 编码工具默认不了解你的项目习惯**。如果你不告诉它规则，它可能会做几类危险操作：一是新建一堆和现有结构不一致的文件；二是把业务逻辑写进 router；三是改一个小需求却顺手重构很多无关代码；四是不跑测试就说完成；五是硬编码密钥、忽略日志、忽略错误处理。

`AGENTS.md` 的作用就是把这些隐性经验显式写下来，让 AI 每次进项目都先读规则。OpenAI Codex 官方文档明确说明，Codex 会在开始工作前读取 `AGENTS.md`，并且可以通过全局规则和项目规则叠加，让不同仓库都保持一致的工作预期。([OpenAI开发者](https://developers.openai.com/codex/guides/agents-md?utm_source=chatgpt.com)) Cursor 也支持通过 Project、Team、User Rules 以及 `AGENTS.md` 配置持久化编码规则。([Cursor](https://cursor.com/docs/rules?utm_source=chatgpt.com))

你可以把它理解成：**AGENTS.md = 给 AI 编码员工的入职手册**。它不用讲很多理论，而是告诉它：“这个项目怎么干活，怎么别添乱。”

**AGENTS.md 应该放在哪里？**

最常见的是放在项目根目录：

```plain
your-project/
├── AGENTS.md
├── README.md
├── backend/
├── frontend/
├── tests/
└── docs/
```

如果你的项目很大，也可以在子目录放更具体的规则，比如：

```plain
your-project/
├── AGENTS.md                 # 全项目通用规则
├── backend/
│   └── AGENTS.md             # 后端专用规则
├── frontend/
│   └── AGENTS.md             # 前端专用规则
└── agent/
    └── AGENTS.md             # Agent 工具调用专用规则
```

这样做的好处是：根目录规则讲通用原则，子目录规则讲局部细节。比如后端目录规定 FastAPI 分层，前端目录规定 Vue 组件拆分，Agent 目录规定工具注册、trace、降级策略。

**AGENTS.md 里应该写什么？**

对于小白来说，不需要一开始写得很复杂。一个好用的 `AGENTS.md` 一般包含这几类内容：

**第一，项目背景。**  
告诉 AI 这个项目是什么，用了什么技术栈。比如：这是一个 FastAPI + PostgreSQL + Redis + Kafka + Vue 的全栈项目，后端主要负责 API、Agent 工具调用、数据访问和任务编排。

**第二，目录结构。**  
告诉 AI 哪些目录放什么，避免它乱建文件。

**第三，分层规范。**  
比如 router 只接收请求，service 写业务逻辑，repository 查数据库，clients/tools 调外部服务。

**第四，开发命令。**  
比如怎么安装依赖、怎么启动、怎么格式化、怎么跑测试。

**第五，测试要求。**  
告诉 AI：修改业务逻辑必须补测试，修 bug 必须加回归测试，不能为了通过测试删除测试。

**第六，安全要求。**  
比如不能硬编码 API Key，不能提交 `.env`，不能在日志里打印 token、手机号、身份证、银行卡号。

**第七，AI 工作约束。**  
比如每次只做一个明确任务，先读代码再改，不做无关重构，完成后说明修改文件和测试结果。

**一个适合你技术栈的 AGENTS.md 示例**

你可以先直接用下面这个版本作为初稿：

```markdown
# AGENTS.md

## Project Overview

本项目是一个 Python/FastAPI + PostgreSQL + Redis + Kafka + Vue 的全栈项目，主要包含后端 API、数据库访问、缓存、消息队列、Agent 工具调用和前端页面。

AI 编码助手在修改代码前，必须先阅读本文件、README.md、相关模块代码和已有测试，不允许凭空创建与现有结构冲突的新实现。

## Tech Stack

- Backend: Python, FastAPI
- Database: PostgreSQL
- Cache: Redis
- Message Queue: Kafka
- Frontend: Vue
- Testing: pytest
- Code Quality: ruff
- API Schema: Pydantic

## Architecture Rules

后端代码必须遵守分层架构：

- router.py：只负责接收请求、依赖注入和返回响应，不写复杂业务逻辑。
- schemas.py：只定义请求和响应数据结构。
- service.py：负责业务流程编排。
- repository.py：负责数据库读写。
- clients/：负责封装外部 API 调用。
- tools/：负责封装 Agent 可调用工具。
- tests/：负责单元测试、集成测试和回归测试。

禁止在 router.py 中直接访问数据库、调用外部 API、拼接复杂业务逻辑。

## Backend Development Rules

新增一个后端功能时，必须检查是否需要同时修改：

1. router.py
2. schemas.py
3. service.py
4. repository.py
5. tests/
6. API 文档或注释
7. 日志和错误处理

如果只是改一个小功能，不允许顺手进行大规模重构。

## Database Rules

- 禁止在业务代码中拼接 SQL 字符串。
- 数据库访问必须通过 repository 层。
- 表结构变更必须新增 migration。
- 查询大表时必须考虑索引、分页和 limit。
- 涉及事务时，事务边界应在 service 层明确控制。

## Redis Rules

- Redis 主要用于缓存、限流、会话状态或短期任务状态。
- Redis key 必须有清晰命名空间，例如 `user:profile:{user_id}`。
- 缓存必须设置合理 TTL，避免长期脏数据。
- 不允许把重要业务真相只存 Redis，核心数据必须落 PostgreSQL。

## Kafka Rules

- Kafka 用于异步任务、事件通知和削峰。
- 消息消费必须考虑幂等性。
- 消费失败必须有重试或死信处理方案。
- 不允许在消息体中放敏感明文数据。
- topic 名称必须表达业务含义。

## Frontend Rules

- Vue 组件应保持单一职责。
- API 请求逻辑应集中封装，不要散落在多个组件中。
- 组件命名应清晰表达用途。
- 不要在前端硬编码后端地址、密钥或敏感配置。

## Agent Tool Rules

如果项目包含 Agent 工具调用，必须遵守：

- 工具必须通过统一 registry 注册。
- 每个工具必须定义 name、description、input_schema、output_schema、timeout。
- 工具失败时返回结构化错误，不允许抛出未处理异常。
- 实时数据不足时必须降级回答，禁止编造。
- 每次工具调用必须记录 run_id、tool_name、latency、status、error。

## Testing Rules

修改业务逻辑时，必须新增或更新测试。

至少考虑：

- 正常路径
- 参数错误
- 空结果
- 外部依赖失败
- 权限不足
- 边界条件

修复 bug 时，必须增加回归测试，防止同类问题再次出现。

## Security Rules

- 禁止硬编码 API Key、数据库密码、Token、Cookie。
- 禁止提交 .env、私钥、证书和真实生产配置。
- 所有外部输入必须经过 Pydantic/schema 校验。
- 数据库查询必须使用 ORM 或参数化查询。
- 日志中禁止打印手机号、身份证、银行卡号、完整 token。
- 涉及权限、支付、账户、数据删除等高风险操作时，必须显式提醒风险。

## Commands

常用命令：

```bash
ruff format .
ruff check .
pytest
```

如果项目中存在更具体的测试命令，应优先使用相关模块的测试命令。

AI 编码助手必须遵守：

+ 先理解现有代码，再进行修改。
+ 优先复用已有模式，不重复造轮子。
+ 一次只完成一个明确任务。
+ 不做无关重构。
+ 不删除已有测试来让测试通过。
+ 不弱化断言来掩盖问题。
+ 修改完成后必须说明：
    - 改了哪些文件
    - 为什么这样改
    - 是否运行测试
    - 测试结果是什么
    - 还有哪些风险或未完成事项

```plain
这个版本已经能覆盖你现在个人项目里最常见的开发约束：**FastAPI 分层、PostgreSQL、Redis、Kafka、Vue、Agent 工具调用、安全、测试、工作方式**。

**AGENTS.md 和 Cursor Rules 有什么区别？**

你可以这样理解：

`AGENTS.md` 是**项目总说明书**，适合放全项目通用规则，Codex、Cursor、Copilot 等多个工具都可能支持它。AGENTS.md 官方就是希望给不同 coding agents 一个统一、可预测的位置来读取项目指令。:contentReference[oaicite:3]{index=3}

`.cursor/rules/*.mdc` 是 **Cursor 专用规则**，适合更细粒度控制，比如只在 `backend/**/*.py` 生效，或者只在 `frontend/**/*.vue` 生效。Cursor 官方规则系统支持 Project、Team、User Rules 和 AGENTS.md，你可以把它们配合使用。:contentReference[oaicite:4]{index=4}

所以推荐做法是：

```text
AGENTS.md
  放全项目通用规则

.cursor/rules/10-backend.mdc
  放 FastAPI 后端规则

.cursor/rules/20-frontend-vue.mdc
  放 Vue 前端规则

.cursor/rules/30-agent-tools.mdc
  放 Agent 工具调用规则
```

不要把所有规则都堆进一个超长 `AGENTS.md`。太长之后，AI 反而容易抓不住重点。

**AGENTS.md 和 Skill 又有什么区别？**

`AGENTS.md` 适合写**长期规则**，比如“不要硬编码密钥”“router 不写业务逻辑”“改完要跑测试”。

`SKILL.md` 适合写**具体任务流程**，比如“新增一个后端接口应该分 8 步做”“接入一个 Agent 工具应该先定义 schema，再注册工具，再补测试”。Codex 官方对 Skills 的定义是：它可以把指令、资源和可选脚本打包起来，让 Codex 在特定任务中按流程执行。([OpenAI开发者](https://developers.openai.com/codex/skills?utm_source=chatgpt.com))

所以你可以这样分工：

```plain
AGENTS.md：
告诉 AI 平时做项目要遵守什么规矩。

SKILL.md：
告诉 AI 遇到某类任务时按什么步骤做。
```

比如你以后可以做：

```plain
.agents/skills/backend-feature-development/SKILL.md
.agents/skills/agent-tool-integration/SKILL.md
.agents/skills/debugging-and-regression/SKILL.md
```

**编写 AGENTS.md 的建议**

**第一，规则要短而硬，不要写成技术论文。**  
比如“router.py 不写复杂业务逻辑”比“为了提高系统可维护性，我们应该遵循良好的软件工程思想……”更有效。AI 编码工具更适合执行明确规则，不适合从长篇理念中猜你的真实要求。

**第二，要写具体命令。**  
不要只写“运行测试”，而要写：

```bash
ruff check .
ruff format .
pytest
```

这样 AI 才知道该跑什么。

**第三，要写禁止事项。**  
很多小白只写“应该怎么做”，但更重要的是写“不能怎么做”。比如：

```markdown
- 不允许在 router.py 中直接访问数据库。
- 不允许为了通过测试删除测试。
- 不允许硬编码密钥。
- 不允许做无关重构。
```

这些规则对 vibe coding 特别重要，因为 AI 最容易“过度发挥”。

**第四，要写项目真实结构，不要照搬别人模板。**  
如果你的项目没有 `dao/`，就不要写“必须使用 dao 层”；如果你用的是 `repository.py`，就写 repository。否则 AI 会按别人的模板给你新建一套不一致的目录。

**第五，先写最小版本，再逐步迭代。**  
不要第一天就写 1000 行 AGENTS.md。建议先写 50～150 行，把最核心的目录结构、命令、分层、安全、测试写清楚。等你发现 AI 总犯某类错误，再把这类错误补进规则。

**第六，规则要和测试、lint 配合。**  
AGENTS.md 只是“告诉 AI 应该怎么做”，但真正兜底还要靠 `pytest`、`ruff`、`mypy/pyright`、pre-commit、CI。否则 AI 可能嘴上遵守，代码实际没过。

**你现在最适合的落地方式**

对你来说，我建议分三步：

第一步，在每个个人项目根目录放一个 `AGENTS.md`，先用上面那版模板。

第二步，把更细的技术栈规则拆到 Cursor：

```plain
.cursor/rules/
├── 10-fastapi-backend.mdc
├── 20-postgresql.mdc
├── 30-redis.mdc
├── 40-kafka.mdc
├── 50-vue.mdc
└── 60-agent-tools.mdc
```

第三步，把重复任务做成 Skills：

```plain
.agents/skills/
├── backend-feature-development/
├── api-design-review/
├── agent-tool-integration/
└── debugging-and-regression/
```

**一句话总结：**`**AGENTS.md**`** 的价值不是“多一个文档”，而是把你每次反复提醒 AI 的开发要求固定下来，让 Cursor、Codex 进入项目后默认知道：这个项目怎么分层、怎么测试、怎么保证安全、怎么避免乱改。对你这种正在搭建个人 vibe coding 框架的人来说，它是项目级规则体系的入口文件。**

### 功能新增需要注意的规则
**核心原则：大厂做功能新增和二次开发，不是“能跑就行”，而是要保证新功能可理解、可测试、可回滚、可观测、可长期维护。**  
公开工程实践里，Google 代码评审规范强调代码评审的目标是持续改善代码库整体健康，而不是只看这一次功能能不能合并；Google 也明确建议开发者提交小而自包含的变更，因为小变更更容易设计、评审和降低风险。微软 REST API 指南也强调 API 应先识别用例、设计契约、保持状态码/版本/错误响应一致，并通过 PR 评审。([Google GitHub](https://google.github.io/eng-practices/review/reviewer/standard.html?utm_source=chatgpt.com))

**一、需求进入开发前：先讲清楚“做什么、不做什么、怎么验收”**

大厂不会让开发者看到一句“加个功能”就直接写代码。标准做法是先明确**需求背景**、**目标用户**、**输入输出**、**影响范围**、**验收标准**和**不做事项**。比如你要给 Agent 系统新增“基金对比”功能，不能只写“支持基金对比”，而要写清楚：用户输入什么、最多比较几只基金、数据来源是什么、返回哪些字段、实时数据缺失时怎么降级、哪些投资建议不能输出。

可以用这份模板约束：

```markdown
## Feature Requirement

背景：为什么要做这个功能？
目标：这次具体交付什么？
输入：用户/接口会传入哪些字段？
输出：系统应该返回什么？
范围：本次改哪些模块？
不做：哪些内容本次明确不做？
验收：什么情况下认为完成？
风险：可能影响哪些接口、数据表、缓存、消息队列？
```

**规则一句话：先定义清楚需求边界，再进入代码开发；边界不清楚时，不允许直接大改。**

**二、开发前影响面分析：先看旧代码，不要凭空新建一套**

二次开发最怕的是：原项目已经有一套实现，开发者或 AI Agent 没看懂，就重新写一套相似模块，导致重复代码、接口冲突、数据逻辑不一致。大厂通常要求先做**影响面分析**（看本次变更会影响哪些接口、服务、数据库表、缓存 key、消息 topic、权限逻辑和测试用例）。

比如 FastAPI 项目里新增一个“用户画像查询”功能，开发前应先搜索：

```bash
rg "user_profile"
rg "profile"
rg "repository"
rg "router"
rg "service"
```

然后判断是复用已有 `user_repository.py`，还是新增一个独立模块。**二次开发的第一原则是优先复用现有模式，而不是凭感觉新建目录。**

**三、代码分层规则：入口薄、业务清、数据独立、外部依赖隔离**

后端新增功能时，必须遵守分层。对你这种 **FastAPI + PostgreSQL + Redis + Kafka + Agent** 项目来说，推荐规则是：

```plain
router.py        只负责接请求、参数依赖、返回响应
schemas.py       定义请求/响应 Pydantic 模型
service.py       编排业务流程
repository.py    访问 PostgreSQL
cache.py         访问 Redis
producer.py      发送 Kafka 消息
consumer.py      消费 Kafka 消息
tools/           封装 Agent 可调用工具
observability/   记录日志、trace、指标
```

比如新增接口时，**router 不应该直接查数据库**：

```python
# 不推荐：router 里直接写数据库逻辑
@router.get("/users/{user_id}")
def get_user(user_id: str):
    return db.query(User).filter(User.id == user_id).first()
```

更推荐：

```python
@router.get("/users/{user_id}", response_model=UserProfileResponse)
def get_user_profile(user_id: str, service: UserService = Depends(get_user_service)):
    return service.get_user_profile(user_id)
```

**规则一句话：router 是入口，不是业务大脑；service 负责编排，repository 负责数据。**

**四、API 契约规则：先定义输入输出，再写业务逻辑**

大厂做 API 功能时通常会先明确**接口契约**（接口路径、HTTP 方法、请求参数、响应结构、错误码、版本兼容）。微软 REST API 指南强调 API 应围绕资源设计，并保持状态码、版本和错误响应风格一致。([Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design?utm_source=chatgpt.com))

推荐规则：

```plain
GET    /users/{user_id}
POST   /agent-runs
GET    /agent-runs/{run_id}
GET    /agent-runs/{run_id}/trace
POST   /fund-comparisons
```

不推荐：

```plain
/getUserInfo
/runAgentNow
/doFundCompare
```

统一响应可以这样设计：

```json
{
  "code": "SUCCESS",
  "message": "ok",
  "data": {},
  "request_id": "req_xxx"
}
```

**规则一句话：接口要像合同一样稳定，不能今天一个返回格式、明天一个返回格式。**

**五、数据库与缓存规则：核心数据进 PostgreSQL，临时状态进 Redis**

新增功能时，必须明确数据放在哪里。一般来说，**PostgreSQL** 存核心业务数据，比如用户、订单、会话、Agent 执行记录；**Redis** 存缓存、限流、短期状态和幂等 key；**Kafka** 负责异步事件和任务削峰。

推荐规则：

```plain
PostgreSQL：存长期、可靠、可审计的数据
Redis：存短期缓存、会话状态、限流 key、任务临时状态
Kafka：传递异步事件，例如 report_requested、tool_call_failed
```

同时要遵守：

```plain
- 表结构变更必须写 migration
- 大表查询必须加 limit、分页和索引评估
- Redis key 必须有命名空间和 TTL
- Kafka 消费必须考虑幂等性
- 不能把核心业务真相只存在 Redis
```

12-Factor App 的配置原则也强调，数据库地址、外部服务凭据等随环境变化的配置不应写死在代码中，而应从环境中注入。([12factor.net](https://12factor.net/config?utm_source=chatgpt.com))

**规则一句话：数据库管真相，Redis 管速度，Kafka 管异步，不要混用。**

**六、安全规则：所有输入要校验，所有权限要显式，所有密钥不能进代码**

功能新增时，不能只考虑“功能能不能跑”，还要考虑安全。尤其是 Agent 项目，模型可能会生成错误参数、误选工具、输出敏感信息，所以更需要安全约束。

必须遵守：

```plain
- 外部输入必须经过 Pydantic/schema 校验
- 数据库查询必须用 ORM 或参数化查询
- 不允许硬编码 API Key、Token、数据库密码
- 不允许提交 .env、私钥、证书
- 日志里不能打印完整 token、手机号、身份证、银行卡号
- 高风险工具必须经过白名单和二次确认
```

比如 Agent 工具调用不要裸调：

```python
# 不推荐
result = requests.get(user_provided_url)
```

而应该走工具注册和参数校验：

```python
tool = tool_registry.get("fetch_stock_price")
validated_input = tool.input_schema.model_validate(payload)
result = tool.execute(validated_input)
```

**规则一句话：新增功能必须默认不信任外部输入，也不能默认信任模型输出。**

**七、错误处理与降级规则：失败要可控，不能直接炸给用户**

产业级系统必须考虑失败路径。新增功能时要问：

```plain
数据库查不到怎么办？
Redis 连接失败怎么办？
Kafka 发送失败怎么办？
外部 API 超时怎么办？
LLM 返回格式错误怎么办？
Agent 工具空返回怎么办？
```

推荐错误返回结构：

```json
{
  "code": "TOOL_TIMEOUT",
  "message": "工具调用超时，已使用缓存结果降级返回",
  "request_id": "req_xxx"
}
```

Agent 项目里尤其要有降级策略：

```plain
实时行情失败 → 使用最近缓存并标注时间
新闻源失败 → 返回基础分析，不做新闻因子判断
工具参数错误 → 自动修正一次，仍失败则返回明确错误
证据不足 → 不输出强结论
```

**规则一句话：失败不可怕，不可控、不可解释、不可排查才可怕。**

**八、日志与可观测性规则：每次新增功能都要能排查**

新增功能时要同步考虑日志、指标和 trace。对普通后端接口，至少记录：

```plain
request_id
user_id
endpoint
status_code
latency_ms
error_code
```

对 Agent 功能，还要记录：

```plain
run_id
intent
selected_skill
plan
tool_calls
tool_latency
tool_error
evidence_count
degradation_reason
```

这样当用户说“刚才回答错了”，你能查到是**路由错了**、**工具选错了**、**工具超时了**，还是**最终总结阶段幻觉了**。

**规则一句话：没有日志和 trace 的功能，不算真正可上线。**

**九、测试规则：新增功能必须测正常、异常、边界、回归**

大厂不会只测“正常输入能不能跑”。标准新增功能至少要覆盖：

```plain
正常路径：合法输入返回正确结果
参数错误：缺字段、类型错、非法值
空结果：数据库查不到、工具返回空
外部失败：Redis/Kafka/API/LLM 超时
权限不足：用户不能访问别人的数据
边界情况：超长输入、重复请求、并发请求
回归测试：修过的 bug 不再复发
```

如果你是 Agent 功能，还要额外测：

```plain
意图识别是否正确
工具选择是否正确
工具参数是否符合 schema
证据不足是否降级
最终回答是否引用了真实工具结果
```

**规则一句话：没有测试的功能，只是“看起来能跑”，不是“稳定可交付”。**

**十、变更粒度规则：小步提交，不要一次性全改**

Google 工程实践明确建议小而自包含的变更，因为小变更更容易设计、评审、并降低阻塞；代码评审的目标是维护代码库长期健康。([Google GitHub](https://google.github.io/eng-practices/review/developer/small-cls.html?utm_source=chatgpt.com))

你做二次开发时建议按任务拆：

```plain
Task 1：只补 schema 和接口契约
Task 2：只写 service 业务逻辑
Task 3：只接 repository / cache / MQ
Task 4：只补测试
Task 5：只补日志、文档和清理
```

每一步都要：

```plain
看 diff → 跑测试 → 记录结果 → commit
```

**规则一句话：一次只解决一个问题，避免“一个 PR 改半个项目”。**

**十一、代码评审规则：不仅看能不能跑，还看长期能不能维护**

PR 或 MR 至少要写清楚：

```markdown
## 改了什么
说明本次新增/修改的功能。

## 为什么改
说明需求背景。

## 影响范围
列出影响的接口、服务、数据库、缓存、消息队列、前端页面。

## 测试结果
说明跑了哪些测试，结果是什么。

## 风险与回滚
说明可能风险和出问题怎么回滚。
```

评审时重点看：

```plain
功能是否满足需求
是否破坏旧逻辑
分层是否清晰
错误处理是否完整
是否有测试
是否有安全风险
是否有日志和 trace
是否存在无关重构
```

**规则一句话：PR 不是代码上传入口，而是团队理解、审查和沉淀变更的入口。**

**十二、上线与回滚规则：功能要能灰度、能观察、能回退**

新增功能上线前要确认：

```plain
配置是否已准备
数据库 migration 是否验证
缓存 key 是否兼容旧数据
Kafka topic 是否存在
监控指标是否配置
异常日志是否可查
回滚方案是否明确
```

如果是高风险功能，推荐加：

```plain
feature flag（功能开关）
灰度发布
小流量验证
人工审批
回滚脚本
```

**规则一句话：上线不是结束，能监控、能灰度、能回滚，才算完整交付。**

### Debug流程
**大厂工程师做 Debug 的核心不是“看到报错就让 AI 改”，而是按一套固定链路排查：复现问题 → 缩小范围 → 看日志/trace → 提出假设 → 最小修复 → 补回归测试 → 看 diff → 再提交。**  
对你这种用 **Cursor + FastAPI + PostgreSQL + Redis + Kafka + Agent** 的小白来说，最重要的是先养成一个习惯：**不要一上来就对 Cursor 说“帮我修 bug”，而是先让它帮你定位、解释、列假设，再让它小步修改。** Cursor 官方的 agent 开发实践也强调，要给 Agent 清晰、可验证的目标，比如类型检查、lint 和测试信号；不要只让它凭感觉改代码。([Cursor](https://cursor.com/blog/agent-best-practices?utm_source=chatgpt.com))

**一、大厂 Debug 的标准思路：先复现，再修复**

大厂工程师一般不会看到线上报错就直接改代码，而是先问几个问题：**这个问题能不能稳定复现？影响哪个接口？最近改了什么？错误发生在哪一层？是输入问题、业务逻辑问题、数据库问题、缓存问题、消息队列问题，还是外部工具问题？**

你可以把 Debug 想成医生看病。不能只听患者说“我不舒服”，就马上开药；要先问症状、量体温、验血、看检查结果，最后才给治疗方案。开发里也是一样：**日志、测试、断点、trace、错误栈**就是检查报告。Python 官方 logging 模块就是为应用和库提供灵活日志系统的标准工具；FastAPI 官方也推荐用 `TestClient` 配合 pytest 写自动化测试，先复现接口问题。([Python documentation](https://docs.python.org/3/library/logging.html?utm_source=chatgpt.com))

**二、你在 Cursor 里应该怎么操作？**

你可以按这个流程来，不要跳步。

**第一步：先固定现场，不要让 Cursor 直接乱改**

在 Cursor 里打开项目后，先确认当前代码状态：

```bash
git status
```

如果当前有很多未提交改动，先不要 Debug。因为你不知道 bug 是原来就有，还是你刚才改出来的。大厂工程师通常会先保证工作区干净，或者至少知道哪些文件是自己刚改的。

然后你可以在 Cursor Chat 里这样问：

```plain
请先不要修改代码。请根据当前项目结构，帮我分析这个报错可能发生在哪几层：
1. API/router 层
2. service 业务层
3. repository 数据库层
4. Redis 缓存层
5. Kafka 消息队列层
6. 外部 API / Agent tool 层

请先列排查计划，不要直接改代码。
```

这个提示词的重点是：**先定位，不修改**。

**第二步：复现问题，拿到最小报错**

比如你现在有一个 FastAPI 接口：

```bash
uvicorn src.main:app --reload
```

然后请求接口：

```bash
curl http://127.0.0.1:8000/users/999
```

如果报错，不要只截图给 Cursor，而是尽量复制完整信息：

```plain
请求路径：GET /users/999
期望结果：如果用户不存在，返回 404
实际结果：返回 500
错误日志：
AttributeError: 'NoneType' object has no attribute 'name'
```

然后在 Cursor 里问：

```plain
请根据这个错误栈定位根因。要求：
1. 先解释错误是什么意思；
2. 再判断可能在哪个文件；
3. 只给排查建议，不要改代码；
4. 如果需要查看文件，请告诉我应该看哪些文件。
```

这样 Cursor 不会一上来就大改，而是会先帮你建立排查路径。

**第三步：用 @ 文件精确给 Cursor 上下文**

假设你的项目结构是：

```plain
src/
├── api/users_router.py
├── services/user_service.py
├── repositories/user_repository.py
└── schemas/user_schema.py
```

在 Cursor 里你可以引用相关文件：

```plain
@src/api/users_router.py
@src/services/user_service.py
@src/repositories/user_repository.py

请分析 GET /users/{user_id} 返回 500 的原因。要求只定位问题，不要修改代码。
```

这比你直接说“帮我修接口”好很多，因为它把 Cursor 的注意力限制在相关文件，不会乱翻整个项目。Cursor 官方文档说明 Cursor 支持通过 Rules、Agent、Skills、MCP 等方式配置和引导编码行为；你在 Debug 时也应该通过明确上下文来约束 Agent。([Cursor](https://cursor.com/docs?utm_source=chatgpt.com))

**三、用一个 FastAPI 代码例子讲清楚 Debug 过程**

假设现在代码是这样的。

`repositories/user_repository.py`：

```python
class UserRepository:
    def get_by_id(self, user_id: int):
        # 假设这里查数据库
        if user_id == 1:
            return {"id": 1, "name": "Alice"}
        return None
```

`services/user_service.py`：

```python
class UserService:
    def __init__(self, repository):
        self.repository = repository

    def get_profile(self, user_id: int):
        user = self.repository.get_by_id(user_id)
        return {
            "id": user["id"],
            "name": user["name"]
        }
```

`api/users_router.py`：

```python
from fastapi import APIRouter
from src.repositories.user_repository import UserRepository
from src.services.user_service import UserService

router = APIRouter()

@router.get("/users/{user_id}")
def get_user(user_id: int):
    service = UserService(UserRepository())
    return service.get_profile(user_id)
```

当你访问：

```bash
curl http://127.0.0.1:8000/users/999
```

会报错：

```plain
TypeError: 'NoneType' object is not subscriptable
```

小白可能会说：“是不是 FastAPI 坏了？”  
大厂工程师会这样拆：

**第一层：API 层有没有拿到参数？**  
`user_id=999` 能正常传入，说明 router 层基本没问题。

**第二层：service 层有没有处理空值？**  
`repository.get_by_id(999)` 返回 `None`，但 service 直接 `user["id"]`，所以这里出错。

**第三层：repository 层返回 None 是否合理？**  
用户不存在时返回 None 是可以的，但 service 必须处理。

所以根因是：**service 层没有处理用户不存在的情况，导致 None 被当成字典使用。**

修复方式：

```python
from fastapi import HTTPException


class UserService:
    def __init__(self, repository):
        self.repository = repository

    def get_profile(self, user_id: int):
        user = self.repository.get_by_id(user_id)

        if user is None:
            raise HTTPException(status_code=404, detail="User not found")

        return {
            "id": user["id"],
            "name": user["name"]
        }
```

但更产业级一点，不建议 service 直接依赖 FastAPI 的 `HTTPException`，因为 service 层应该尽量和 Web 框架解耦。更推荐：

```python
class UserNotFoundError(Exception):
    pass


class UserService:
    def __init__(self, repository):
        self.repository = repository

    def get_profile(self, user_id: int):
        user = self.repository.get_by_id(user_id)

        if user is None:
            raise UserNotFoundError(f"user_id={user_id} not found")

        return {
            "id": user["id"],
            "name": user["name"]
        }
```

然后在 router 层转成 HTTP 响应：

```python
from fastapi import APIRouter, HTTPException
from src.repositories.user_repository import UserRepository
from src.services.user_service import UserService, UserNotFoundError

router = APIRouter()

@router.get("/users/{user_id}")
def get_user(user_id: int):
    service = UserService(UserRepository())

    try:
        return service.get_profile(user_id)
    except UserNotFoundError:
        raise HTTPException(status_code=404, detail="User not found")
```

这样分层更清楚：**service 表达业务异常，router 负责转 HTTP 响应。**

**六、Debug 时不要乱用 print，要用日志**

小白最常见的 Debug 方法是到处写：

```python

print(result)
print("到这里了")
```

短期能用，但不适合真实项目。更推荐用 `logging`：

```python
import logging

logger = logging.getLogger(__name__)


class UserService:
    def __init__(self, repository):
        self.repository = repository

    def get_profile(self, user_id: int):
        logger.info("fetching user profile", extra={"user_id": user_id})

        user = self.repository.get_by_id(user_id)

        if user is None:
            logger.warning("user not found", extra={"user_id": user_id})
            raise UserNotFoundError(f"user_id={user_id} not found")

        return {
            "id": user["id"],
            "name": user["name"]
        }
```

Python 官方 logging HOWTO 建议通过 `logging.getLogger(__name__)` 创建 logger，并使用 debug、info、warning、error、critical 等不同级别记录信息。([Python documentation](https://docs.python.org/3/howto/logging.html?utm_source=chatgpt.com))

小白可以这样理解日志级别：

```plain

info：正常关键流程
warning：不影响系统但需要注意
error：功能失败
critical：系统严重故障
```

### 数据库开发规范
**核心结论：大厂做 MySQL / PostgreSQL 开发时，最重视的不是“SQL 会不会写”，而是数据库变更能不能做到：数据正确、性能可控、上线不锁表、安全不泄露、问题可回滚、查询可观测。**  
我重点参考了 GitLab 的数据库开发规范、数据库评审规范、迁移规范、索引规范、外键规范、查询性能规范，以及 PostgreSQL、MySQL、SQLAlchemy、OWASP 的官方文档。GitLab 的规范非常适合学习产业级数据库开发，因为它明确要求：只要应用更新触及数据库，就需要数据库相关 review，并重点关注迁移、复杂 SQL、索引和大规模数据下的性能问题。([GitLab 文档](https://docs.gitlab.com/development/database/?utm_source=chatgpt.com))

**一、数据库在后端项目里应该放在哪一层？**

对小白来说，先记住一句话：**API 层不要直接操作数据库，数据库读写必须放到 repository / dao 层。**

在 FastAPI 项目里，一个比较清晰的结构是：

```plain
app/
├── api/
│   └── user_router.py          # 接收请求
├── services/
│   └── user_service.py         # 业务流程
├── repositories/
│   └── user_repository.py      # 数据库读写
├── models/
│   └── user_model.py           # ORM 表模型
├── schemas/
│   └── user_schema.py          # 请求/响应结构
└── db/
    ├── session.py              # 数据库连接和 session
    └── migrations/             # Alembic 迁移
```

小白可以这样理解：**router 是前台，service 是业务经理，repository 是数据库管理员。** 前台不能直接翻数据库，应该把业务请求交给 service，service 再调用 repository。

错误写法：

```python
@router.get("/users/{user_id}")
def get_user(user_id: int):
    # 不推荐：router 直接查数据库
    user = db.query(User).filter(User.id == user_id).first()
    return user
```

推荐写法：

```python
@router.get("/users/{user_id}", response_model=UserResponse)
def get_user(
    user_id: int,
    service: UserService = Depends(get_user_service),
):
    return service.get_user_profile(user_id)
```

**原因很简单：如果数据库逻辑散落在 router、service、agent、worker 里，后续换表结构、加缓存、加事务、做测试都会很痛苦。**

**二、表设计规范：先保证数据正确，再考虑性能**

大厂做表设计时，通常会先关注几个问题：这张表存什么业务实体？主键是什么？哪些字段不能为空？哪些字段必须唯一？哪些字段需要外键？哪些字段以后会被查询、排序、过滤？GitLab 的外键规范明确提到，在 PostgreSQL 中新增外键时，外键列不会自动建索引，因此需要先补并发索引，否则删除被引用记录时可能触发表扫描并导致超时。([GitLab 文档](https://docs.gitlab.com/development/database/foreign_keys/?utm_source=chatgpt.com))

推荐表字段基本规范：

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    username VARCHAR(64) NOT NULL,
    email VARCHAR(255) NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at TIMESTAMP NULL,
    CONSTRAINT uq_users_email UNIQUE (email)
);
```

小白要重点理解这些字段：

`id` 是**主键**，用于唯一标识一条记录。  
`NOT NULL` 是**非空约束**，防止关键字段为空。  
`UNIQUE` 是**唯一约束**，防止邮箱、订单号、任务号重复。  
`created_at / updated_at` 是**审计字段**，方便排查数据什么时候创建、什么时候修改。  
`deleted_at` 是**软删除字段**，表示业务上删除，但数据库里暂时保留。

表设计建议：

```plain
1. 每张业务表都要有主键。
2. 重要业务唯一性要用数据库约束保证，不能只靠代码判断。
3. 关键字段尽量 NOT NULL。
4. 高频查询字段提前考虑索引。
5. 金额、计数、状态、时间字段要选对类型。
6. 不要把所有东西都塞进 JSON 字段，除非它确实是半结构化数据。
7. 大字段、日志、历史记录、向量数据尽量和核心业务表拆开。
```

**三、命名规范：让别人一眼看懂表和字段的含义**

推荐统一使用小写蛇形命名：

```plain
表名：users、agent_runs、tool_call_logs
字段名：user_id、created_at、updated_at、deleted_at
索引名：idx_agent_runs_user_id_created_at
唯一索引名：uq_users_email
外键名：fk_orders_user_id
```

不推荐：

```plain
UserTable
tbl_user
userInfo
createTime
x1
data_json_everything
```

建议你个人项目里采用这套规范：

```plain
主键统一叫 id。
外键统一叫 xxx_id。
创建时间统一叫 created_at。
更新时间统一叫 updated_at。
软删除时间统一叫 deleted_at。
状态字段统一叫 status。
布尔字段用 is_ / has_ 开头，例如 is_active、has_paid。
```

**四、迁移规范：生产环境不要手动改表，必须用 migration**

大厂数据库开发非常重视 migration，也就是**数据库迁移脚本**。原因是：代码可以回滚，数据库结构也必须可追踪、可审查、可回放。GitLab 的 Migration Style Guide 明确强调，迁移会在大量不同规模的组织中运行，因此必须小心编写，并尽量做到在线执行，避免升级时停服。([GitLab 文档](https://docs.gitlab.com/development/migration_style_guide/?utm_source=chatgpt.com))

在 Python / FastAPI 项目里，通常用 **Alembic** 管理迁移：

```bash
alembic revision -m "add users table"
alembic upgrade head
alembic downgrade -1
```

迁移规范建议：

```plain
1. 不允许直接在生产库手动 ALTER TABLE。
2. 表结构变更必须写 migration。
3. migration 文件必须能被 review。
4. 能写 downgrade 就写 downgrade，至少说明不可逆原因。
5. 大表变更要拆步骤，避免长时间锁表。
6. schema migration 和 data migration 尽量分开。
7. 大批量数据修复要分批，不要一个 SQL 更新全表。
```

危险示例：

```sql
-- 危险：大表上直接加 NOT NULL，可能长时间锁表
ALTER TABLE orders ADD COLUMN user_id BIGINT NOT NULL;
```

更稳妥的思路：

```plain
第一步：新增 nullable 字段。
第二步：代码开始写入新字段。
第三步：后台分批回填历史数据。
第四步：校验数据完整性。
第五步：再加 NOT NULL 或约束。
```

GitLab 对大规模数据迁移也有明确思路：如果普通迁移会超过时间限制，就应该使用批量后台迁移，尤其是高流量大表或大量单行更新场景。([GitLab 文档](https://docs.gitlab.com/development/database/batched_background_migrations/?utm_source=chatgpt.com))

**五、索引规范：索引不是越多越好，而是要服务查询**

索引可以加速查询，但也会增加写入成本和存储成本。所以大厂通常要求：**新增索引前要说明对应的查询场景。**

比如你经常查某个用户最近的 Agent 执行记录：

```sql
SELECT *
FROM agent_runs
WHERE user_id = 123
ORDER BY created_at DESC
LIMIT 20;
```

那索引应该围绕 `user_id + created_at` 设计：

```sql
CREATE INDEX idx_agent_runs_user_id_created_at
ON agent_runs (user_id, created_at DESC);
```

常见索引规则：

```plain
1. WHERE 条件里的高频字段适合建索引。
2. JOIN 字段适合建索引。
3. ORDER BY + LIMIT 的字段组合要考虑联合索引。
4. 外键字段通常需要索引。
5. 低区分度字段不要盲目单独建索引，例如 gender、status。
6. 不要给每个字段都建索引。
7. 建索引后要用 EXPLAIN / EXPLAIN ANALYZE 验证效果。
```

PostgreSQL 官方文档说明，数据库会为每个查询生成执行计划，`EXPLAIN` 可以查看查询计划，而选择正确计划对性能非常关键。([PostgreSQL](https://www.postgresql.org/docs/current/using-explain.html?utm_source=chatgpt.com)) GitLab 也有专门的 EXPLAIN 指南，说明 PostgreSQL 的 `EXPLAIN` 对判断查询性能非常有价值。([GitLab 文档](https://docs.gitlab.com/development/database/understanding_explain_plans/?utm_source=chatgpt.com))

**六、查询规范：不要写“能查出来但拖垮数据库”的 SQL**

常见危险写法：

```sql
SELECT * FROM users;
```

问题是：字段太多、数据太多、网络传输太多。

更推荐：

```sql
SELECT id, username, email
FROM users
WHERE status = 'active'
ORDER BY created_at DESC
LIMIT 20;
```

查询规范建议：

```plain
1. 禁止无条件查全表。
2. 禁止线上接口 SELECT *。
3. 列表查询必须分页。
4. 分页必须有最大 page_size。
5. 大 offset 分页要谨慎，数据量大时优先考虑 cursor/keyset pagination。
6. 避免 N+1 查询。
7. JOIN 前确认关联字段有索引。
8. 慢 SQL 必须 EXPLAIN。
```

GitLab 的分页性能规范专门讨论了 JOIN、ORDER BY、LIMIT 等组合对查询计划的影响，并建议开发者理解数据库如何估算成本和选择执行顺序。([GitLab 文档](https://docs.gitlab.com/development/database/pagination_performance_guidelines/?utm_source=chatgpt.com))

**七、事务规范：一组必须同时成功的操作，必须放进事务**

事务就是：**一组操作要么都成功，要么都失败。**

比如下单场景：

```plain
1. 创建订单
2. 扣减库存
3. 记录支付流水
```

这三步不能只成功一部分。如果订单创建成功但库存没扣，就会数据不一致。

SQLAlchemy 官方文档说明，Session 会管理事务，失败后需要 rollback，连接和事务资源也需要正确关闭或重置。([docs.sqlalchemy.org](https://docs.sqlalchemy.org/en/latest/orm/session_basics.html?utm_source=chatgpt.com))

推荐写法：

```python
async def create_order(
    session: AsyncSession,
    user_id: int,
    product_id: int,
):
    try:
        order = Order(user_id=user_id, product_id=product_id)
        session.add(order)

        product = await session.get(Product, product_id)
        if product.stock <= 0:
            raise ValueError("库存不足")

        product.stock -= 1

        await session.commit()
        return order

    except Exception:
        await session.rollback()
        raise
```

更推荐在 service 层控制事务：

```plain
router：接请求
service：控制事务边界
repository：只做具体读写，不随便 commit
```

不推荐每个 repository 方法里自己 `commit()`，因为 service 很难保证多个数据库操作的原子性。

**八、连接池和 Session 规范：不要每次请求都新建连接**

数据库连接是昂贵资源。SQLAlchemy 官方说明，连接池是服务端 Web 应用的标准技术，用于复用长期连接，并管理应用同时使用的连接总数。([docs.sqlalchemy.org](https://docs.sqlalchemy.org/en/latest/core/pooling.html?utm_source=chatgpt.com))

推荐原则：

```plain
1. 应用启动时创建 engine，不要每个请求创建 engine。
2. 每个请求使用一个 session，用完关闭。
3. 连接池大小要根据服务并发和数据库承载能力配置。
4. 查询失败后要 rollback。
5. 不要让长事务占住连接。
6. 不要在事务里做耗时外部 API 调用。
```

示例：

```python
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

engine = create_async_engine(
    DATABASE_URL,
    pool_size=10,
    max_overflow=20,
    pool_pre_ping=True,
)

AsyncSessionLocal = async_sessionmaker(
    engine,
    expire_on_commit=False,
)
```

FastAPI 中常见做法：

```python
async def get_db():
    async with AsyncSessionLocal() as session:
        yield session
```

小白理解：**连接池就像共享充电宝柜，不要每个人都临时造一个充电宝。**

**九、安全规范：防 SQL 注入、最小权限、敏感数据不进日志**

数据库安全最重要的第一条：**不要拼接用户输入生成 SQL。** OWASP SQL Injection Prevention Cheat Sheet 明确建议使用 prepared statements / parameterized queries 防止 SQL 注入；OWASP Query Parameterization Cheat Sheet 也说明，SQL 注入最好的防护方式是使用参数化查询。([OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html?utm_source=chatgpt.com))

危险写法：

```python
sql = f"SELECT * FROM users WHERE email = '{email}'"
result = session.execute(sql)
```

安全写法：

```python
from sqlalchemy import text

stmt = text("SELECT * FROM users WHERE email = :email")
result = await session.execute(stmt, {"email": email})
```

或者用 ORM：

```python
stmt = select(User).where(User.email == email)
result = await session.execute(stmt)
```

安全规则：

```plain
1. 禁止字符串拼接 SQL。
2. 使用 ORM 或参数化查询。
3. 数据库账号使用最小权限。
4. 应用账号不要使用 root / superuser。
5. 不要在日志里打印完整 SQL 参数中的手机号、身份证、token。
6. .env、数据库密码、连接串不能提交到 Git。
7. 生产库操作必须有审计和审批。
```

MySQL InnoDB 官方文档也明确提到，InnoDB 支持外键约束，用于维护数据完整性。([MySQL开发者区](https://dev.mysql.com/doc/en/innodb-introduction.html?utm_source=chatgpt.com)) 这说明数据完整性不能只靠应用代码，数据库本身也应该承担约束职责。

**十、MySQL 和 PostgreSQL 开发时要注意的差异**

如果你同时关注 MySQL 和 PostgreSQL，要注意它们默认行为不完全一样。

```plain
PostgreSQL：
- 更强调标准 SQL、复杂查询、JSONB、窗口函数、事务一致性。
- 常用 EXPLAIN / EXPLAIN ANALYZE 看执行计划。
- 创建索引、外键、大表变更时要特别注意锁。
- 外键列不会自动创建索引，需要自己补。

MySQL：
- 常见生产引擎是 InnoDB。
- InnoDB 默认事务隔离级别是 REPEATABLE READ。
- 字符集、排序规则、索引长度、隐式类型转换要特别注意。
- 大表 ALTER TABLE 也要非常谨慎。
```

MySQL 文档说明，InnoDB 支持 SQL 标准定义的四种隔离级别，默认隔离级别是 `REPEATABLE READ`。([MySQL开发者区](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html?utm_source=chatgpt.com)) 所以在 MySQL 中排查并发读写问题时，要理解默认隔离级别带来的可重复读、锁、间隙锁等行为。

# Database Development Rules

## 1. 分层规则

- API/router 层禁止直接访问数据库。
- service 层负责业务流程和事务边界。
- repository/dao 层只负责数据库读写。
- models 层只定义 ORM 表结构。
- schemas 层只定义请求和响应结构。
- 不允许在多个层里重复写相同 SQL 逻辑。

## 2. 表设计规则

- 每张业务表必须有主键。
- 关键业务唯一性必须用唯一约束或唯一索引保证。
- 关键字段应尽量 NOT NULL。
- 业务表建议包含 created_at、updated_at。
- 需要软删除时使用 deleted_at。
- 金额、状态、时间、JSON 字段必须选择合适数据类型。
- 不要把所有业务字段都塞进 JSON。

## 3. 命名规则

- 表名和字段名使用 snake_case。
- 主键统一叫 id。
- 外键统一使用 xxx_id。
- 创建时间使用 created_at。
- 更新时间使用 updated_at。
- 软删除时间使用 deleted_at。
- 索引命名建议：idx_table_column。
- 唯一索引命名建议：uq_table_column。
- 外键命名建议：fk_table_column。

## 4. Migration 规则

- 禁止手动修改生产数据库结构。
- 表结构变更必须通过 migration。
- migration 必须可 review、可追踪、可回滚。
- 大表变更必须拆分步骤，避免长时间锁表。
- schema migration 和 data migration 尽量分开。
- 大批量数据修复必须分批执行，不允许一次性全表更新。
- 新增 NOT NULL 字段时，优先先加 nullable 字段，再回填，再加约束。
- 删除字段或表前，必须确认代码已不再读取。

## 5. 索引规则

- 新增索引前必须说明对应查询场景。
- WHERE / JOIN / ORDER BY 高频字段优先考虑索引。
- 外键字段通常需要索引。
- 联合索引必须注意字段顺序。
- 禁止盲目给每个字段建索引。
- 建索引后应使用 EXPLAIN 或 EXPLAIN ANALYZE 验证。
- 大表新增索引必须考虑并发索引或在线 DDL。

## 6. 查询规则

- 禁止线上接口无条件查全表。
- 禁止 SELECT *，只查询需要字段。
- 列表接口必须分页。
- page_size 必须有最大限制。
- 大数据量分页优先考虑 cursor/keyset pagination。
- 避免 N+1 查询。
- JOIN 查询必须确认关联字段有索引。
- 慢查询必须分析执行计划。

## 7. 事务规则

- 一组必须同时成功或失败的数据库操作必须放进同一个事务。
- service 层负责 commit / rollback 边界。
- repository 层不应随意 commit。
- 事务中不要调用耗时外部 API。
- 发生异常时必须 rollback。
- 并发更新场景必须考虑幂等、锁或乐观并发控制。

## 8. 连接池和 Session 规则

- 应用启动时创建 engine，不要每次请求创建 engine。
- 每个请求使用独立 session，用完关闭。
- 连接池大小必须与应用并发和数据库容量匹配。
- 查询失败后必须 rollback。
- 不允许长时间占用数据库连接。
- 不允许把 session 当全局变量到处传递。

## 9. 安全规则

- 禁止字符串拼接 SQL。
- 必须使用 ORM 或参数化查询。
- 数据库账号必须使用最小权限。
- 应用账号禁止使用 root / superuser。
- 禁止提交 .env、数据库密码、连接串、生产凭据。
- 日志中禁止打印完整 token、手机号、身份证、银行卡号等敏感信息。
- 生产库操作必须谨慎，必要时需要审批和审计。

## 10. MySQL / PostgreSQL 差异提醒

- PostgreSQL 外键列不会自动创建索引，需要手动补索引。
- PostgreSQL 大表建索引要考虑 CONCURRENTLY。
- MySQL InnoDB 默认事务隔离级别通常是 REPEATABLE READ。
- MySQL 要注意字符集、排序规则、隐式类型转换和在线 DDL。
- 不要假设 MySQL 和 PostgreSQL 的 SQL 行为完全一致。

## 11. 测试规则

数据库相关改动必须至少考虑：

- Repository 查询测试。
- API + DB 集成测试。
- Migration 升级测试。
- Migration 回滚测试。
- 参数错误和空结果测试。
- 唯一约束、外键约束、事务回滚测试。
- 关键慢查询的 EXPLAIN 验证。

## 12. Review Checklist

提交数据库相关代码前，必须检查：

- 是否修改了表结构？
- 是否需要 migration？
- 是否影响历史数据？
- 是否会锁大表？
- 是否需要索引？
- 是否会产生慢查询？
- 是否存在 SQL 注入风险？
- 是否影响事务一致性？
- 是否有测试覆盖？
- 是否有回滚方案？
```

## **测试部分**
**先给你一个总判断：大厂做测试不是“测试同学最后点一点页面”，而是开发、测试、CI、监控一起构成质量闭环。**  
公开工程实践里，Google 和 GitLab 都强调**测试金字塔**（底层大量单元测试，中间适量集成测试，顶层少量端到端测试）：Google Testing Blog 曾给出一个粗略经验比例 **70% 单元测试、20% 集成测试、10% 端到端测试**，GitLab 也说明大多数测试应在单元层，越往上数量越少，因为端到端测试更慢、更贵、更难维护。([Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html?utm_source=chatgpt.com))

**一、大厂测试的核心思路：质量左移**

所谓**质量左移**（把质量保障提前到开发阶段，而不是等上线前才测），意思是：开发写代码时就要想清楚这个功能怎么验证。一个功能不是“我本地跑通了”就结束，而是要有**单元测试**（测函数对不对）、**集成测试**（测模块之间能不能配合）、**接口测试**（测 API 契约）、**回归测试**（防止老 bug 复发）、**端到端测试**（模拟用户完整流程）、**线上监控**（上线后持续观察）。

你可以把它理解成造车：开发不是只把发动机装上去，还要做零件测试、整车测试、刹车测试、碰撞测试、上路监控。软件也是一样，越是大厂项目，越不会只靠人工点点页面。

**二、开发主要负责哪些测试？**

开发最应该负责的是：**自己写的代码能不能被自动验证**。一般来说，开发至少要负责四类测试。

第一类是**单元测试**（unit test，测试一个小函数或一个类的逻辑）。比如你写了一个“计算用户风险等级”的函数，就要测低风险、中风险、高风险、非法输入分别会返回什么。Google 把 small test 大致对应到 unit test，强调它覆盖小范围代码，速度快、定位问题快。([Google Testing Blog](https://testing.googleblog.com/2010/12/test-sizes.html?utm_source=chatgpt.com))

第二类是**服务层/模块测试**。比如你写了 `UserService`，它会调用 `UserRepository`，开发要用假的 repository 或 mock 来测试业务逻辑，不应该每次都连真实数据库。pytest 官方的 `monkeypatch` 可以安全替换函数、环境变量、对象属性，常用于隔离外部依赖。([pytest 文档](https://docs.pytest.org/en/stable/how-to/monkeypatch.html?utm_source=chatgpt.com))

第三类是**接口测试**。比如 FastAPI 的 `/users/{id}` 接口，开发要测正常返回、参数错误、用户不存在、权限不足等。FastAPI 官方提供 `TestClient`，可以像发 HTTP 请求一样测试接口，并要求测试函数通常以 `test_` 开头，这是 pytest 的约定。([FastAPI](https://fastapi.tiangolo.com/tutorial/testing/?utm_source=chatgpt.com))

第四类是**回归测试**（regression test，修 bug 后补一条测试，防止以后再次犯同样错误）。大厂非常重视这个，因为线上 bug 修完如果没有测试保护，下一次重构很可能又改坏。

测试同学通常更关注**测试策略、测试用例设计、端到端流程、兼容性、性能压测、验收测试、探索性测试**；但开发不能把质量全部甩给测试。大厂更常见的责任边界是：**开发保证代码级和接口级质量，测试保证业务流程和用户视角质量，CI 保证每次合并前自动检查，监控保证上线后持续发现问题。**

**三、测试怎么分类？分别有什么作用？**

**1. 单元测试：测一个最小逻辑块**

单元测试就是测一个函数、一个类、一个小模块。它的特点是**快、稳定、定位准**。比如你写了一个函数：

```python
def calculate_risk_score(age: int, balance: float) -> str:
    if age < 0 or balance < 0:
        raise ValueError("invalid input")
    if balance < 10_000:
        return "low"
    if balance < 100_000:
        return "medium"
    return "high"
```

对应测试可以这样写：

```python
import pytest
from app.services.risk import calculate_risk_score


def test_calculate_risk_score_low():
    assert calculate_risk_score(age=25, balance=5000) == "low"


def test_calculate_risk_score_medium():
    assert calculate_risk_score(age=25, balance=50000) == "medium"


def test_calculate_risk_score_invalid_input():
    with pytest.raises(ValueError):
        calculate_risk_score(age=-1, balance=5000)
```

小白理解：**单元测试就是给一个小函数做“小测验”，看它在正常、异常、边界情况下是不是都答对。**

**2. 集成测试：测多个模块能不能配合**

集成测试（integration test，测试多个模块组合起来是否能正常工作）关注的是：service 调 repository、repository 连数据库、API 调 service，这些模块拼起来会不会出问题。GitLab 文档也把测试金字塔作为测试分布指导，强调越往上测试越少但覆盖链路更完整。([GitLab 文档](https://docs.gitlab.com/development/testing_guide/testing_levels/?utm_source=chatgpt.com))

比如你的 FastAPI 接口调用 service，service 调 repository，可以写：

```python
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)


def test_get_user_not_found():
    response = client.get("/users/999")

    assert response.status_code == 404
    assert response.json()["detail"] == "User not found"
```

这个测试不是单独测函数，而是从 API 入口走一遍，看路由、参数解析、异常处理、响应格式是否正确。

**3. 接口契约测试：测 API 输入输出是否稳定**

接口契约测试（contract test，测试接口约定是否被破坏）主要防止“后端改了字段，前端突然挂了”。比如接口以前返回：

```json
{
  "code": "SUCCESS",
  "data": {
    "user_id": 1,
    "name": "Alice"
  },
  "request_id": "req_123"
}
```

测试里就应该断言关键字段存在：

```python
def test_get_user_response_contract():
    response = client.get("/users/1")
    body = response.json()

    assert response.status_code == 200
    assert "code" in body
    assert "data" in body
    assert "request_id" in body
    assert "user_id" in body["data"]
    assert "name" in body["data"]
```

小白理解：**接口契约测试就是检查“合同有没有被偷偷改掉”。**

**4. 回归测试：修过的 bug 必须锁住**

假设你之前有个 bug：用户不存在时系统返回 500。修复后你必须补测试：

```python
def test_missing_user_should_return_404_not_500():
    response = client.get("/users/999")

    assert response.status_code == 404
```

这条测试的意义不是证明新功能多厉害，而是防止以后别人又把这个 bug 改回来。大厂很重视回归测试，因为它能把线上事故沉淀成长期保护。

**5. 端到端测试：模拟真实用户完整流程**

端到端测试（E2E test，从用户入口到系统最终结果的完整链路测试）比如模拟：用户登录 → 发起 Agent 问答 → 系统调用工具 → 返回答案 → 前端展示结果。Atlassian 对 E2E 的解释是，它会在完整应用环境中复制用户行为，验证用户流程是否符合预期。([Atlassian](https://www.atlassian.com/continuous-delivery/software-testing/types-of-software-testing?utm_source=chatgpt.com))

它的优点是最接近真实用户，缺点是慢、维护成本高、失败定位困难。所以大厂一般不会把所有东西都写成 E2E，而是只覆盖**最核心业务路径**，比如登录、支付、下单、报告生成、核心 Agent 问答。

**6. 冒烟测试：上线前快速确认系统没“冒烟”**

冒烟测试（smoke test，发布前快速检查核心功能是否基本可用）就像开机自检。比如上线后先测：

```plain
1. 服务能否启动
2. 健康检查接口是否正常
3. 登录是否正常
4. 核心接口是否正常
5. 数据库/Redis/Kafka 是否连通
```

它不追求覆盖全部细节，只是确认系统没有一上线就崩。

**7. 性能测试和压测：测系统能不能扛住流量**

性能测试关注延迟、吞吐、并发、资源占用。比如你的 Agent 系统要测：

```plain
单轮问答平均延迟是多少？
并发 50 个用户时是否超时？
Redis 缓存命中率如何？
Kafka 消息是否积压？
PostgreSQL 慢查询是否增加？
```

这类测试通常由开发、测试、运维/平台一起做。开发负责优化代码和数据库查询，测试负责压测场景，平台负责监控和容量评估。

**8. Agent/RAG 专项测试：测“智能链路”是否可靠**

如果是你的 Agent/RAG 项目，还要额外测几类：

```plain
意图识别测试：用户问题能不能分到正确路线
工具选择测试：是否选对 Tushare、搜索、数据库等工具
工具参数测试：模型生成的参数是否符合 schema
RAG 召回测试：知识库能不能召回正确文档
证据一致性测试：最终回答是否真的基于工具结果
降级测试：工具失败时是否明确说明，而不是编造
```

例如：

```python
def test_agent_should_not_answer_without_evidence(fake_agent):
    result = fake_agent.run("分析一个不存在的股票代码 ABC999")

    assert result.status == "degraded"
    assert "无法获取可靠数据" in result.answer
```

小白理解：普通后端测试主要测“代码逻辑对不对”，Agent 测试还要测“模型有没有乱选工具、乱用证据、乱编答案”。

**四、开发做测试时应该遵守什么流程？**

一个比较标准的大厂开发流程是：

```plain
写代码前：明确验收标准
写代码中：边写边补单元测试
写完后：补接口测试和异常路径
修 bug 后：补回归测试
提交前：本地跑 pytest / lint
合并前：CI 自动跑测试
上线后：看日志、指标、trace
```

OpenTelemetry 把系统发出的 telemetry 数据分为 traces、metrics、logs，这些数据能帮助判断服务是否按用户预期工作；所以大厂测试不是只在上线前发生，上线后还要通过日志、指标和链路追踪持续验证。([OpenTelemetry](https://opentelemetry.io/docs/concepts/observability-primer/?utm_source=chatgpt.com))

**五、你作为后端开发，最低要做到什么？**

对于你的技术栈 **FastAPI + PostgreSQL + Redis + Kafka + Agent/RAG**，我建议你至少做到：

```plain
1. 每个 service 核心逻辑有单元测试
2. 每个核心 API 有接口测试
3. 数据库 repository 有集成测试或 mock 测试
4. Redis 缓存逻辑测命中、未命中、过期
5. Kafka 消费逻辑测重复消息、失败重试、幂等
6. 每个 bug 修复必须补回归测试
7. Agent 工具必须测参数校验、工具失败、降级回答
8. 提交前跑 pytest 和 ruff
```

你可以在 Cursor 里写一个规则：

```markdown
# Testing Rules

- 修改业务逻辑必须新增或更新测试。
- 优先补单元测试，再补接口/集成测试。
- 修复 bug 必须补回归测试。
- 外部 API、LLM、Redis、Kafka 默认使用 mock 或测试环境，不依赖真实生产服务。
- 不允许为了通过测试删除测试、弱化断言或跳过异常处理。
- 提交前必须运行 pytest 和 ruff check，并说明测试结果。
```

**六、一句话总结**

大厂测试的核心不是“测试同学最后找 bug”，而是**开发阶段就把质量内置进去**：开发负责单元测试、接口测试、回归测试和可测试代码设计；测试同学负责测试策略、端到端流程、验收、探索性测试和质量风险；CI 负责自动拦截问题；上线后通过日志、指标、trace 继续观察。你作为后端开发，最重要的是先把**单元测试、接口测试、回归测试**养成习惯，再逐步补充集成测试、E2E、压测和 Agent 专项评测。

### 灰度测试
**灰度测试**，也叫**灰度发布**或**金丝雀发布**，就是：**新功能不上来就给所有用户用，而是先开放给一小部分用户、机器或流量，观察没问题后再逐步扩大范围**。

你可以把它理解成：做饭时不要一整锅都放新调料，而是先盛一小碗试味道。如果这小碗没问题，再推广到整锅。

**为什么要做灰度测试？**

因为线上环境很复杂。你本地测试、测试环境测试都通过了，也不代表真实用户、真实数据、真实并发、真实网络下一定没问题。

比如你开发了一个新的 **Agent 股票分析功能**，本地看起来回答正常，但上线后可能出现：

用户问题更复杂，**意图识别**错了；  
实时行情接口超时，**工具调用**失败；  
Redis 缓存没命中，延迟变高；  
PostgreSQL 查询慢，接口卡住；  
模型输出不稳定，回答质量下降。

如果你直接全量上线，所有用户都会受影响；但如果你先灰度给 **5% 用户**，即使出问题，也只影响少量用户，并且可以快速回滚。

**灰度测试一般怎么做？**

最常见的方式是按比例逐步放量：

```plain
第 1 步：只给内部员工使用
第 2 步：开放给 1% 用户
第 3 步：扩大到 5% 用户
第 4 步：扩大到 20% 用户
第 5 步：没有明显问题后全量上线
```

每一步都要观察几个核心指标：

```plain
错误率有没有升高？
接口延迟有没有变慢？
CPU / 内存 / 数据库压力是否异常？
用户投诉是否增加？
Agent 工具调用成功率是否下降？
回答质量是否变差？
```

**举个后端例子**

假设你有一个旧版推荐接口和一个新版推荐接口：

```python
def old_recommend(user_id: str):
    return "旧版推荐结果"


def new_recommend(user_id: str):
    return "新版推荐结果"
```

你可以用一个简单的灰度开关控制：只有部分用户走新版。

```python
def is_gray_user(user_id: str) -> bool:
    # 简单示例：让用户 ID 尾号为 0 的用户进入灰度，大约 10%
    return user_id[-1] == "0"


def recommend(user_id: str):
    if is_gray_user(user_id):
        return new_recommend(user_id)
    return old_recommend(user_id)
```

这就是最简单的灰度思想：**不是所有用户都走新逻辑，而是只有一部分用户先试用新逻辑**。

真实大厂里不会写得这么随意，通常会用 **配置中心**（统一管理开关和参数的系统）、**Feature Flag**（功能开关）、**网关流量控制**、**Kubernetes 滚动发布**、**AB 实验平台** 来控制。

**灰度测试和普通测试有什么区别？**

普通测试更多发生在上线前，比如单元测试、接口测试、集成测试、测试环境验证。

灰度测试发生在**真实线上环境**，只是控制影响范围。它测的是：**真实用户、真实流量、真实数据下，新功能是否稳定可靠**。

可以这样区分：

```plain
单元测试：测一个函数对不对
接口测试：测一个 API 对不对
集成测试：测多个模块配合对不对
灰度测试：测新功能在线上小范围运行是否安全
```

**灰度测试和 AB 测试有什么区别？**

它们很像，但目标不同。

**灰度测试**主要关注**稳定性和风险控制**。问题是：“新版本会不会出事故？”

**AB 测试**主要关注**效果对比**。问题是：“新版效果是不是比旧版更好？”

比如金融 Agent：

灰度测试关心：新版 Agent 会不会报错、延迟会不会升高、工具调用会不会失败。  
AB 测试关心：新版 Agent 的用户满意度、点击率、留存率是否比旧版更好。

**在你的 Agent 项目里，灰度测试可以怎么用？**

比如你新增了一个 **新闻情绪分析 Agent**，不要直接替换原来的回答链路。可以这样做：

```plain
旧链路：用户问题 → 行情工具 → 基础分析 → 回复
新链路：用户问题 → 行情工具 + 新闻工具 + 情绪分析 → 综合回复
```

灰度方案可以是：

```plain
内部账号先走新链路
少量测试用户走新链路
只对“新闻分析类问题”启用新链路
只在白天低峰期启用
如果工具失败率超过阈值，自动切回旧链路
```

这就是比较工程化的做法：**新能力先小范围验证，出了问题可以立刻降级到旧能力**。

**灰度测试最关键的不是“放量”，而是“可回滚”**

一个合格的灰度方案必须回答三个问题：

```plain
怎么判断新功能有问题？
出问题后怎么快速关闭？
关闭后用户是否能继续使用旧功能？
```

所以灰度通常会配合 **降级方案**（新功能失败后走旧逻辑）、**回滚机制**（恢复到旧版本）、**监控告警**（发现错误率、延迟、失败率异常）。

**一句话总结**

**灰度测试就是把新功能先给少量真实用户或少量真实流量使用，通过监控错误率、延迟、成功率和用户反馈来判断是否安全，再逐步扩大范围；它的核心价值是降低上线风险，让新功能即使出问题也能快速发现、快速回滚、少影响用户。**

### 什么是CI/CD测试？
**CI/CD 测试**，简单来说就是：**把测试放进自动化流水线里，让代码每次提交、合并、发布前都自动跑一遍检查，避免“人忘了测”导致线上出问题。**

你可以把它理解成工厂里的**自动质检线**。开发写完代码，相当于生产了一个零件；CI/CD 测试就是让这个零件自动经过格式检查、单元测试、接口测试、安全扫描、构建检查，只有都通过了，才允许进入下一步。

**CI 是什么？**

**CI** 是 **Continuous Integration（持续集成）**，意思是：开发每次提交代码后，系统自动帮你检查这次代码有没有问题。

比如你把代码 push 到 GitHub，CI 会自动做这些事：

```plain
1. 拉取最新代码
2. 安装依赖
3. 检查代码格式
4. 运行单元测试
5. 运行接口测试
6. 检查类型错误
7. 生成测试报告
```

如果有一步失败，系统就会提示：**这次提交不能合并**。

对于你这种 **FastAPI 后端项目**，CI 里常见命令是：

```bash
ruff check .
ruff format --check .
pytest
```

其中，**ruff** 是代码格式和静态检查工具（提前发现格式、未使用变量、低级错误），**pytest** 是 Python 测试框架（自动运行测试用例）。

**CD 是什么？**

**CD** 一般有两种含义：

**Continuous Delivery（持续交付）**：代码通过测试后，自动打包好，随时可以发布，但是否上线由人确认。

**Continuous Deployment（持续部署）**：代码通过测试后，自动发布到测试环境、预发布环境，甚至生产环境。

小白可以这样理解：

```plain
CI：先检查代码有没有问题
CD：检查通过后，把代码自动打包、部署出去
```

所以 **CI/CD 测试** 就是：**在代码从提交到上线的整个过程中，自动跑各种测试，确保代码质量。**

**举个最简单的例子**

假设你写了一个 FastAPI 接口：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health_check():
    return {"status": "ok"}
```

你写一个测试：

```python
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_health_check():
    response = client.get("/health")
    assert response.status_code == 200
    assert response.json()["status"] == "ok"
```

如果你本地运行：

```bash
pytest
```

测试通过，说明这个接口没问题。

但是在大厂里，不能只靠你自己手动跑。因为你可能会忘，也可能本地环境和服务器环境不一样。所以会把它放进 CI 里，让 GitHub Actions、GitLab CI、Jenkins 这类工具自动跑。

比如 GitHub Actions 可以这样写：

```yaml
name: Backend CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: 拉取代码
        uses: actions/checkout@v4

      - name: 安装 Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: 安装依赖
        run: |
          pip install -r requirements.txt

      - name: 代码检查
        run: |
          ruff check .

      - name: 运行测试
        run: |
          pytest
```

这段配置的意思是：只要有人向 `main` 分支提交代码，或者发起 Pull Request，系统就自动安装环境、检查代码、运行测试。

**CI/CD 里一般会跑哪些测试？**

第一类是**代码格式检查**。它检查代码有没有明显不规范的地方，比如未使用变量、导入顺序混乱、格式不统一。作用是让代码风格保持一致。

第二类是**单元测试**。它测试一个函数、一个类、一个 service 是否正确。比如测试风险评分函数、金额计算函数、参数校验函数。

第三类是**接口测试**。它测试 API 是否返回正确状态码和响应结构。比如 `/users/{id}` 用户不存在时是否返回 404，而不是 500。

第四类是**集成测试**。它测试多个模块组合起来是否正常，比如 FastAPI + PostgreSQL + Redis 是否能配合工作。

第五类是**安全检查**。它检查是否有硬编码密钥、依赖漏洞、危险代码、SQL 注入风险等。

第六类是**构建测试**。它检查 Docker 镜像能不能正常构建，项目能不能正常启动。

第七类是**部署后冒烟测试**。它在部署后快速访问几个核心接口，比如 `/health`、登录接口、核心业务接口，确认系统没直接崩。

**在你的项目里，CI/CD 可以怎么设计？**

如果你的项目是 **FastAPI + PostgreSQL + Redis + Kafka + Vue + Agent/RAG**，一个比较合理的 CI/CD 测试链路是：

```plain
提交代码
  ↓
代码格式检查：ruff / eslint
  ↓
后端单元测试：pytest
  ↓
接口测试：FastAPI TestClient
  ↓
数据库迁移检查：Alembic migration
  ↓
前端构建测试：npm run build
  ↓
Docker 构建测试
  ↓
部署到测试环境
  ↓
冒烟测试
  ↓
人工确认或自动发布
```

对于 Agent 项目，还可以加：

```plain
Agent 工具调用测试
RAG 检索测试
Prompt 输出格式测试
降级逻辑测试
trace 是否正常记录
```

比如你可以测试：当实时行情工具失败时，Agent 是否会降级，而不是编造数据。

**CI/CD 测试和本地测试有什么区别？**

**本地测试**是你自己在电脑上跑，速度快，适合开发时随时检查。

**CI/CD 测试**是在远程服务器上自动跑，环境更干净，更接近团队统一标准，适合合并代码前做质量门禁。

可以这样理解：

```plain
本地测试：自己先检查一遍作业
CI 测试：老师统一批改
CD 测试：交卷前最后确认能不能正式提交
```

**为什么大厂特别重视 CI/CD 测试？**

因为大厂项目通常多人协作，代码每天都在变。如果没有自动测试，就会出现：

```plain
A 改了接口，B 的前端页面挂了
C 改了数据库字段，老功能查不到数据
D 修了一个 bug，却引入另一个 bug
E 本地能跑，服务器跑不起来
```

CI/CD 测试的价值就是：**在代码合并和发布前，尽早发现问题，降低线上事故概率。**

**一句话总结**

**CI/CD 测试就是把代码检查、单元测试、接口测试、集成测试、安全扫描、构建和部署验证放进自动化流水线里，让每次提交代码后系统自动帮你质检；CI 负责“合并前测代码”，CD 负责“发布前后测部署”，核心目标是减少人工遗漏，保证代码稳定上线。**
