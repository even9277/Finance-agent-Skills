## 1、**这一部分在 Harness Engineering 中的定位**

在 Harness Engineering（Agent 运行承载工程）里，**验证、观测与评测** 是把 Agent 从“能跑 demo”推进到“能上线、能排查、能持续迭代”的关键层。前面讲的工作空间、工具调用、记忆、上下文、HITL、安全边界，解决的是 **Agent 能不能执行任务**；这一部分解决的是 **执行过程是否可见、结果是否可靠、错误是否能定位、系统是否能持续变好**。因为 Agent 和传统后端接口不一样，它不是固定输入对应固定输出，而是同一个用户问题可能触发不同检索结果、不同工具链、不同路径和不同回答。所以只看最后一句回答，根本无法判断它中间有没有走错路。

可以把它理解成给 Agent 装三套系统：第一套是 **观测系统**，像行车记录仪，记录 Agent 每一步做了什么；第二套是 **验证系统**，像质检员，检查工具调用、证据、格式、安全边界是否符合要求；第三套是 **评测系统**，像考试和回归测试，用固定样本集反复测试系统版本，判断改 prompt、换模型、调 RAG、改工具后到底变好了还是变差了。LangSmith 官方把 observability 描述为从单条 trace 到生产级性能指标的可见性；Langfuse 也强调 LLM 应用 tracing 要记录 prompt、模型响应、token、延迟、工具调用和检索步骤，因为没有这些观测，调试基本就是猜。([LangChain 文档][1])

**这一节最终要学会什么**

这一节的主线可以概括成一句话：**观测让 Agent 的执行过程可见，验证让每一步符合规则，评测让系统改动可量化，回放和回归集让问题不会反复出现。** 真正大厂关注的不是“我的 Agent 回答看起来不错”，而是它能不能回答这几个问题：这次用了哪些上下文？调用了哪些工具？为什么选这个工具？参数从哪里来？工具有没有成功？最终答案是否基于证据？成本和延迟是否可接受？高风险动作是否被拦截？版本升级后有没有回归？

**面试口述版**

在 Harness Engineering 里，验证、观测和评测是 Agent 从 demo 走向上线的关键层。因为 Agent 不是固定流程，同一个输入可能触发不同上下文、不同工具和不同执行轨迹，所以不能只看最终答案。我的设计会分三层：第一层是 observability，也就是给每次运行记录 trace，包含用户输入、上下文来源、planner 决策、工具调用、工具参数、工具返回、token、延迟、成本、最终回答和错误类型；第二层是 validation，在工具调用前检查权限、参数和 schema，在工具返回后检查是否成功和是否有证据，在最终生成后检查格式、引用和安全边界；第三层是 evaluation，用固定数据集评测任务完成率、工具调用成功率、参数错误率、轨迹一致性、引用准确率、成本延迟和安全违规率。数据集可以来自人工设计的高频场景、边界样本、线上失败 trace 和合成样本，评测方法可以结合规则、代码、LLM-as-Judge 和人工标注。上线后把失败 trace 加回回归集，修复后再跑离线实验，确认指标提升且没有引入新问题。这样 Agent 的迭代就不是凭感觉改 prompt，而是基于 trace 和 eval 的闭环优化。

## 2、**为什么 Agent 不能只评最终答案**

**先给结论**

Agent 不能只评最终答案，因为 Agent 的结果不是一次模型生成，而是一条完整执行链路：**上下文选择 → 规划决策 → 工具选择 → 工具参数 → 权限审批 → 工具执行 → 状态写回 → artifact 生成 → 最终回答**。最终答案看起来对，不代表中间过程安全、可靠、可复现；最终答案错，也不一定是模型生成问题，可能是路由错、RAG 证据错、工具参数错、权限没拦住、checkpoint 恢复错。所以产业级 Agent 评测必须评 **trajectory（执行轨迹）**，也就是每一步到底做了什么，而不是只看最后一句话。LangSmith 的 Agent Evaluation 也明确强调，Agent 评测会捕获完整步骤轨迹、工具调用和中间决策，用来定位复杂 workflow 到底哪里出错。([LangChain][1])

**为什么最终答案不够**

普通问答系统主要评最终回答就够了，因为它大多只做一次模型生成；但 Agent 是一个能规划、调用工具、读写文件、生成产物、跨多轮恢复的系统。一个最终答案可能“看起来合理”，但中间过程可能有严重问题。比如金融 Agent 最后说“这只基金短期风险较高，建议谨慎”，这句话本身可能没错，但如果它没有查最新行情、引用了过期研报、没有读取用户风险偏好，或者跳过了合规提示，那这个答案在工程上仍然是不合格的。

反过来，最终答案不理想时，也不能只说“模型不行”。可能是 **Context Gateway** 没注入正确上下文，可能是 **Tool Router** 没给正确工具，可能是 **RAG** 召回了错误文档，可能是 **Observation Builder** 把工具结果摘要错了，也可能是 **artifact** 版本错乱。OpenClaw 对 Agent loop 的定义很适合说明这一点：真实 agent run 包含 intake、context assembly、model inference、tool execution、streaming replies、persistence，这才是从消息变成动作和最终回复的权威路径。([OpenClaw][2])

**只评最终答案会漏掉哪些问题**

第一，会漏掉 **工具误用**。比如用户问“查基金净值”，Agent 最终给了一个净值表，但中间其实没有调用基金净值工具，而是用模型猜了一个数字。最终回答如果没有人工逐项核验，很难发现它没有真实查证。

第二，会漏掉 **参数错误**。Agent 可能调用了正确工具，但股票代码、日期范围、市场类型传错了。例如把 `600519.SH` 误识别成港股代码，最终答案看起来像金融分析，但底层数据是错的。

第三，会漏掉 **权限和安全问题**。Agent 可能最后回答正常，但过程中尝试读取 `.env`、调用 Bash、访问 CRM、写数据库或外发草稿。如果只评最终答案，就看不到这些高风险尝试。

第四，会漏掉 **证据链问题**。最终答案可能引用“根据最新数据”，但实际 RAG 证据是旧文档，Web Search 没有执行，或者工具结果没有 timestamp。产业级金融、销售、客服系统必须知道结论来自哪里。

第五，会漏掉 **状态和恢复问题**。Agent 可能本轮答对了，但 checkpoint 没保存、tool ledger 没写入、artifact 没登记。下次用户说“继续上一版”时，系统就无法恢复。

第六，会漏掉 **成本和延迟问题**。最终答案对，但调用了 20 次无关工具、重复查同一个 API、上下文塞了大量无关历史，线上就会很慢、很贵、不可扩展。

**Agent 应该评哪些中间环节**

我会把 Agent 评测拆成七层：

| 评测层    | 看什么                                  | 例子                   |
| ------ | ------------------------------------ | -------------------- |
| 上下文评测  | 是否注入了正确状态、记忆、RAG、tool ledger         | “继续上一版”是否加载 artifact |
| 路由评测   | 是否选对 function/MCP/Skill/Bash/Code    | 查行情是否走行情工具           |
| 规划评测   | plan 是否合理、步骤是否多余或遗漏                  | 基金报告是否先取数再分析         |
| 工具评测   | 工具名、参数、重试、错误处理是否正确                   | 基金代码、日期范围是否正确        |
| 安全评测   | 是否越权、是否需要审批、是否进 sandbox              | 外发报告是否 HITL          |
| 状态评测   | checkpoint、tool ledger、artifact 是否写对 | 工具成功后是否可恢复           |
| 最终答案评测 | 回答是否准确、完整、可读、合规                      | 是否有风险提示和证据引用         |

所以最终答案只是最后一层，不是全部。

**执行轨迹为什么重要**

Agent 的执行轨迹（trajectory）就是一次任务中所有关键步骤的记录，包括模型每次调用、工具调用、检索步骤、中间输出和决策顺序。LangChain 2026 年关于 Agent 改进的文章也强调，trace 会捕获完整 agent run：每次 LLM 调用、每次工具调用、每次检索步骤、每个中间输出，以及这些决策之间的顺序关系；它是“Agent 在这次输入、这些条件下实际做了什么”的记录。([LangChain][3])

这对排查非常关键。比如金融 Agent 答错了“黄金最近为什么下跌”，如果有 trace，我们可以看：

* Gateway 有没有判断这是最新事实问题；
* 有没有触发 Web Search 或实时行情工具；
* 检索结果是不是最新；
* 是否引用了权威来源；
* 模型是否把旧记忆当成当前事实；
* 工具是否超时后被错误降级；
* 最终答案是否遗漏了风险提示。

没有轨迹，只能看最终答案，基本就是猜。

**仓库证据摘要**

**DeerFlow 2.0** 的启发是：它不是一个单轮问答系统，而是一个 SuperAgent harness，官方描述中包含 **sub-agents、memory、sandboxes、tools、skills**，用于处理可能持续分钟到小时的 research、coding、creation 任务。这样的系统天然不能只看最终回答，因为中间的 subagent 分工、sandbox 执行、memory 使用、tool 调用和 artifact 产出都会影响结果质量。([DeerFlow][4])

**OpenClaw** 的启发是：它把 Agent loop 明确定义为 **intake → context assembly → model inference → tool execution → streaming replies → persistence**。这说明“最终回复”只是 loop 的最后阶段之一，前面的上下文组装、工具执行和状态持久化都必须进入评测范围。([OpenClaw][2])

**Hermes Agent** 的启发是：它的新版本强调 durable multi-agent board，包括 heartbeat、reclaim、zombie detection、per-task retries、hallucination recovery；同时 Checkpoints v2 重写 state persistence，Gateway 支持重启后自动恢复中断 session。([GitHub][5]) 这说明长任务 Agent 的评测不能只看输出内容，还要看任务是否能恢复、是否卡死、是否重复执行、是否有 checkpoint。

**cc-haha** 的启发是：它在桌面端提供多会话工作台、branch/worktree、右侧代码改动面板、diff、权限确认流、用量统计等能力。([GitHub][6]) 它的 AGENTS.md 还把 agent-loop、tool execution、provider routing、model selection、permissions、session resume 等核心路径列为需要测试或质量门禁覆盖的路径。([GitHub][7]) 这说明真实 Coding Agent 不只评最终回答，而要评工具执行、权限、会话恢复和代码变更过程。

**LangSmith** 的证据更直接：它的评测文档明确说 human evaluation 可以 review application outputs and traces，也就是同时看最终输出和所有中间步骤；LangSmith Evaluation 还说明 Agent evaluation 会捕获完整步骤轨迹、工具调用和推理过程，用于调试复杂 workflow。([LangChain 文档][8])

**放到金融投资顾问 Agent 项目里怎么讲**

结合你的金融投资顾问 Agent，不能只评“最后回答像不像金融分析”。比如用户问“帮我对比三只半导体基金”，最终报告看起来结构完整还不够，还要评：

第一，**路由是否正确**：是否识别为基金对比 Skill，而不是普通聊天回答。
第二，**上下文是否正确**：是否读取用户风险偏好、当前任务状态、最新行情、上一版 artifact。
第三，**工具是否正确**：是否调用基金净值、基金持仓、行业指数、新闻检索，而不是凭模型常识生成。
第四，**参数是否正确**：基金代码、日期范围、复权口径、交易日是否正确。
第五，**代码计算是否正确**：收益率、最大回撤、波动率是否由 Python 计算，而不是模型口算。
第六，**证据是否绑定**：报告中的关键结论是否有 source_refs。
第七，**安全是否合规**：有没有越界给出确定性买卖建议，是否加了风险提示。
第八，**状态是否写回**：报告 artifact 是否有版本、状态、审核记录，tool ledger 是否记录工具结果。
第九，**最终答案是否可读**：结构是否清楚，是否适合用户理解。

这样才能证明这个 Agent 不只是“会写一段金融话术”，而是一个可控、可恢复、可审计的工程系统。

**常见错误回答**

不建议只说：“因为 Agent 中间有工具调用，所以要看工具调用。”这句话太浅。面试官更想听的是：**Agent 是多步骤状态机，最终答案只是末端表现；只有评轨迹，才能判断错误来自上下文、规划、工具、权限、状态、证据还是生成。**

也不要说：“只要最终答案对，中间过程不重要。”这在普通聊天里可能勉强成立，但在金融、客服、销售、代码修改、数据分析场景不成立。因为中间过程可能涉及真实外部副作用，比如写库、发邮件、删文件、提交 PR。即使最终答案看起来正常，中间越权调用也属于严重事故。

**可以怎么设计评测集**

我会设计两类评测：

第一类是 **结果评测**：回答准确性、完整性、可读性、合规性、引用质量。
第二类是 **过程评测**：上下文命中、工具选择、参数正确、证据绑定、审批触发、重试降级、checkpoint 写入、artifact 版本。

例如 100 条金融 Agent 测试样例中，可以人工标注：

```text
应该调用的 Skill：fund_compare_skill
必须调用的工具：get_fund_nav、get_fund_holding、get_market_index
必须注入的上下文：user_risk_profile、latest_trading_day
必须生成的 artifact：fund_compare_report_draft
禁止行为：直接给买入/卖出指令、外发报告
```

跑完后不仅看最终报告，还看 trace：有没有用对工具、有没有调用多余高风险工具、有没有写 artifact、有没有绑定证据。

**评测指标可以这样设计**

| 指标                       | 含义                          |
| ------------------------ | --------------------------- |
| Tool Selection Accuracy  | 工具选择是否正确                    |
| Tool Argument Accuracy   | 工具参数是否正确                    |
| Evidence Grounding Rate  | 关键结论是否有证据                   |
| Context Hit Rate         | 是否注入了正确状态/记忆/RAG            |
| Unsafe Tool Call Rate    | 是否误调用高风险工具                  |
| HITL Trigger Rate        | 高风险动作是否进入审批                 |
| Checkpoint Write Success | 长任务状态是否可恢复                  |
| Artifact Traceability    | artifact 是否有版本和 source_refs |
| Redundant Tool Call Rate | 是否重复调用无关工具                  |
| Final Answer Quality     | 最终回答是否准确、可读、合规              |

**一句话总结**

Agent 不能只评最终答案，因为最终答案只是执行链路的末端；真正决定系统是否可靠的是它有没有拿对上下文、选对工具、传对参数、守住权限、写好状态、绑定证据，并能在出错时通过 trace 找到问题。

**2–5 分钟面试口述版**

我理解 Agent 不能只评最终答案，是因为 Agent 不是一次普通模型生成，而是一条完整的执行链路。普通聊天机器人主要风险是最后回答对不对；但 Agent 会做上下文选择、任务规划、工具调用、文件读写、代码执行、状态持久化和 artifact 生成，所以最终答案只是最后一个结果，不能代表整个过程安全、可靠、可复现。

比如金融投资顾问 Agent 最后生成了一段基金分析，表面看结构完整、语气专业，但中间可能没有查最新行情，可能基金代码传错了，可能用了过期 RAG 证据，可能没有读取用户风险偏好，也可能跳过了风险提示。更严重的是，它可能过程中尝试调用外发邮件、写 CRM 或删除文件，只是最终答案没暴露出来。如果只评最终答案，这些过程风险都看不到。

所以产业级 Agent 要评 trajectory，也就是执行轨迹。这个轨迹包括 Context Gateway 有没有注入正确状态、Router 有没有选对 Skill 或工具、工具参数是否正确、RAG 证据是否最新可信、工具失败有没有重试或降级、权限审批是否触发、checkpoint 是否写入、artifact 是否带版本和 source_refs。LangSmith 的 Agent Evaluation 就强调要捕获完整步骤轨迹、工具调用和中间决策，用来定位复杂 workflow 到底哪里出错。

从实践看，OpenClaw 把 Agent loop 定义为 intake、context assembly、model inference、tool execution、streaming replies、persistence，这说明最终回复只是其中一环。DeerFlow 2.0 是 SuperAgent harness，组织 sub-agents、memory、sandboxes、tools、skills，处理分钟到小时级任务，这类系统显然不能只看最后报告。Hermes Agent 的 Kanban、heartbeat、checkpoint、auto-resume 说明长任务还要评恢复能力、卡死检测和状态持久化。cc-haha 的桌面端也把 diff、权限审批、tool execution、session resume、provider routing 放进质量路径里，这说明真实 Agent 产品要评过程，而不是只评一段文字。

如果结合我的金融 Agent，我会同时评结果和过程。结果上看报告是否准确、完整、可读、合规；过程上看是否识别为基金对比 Skill，是否调用净值、持仓、行业指数和新闻工具，是否用 Python 计算收益率和最大回撤，是否绑定证据，是否读取用户风险偏好，是否触发外发审批，是否写入 artifact 和 tool ledger。这样才能证明这个 Agent 不是“碰巧写对”，而是每一步都可控、可恢复、可审计。

我的一句话总结是：Agent 的评测不能只看最终答案，因为最终答案是表象；真正的大厂 Agent 评测要看完整执行轨迹，判断它是否拿对上下文、选对工具、传对参数、守住权限、绑定证据、写好状态，并能通过 trace 复盘每一步。




## 2-1、一次 trace 应该记录哪些内容？如果用户反馈“回答错了”，为什么没有 trace 就很难复现？trace 和普通后端日志有什么区别？
**先给结论**

一次 Agent trace（执行轨迹）应该记录的不是“最后回答”，而是一次请求从进入系统到完成交付的完整链路：**用户输入、上下文选择、模型调用、规划过程、工具调用、参数、工具结果、权限审批、错误重试、状态写回、artifact 版本、最终输出、耗时与成本**。如果用户反馈“回答错了”，没有 trace 就只能看最终文本，很难判断错误到底来自 **上下文没取到、RAG 召回错、工具参数错、模型生成错、状态恢复错、还是权限/审批漏了**。LangSmith 对 tracing 的定义就是捕获一次请求中从输入到最终输出的每一步完整记录；OpenAI Agents SDK 的 tracing 也覆盖 LLM generation、tool calls、handoffs、guardrails 和自定义事件。([LangChain 文档][1])

**一次 trace 应该记录哪些内容**

我会把一次 Agent trace 拆成 **root trace + 多个 span（一次 trace 里的子步骤）**。OpenTelemetry 里 span（跨度，一次具体操作）包含名称、父 span、起止时间、属性、事件、状态等信息；多个 span 通过同一个 trace_id 和父子关系串起来，形成一次请求的端到端视图。([OpenTelemetry][2])

| Trace 内容            | 应该记录什么                                                     | 用来排查什么        |
| ------------------- | ---------------------------------------------------------- | ------------- |
| **请求入口**            | `trace_id`、`user_id`、`session_id`、`task_id`、时间、入口渠道、用户原始问题 | 确认是哪次请求       |
| **上下文路由**           | Gateway 判断、调用了短期状态/长期记忆/RAG/Web/tool ledger 哪些源            | 为什么模型看到这些上下文  |
| **Context Packing** | 注入了哪些候选上下文、token 数、哪些被裁剪、裁剪原因                              | 是否漏掉关键证据或塞入噪声 |
| **模型调用**            | 模型名、temperature、prompt/messages 摘要、输出、usage、延迟             | 判断是否是模型生成问题   |
| **规划与路由**           | 选择了哪个 Skill、Agent、工具路线、plan 步骤                             | 判断规划是否合理      |
| **工具调用**            | 工具名、参数、参数 hash、开始/结束时间、返回状态、错误、重试次数                        | 判断工具是否选错或参数错  |
| **RAG/Web 检索**      | query、Top-K 片段、文档 ID、source_ref、时间戳、rerank 分数              | 判断证据是否正确、是否过期 |
| **权限审批**            | 是否命中 policy、审批人、approve/reject/edit、审批前后参数 hash            | 判断高风险动作是否越权   |
| **状态写回**            | checkpoint、tool ledger、memory write、artifact metadata 写入状态 | 判断能否恢复和复现     |
| **Artifact**        | artifact_id、version、status、source_refs、diff、审核状态           | 判断交付的是哪一版     |
| **最终输出**            | 最终回答、引用、风险提示、输出格式                                          | 判断用户看到什么      |
| **性能与成本**           | 总延迟、每个 span 延迟、token、费用、缓存命中                               | 判断慢在哪里、贵在哪里   |
| **异常与降级**           | timeout、retry、fallback、human fallback、degradation reason   | 判断系统是否正确降级    |

这里的关键是：**trace 不是一堆散乱日志，而是一棵有父子关系的执行树**。例如一次金融报告生成任务，root trace 是 `generate_fund_report`，下面可以有 `context_gateway`、`rag_retrieve`、`get_fund_nav`、`get_fund_holding`、`llm_generate_draft`、`artifact_write`、`compliance_check` 等 span。

**如果用户反馈“回答错了”，为什么没有 trace 很难复现**

因为 Agent 的错误往往不是最后一步才发生，而是在中间某一步已经埋下了问题。没有 trace，只能看到用户问题和最终回答，排查时会陷入“猜测”。

比如用户说“这个基金分析错了”，如果没有 trace，你不知道：

第一，**当时模型看到的上下文是什么**。它有没有读到用户风险偏好？有没有读到上一版报告？有没有拿到最新交易日？有没有把旧记忆当成当前事实？

第二，**RAG 或 Web Search 检索到了什么**。它是否召回了错误文档？是否使用了过期新闻？是否把低可信网页当成权威证据？

第三，**工具是否真的执行成功**。模型说“根据最新持仓”，但它可能根本没调用持仓工具，也可能工具 timeout 后用了缓存，还可能参数传错基金代码。

第四，**工具参数是否正确**。金融场景里代码、日期、复权方式、交易市场、时间窗口传错，最终分析就会系统性错误。

第五，**中间状态有没有写入**。如果 tool ledger 没记录，artifact 没版本，checkpoint 没保存，下一次用户说“继续刚才那个”，系统就无法恢复同一现场。

第六，**是否触发了降级或审批**。比如外发报告前是否通过合规检查？工具失败后是否进入 fallback？没有 trace 就看不到这些决策。

所以没有 trace 的本质问题是：**无法重建当时模型的输入、工具环境、执行顺序、状态版本和证据来源**。用户看到的是“错的回答”，工程师需要知道的是“哪一个环节让它错了”。

**trace 和普通后端日志有什么区别**

普通后端日志更像“某个组件在某个时间打印了一行事件”；trace 更像“某个用户请求从入口到出口的完整路径”。Microsoft 的工程实践文档也区分了 logs 和 traces：日志记录组件内离散事件，而 trace 提供更连续的应用流程视图，能看到函数、持续时间、参数、执行到多深等信息。([GitHub Microsoft][3]) OpenTelemetry 也把 trace 理解成带上下文、关联关系和层级结构的结构化日志集合，因此能跨进程、服务和机器表示端到端系统视图。([OpenTelemetry][2])

| 对比项          | 普通后端日志                   | Agent Trace                         |
| ------------ | ------------------------ | ----------------------------------- |
| **粒度**       | 单个事件                     | 一次请求的完整执行树                          |
| **组织方式**     | 时间顺序散落                   | `trace_id + span_id + parent_id` 串联 |
| **关注点**      | 某组件发生了什么                 | 一次 Agent run 为什么这样执行                |
| **可复现性**     | 需要人工拼日志                  | 可以按链路回放                             |
| **LLM 相关信息** | 通常不记录 prompt、工具选择、RAG 证据 | 记录上下文、模型调用、工具调用、证据                  |
| **排错方式**     | grep 关键字                 | 看完整 trajectory                      |
| **适用问题**     | 某服务报错、接口超时               | Agent 答错、误用工具、证据错、上下文错              |
| **评测价值**     | 辅助定位异常                   | 可转成离线 eval 样例和 bad case             |

简单说：**日志回答“某个点发生了什么”，trace 回答“这次请求是怎么一步步走到这个结果的”。**

**Agent trace 和传统微服务 trace 的不同点**

传统微服务 trace 主要记录 HTTP、数据库、缓存、消息队列等调用链；Agent trace 还必须记录 **模型输入输出、上下文候选、工具选择、RAG 证据、memory 命中、审批状态、artifact 版本**。OpenAI Agents SDK 的 tracing 明确覆盖 LLM generations、tool calls、handoffs、guardrails 和 custom events；DeerFlow 2.0 backend 也说明启用 LangSmith 后，LLM calls、agent runs、tool executions、middleware processing 都会进入 trace。([OpenAI][4])

所以 Agent trace 更关注“智能决策链路”：

```text
用户问题
 → Gateway 为什么选这些上下文
 → Router 为什么选这个 Skill
 → LLM 为什么调用这个工具
 → 工具参数是什么
 → 工具结果是什么
 → 模型如何根据 observation 改写 plan
 → 是否触发 guardrail / approval
 → 最终 artifact 和回答是什么
```

这比普通接口日志更接近“审计 Agent 思考和行动过程”。

**金融投资顾问 Agent 里 trace 应该怎么落地**

结合你的金融 Agent 项目，一次 trace 可以这样设计：

**用户反馈“回答错了”的排查流程**

如果用户说“回答错了”，我会按 trace 逐层查：

1. **查入口**：用户原始问题有没有被正确解析？是否有歧义？
2. **查 Gateway**：是否加载了正确用户、会话、task_id 和上下文源？
3. **查 Packer**：关键证据有没有被 token 裁剪掉？长期记忆有没有错误注入？
4. **查 RAG/Web**：检索 query 是否正确？文档是否旧？source_ref 是否权威？
5. **查工具**：工具是否调用？参数是否正确？返回是否成功？是否用了缓存？
6. **查模型输出**：模型是否误读 observation？是否把推测说成事实？
7. **查状态写回**：artifact 版本是否正确？tool ledger 是否写入？
8. **查最终回答**：是否引用了正确证据？是否符合合规和格式要求？

这样就能把“回答错了”拆成可定位的工程问题，而不是泛泛地说“模型幻觉”。

**如何避免 trace 本身带来隐私和成本问题**

Trace 不能无脑全量记录所有内容。金融、企业知识库和用户隐私场景要做几件事：

第一，**敏感字段脱敏**，例如身份证、手机号、token、邮箱正文、持仓明细只存摘要或 hash。
第二，**分级保存**，开发环境可以记录更详细，生产环境默认记录摘要和 source_ref。
第三，**可配置采样**，普通成功请求采样，高风险、失败、投诉请求全量保留。
第四，**保留周期控制**，不同 trace 类型设置 TTL。
第五，**权限隔离**，不是所有工程师都能看用户完整 trace。
第六，**关联而不复制**，artifact、RAG 文档、工具结果尽量存引用，不重复存全文。

这样 trace 才是可用的观测系统，而不是新的数据泄露源。

**仓库证据摘要**

DeerFlow 2.0 的 backend README 明确写到内置 LangSmith 和 Langfuse tracing；启用 LangSmith 后，**LLM calls、agent runs、tool executions、middleware processing** 都会在 LangSmith dashboard 中可见，这很适合说明 SuperAgent 不只记录最终答案，而要记录模型、工具和中间件完整链路。([GitHub][5])

OpenAI Agents SDK 的 tracing 文档说明，它内置 tracing，会收集 agent run 中的 **LLM generations、tool calls、handoffs、guardrails、自定义事件**，用于开发和生产环境中的调试、可视化和监控。([OpenAI][4])

LangSmith Observability 文档说明，它提供从 individual traces 到 production-wide performance metrics 的完整可见性，并支持查看 traces、监控性能、收集 feedback、自动检测 recurring issues 等；Tracing quickstart 也把 trace 定义为一次请求中从输入到最终输出的每一步完整记录。([LangChain 文档][6])

OpenTelemetry 和 Microsoft 工程实践提供了 trace 与日志区别的底层解释：trace 由带父子关系的 span 组成，用 `trace_id` 串起跨服务端到端路径；日志更偏离散事件，trace 更能表示一次请求在系统中的连续流程。([OpenTelemetry][2])

**一句话总结**

一次 Agent trace 应该记录“这次请求如何从用户输入走到最终输出”的完整执行树；没有 trace，用户说回答错了时就无法复原当时的上下文、工具、证据、参数、状态和模型决策，只能凭最终文本猜原因。

**2–5 分钟面试口述版**

我理解一次 Agent trace 不是普通日志，而是一次请求的完整执行轨迹。因为 Agent 的结果不是一次模型生成，而是经过上下文选择、模型规划、工具调用、权限审批、状态写回、artifact 生成和最终回答多个步骤。Trace 要记录的就是这条链路中每一步到底发生了什么。

具体来说，一次 trace 至少要有 trace_id、user_id、session_id、task_id、用户原始输入、入口时间。然后要记录 Context Gateway 的决策，比如本轮是否读取了短期状态、长期记忆、RAG、Web Search、tool ledger；Context Packer 最终注入了哪些上下文、用了多少 token、哪些内容因为预算被裁剪。接下来要记录每次模型调用，包括模型名、参数、输入摘要、输出、token、延迟。还要记录工具调用，包括工具名、参数 hash、执行状态、返回引用、错误、重试次数。对于 RAG 和 Web Search，要记录 query、召回文档、source_ref、时间戳和 rerank 分数。对于高风险动作，要记录权限审批结果。最后还要记录 checkpoint、tool ledger、artifact_id、artifact version、source_refs 和最终输出。

如果用户反馈“回答错了”，没有 trace 就很难复现。因为我们只看到最后一段回答，却不知道当时模型看到了什么上下文、有没有拿到最新证据、工具有没有成功、参数有没有传错、是否用了旧缓存、有没有发生降级、上一版 artifact 是不是被错误引用。比如金融 Agent 说“根据最新持仓”，但没有 trace 我们不知道它是不是真的调用了持仓工具，还是模型自己猜的；也不知道基金代码、日期范围、交易日是否正确。所以没有 trace，排查只能靠猜；有 trace，才能逐层判断是 Gateway、RAG、工具、模型、状态还是 artifact 的问题。

Trace 和普通后端日志的区别在于，日志通常是某个组件在某个时间打印的一条离散事件，比如接口报错、数据库超时；trace 是一次请求从入口到出口的完整执行树。它用 trace_id 把所有步骤串起来，用 span_id 和 parent_id 表示父子关系。OpenTelemetry 里 span 就代表一次具体操作，比如一次 HTTP 请求、一次数据库调用或一次工具执行。对于 Agent 来说，span 可以是一次模型调用、一次 RAG 检索、一次工具调用、一次审批、一次 artifact 写入。普通日志回答“某个点发生了什么”，trace 回答“这次请求是怎么一步步走到这个结果的”。

结合我的金融投资顾问 Agent，我会把每次报告生成都作为一个 root trace。下面包括 route_skill、context_pack、get_fund_nav、get_fund_holding、search_news、python_compute_metrics、generate_report_draft、compliance_check、write_artifact 等 span。用户说“报告错了”，我就能打开 trace，看它是否识别对 Skill、是否读取了用户风险偏好、是否拿到最新交易日、是否调用正确基金代码、是否绑定 source_refs、最终 artifact 是 draft 还是 approved。

同时 trace 也不能无脑存所有明文内容。生产环境要做脱敏、采样、权限隔离和保留周期控制。敏感字段存 hash 或 source_ref，失败请求和高风险请求保留更详细，普通成功请求可以采样。这样既能排查问题，又不会把 trace 变成新的隐私风险。

我的总结是：Agent trace 的价值是把“回答错了”从一个模糊反馈变成可定位的工程问题；它记录上下文、工具、证据、参数、状态和输出的完整链路，让我们能复现、评测和持续改进 Agent。





## 3、一次 Agent Run 的观测数据应该记录哪些字段？

**先给结论**

一次 **Agent Run（一次 Agent 任务执行）** 的观测数据，不能只记录“用户问了什么、模型答了什么”，而要记录从 **用户输入 → 路由 → 上下文组装 → Planner 计划 → 工具调用 → Observation 生成 → Replan/Stop → 最终输出 → 评测反馈** 的完整链路。也就是说，每一次 Agent Run 都应该有一个 **trace_id（链路追踪 ID）**，每个关键步骤都应该形成一个 **span（链路中的一个子步骤，例如一次模型调用、一次工具调用、一次检索）**。OpenAI Agents SDK 的 tracing 文档也明确说明，tracing 默认记录 agent run、LLM generations、tool calls、handoffs、guardrails 和自定义事件，这说明 Agent 已经被当成多步骤工作流来观测，而不是一次模型调用。([OpenAI][1])

**一条最小 Agent Run 链路**

你可以把一次 Agent Run 设计成下面这种结构：

```text
Root Trace: agent_run
  ├─ request_received
  ├─ intent_routing
  ├─ context_gateway
  ├─ context_packing
  ├─ planner_generation
  ├─ tool_selection
  ├─ tool_call
  ├─ observation_builder
  ├─ replan_or_continue
  ├─ final_generation
  ├─ artifact_write
  ├─ eval_scoring
  └─ user_feedback
```

这里的重点是：**trace 负责串起整次任务，span 负责记录每个步骤。** OpenAI Agents SDK 对 trace 和 span 的定义也类似：trace 表示一次端到端 workflow，span 表示有开始和结束时间的具体操作，并且 span 会带有 `trace_id` 和 `parent_id` 来表达父子关系。([OpenAI][1])

**第一类：请求与身份字段**

一次 Agent Run 首先要记录入口信息：

| 字段                       | 说明                          |
| ------------------------ | --------------------------- |
| `trace_id`               | 一次完整任务的唯一 ID                |
| `run_id`                 | 一次 Agent 执行 ID，可属于某个 trace  |
| `session_id / thread_id` | 会话或线程 ID，用于多轮连续任务           |
| `task_id`                | 长任务 ID，用于恢复、重试和 artifact 绑定 |
| `user_id / tenant_id`    | 用户与租户，生产中要脱敏或哈希             |
| `channel`                | 入口渠道，例如 Web、API、Slack、企业微信  |
| `created_at`             | 请求进入时间                      |
| `user_query_raw`         | 用户原始输入，必要时脱敏                |
| `request_mode`           | 对话、报告、工具执行、外发审批等模式          |
| `environment`            | dev、staging、prod            |

这些字段解决的是“这次请求是谁发的、从哪里来、属于哪个任务、后续怎么串起来”。

**第二类：意图识别与路由字段**

Agent 的第一步通常是判断任务类型，所以要记录：

| 字段                  | 说明                                        |
| ------------------- | ----------------------------------------- |
| `intent`            | 用户意图，例如行情查询、基金对比、继续报告                     |
| `intent_confidence` | 意图识别置信度                                   |
| `route_type`        | 走普通问答、RAG、Web Search、Skill、工具执行还是多 Agent  |
| `selected_agent`    | 命中的子 Agent，例如 research_agent、report_agent |
| `selected_skill`    | 命中的 Skill，例如 fund_compare_skill           |
| `routing_reason`    | 为什么这么路由                                   |
| `fallback_route`    | 路由失败时的备选路径                                |
| `router_latency_ms` | 路由耗时                                      |

这部分很重要，因为很多 Agent 错误不是模型不会答，而是第一步就走错路线。比如用户要“对比三只基金”，系统却走了普通聊天链路，最终答案再像样也不可靠。

**第三类：上下文组装字段**

Context Engineering 的观测数据要记录 Gateway 和 Packer 的决策：

| 字段                          | 说明                    |
| --------------------------- | --------------------- |
| `context_sources_requested` | Gateway 判断需要哪些上下文源    |
| `context_candidates`        | 候选上下文 ID 列表           |
| `context_selected`          | 最终注入模型的上下文            |
| `context_discarded`         | 被丢弃的上下文及原因            |
| `short_term_state_refs`     | 短期状态、checkpoint 引用    |
| `long_term_memory_refs`     | 长期记忆命中的条目             |
| `rag_refs`                  | RAG 命中的文档片段           |
| `web_refs`                  | Web Search 命中的来源      |
| `tool_ledger_refs`          | 工具账本记录                |
| `artifact_refs`             | 上一版报告、草稿、表格等 artifact |
| `packed_prompt_tokens`      | 本轮上下文占用 token         |
| `context_compression_ratio` | 压缩比例                  |
| `context_policy_flags`      | 权限、敏感信息、过期数据等标记       |

这部分能回答：“模型当时到底看到了什么？”如果用户反馈“回答错了”，第一步就要看是不是 **上下文没注入、注入错了、注入了旧证据、或者把噪声塞进去**。

**第四类：Planner 与 Replan 字段**

如果 Agent 有 Planner（计划器，负责拆解任务步骤），就要记录：

| 字段               | 说明          |
| ---------------- | ----------- |
| `plan_id`        | 本次计划 ID     |
| `plan_steps`     | 计划步骤列表      |
| `plan_version`   | Replan 后的版本 |
| `plan_reason`    | 计划理由摘要      |
| `expected_tools` | 计划中预计调用的工具  |
| `stop_condition` | 停止条件        |
| `replan_count`   | 重规划次数       |
| `replan_reason`  | 为什么重规划      |
| `plan_validated` | 是否通过规则/模型校验 |

比如基金报告任务，合理计划应该是“识别基金 → 查净值 → 查持仓 → 查行业指数 → 查新闻 → 计算指标 → 生成报告”。如果 trace 里 plan 一开始就漏掉了“查持仓”，后面报告错误就能定位到规划层。

**第五类：模型调用字段**

每次 LLM 调用都应该形成一个 span，记录：

| 字段                    | 说明                               |
| --------------------- | -------------------------------- |
| `model_provider`      | OpenAI、Anthropic、Qwen、DeepSeek 等 |
| `model_name`          | 具体模型                             |
| `temperature / top_p` | 采样参数                             |
| `input_tokens`        | 输入 token                         |
| `output_tokens`       | 输出 token                         |
| `cached_tokens`       | 缓存命中 token                       |
| `llm_latency_ms`      | 模型耗时                             |
| `finish_reason`       | 停止原因                             |
| `prompt_version`      | system prompt / skill prompt 版本  |
| `input_summary`       | 输入摘要，生产中避免全量明文                   |
| `output_summary`      | 输出摘要                             |
| `cost`                | 本次模型成本                           |

OpenAI Agents SDK 的 tracing 默认会把 LLM generations 包成 generation span，所以模型调用本身就是 Agent Run 观测的一部分。([OpenAI][1])

**第六类：工具调用字段**

工具调用是 Agent 观测的核心。每个工具都要记录：

| 字段                      | 说明                                |
| ----------------------- | --------------------------------- |
| `tool_call_id`          | 工具调用唯一 ID                         |
| `tool_name`             | 工具名                               |
| `tool_type`             | function、MCP、Bash、Code、Web、DB、RAG |
| `tool_risk_level`       | 风险等级                              |
| `tool_args`             | 工具参数，敏感字段脱敏                       |
| `args_hash`             | 参数 hash，用于审批和幂等                   |
| `start_time / end_time` | 起止时间                              |
| `tool_latency_ms`       | 工具耗时                              |
| `status`                | success、error、timeout、cancelled   |
| `error_type`            | 参数错误、权限错误、限流、超时、空返回               |
| `retry_count`           | 重试次数                              |
| `idempotency_key`       | 幂等键，防止重复写入/外发                     |
| `result_ref`            | 结果文件或对象引用                         |
| `raw_result_size`       | 原始结果大小                            |
| `observation_id`        | Observation Builder 生成的摘要 ID      |

工具指标可以从这些字段里聚合出来：**工具成功率、误选率、参数错误率、超时率、重试率、重复调用率**。Langfuse 对 LangChain 的集成会捕获 LangChain executions、LLMs、tools 和 retrievers，用于评估和调试，这也说明工具与检索都应进入 trace。([Langfuse][2])

**第七类：Observation Builder 字段**

Observation Builder（观察构造器，负责把工具结果转成模型可读的结构化观察）也要被观测，因为工具结果摘要错了，模型后面一定会错。

| 字段                    | 说明                          |
| --------------------- | --------------------------- |
| `observation_id`      | Observation ID              |
| `source_tool_call_id` | 来源工具调用                      |
| `observation_status`  | success、partial、empty、error |
| `summary`             | 给模型看的摘要                     |
| `source_refs`         | 原始数据引用                      |
| `timestamp`           | 数据更新时间                      |
| `confidence`          | 可信度                         |
| `staleness`           | 是否过期                        |
| `lossy_compression`   | 是否有损压缩                      |
| `redaction_applied`   | 是否脱敏                        |
| `message_for_model`   | 传给模型的安全摘要                   |

比如金融 Agent 中，Tushare 返回一大段持仓表，Observation Builder 应该记录摘要依据、原始结果引用和时间戳。否则后续模型如果误读，就无法知道是工具返回错，还是摘要构造错。

**第八类：RAG / Web Search 字段**

RAG 和 Web Search 需要单独记录检索链路：

| 字段                          | 说明                     |
| --------------------------- | ---------------------- |
| `query`                     | 检索 query               |
| `rewrite_query`             | 改写后的 query             |
| `retriever_type`            | BM25、vector、hybrid、web |
| `top_k`                     | 召回数量                   |
| `doc_ids`                   | 文档 ID                  |
| `chunk_ids`                 | 片段 ID                  |
| `rerank_scores`             | 重排分数                   |
| `source_url / source_name`  | 来源                     |
| `published_at / updated_at` | 发布时间/更新时间              |
| `source_authority`          | 来源权威性                  |
| `evidence_used`             | 最终是否被引用                |
| `citation_accuracy`         | 引用是否准确                 |

LangSmith Observability 文档说明，它可以从 individual traces 到 production-wide performance metrics 提供可见性，并支持查看 traces、监控性能和收集反馈；这类能力非常适合把 RAG/Web 的检索质量和最终答案质量关联起来。([LangChain 文档][3])

**第九类：权限、安全与合规字段**

安全不是上线后再看，而是每次 Run 都要记录：

| 字段                        | 说明                               |

OpenAI Agents SDK tracing 默认也覆盖 guardrail span，说明安全检查本身应该作为链路中的可观测步骤，而不是只在最终结果里体现。([OpenAI][1])

**第十一类：质量、性能、成本、安全指标**

| 指标类型       | 具体指标                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| **质量指标**   | 任务完成率、回答正确率、证据一致性、引用准确率、人工通过率、用户满意度                                    |
| **工具指标**   | 工具成功率、工具误选率、参数错误率、超时率、重试率、重复调用率                                        |
| **性能成本指标** | 端到端延迟、模型耗时、工具耗时、P95/P99 延迟、总 token、prompt token、completion token、单任务成本 |
| **安全合规指标** | 高风险工具触发次数、HITL 审批率、违规内容命中率、PII 泄露风险、越权调用拦截次数                           |

LangSmith Observability 官方文档也强调，它既能看 individual traces，也能看 production-wide performance metrics，并提供 monitoring、feedback、online evaluators 等能力；这说明观测数据不仅用于排错，也用于持续评测和质量改进。([LangChain 文档][3])

**金融 Agent 示例：黄金行情问题怎么记录**

如果用户问：“黄金最近为什么跌，未来一个月怎么看？”一次 trace 至少要看到：

1. **意图识别**：识别为“最新市场分析 + 风险解释”，不是普通金融知识问答。
2. **上下文路由**：触发 Web Search / 实时行情工具，而不是只用长期记忆。
3. **检索来源**：查了哪些权威新闻、机构观点、金价数据、美元指数、利率预期。
4. **时间戳**：每条证据的发布时间和数据更新时间。
5. **用户画像**：是否读取用户黄金仓位、风险偏好、投资期限。
6. **工具结果**：行情工具是否成功、参数是否正确、是否用了最新交易日。
7. **Observation**：是否把市场原因总结成“美元、利率、避险情绪、资金流向”等结构化观察。
8. **最终回答**：是否引用对应证据，是否说明不确定性。
9. **合规检查**：是否加入“不构成投资建议”的风险提示。
10. **反馈记录**：用户是否认为回答有帮助，是否标记“观点过于笼统/数据不新”。

如果最后用户说“你这个黄金分析错了”，我们就能沿 trace 判断：是搜索没搜到、来源不权威、行情工具参数错、用户持仓没注入、模型总结错，还是合规模板漏了。

**仓库证据摘要**

OpenAI Agents SDK 的 tracing 是最直接参考：它内置 tracing，会记录 agent run 中的 LLM generations、tool calls、handoffs、guardrails 和 custom events，并用 trace/span 表达端到端 workflow 和子操作。([OpenAI][1])

OpenClaw 的 agent loop 文档把真实 agent run 定义为 **intake → context assembly → model inference → tool execution → streaming replies → persistence**，这和我们要记录“从用户输入到状态持久化”的完整链路完全一致。([OpenClaw][5])

DeerFlow 2.0 backend README 提到内置 LangSmith 与 Langfuse tracing，启用后 LLM calls、agent runs、tool executions、middleware processing 都能在可观测平台里看到，说明 SuperAgent harness 的观测范围已经覆盖模型、工具和运行时中间层。([GitHub][4])

Hermes Agent v0.13.0 的 release 提到 durable multi-agent board、heartbeat、reclaim、zombie detection、per-task retries、hallucination recovery、Checkpoints v2、Gateway auto-resume 和 redaction 默认开启，这说明长任务 Agent 的观测不仅要看答案，还要看任务是否卡死、是否恢复、是否重试、是否脱敏。([GitHub][6])

cc-haha 的 AGENTS.md 明确把 agent-loop、tool execution、provider routing、model selection、permissions、session resume 等核心 Coding Agent 路径列为高风险质量门禁覆盖对象，这说明真实工程会把 Agent Run 的关键路径作为测试和观测重点，而不是只看最终文本。([GitHub][7])

**面试中可以怎么说**

如果面试官问“一次 Agent Run 观测数据记录哪些字段”，我会先说：我会用 **trace + span** 的方式记录整条执行链路，而不是只存普通日志。Root trace 记录一次完整任务，span 记录每个关键步骤，比如路由、上下文组装、模型调用、RAG 检索、工具调用、审批、artifact 写入、最终回答和反馈。

然后我会分层讲：第一层记录请求信息，包括 user_id、session_id、task_id、原始问题和入口渠道；第二层记录路由信息，包括 intent、selected_skill、selected_agent 和 routing_reason；第三层记录上下文信息，包括短期状态、长期记忆、RAG、Web Search、tool ledger、artifact 这些上下文源是否被选中、哪些被打包、哪些被裁剪；第四层记录模型调用，包括模型名、prompt 版本、输入输出 token、延迟和成本；第五层记录工具调用，包括工具名、参数 hash、状态、错误、重试、结果引用和幂等键；第六层记录安全合规，包括权限决策、审批状态、guardrail 命中、PII 脱敏和高风险工具拦截；第七层记录状态和产物，包括 checkpoint、memory write、artifact_id、artifact_version、source_refs 和 delivery_status；最后记录质量评分和用户反馈。

这样设计的价值是，用户反馈“回答错了”时，我可以沿着 trace 逐层定位：是路由错、上下文错、检索错、工具错、参数错、模型总结错、合规漏了，还是 artifact 版本错。比如我的金融投资顾问 Agent 里，用户问“黄金最近为什么跌”，trace 里应该能看到是否触发 Web Search、查了哪些来源、是否用了最新日期、是否调用行情工具、是否读取用户持仓和风险偏好、最终回答是否引用证据、是否加了风险提示。如果没有这些字段，最后只能看一段回答，很难复现和改进。

**一句话总结**

一次 Agent Run 的观测数据，本质上要把“用户请求如何一步步变成最终回答或 artifact”的全过程结构化记录下来：入口、路由、上下文、计划、模型、工具、Observation、重规划、安全、状态、产物、指标和反馈都要有 trace/span，才能排错、评测、审计和持续优化。

## 4、**错误定位应该怎么做**

排查 Agent 错误时，不要一上来就说“模型不行”。大厂更常用的是按链路逐层定位。第一层看 **输入层**：用户问题是否模糊，实体是否识别错，比如“苹果”是公司还是水果。第二层看 **上下文层**：短期记忆、长期记忆、RAG、Web Search 有没有注入错误或过期信息。第三层看 **规划层**：Planner 是否拆错任务，是否漏了必要步骤。第四层看 **工具层**：工具是否选错，参数是否合法，接口是否超时，返回是否为空。第五层看 **生成层**：模型是否正确使用工具结果，是否自己脑补。第六层看 **安全层**：是否触发了不该触发的工具，是否绕过了审批。第七层看 **观测层**：trace 是否足够完整，是否能复现。

举个简单例子：用户问“帮我比较 A 基金和 B 基金风险”。如果结果明显错，排查顺序应该是：先看基金代码是否识别对；再看净值、回撤、波动率工具有没有调用；再看工具参数日期是否正确；再看计算代码有没有报错；再看最终回答是否引用了计算结果；最后看是否根据用户风险偏好做了过度建议。这样你就能判断是工具问题、数据问题、上下文问题，还是生成问题。

这也是为什么 LangSmith / Langfuse 这类平台会强调 trace、session、observations、token usage、latency、cost 和工具调用可视化。Langfuse 官方说明，LLM tracing 应记录完整请求生命周期，包括 LLM 调用、检索步骤、工具执行、自定义逻辑、时间、输入输出和 metadata；LangSmith 则提供 trace 查看、过滤、反馈、监控、告警和 online evaluation。([Langfuse][5])

## 5、Agent 观测中最重要的指标有哪些？
**先给结论**

Agent 观测中最重要的指标，可以分成八类：**任务质量、工具调用、上下文质量、RAG/检索质量、性能成本、安全合规、状态与恢复、用户反馈**。其中面试最核心的不是“日志多不多”，而是能不能回答三个问题：**这次任务有没有完成？为什么成功/失败？下次该改 prompt、RAG、工具、路由、模型还是权限策略？** OpenAI Agents SDK 的 tracing 默认覆盖 agent run、LLM generation、tool call、handoff、guardrail 和自定义事件，说明 Agent 观测的对象是一条完整工作流，而不是单次模型输出。([OpenAI][1])

**一、最核心的北极星指标：任务完成率**

Agent 最重要的指标是 **Task Success Rate（任务完成率）**，也就是用户目标是否真的完成。比如用户要“生成一份半导体基金对比报告”，不是模型回答了一段金融文字就算成功，而是要看是否正确识别基金、查到数据、完成计算、生成 artifact、绑定证据、满足合规要求。

在面试里可以说：**最终答案质量只是任务完成率的一部分，真正的 Agent 成功要看任务是否按链路完成。**

常见子指标包括：

| 指标        | 含义                    |
| --------- | --------------------- |
| **任务完成率** | 用户目标是否完成              |
| **一次成功率** | 不需要人工补救、不需要多次重试就完成    |
| **人工通过率** | 人工审核是否接受最终结果          |
| **可交付率**  | 是否生成可保存、可审计的 artifact |
| **用户满意度** | 点赞、采纳、继续追问、投诉等反馈      |

LangSmith Observability 强调要从单个 trace 到生产级性能指标观察 LLM 应用，并结合反馈和评测持续监控，这类平台的核心价值正是把“单次输出”变成“任务链路质量”的持续观测。([LangChain 文档][2])

**二、工具调用指标：Agent 是否真的会做事**

Agent 和普通问答最大的区别是会调用工具，所以工具指标非常关键。只看最终答案，无法知道模型是不是“查了数据”还是“编了数据”。

| 指标                                   | 重点看什么               |
| ------------------------------------ | ------------------- |
| **Tool Selection Accuracy（工具选择准确率）** | 是否选对工具或 Skill       |
| **Tool Call Success Rate（工具调用成功率）**  | 工具是否成功返回            |
| **Tool Argument Accuracy（参数准确率）**    | 股票代码、基金代码、日期、市场是否传对 |
| **Tool Timeout Rate（超时率）**           | 外部 API 是否慢或不可用      |
| **Retry Rate（重试率）**                  | 是否频繁失败重试            |
| **Redundant Tool Call Rate（重复调用率）**  | 是否重复查同一个接口          |
| **Unsafe Tool Call Rate（高风险误调用率）**   | 是否误调用写库、发邮件、删文件等工具  |

比如金融 Agent 中，用户问“黄金最近为什么跌”，如果没有调用行情工具、Web Search 或新闻检索，最终回答再流畅也不可靠。Langfuse 的观测能力强调可以捕获 LLM call、tool invocation 和 retrieval step，并按用户、session、cost、latency 等维度过滤，这说明工具调用本身必须进入可观测链路。([Langfuse][3])

**三、上下文指标：模型看到的信息对不对**

Context Engineering 相关指标非常重要，因为很多错误不是模型不会答，而是模型没看到正确上下文。

| 指标                                     | 含义                               |
| -------------------------------------- | -------------------------------- |
| **Context Hit Rate（上下文命中率）**           | 是否注入了正确短期状态、长期记忆、RAG、tool ledger |
| **Context Precision（上下文精度）**           | 注入的信息是否真的相关                      |
| **Context Noise Rate（上下文噪声率）**         | 是否塞入无关历史、旧工具日志、旧 artifact        |
| **Stale Context Rate（过期上下文率）**         | 是否用了过期行情、旧新闻、旧报告                 |
| **Memory Retrieval Accuracy（记忆召回准确率）** | 是否召回了正确用户偏好                      |
| **Context Token Ratio（上下文 token 占比）**  | 上下文是否过长、是否挤压模型输出空间               |

这类指标决定了 Agent 的“信息输入质量”。如果用户说“继续上一版报告”，但系统没有加载 task_state、artifact metadata 和 tool ledger，那最终答案错不一定是模型问题，而是 Gateway/Packer 的问题。

**四、RAG / Web Search 指标：证据是否可信、最新、可引用**

RAG 和 Web Search 的指标要单独看，因为它们决定事实依据质量。

| 指标                                    | 含义             |
| ------------------------------------- | -------------- |
| **Retrieval Recall@K**                | 正确文档是否进入 Top-K |
| **Rerank Hit Rate**                   | 正确证据是否排在前面     |
| **Evidence Grounding Rate（证据支撑率）**    | 关键结论是否有证据      |
| **Citation Accuracy（引用准确率）**          | 引用是否真的支持结论     |
| **Freshness（新鲜度）**                    | 证据是否是最新时间      |
| **Source Authority（来源权威性）**           | 来源是否可靠         |
| **Hallucinated Citation Rate（虚假引用率）** | 是否编造来源或错引      |

比如金融场景里，“未来一个月黄金怎么看”必须看最新宏观数据、美元指数、利率预期、金价走势和权威新闻，不能只靠历史 RAG 或长期记忆。LangSmith 的评测能力支持在线 evaluators、质量规则、LLM-as-judge 和反馈闭环，适合把证据一致性、格式、安全和质量等指标接入生产 trace。([LangChain 文档][4])

**五、性能与成本指标：系统能不能上线**

Agent 能答对还不够，还要看能不能稳定、便宜、低延迟地运行。

| 指标                                    | 含义                     |
| ------------------------------------- | ---------------------- |
| **End-to-End Latency（端到端延迟）**         | 从用户输入到最终输出总耗时          |
| **P95 / P99 Latency**                 | 线上长尾延迟                 |
| **LLM Latency**                       | 模型调用耗时                 |
| **Tool Latency**                      | 工具/API/数据库耗时           |
| **Total Tokens**                      | 总 token                |
| **Prompt Tokens / Completion Tokens** | 输入和输出 token 分布         |
| **Cost per Run（单次任务成本）**              | 一次 Agent Run 花多少钱      |
| **Cache Hit Rate（缓存命中率）**             | prompt、工具结果、RAG 结果是否复用 |
| **Concurrency / Throughput**          | 并发能力和吞吐量               |

Langfuse 官方文档明确提供 token usage 和 cost tracking，可以按 generation 和 embedding 观测使用量与成本；这类指标对 Agent 上线非常关键，因为多工具、多轮调用会显著放大成本。([Langfuse][5])

**六、安全与合规指标：有没有守住边界**

Agent 具备工具调用和外部副作用后，安全指标必须单独列出来。

| 指标                               | 含义                         |
| -------------------------------- | -------------------------- |
| **Unsafe Tool Block Rate**       | 高风险工具是否被正确拦截               |
| **HITL Trigger Rate**            | 发邮件、写库、外发报告等是否进入审批         |
| **Approval Pass / Reject Rate**  | 人工审批通过和拒绝比例                |
| **Policy Violation Rate**        | 是否触发合规规则                   |
| **PII Redaction Rate**           | 是否正确脱敏个人敏感信息               |
| **Permission Deny Count**        | 越权访问被拒绝次数                  |
| **Secret Leakage Rate**          | 是否泄露 token、密钥、连接串          |
| **Sandbox Escape Attempt Count** | 是否尝试访问宿主机、`.env`、SSH key 等 |

OpenAI Agents SDK tracing 会记录 guardrail span；这说明安全检查和内容/工具护栏本身也应该成为 trace 的一部分，而不是只在最终回答里靠肉眼检查。([OpenAI][1])

**七、状态与恢复指标：长任务是否可靠**

长任务 Agent 不能只看一次回答，还要看任务是否可恢复、可续跑、可回放。

| 指标                                | 含义                   |
| --------------------------------- | -------------------- |
| **Checkpoint Write Success Rate** | 检查点是否成功写入            |
| **Resume Success Rate**           | 中断后是否能恢复             |
| **Tool Ledger Completeness**      | 工具账本是否完整             |
| **Artifact Traceability**         | artifact 是否有版本、状态、证据 |
| **Duplicate Side Effect Rate**    | 是否重复发邮件、重复写库、重复调用支付  |
| **Zombie Task Rate**              | 任务是否卡死无人处理           |
| **Replan Count**                  | 重规划次数是否异常            |

OpenTelemetry 的 trace/span 模型可以把一次请求拆成有父子关系的 span，并记录起止时间、属性、事件和状态；这种结构很适合表达 Agent 长任务中的模型调用、工具调用、审批、artifact 写入和恢复步骤。([OpenTelemetry][6])

**八、用户反馈与评测指标：能不能持续改进**

最后一类是反馈和评测指标，用来把线上问题沉淀成改进闭环。

| 指标                           | 含义           |
| ---------------------------- | ------------ |
| **User Satisfaction**        | 点赞、差评、采纳率    |
| **Correction Rate**          | 用户要求纠错或重写的比例 |
| **Human Review Score**       | 人工评审分数       |
| **LLM-as-Judge Score**       | 评测模型打分       |
| **Regression Pass Rate**     | 回归测试通过率      |
| **Bad Case Recurrence Rate** | 同类错误是否复发     |
| **Eval Dataset Coverage**    | 评测集是否覆盖关键场景  |

LangSmith Evaluation 文档强调可以在生产 trace 上运行 evaluator，并建立反馈闭环；这说明观测不是为了“看日志”，而是为了把线上失败样例变成可重复评测的数据集。([LangChain 文档][4])

**面试中最应该优先说的 10 个指标**

如果面试时间有限，我建议优先说这 10 个：

| 核心指标                    | 为什么重要                    |
| ----------------------- | ------------------------ |
| **任务完成率**               | 判断 Agent 是否真正完成用户目标      |
| **回答正确率 / 人工通过率**       | 判断最终结果质量                 |
| **证据支撑率**               | 判断回答是否基于可信来源             |
| **工具选择准确率**             | 判断 Agent 是否会选工具          |
| **工具参数准确率**             | 判断工具是否用对                 |
| **工具成功率 / 超时率**         | 判断外部依赖是否稳定               |
| **上下文命中率**              | 判断 Gateway/Packer 是否给对信息 |
| **端到端延迟 / P95 延迟**      | 判断线上体验                   |
| **单次任务成本 / token 消耗**   | 判断是否可规模化                 |
| **高风险工具拦截率 / HITL 覆盖率** | 判断安全边界是否有效               |

这一组指标覆盖了 **质量、过程、成本、安全** 四个维度，面试里最有工程含金量。

**放到你的金融投资顾问 Agent 项目里怎么讲**

结合你的金融 Agent，可以这样回答：我不会只看“最后回答像不像金融分析”，而会重点看三层指标。

第一层是**业务质量**：基金对比报告是否完成、关键结论是否有证据、引用是否准确、是否符合“不构成投资建议”的合规要求、人工审核通过率是多少。

第二层是**执行过程**：是否命中正确 Skill，是否调用行情、基金净值、持仓、行业指数、新闻检索等工具，基金代码和日期参数是否正确，工具是否超时，Observation Builder 是否把工具结果转成带时间戳和 source_refs 的摘要。

第三层是**工程稳定性**：端到端延迟、P95 延迟、token 成本、工具重试率、checkpoint 写入成功率、artifact 是否有版本和证据、高风险外发是否进入审批。

比如用户问“黄金最近为什么跌，未来一个月怎么看”，trace 里至少要看：是否触发 Web Search 或实时行情工具；是否检索到最新权威来源；是否注入用户持仓和风险偏好；最终回答是否引用对应证据；是否加入风险提示；整体延迟和成本是否可接受。

**常见错误回答**

不要只说：“看准确率、延迟、成本。”这太像普通 LLM 应用指标，没有体现 Agent 特点。

更好的回答是：**Agent 指标要同时看最终结果和中间过程，既看任务完成率，也看工具选择、工具参数、上下文命中、证据支撑、安全审批、状态恢复和 artifact 可追溯。**

**一句话总结**

Agent 观测最重要的指标不是单一准确率，而是围绕一次 Agent Run 的完整链路建立指标体系：**结果是否正确、工具是否用对、上下文是否命中、证据是否可靠、成本延迟是否可控、安全边界是否守住、状态和产物是否可恢复可审计。**

**2–5 分钟面试口述版**

我理解 Agent 观测里最重要的指标，不能只看最终回答准确率，而要覆盖一次 Agent Run 的完整链路。因为 Agent 不是一次模型调用，而是包含路由、上下文组装、Planner、工具调用、Observation Builder、重规划、状态写回和最终回答的多步骤工作流。OpenAI Agents SDK 的 tracing 默认会记录 agent run、LLM generation、tool call、guardrail、handoff 等 span，这说明优秀实践已经把 Agent 当成完整 workflow 来观测。

我会把指标分成几类。第一类是质量指标，比如任务完成率、回答正确率、人工通过率、证据一致性、引用准确率。这里最核心的是任务完成率，因为 Agent 的目标不是生成一段看起来合理的话，而是真正完成用户任务。

第二类是工具指标，比如工具选择准确率、工具调用成功率、参数错误率、超时率、重试率、重复调用率和高风险工具误调用率。因为 Agent 的价值来自工具执行，如果工具选错、参数传错，最终回答就算流畅也不可信。

第三类是上下文指标，比如上下文命中率、上下文精度、噪声率、过期上下文率、长期记忆召回准确率和上下文 token 占比。很多 Agent 错误不是模型不会推理，而是 Gateway 没给对短期状态、长期记忆、RAG 证据、tool ledger 或 artifact 摘要。

第四类是 RAG 和 Web Search 指标，比如 Recall@K、rerank 命中率、证据支撑率、引用准确率、来源权威性和时效性。尤其在金融场景里，最新事实不能靠模型记忆，必须看来源和时间戳。

第五类是性能成本指标，比如端到端延迟、P95/P99 延迟、模型耗时、工具耗时、总 token、prompt token、completion token、缓存命中率和单次任务成本。Agent 通常会多轮调用模型和工具，如果不监控成本延迟，很难上线。

第六类是安全合规指标，比如高风险工具拦截率、HITL 审批覆盖率、越权调用拦截次数、PII 脱敏率、违规内容命中率和密钥泄露风险。对于金融 Agent 来说，外发报告、写 CRM、交易相关动作都必须有审批和审计。

第七类是状态和产物指标，比如 checkpoint 写入成功率、恢复成功率、tool ledger 完整性、artifact 版本可追溯、source_refs 完整性和重复副作用率。长任务 Agent 如果不能恢复和追溯，就不适合生产。

结合我的金融投资顾问 Agent，我会重点看：是否命中正确 Skill，是否调用行情、基金净值、基金持仓、行业指数和新闻工具，工具参数是否正确，报告结论是否绑定证据，是否加入风险提示，artifact 是否有版本，外发是否进入审批，端到端延迟和 token 成本是否可控。如果用户反馈“黄金分析错了”，我能沿着这些指标判断是搜索没触发、证据过期、工具参数错、上下文没注入、模型总结错，还是合规模板漏了。

我的总结是：Agent 观测最重要的指标不是单点准确率，而是围绕完整执行链路建立质量、工具、上下文、证据、性能、安全、状态和反馈指标，这样才能真正做到可排查、可评测、可审计、可持续优化。




## 6、**Agent 评测要评哪些环节**

评测可以按 Agent 链路拆成五层。第一层是 **意图和路由评测**：用户问题来了，系统是否分到正确模式，比如普通问答、RAG、Web Search、工具调用、长任务报告。第二层是 **上下文评测**：是否召回了正确记忆、正确文档、最新网页，是否过滤了无关内容。第三层是 **工具评测**：是否选择了正确工具，参数是否正确，是否漏调或乱调。第四层是 **轨迹评测**：执行步骤是否符合预期，比如“先查数据→再计算→再生成报告→再做风险提示”。第五层是 **最终回答评测**：答案是否正确、清楚、可追溯、安全、符合格式。

Google ADK 把 Agent 评测拆为 trajectory/tool use 和 final response 两部分，并支持 test file 与 evalset 两种方式：简单单轮或短会话适合 test file，复杂多轮会话适合 evalset。LangSmith 的评测流程也很清楚：先创建 dataset，再定义 evaluator，然后运行 experiment，最后比较实验结果、做回归测试，并把生产失败 trace 加回 dataset 形成闭环。([Google GitHub][2])

**先给结论**

`trajectory evaluation` 就是评测 Agent 的“执行过程”，不只看最后答案对不对，还看它有没有选对工具、参数是否正确、调用顺序是否合理、观察结果有没有被正确利用、是否超时重试、是否越权、是否在合适时停止。它比只评最终答案更重要，因为 Agent 的风险往往藏在过程中：最后答对了也可能是误打误撞，最后答错了也可能前 80% 都做对了，只是最后一步生成失败。

## **6-1、什么是 trajectory evaluation**

可以把一次 Agent 运行拆成：

`用户输入 -> 意图识别 -> 计划 / 路由 -> 工具选择 -> 参数生成 -> 工具执行 -> Observation -> 状态更新 -> 是否继续循环 -> 最终回答`

`trajectory evaluation` 评的就是这条链路。OpenAI 的 trace grading 也把 trace 定义成包含决策、工具调用和推理步骤的端到端日志，用结构化分数或标签评估 correctness / quality / adherence；官方也强调 trace eval 能帮助理解 Agent 为什么成功或失败，而不是只做黑盒评测。参考：OpenAI trace grading 文档 https://developers.openai.com/api/docs/guides/trace-grading

为什么它更重要：

| 只评最终答案的问题 | trajectory eval 能解决什么 |
|---|---|
| 看不出错在哪一步 | 能定位是 planning 错、tool routing 错、参数错、工具失败、还是最终生成错 |
| 答案对但过程危险 | 能发现越权工具调用、重复写入、错误 API、无意义搜索 |
| 答案错但中间有价值 | 能给 partial credit，知道 Agent 哪些步骤已经可靠 |
| 难做回归 | 可以比较升级前后工具调用路径、步数、成本、延迟和错误类型 |
| 难上线治理 | 可以沉淀 trace、replay、灰度、A/B、告警和回滚依据 |

LangChain / LangSmith 的 agent eval 文档也明确提到，复杂 Agent 不适合只做 pass/fail，trajectory evaluation 可以在 Agent 做对部分步骤时给部分分。参考：LangSmith complex agent eval https://docs.langchain.com/langsmith/evaluate-complex-agent

## **6-2、工具调用应该怎么评测**

工具调用评测要分四层：**选没选对工具、参数对不对、执行结果处理对不对、运行时是否稳定安全**。

| 评测维度 | 具体看什么 |
|---|---|
| Tool selection | 该调用时是否调用，不该调用时是否乱调，是否选错相似工具 |
| Schema / 参数 | 必填字段是否齐全，类型是否正确，枚举值是否合法，是否参数幻觉 |
| 调用顺序 | 多工具任务里顺序是否正确，比如先检索再总结，先查权限再写入 |
| Observation 使用 | 工具返回为空、失败、部分结果时，是否正确重试、降级或解释 |
| 稳定性 | timeout、retry、backoff、circuit breaker、max steps、幂等控制 |
| 安全权限 | 是否越权读写，是否调用高风险工具前做人审或确认 |
| 成本效率 | 工具调用次数、重复调用率、p95 延迟、token 成本、缓存命中率 |

工程上一般这样做：

1. 离线 golden set：为每个样本标注 expected tool、expected args、allowed alternative trajectory、expected final answer。
2. deterministic check：能精确评的就用规则评，比如工具名、参数 schema、调用顺序、是否越权。
3. LLM-as-judge：开放式任务用 judge 评“路径是否合理”，但要配 rubric，不能只问“好不好”。
4. sandbox / mock tools：评测时不要真发邮件、真扣费、真改库，用 mock 返回可控 observation。
5. trace replay：线上失败 trace 脱敏后加入回归集，每次改 prompt、模型、tool schema 都重跑。
6. 线上监控：记录 tool_call_id、tool_name、args_hash、status、latency、error_type、retry_count、session_id、turn_id。

LangChain 的 AgentEvals 支持 trajectory match 和 LLM-as-judge 两类方式，前者适合已知预期工具路径，后者适合开放式路径质量判断。参考：LangChain Agent Evals https://docs.langchain.com/oss/python/langchain/test/evals

## **7、Agent 评测数据集怎么构建**

Agent 数据集不要只收集“问题-答案”，而要收集“任务-上下文-可用工具-期望轨迹-期望结果-评测规则”。

推荐字段：

| 字段 | 含义 |
|---|---|
| `input` | 用户原始问题，多轮任务要带 history |
| `state` | session state、memory、用户权限、租户、业务上下文 |
| `tools` | 可用工具列表、版本、schema、权限等级 |
| `expected_final` | 期望最终答案或业务状态 |
| `expected_trajectory` | 期望工具序列、关键参数、关键 observation |
| `allowed_variants` | 允许的等价路径，避免过度约束 |
| `rubric` | 评分标准：任务成功、工具正确、参数正确、安全、效率 |
| `tags` | 场景、难度、工具类型、风险等级、失败类型 |
| `source` | 人工构造、线上 trace、事故复盘、回归样本 |
| `version` | 数据集版本、工具版本、prompt 版本、模型版本 |

构建流程：

1. 先按业务场景分层：客服、检索、下单、审批、代码执行、文件操作、跨系统任务。
2. 每类都覆盖 happy path、边界输入、歧义输入、工具失败、权限不足、超时、空结果、恶意输入。
3. 从线上 trace 采样，脱敏后沉淀真实失败样本。
4. 人工补充高风险样本，比如越权写入、重复提交、错误收件人、错误金额。
5. 标注 final answer + trajectory，不要只标答案。
6. 建版本化数据集，保证同一版本可复现实验。
7. 每次模型、prompt、tool schema、检索索引升级前跑离线回归，线上再灰度抽样评测。

Langfuse 的 dataset 文档也强调可以从 production trace 的 span / event / generation 加入 dataset，并支持 dataset version，用来复现实验和比较版本变化。参考：Langfuse datasets https://langfuse.com/docs/evaluation/experiments/datasets


评测数据集不要一上来追求很大，个人项目或实习项目可以先做 50–200 条高质量样本。关键是覆盖真实错误，而不是随便写几个“正常问题”。我建议按四类构造。

第一类是 **黄金路径样本**，也就是系统应该稳定答对的高频问题。例如金融 Agent 中：“查询某只股票今日行情”“比较两个基金近一年收益”“生成某行业简报”。这类样本验证基本能力是否稳定。

第二类是 **边界样本**，专门测容易出错的地方。例如用户只说“它最近怎么样”，需要依赖短期记忆；用户问“最新政策”，需要 Web Search；用户给了错误基金代码，系统应该澄清或报错；用户要求“给我直接买入建议”，系统应该拒绝过度投资建议。

第三类是 **工具轨迹样本**，每条样本不只写期望答案，还写期望工具链。例如“基金风险对比”应该调用基金净值工具、计算回撤和波动率、生成风险说明，而不是直接让模型凭记忆回答。ADK 的 eval case 就包含 expected tool use trajectory，这个思路非常适合 Agent。([Google GitHub][2])

第四类是 **线上失败样本**，来自真实 trace。比如用户反馈“你引用错了”“你没查最新数据”“你重复调用工具”“你忘了我的偏好”，这些都应该沉淀成 regression set（回归集，后续每次改系统都要重新测试的样本）。LangSmith 的 evaluation workflow 明确建议把 failing production traces 加入 dataset，再创建针对性 evaluator，离线验证修复后再重新部署。([LangChain 文档][6])

## 7-1、每条 Agent 评测样本应该包含哪些标注？哪些字段适合人工标注？哪些字段可以从 trace 自动生成？
**先给结论**

每条 Agent 评测样本不要只标 `input -> expected_answer`，而要标成一个“可回放任务包”：**输入、上下文、可用工具、期望结果、期望轨迹、评分规则、风险标签、版本信息**。人工适合标“语义正确性、业务目标、允许的工具路径、安全边界”；trace 适合自动生成“实际调用了什么、参数是什么、耗时多少、失败在哪、token / 成本 / 步数是多少”。

**本质与原理**

Agent 评测样本和普通问答样本最大的区别是：Agent 的正确性不只在最终回答里，还在执行过程里。比如一个报销审批 Agent，最后说“已提交”不够，评测还要看它有没有先查权限、有没有读对单据、有没有调用正确审批 API、有没有重复提交、失败后有没有降级。

所以一条样本最好分成三类字段：

| 类型 | 作用 | 谁来生成 |
|---|---|---|
| 任务定义字段 | 定义这条样本到底要测什么 | 人工为主 |
| 期望标注字段 | 定义怎样算对、怎样算错 | 人工为主，部分可辅助生成 |
| 运行 trace 字段 | 记录 Agent 实际怎么跑 | 系统自动生成 |

**工程实现 / 落地方案**

一条比较完整的 Agent eval sample 可以这样设计：


**哪些字段适合人工标注**

人工标注应该集中在“机器很难从日志里判断对错”的部分：

| 人工标注字段 | 为什么需要人工 |
|---|---|
| `intent` / 任务意图 | 用户表达可能很口语，自动分类容易误判 |
| `success_criteria` | 业务上怎样算完成，需要产品和业务规则 |
| `expected_final_answer` | 最终回答是否满足用户目标，不只是字符串匹配 |
| `expected_trajectory` | 哪些工具必须调用、哪些路径可接受，需要工程经验 |
| `allowed_variants` | Agent 可能有多条合理路径，不能只标唯一答案 |
| `forbidden_actions` | 哪些工具不能调用、哪些写操作必须人审 |
| `risk_level` | 退款、支付、发邮件、删文件这类风险要人工定级 |
| `rubric` / 权重 | 不同业务对准确率、安全、成本的优先级不同 |
| `gold_evidence` | 哪些文档、订单、数据库记录是标准依据 |
| `edge_case_tag` | 模糊输入、权限不足、工具超时、空结果等边界类型 |

一句话：**人工负责定义“什么叫对”和“什么叫安全”。**

**哪些字段可以从 trace 自动生成**

trace 自动生成适合记录事实、计数、状态和运行时指标：

| 自动生成字段 | 来源 |
|---|---|
| `trace_id / session_id / turn_id` | 请求链路日志 |
| `actual_messages` | 对话记录 |
| `actual_tool_calls` | assistant tool_calls |
| `tool_name / tool_call_id` | 工具调用事件 |
| `actual_args` | 工具参数 |
| `tool_result / observation` | 工具返回 |
| `status / error_type` | 工具执行状态 |
| `latency_ms` | 每步耗时 |
| `step_count` | Agent loop 次数 |
| `retry_count / timeout_count` | 运行时控制 |
| `token_usage / cost` | 模型调用统计 |
| `model_version / prompt_version` | 发布版本 |
| `retrieved_doc_ids` | RAG / 搜索结果 |
| `final_output` | Agent 最终回答 |
| `completed / partial` | 是否完整结束 |

本地 `hermes-agent` 的 [batch_runner.py](C:/Users/27411/Desktop/实习/面试真题/hermes-agent/batch_runner.py:461) 就是一个很好的例子：它会保存 `conversations`、`metadata`、`completed`、`partial`、`api_calls`、`toolsets_used`、`tool_stats`、`tool_error_counts`。这些都属于可以从运行过程自动抽取的评测字段。

**哪些字段适合“自动生成 + 人工复核”**

有些字段不建议完全自动，也不值得完全手标，适合半自动：

| 半自动字段 | 做法 |
|---|---|
| `failure_type` | 先由规则或 LLM 根据 trace 预标，再人工确认 |
| `difficulty` | 根据工具数量、轮数、上下文长度预估，再人工抽检 |
| `trajectory_score` | deterministic match 先算，再对复杂样本人工复核 |
| `safety_violation` | 规则发现高危调用，再人工判断是否真违规 |
| `answer_correctness` | LLM judge 初评，人类抽样校准 |
| `dataset_tags` | 自动打标签，人类维护标签体系 |

**常见问题与排查**

第一个问题是只标最终答案，不标工具路径。这样会导致 Agent “答案看起来对，但过程不可控”。解决办法是至少标 `expected_tools`、`forbidden_tools`、`allowed_variants`。

第二个问题是 expected trajectory 标得太死。真实 Agent 可能有多条合理路径，比如先查订单再查退款，或者用户信息不足时先追问。解决办法是标“关键约束”，而不是强制每一步完全一致。

第三个问题是把 trace 当 gold label。线上 trace 只能说明“历史上这么跑过”，不代表它是正确答案。生产 trace 进入数据集前要脱敏、去重、筛选，并补人工 gold 标注。

第四个问题是泄露隐私或内部推理。评测数据集应该保存可观测执行事件，比如工具名、参数、返回、证据和状态，不应该依赖或暴露模型隐藏 chain-of-thought。

**案例与收敛实践**

OpenAI trace grading 文档把 trace grading 定义为对 Agent trace 的结构化打分，trace 包括决策、工具调用和推理步骤，用来判断正确性、质量和是否遵守预期。参考：https://developers.openai.com/api/docs/guides/trace-grading

Langfuse 的 dataset 文档支持从生产 trace 的 observation / span / generation 加入数据集，并支持 dataset version，这说明真实工程里会把线上 trace 沉淀成可复现实验集。参考：https://langfuse.com/docs/evaluation/features/datasets

本地证据里，`hermes-agent` 的 `batch_runner.py` 已经有 trajectory 保存、tool success / failure 统计、`partial` 标记和 `max_turns`。`cc-haha` 里有 tracer provider、registered hooks、last API request message 等状态，说明评测数据集要和 trace、hook、结构化输出结合，而不是手写几个 QA 样本就完事。

**一句话总结**

Agent 评测样本的人工标注负责定义“目标和标准”，trace 自动字段负责记录“真实执行过程”，两者结合才能评出 Agent 是否真的可靠。

**2 分钟面试口述版**

如果让我设计 Agent 评测样本，我不会只存用户问题和标准答案，而会把每条样本设计成一个可回放的任务包。它至少要包含输入消息、历史上下文、用户权限、可用工具、工具 schema 版本、期望最终结果、期望工具轨迹、允许的替代路径、评分 rubric、风险等级和数据集版本。

这里面适合人工标注的是那些带业务判断和语义判断的字段，比如用户意图、任务成功标准、最终答案是否正确、哪些工具必须调用、哪些工具禁止调用、哪些路径是等价可接受的、风险等级是多少。因为这些东西不是日志天然能告诉我们的，必须由业务、算法和工程一起定义。

适合从 trace 自动生成的是运行事实，比如 trace_id、session_id、turn_id、实际调用了哪些工具、tool_call_id、参数、工具返回、错误类型、耗时、重试次数、step_count、token 消耗、模型版本、prompt 版本、最终输出，以及这次运行是 completed 还是 partial。这些字段应该由 Agent runtime 或 observability 系统自动采集。

还有一类字段适合自动生成后人工复核，比如 failure_type、trajectory_score、answer_correctness、safety_violation。可以先用规则或 LLM judge 预打标签，然后人工抽样校准。

我觉得这里最容易犯的错误有两个：第一，只标最终答案，不标执行过程，这样看不出 Agent 是不是靠错误工具误打误撞答对的；第二，把线上 trace 直接当标准答案，实际上 trace 只是历史行为，不一定正确。正确做法是线上 trace 脱敏采样后进入候选集，再补人工 gold label，最后形成版本化数据集。这样每次改模型、prompt、tool schema 或检索链路，都可以离线 replay，评估任务成功率、工具调用准确率、安全违规率、p95 延迟和成本变化。

## 8、Agent 评测方法应该怎么选：规则、代码、LLM Judge、人工标注分别适合什么？

评测方法可以分成四种。第一种是 **规则评测**，适合确定性要求，比如 JSON 格式是否合法、是否包含风险提示、是否引用来源、是否调用了某个工具。第二种是 **代码评测**，适合计算类任务，比如收益率、最大回撤、SQL 结果、单元测试是否通过。第三种是 **LLM-as-a-Judge（用大模型当裁判）**，适合开放回答，比如判断回答是否完整、是否贴合用户意图、是否有幻觉；但它不能完全替代人工，因为裁判模型也会偏。第四种是 **人工标注**，适合高风险、高价值任务，比如金融建议、医疗、合规内容、客户外发话术。

LangSmith 支持 human review、code rules、LLM-as-judge、pairwise comparison 等 evaluator；Langfuse 也把 evals 定位为可重复检查 LLM 应用行为、避免靠感觉判断，并支持 dataset、experiment、live evaluator。([LangChain 文档][6])

举个例子，如果评估你的“基金对比 Agent”，可以这样设计：规则评测检查是否包含“风险提示”和“数据日期”；代码评测检查最大回撤计算是否正确；轨迹评测检查是否调用了净值工具和计算工具；LLM-as-Judge 评估回答是否清楚、客观、没有过度承诺；人工抽检 20 条高风险回答，看是否符合金融合规表达。

## 9、如何评估 RAG / Web Search / 上下文是否真的帮到了 Agent？
**先给结论**

评估 RAG / Web Search / 上下文是否真的帮到了 Agent，不能只看“有没有检索”或“召回分数高不高”，而要做 **反事实对照**：同一批任务分别跑 `无检索 / 有 RAG / 有 Web Search / 有记忆上下文 / 有 rerank`，看 Agent 的任务成功率、答案 groundedness、工具决策准确率、幻觉率、成本和延迟是否真的变好。核心问题是：**检索内容有没有被用上，用得对不对，用完后结果有没有更好。**

**本质与原理**

RAG / Web Search / 上下文对 Agent 的帮助，主要体现在四个层面：

| 层面 | 评估问题 |
|---|---|
| Retrieval | 有没有找回正确证据 |
| Context Packing | 正确信息有没有放进上下文，是否被噪声淹没 |
| Grounding | Agent 回答和决策是否基于证据，而不是自己编 |
| Task Outcome | 最终任务是否更准确、更安全、更可解释 |

所以不能只问“TopK 召回了什么”，还要问“这些内容是否改变了 Agent 的下一步行动”。比如客服 Agent 检索到退款政策后，是否因此调用了正确退款查询工具；搜索到网页后，是否引用了最新来源；记忆上下文注入后，是否减少追问但没有污染当前任务。

**工程实现 / 落地方案**

我一般会用五类指标评估：

| 指标类型 | 具体指标 | 判断含义 |
|---|---|---|
| 检索质量 | Recall@K、MRR、nDCG、Context Precision、Context Recall | 是否找到了该找的证据 |
| 上下文质量 | 有效证据占比、重复率、过期率、冲突率、token 占用 | 塞进 prompt 的内容是否干净 |
| 生成质量 | Faithfulness、Answer Correctness、Answer Relevance、引用准确率 | 答案是否忠实于上下文 |
| Agent 轨迹 | 工具选择准确率、错误工具调用率、step count、replan 次数 | 检索是否改善了执行路径 |
| 业务结果 | 任务成功率、人工接管率、投诉率、p95 延迟、成本 | 是否真的对产品有价值 |

最关键的是做 ablation test：

```text
A: 不给 RAG / Search / Memory，只用模型自身能力
B: 给普通 RAG
C: 给 RAG + rerank
D: 给 Web Search
E: 给 RAG + Web Search + 上下文压缩
```

然后比较：

```text
任务成功率是否提升
幻觉率是否下降
工具调用是否更准确
人工接管率是否下降
平均步数是否减少
p95 延迟和成本是否可接受
```

如果准确率只提升 1%，但延迟翻倍、成本翻倍，那这个上下文就不一定“帮到了 Agent”。

**怎么判断“真的被用上了”**

可以做 evidence attribution（证据归因）：

| 检查点 | 方法 |
|---|---|
| 答案是否引用证据 | 检查回答中的 claim 能否被 context 支持 |
| 工具调用是否受证据影响 | 比较检索前后的 tool choice 是否变化 |
| 是否忽略了关键证据 | gold evidence 在 context 中但答案没用，属于 generation failure |
| 是否没检索到关键证据 | gold evidence 不在 context 中，属于 retrieval failure |
| 是否被噪声误导 | context 有无关或错误内容，答案跟着错，属于 context pollution |
| 是否使用过期网页 | 检查 source date、crawl time、updated_at |

这里有一个很好用的排查矩阵：

| 现象 | 说明 |
|---|---|
| 证据没召回，答案错 | 检索 / Web Search 问题 |
| 证据召回了，但没放进上下文 | context packing 问题 |
| 证据在上下文里，但 Agent 没用 | generation / instruction following 问题 |
| 证据在上下文里，但 Agent 选错工具 | planning / routing 问题 |
| 证据本身过期或冲突 | 数据治理问题 |
| 答案对但延迟很高 | 性价比问题 |

**Web Search 单独怎么评**

Web Search 要额外看：

| 维度 | 评估方式 |
|---|---|
| Freshness | 搜索结果是否比知识库更新 |
| Source authority | 是否来自官网、文档、可信媒体，而不是低质转载 |
| Cross-source consistency | 多来源是否互相印证 |
| Citation correctness | 引用链接是否真的支持回答 |
| Search necessity | 这个问题是否真的需要联网搜索 |
| Staleness fallback | 搜索失败时是否降级到本地知识库或说明不确定 |

Web Search 最怕“搜到了，但来源不可靠”或者“明明本地知识库够用，却每次联网导致慢和贵”。

**常见问题与排查**

第一个问题是只看 RAGAS / Faithfulness 分数，不看业务成功率。Faithfulness 高只能说明答案贴合上下文，但如果上下文本身错了，答案仍然会错。

第二个问题是只评最终答案，不评 Agent 轨迹。Agent 场景里，RAG 可能不是直接改善回答，而是改善 tool routing、减少追问、避免越权操作，所以要看 trace。

第三个问题是没有无检索 baseline。没有对照组，就不知道 RAG 是真的帮忙，还是只是增加成本。

第四个问题是没有线上 drift 监控。文档变了、网页变了、索引过期了，离线评测集可能还很好，但线上已经坏了。

**案例与收敛实践**

RAGAS 官方指标里就包含 Context Precision、Context Recall、Faithfulness、Answer Relevancy、Answer Accuracy 等，适合做 RAG 检索和回答质量评估：https://docs.ragas.io/en/latest/concepts/metrics/

LangSmith 的 RAG evaluation 文档也把评估拆成 response correctness、groundedness、retrieval relevance 等维度：https://docs.langchain.com/langsmith/evaluate-rag-tutorial

本地项目里，`openclaw` 的 [active-memory](C:/Users/27411/Desktop/实习/面试真题/openclaw/extensions/active-memory/index.ts:907) 会让 memory search agent 返回“最相关 memory context”，并记录 `searchMs`、`hits`、`backend` 等 debug 信息。这说明上下文注入不只是“塞内容”，还要能观测检索耗时、命中数、fallback 和是否污染当前上下文。

**一句话总结**

判断 RAG / Web Search / 上下文有没有帮到 Agent，最可靠的方法是：做反事实对照，看它是否提升任务成功率和证据忠实度，同时没有明显拉高延迟、成本和错误工具调用。

**2 分钟面试口述版**

我会从反事实对照的角度评估 RAG、Web Search 和上下文是否真的帮到了 Agent。不能只看有没有检索，也不能只看召回分数，而是要比较同一批任务在无检索、有 RAG、有 Web Search、有 rerank、有记忆上下文几种配置下的表现。

指标上我会分五层。第一层是检索质量，比如 Recall@K、MRR、Context Precision、Context Recall，看正确证据有没有被找回来。第二层是上下文质量，看放进 prompt 的内容是否干净，有没有重复、过期、冲突和噪声。第三层是生成质量，比如 Faithfulness、Answer Correctness、Answer Relevance，看答案是否真的被上下文支持。第四层是 Agent 轨迹，看工具选择是否更准、错误工具调用是否减少、step count 是否下降。第五层是业务指标，比如任务成功率、人工接管率、投诉率、p95 延迟和成本。

排查时我会看证据链。如果关键证据没召回，是 retrieval 问题；证据召回了但没放进 prompt，是 context packing 问题；证据在上下文里但答案没用，是生成或指令遵循问题；证据用了但选错工具，是 planning 或 tool routing 问题；证据本身过期，那是数据治理问题。

Web Search 还要额外评估 freshness、source authority、citation correctness 和是否真的需要联网。因为 Web Search 很容易带来不可靠来源和高延迟。

所以我的判断标准是：RAG / Search / 上下文必须在离线回归和线上 A/B 中显著提升任务成功率、降低幻觉和错误工具调用，同时成本、延迟、安全风险可控，才算真的帮到了 Agent。

## 10、如何把线上失败 trace 变成回归测试集？哪些线上失败最值得沉淀？
**先给结论**

把线上失败 trace 变成回归测试集，本质是把“线上事故日志”加工成“可复现、可评分、可长期回放的 eval case”。流程是：**失败检测 -> trace 筛选 -> 脱敏归因 -> 人工补 gold label -> 固化 mock 工具返回 -> 加入版本化数据集 -> 每次模型 / prompt / tool schema / RAG 索引变更前自动回放**。最值得沉淀的是高频、高损失、高风险、根因明确、能复现、能代表一类问题的失败。

**本质与原理**

线上 trace 不能直接当测试集，因为 trace 只是“当时怎么跑的”，不一定是正确路径。要把它变成回归样本，必须补三样东西：

| 需要补什么 | 作用 |
|---|---|
| `gold expectation` | 正确答案、正确工具路径、正确业务状态 |
| `failure label` | 这次到底是检索错、工具错、状态错、权限错，还是生成错 |
| `replay fixture` | 固化工具返回、检索结果、时间、权限、用户状态，保证以后能复现 |

OpenAI trace grading 文档也强调 trace grading 是给 Agent trace 打结构化分数或标签，用于识别错误并改进工作流。参考：https://platform.openai.com/docs/guides/trace-grading  
Langfuse 也支持从 production trace 添加到 dataset，并做 dataset versioning。参考：https://langfuse.com/docs/evaluation/features/datasets

**工程实现 / 落地方案**

我会按 7 步做：

| 步骤 | 做什么 |
|---|---|
| 1. 线上捕获 | 记录 `trace_id / session_id / turn_id / model_version / prompt_version / tool_schema_version` |
| 2. 失败识别 | 通过用户差评、人工接管、异常码、LLM judge、规则检查、SLA 超时发现失败 |
| 3. 自动归因 | 根据 trace 判断是 input、planning、tool、state、retrieval、generation、runtime 哪层失败 |
| 4. 脱敏压缩 | 去掉 PII、token、密钥、订单号明文；保留结构、参数类型和必要证据 |
| 5. 人工标注 | 标正确意图、正确答案、期望工具、禁止动作、允许替代路径、评分 rubric |
| 6. 固化回放 | mock 外部工具、冻结检索结果、固定系统时间、固定权限和 memory snapshot |
| 7. 纳入回归 | 放进 `regression/failures/*.jsonl`，CI 或发布前跑；失败则阻断上线或进入灰度观察 |

一条回归样本可以长这样：

```json
{
  "case_id": "prod_trace_20260528_001",
  "source_trace_id": "trace_xxx",
  "failure_type": "wrong_tool_args",
  "input": {"messages": [...]},
  "state": {"permissions": ["refund.read"], "memory_snapshot": "..."},
  "tool_fixtures": {
    "order_search": {"status": "ok", "result": "..."},
    "refund_query": {"status": "ok", "result": "..."}
  },
  "expected": {
    "final_answer": "应说明退款状态和依据",
    "expected_tools": ["order_search", "refund_query"],
    "forbidden_tools": ["refund_create"],
    "success_criteria": ["不能编造到账时间", "必须引用退款记录"]
  },
  "rubric": {
    "task_success": 0.4,
    "tool_selection": 0.2,
    "tool_args": 0.2,
    "grounding": 0.1,
    "safety": 0.1
  }
}
```

**哪些失败最值得沉淀**

优先级我会这样排：

| 优先级 | 失败类型 | 为什么值得沉淀 |
|---|---|---|
| P0 | 越权读写、误发邮件、误删数据、错误扣费、错误审批 | 安全和业务损失大，必须回归 |
| P0 | 工具参数错但执行成功 | 最危险，表面成功但业务状态错 |
| P0 | 状态污染 / memory 污染 / 多租户串数据 | 影响范围大，很难靠最终答案发现 |
| P1 | 高频用户问题答错 | 对体验影响大，修一次收益高 |
| P1 | RAG 召回错、证据在但没用、引用错 | 知识问答和 Agentic RAG 的核心失败 |
| P1 | Web Search 使用过期或低可信来源 | 容易造成事实错误和信任问题 |
| P1 | 工具调用死循环、max steps 耗尽 | 成本和延迟风险大 |
| P1 | timeout / retry / circuit breaker 降级不合理 | 线上稳定性问题，容易反复出现 |
| P2 | 格式不符合 schema、JSON 解析失败 | 容易自动化检测，适合进 CI |
| P2 | 用户差评但根因明确 | 可转成真实业务回归样本 |

不太值得沉淀的失败：

| 不建议沉淀 | 原因 |
|---|---|
| 单次下游服务偶发 500 | 更适合监控和熔断，不一定进 eval |
| 用户输入完全无效且不可泛化 | 没有代表性 |
| trace 不完整、无法复现 | 只能做事故分析，不能做回归 |
| 只有主观口味差异 | 可进入人工偏好集，但不适合硬回归 |
| 已经被更通用样本覆盖 | 避免测试集膨胀 |

**常见问题与排查**

最常见的坑是把“失败 trace 原样保存”为测试集。这样会把错误路径也固化下来。正确做法是：trace 只作为原始证据，回归样本必须补人工 gold label。

第二个坑是只回放最终问题，不 mock 工具返回。Agent 回归最重要的是复现当时的工具环境、检索结果、权限状态和时间，否则每次 replay 都不稳定。

第三个坑是没有分层指标。一次失败要能判断是 `retrieval miss`、`wrong tool`、`bad args`、`tool timeout`、`state stale`、`hallucination`，否则修复后不知道防住了哪类问题。

**案例与收敛实践**

本地 `hermes-agent` 的 [batch_runner.py](C:/Users/27411/Desktop/实习/面试真题/hermes-agent/batch_runner.py:461) 已经有很接近回归集的结构：保存 `conversations`、`completed`、`partial`、`api_calls`、`tool_stats`、`tool_error_counts`，并支持 checkpoint / resume。  
[run_agent.py](C:/Users/27411/Desktop/实习/面试真题/hermes-agent/run_agent.py:12981) 里也能看到 invalid tool call、max retries、partial、max iterations 等失败信号，这些都适合自动转成候选失败样本。  
`openclaw` 的 [active-memory](C:/Users/27411/Desktop/实习/面试真题/openclaw/extensions/active-memory/index.ts:2241) 有 timeout、partial、searchDebug、circuit breaker 等运行时信号，说明线上失败不仅要沉淀答案错误，也要沉淀稳定性和降级错误。

**一句话总结**

线上失败 trace 进回归集的标准不是“它失败过”，而是“它代表一类可复现、可标注、可防回归的问题”。

**2 分钟面试口述版**

如果要把线上失败 trace 变成回归测试集，我会先把它当成原始证据，而不是直接当标准答案。完整流程是：线上通过用户差评、人工接管、异常码、超时、LLM judge 或规则检测发现失败；然后拉取完整 trace，包括用户输入、session state、memory、RAG 证据、工具调用、参数、工具返回、最终答案、模型版本和 prompt 版本；接着做脱敏和根因分类，判断是检索问题、规划问题、工具选择问题、参数问题、状态问题、生成幻觉，还是运行时超时问题。

之后要人工补 gold label，包括正确意图、正确答案、期望工具路径、禁止调用的工具、允许的替代路径和评分规则。为了让它能稳定回放，还要固定工具 mock 返回、检索结果、系统时间、权限和用户状态。最后把它加入版本化 regression dataset，每次改模型、prompt、tool schema、RAG 索引或 memory 策略之前都跑一遍，比较任务成功率、工具调用准确率、幻觉率、越权率、p95 延迟和成本。

最值得沉淀的是几类失败：第一是高风险失败，比如越权、误写库、误发邮件、误扣费；第二是工具调用表面成功但参数错，这种最危险；第三是高频用户问题答错，修复收益高；第四是 RAG 证据召回了但没用、引用错、Web Search 用了过期来源；第五是 max steps、死循环、timeout、降级不合理这类稳定性问题。

我不会把所有线上失败都放进回归集。偶发下游 500、不可复现 trace、完全无效输入、纯主观偏好问题，更适合做监控或人工分析。回归集要追求代表性和可复现性，目标是防止同一类线上事故在下一次发布后再次出现。

## 11、**评测流程应该怎么跑**

**先给结论**

Agent 评测流程不是“跑几条问题看答案”，而是一套持续迭代闭环：**先定义任务和 baseline，再用固定 dataset + evaluators 对比不同版本，最后把失败 trace 沉淀成回归集**。最重要的是 baseline，因为没有基线就不知道新 prompt、新模型、新 RAG、新路由到底是在优化，还是只是把问题换了个地方爆。

**本质与原理**

Agent 和普通 LLM 应用不同，它有规划、工具调用、状态管理、RAG/Web Search、权限、安全和运行时控制，所以评测也要分层：

| 层级 | 评什么 |
|---|---|
| 任务层 | 任务成功率、最终答案正确性 |
| 轨迹层 | 工具选择、参数、调用顺序、是否越权 |
| 检索层 | 召回质量、证据相关性、faithfulness |
| 运行时层 | max steps、timeout、retry、fallback、circuit breaker |
| 产品层 | 延迟、成本、人工接管率、用户满意度 |
| 安全层 | PII 泄露、越权读写、高风险操作是否人审 |

所以一个 Agent 评测流程应该同时看 **效果、过程、成本、稳定性、安全**，不能只看最终回答。

**工程流程**

比较完整的流程可以这样跑：

| 阶段 | 关键动作 |
|---|---|
| 1. 定义范围 | 明确评哪个 Agent、哪些任务、哪些工具、哪些失败不可接受 |
| 2. 收集样本 | 真实用户问题、线上失败 trace、人工构造边界 case |
| 3. 标注 gold | 期望答案、期望工具轨迹、禁止动作、允许替代路径 |
| 4. 构建 dataset | 分训练/开发/回归/线上抽样集，做版本管理 |
| 5. 定义 evaluators | 规则评测、LLM-as-judge、人审、安全规则、性能统计 |
| 6. 跑 baseline | 冻结当前线上版本，记录所有核心指标 |
| 7. 做实验 | 改 prompt、RAG、工具 schema、模型、路由或 memory |
| 8. 对比结果 | 看相对 baseline 的增益和副作用 |
| 9. 分析失败 trace | 定位 input/planning/tool/state/retrieval/generation/runtime 哪层坏了 |
| 10. 修复回归 | 修完后把失败样本加入 regression set |
| 11. 上线监控 | 灰度、A/B、在线 eval、告警、回滚 |

**Baseline 怎么做**

Baseline 要固定四件事：

| 固定项 | 为什么 |
|---|---|
| `model_version` | 模型变了，结果不可比 |
| `prompt_version` | prompt 变了，行为不可比 |
| `tool_schema_version` | 工具定义变了，轨迹不可比 |
| `dataset_version` | 样本变了，指标不可比 |

对比时不要只看平均分，而要看 tradeoff：

```text
任务成功率: 82% -> 88%
工具调用准确率: 91% -> 95%
幻觉率: 6% -> 3%
P95 延迟: 8s -> 19s
平均成本: +42%
安全违规率: 0.3% -> 0.2%
```

这种情况下不能简单说“变好了”，要看业务目标。如果是客服问答，延迟从 8 秒到 19 秒可能不可接受；如果是高风险审批 Agent，准确率和安全提升可能值得多花几秒。

**Evaluators 怎么设计**

| Evaluator | 适用场景 |
|---|---|
| 规则 evaluator | JSON schema、工具名、参数类型、禁止工具、max steps |
| 轨迹 evaluator | expected tool sequence、allowed variants、tool args match |
| RAG evaluator | context precision、context recall、faithfulness、引用准确率 |
| LLM judge | 开放式答案质量、解释是否充分、是否基于证据 |
| 人工复核 | 高风险、模糊标准、LLM judge 不稳定样本 |
| 性能 evaluator | latency、token、cost、retry、timeout |
| 安全 evaluator | 权限、PII、越权写入、prompt injection |

最稳的做法是：**能规则判断的不用 LLM judge，规则判断不了的再用 LLM judge，高风险样本最后做人审抽检。**

**常见问题**

第一个坑是没有 baseline，只看新版本“感觉更好”。这很危险，因为 Agent 可能回答更像人了，但工具调用更乱、成本更高。

第二个坑是 dataset 太干净，只放 happy path。真实 Agent 最容易挂在歧义问题、权限不足、工具超时、检索为空、多轮状态污染。

第三个坑是只看总分，不看分层指标。总分提升可能掩盖安全违规率上升。

第四个坑是失败 trace 不进回归集。这样同一个线上事故会反复出现。

**案例与证据**

OpenAI 的 trace grading 强调对 Agent trace 做结构化打分，用来定位工作流级错误；LangSmith / Langfuse 也都把 dataset、trace、online eval 和回归实验作为核心能力。  
本地 `hermes-agent` 的 `batch_runner.py` 已经有 dataset 批量运行、trajectory 保存、tool_stats、tool_error_counts、checkpoint/resume，这很接近离线评测 runner。`openclaw` 的 active-memory 里有 timeout、partial、searchDebug、circuit breaker 这类运行时信号，说明 Agent 评测不能只评答案，也要评稳定性和降级行为。

**一句话总结**

Agent 评测流程的核心是：用 baseline 做参照，用 dataset 做复现，用 evaluators 做量化，用失败 trace 做回归，用线上监控防漂移。

**2 分钟面试口述版**

我理解完整的 Agent 评测流程应该是一个闭环。第一步先定义任务范围，比如评客服 Agent、报销 Agent，还是代码 Agent；然后收集真实用户问题和线上失败 case；接着标注期望答案、期望工具轨迹、禁止动作、允许的替代路径和评分维度；之后构建版本化 dataset，并定义 evaluators。

Evaluator 不能只有一个 LLM judge，而要分层。能规则判断的，比如工具名、参数 schema、是否越权、max steps、JSON 格式，就用 deterministic evaluator；开放式答案质量、解释是否充分、是否基于证据，可以用 LLM-as-judge；高风险样本再做人审。RAG 场景还要评 context recall、context precision、faithfulness 和引用准确率。

这里最重要的是 baseline。要先冻结当前线上版本，包括 model version、prompt version、tool schema version 和 dataset version，跑出任务成功率、工具调用准确率、幻觉率、延迟、成本和安全违规率。后面无论改 prompt、工具、RAG、模型还是路由，都必须和 baseline 对比。比如成功率从 82% 到 88% 是提升，但如果 P95 延迟从 8 秒涨到 25 秒，成本也翻倍，那就不一定值得上线。

最后，评测不是一次性的。每次实验后要分析失败 trace，判断是 planning、tool、state、retrieval、generation 还是 runtime 问题。修复后要把这个失败 case 加入回归集。上线后还要做灰度、A/B、在线 eval 和监控，持续观察任务成功率、人工接管率、超时率、成本和安全违规率。这样 Agent 才能稳定迭代，而不是靠主观感觉上线。

## 12、如何根据评测结果反向定位应该改 prompt、工具、RAG、路由还是模型？

评测结果不是为了得一个分数，而是为了定位系统该改哪里。比如工具误选率高，优先改工具 description、schema、路由器和候选工具 shortlist；参数错误率高，优先加参数校验、实体解析、枚举约束；RAG 命中率低，优先改 chunk、metadata、hybrid retrieval、rerank；回答引用错，优先改 evidence binding（证据绑定）和生成模板；延迟高，优先减少工具轮数、缓存、并发执行、模型分层；安全违规高，优先加 guardrails、HITL 和权限策略。

这就是所谓 **eval-driven development（评测驱动开发）**：不是凭感觉改，而是每次修改都能在固定数据集上看效果。LangSmith 明确把评测用于 benchmark、unit tests、regression tests 和 backtesting；线上还可以设置 online evaluators，对真实流量做安全、格式、质量启发式检查，并抽样控制成本。([LangChain 文档][6])

**先给结论**

错误定位不能一上来就说“改 prompt”或者“换模型”，而要按 **trace + eval 结果** 做分层归因：先看错误发生在 **输入理解、路由、上下文、RAG、Planner、工具选择、工具参数、Observation Builder、最终生成、安全策略、状态写回** 哪一层，再决定改哪里。OpenAI 的 Agent Improvement Loop 明确把流程做成：从真实 traces 开始，加入人工和模型反馈，把反馈转成 eval，再用证据生成下一轮 harness 修改建议；这里的 harness 包含 instructions、tools、routing、output requirements 和 validation checks，所以优化对象绝不只是 prompt。([OpenAI开发者][1])

**核心判断原则**

我会用一句话概括：**先定位失败层，再选择最小改动点。**

也就是说，用户说“回答错了”之后，不要马上换模型，也不要马上改提示词，而是先打开 trace，看这次 Agent Run 的链路：

```text
用户输入
→ 意图识别 / 路由
→ 上下文组装
→ RAG / Web / 记忆 / tool ledger
→ Planner 生成计划
→ 工具选择
→ 工具参数
→ 工具返回
→ Observation Builder 摘要
→ Replan / Continue / Stop
→ 最终回答
→ 评测打分 / 用户反馈
```

OpenAI Agents SDK 的 tracing 默认记录 agent run、LLM generations、function tool calls、guardrails、handoffs 和自定义事件；LangSmith 的 Agent Evaluation 也强调要捕获完整 trajectory、工具调用和中间决策，用来定位复杂 workflow 哪里出错。([OpenAI][2]) ([LangChain][3])

**错误定位的总流程**

第一步，**先分类错误现象**。用户反馈“错了”太模糊，要先标注是事实错误、证据缺失、工具没调、工具调错、回答不完整、格式不对、越权、安全风险、延迟过高，还是任务没有完成。

第二步，**看 trace 定位失败层**。如果 trace 显示 RAG 没召回正确文档，那不是 prompt 问题；如果 RAG 证据正确但模型没引用，那才可能是 prompt、Packer 或生成问题；如果工具选对但参数错，就应该改 schema、参数校验或实体解析，而不是换模型。

第三步，**选最小修复点**。能通过路由规则解决的，不优先换模型；能通过工具 schema 和参数校验解决的，不靠 prompt 约束；能通过 RAG 切分和召回解决的，不靠模型“猜”；能通过审批策略解决的，不靠模型自觉。

第四步，**把 bad case 写回评测集**。修复不是改完就结束，要把这类失败样例沉淀成 regression eval（回归评测，用来防止同类问题再次出现）。LangSmith 支持离线评测、线上评测、人工反馈、LLM-as-judge、自定义 evaluator 和 CI/CD 集成，适合把线上 bad case 变成持续验证样例。([LangChain][3])

**错误归因矩阵：看到什么指标，应该改哪里**

| 评测/trace 现象    | 优先怀疑层                        | 应该怎么改                                              |
| -------------- | ---------------------------- | -------------------------------------------------- |
| 意图识别错，走错 Skill | Router                       | 改路由 prompt、意图标签、few-shot、阈值、fallback               |
| 没加载上一轮任务状态     | Context Gateway              | 改 task_id/thread_id 读取、checkpoint、tool ledger 路由   |
| 没注入用户偏好        | Memory Retriever             | 改长期记忆召回、过滤、优先级、profile schema                      |
| RAG 没召回正确文档    | RAG Retriever                | 改 query rewrite、chunk、embedding、BM25/vector、rerank |
| RAG 召回对了但回答不用  | Context Packer / Prompt      | 改证据排序、引用要求、回答模板、evidence binding                   |
| 工具选错           | Tool Router / Tool 描述        | 改工具 shortlist、工具命名、description、tool governance     |
| 工具选对但参数错       | 参数解析 / schema                | 改实体解析、参数校验、枚举约束、默认值、日期处理                           |
| 工具返回太长，模型误读    | Observation Builder          | 改摘要字段、结构化 observation、单位/时间戳                       |
| 工具失败后乱编        | Tool Error Policy            | 改错误分类、fallback、禁止无证据生成                             |
| Plan 漏步骤       | Planner                      | 改 planning prompt、任务模板、计划校验器                       |
| 最终答案不合规        | Guardrail / Output Policy    | 改合规检查、风险提示模板、后置校验                                  |
| 结果对但慢/贵        | Context Packer / Tool Cache  | 改 token 预算、缓存、并发、工具去重                              |
| 高风险工具误调用       | Permission / Tool Governance | 改白名单、短名单、审批、风险分级                                   |
| 同一问题时好时坏       | 模型稳定性 / 评测集                  | 降 temperature、换模型、增加 deterministic validation      |

这个表可以直接用于面试回答：**不同错误信号对应不同修改层，不要所有问题都往 prompt 上归因。**

**什么时候改 prompt**

当 trace 证明 **数据、工具、RAG、上下文都没问题，但模型理解任务或输出格式不稳定** 时，才优先改 prompt。

典型信号是：

模型看到了正确证据，但没有引用；模型知道要比较三只基金，但输出没有按要求分维度；模型反复越过“不要给确定性买卖建议”的合规边界；模型最终回答语气、结构、格式不符合要求。这时候应该改 system/developer prompt、Skill.md、输出模板、few-shot 示例、约束顺序和禁止事项。

但 prompt 不是万能的。如果工具参数错，靠 prompt 反复强调“请传正确参数”不如做 schema 校验；如果 RAG 召回错，靠 prompt 说“请基于资料回答”也没用，因为资料本身就错。

**什么时候改工具**

当 trace 显示 **工具选择正确，但工具执行不稳定、参数容易错、返回难以理解、错误处理不清楚** 时，应该改工具。

典型信号包括：工具超时率高、参数错误率高、空返回率高、重复调用率高、工具返回字段太混乱、同一个概念有多个重复工具。修复方式包括：收紧 input schema、增加必填字段、加入枚举和日期格式校验、返回结构化 JSON、增加错误码、加缓存、加幂等键、增加 retry/fallback。

比如金融 Agent 中，基金代码和股票代码经常混淆，就不该只改 prompt，而应该在工具层增加 `asset_type`、代码格式校验、交易所后缀检查和候选实体确认。

**什么时候改 RAG**

当评测显示 **答案事实错、引用错、证据缺失、引用过期**，并且 trace 显示问题出在检索层，就应该改 RAG。

可以分三种情况：

第一，**没召回正确文档**，改 query rewrite、chunk 粒度、metadata filter、BM25 + vector 混合检索、reranker。
第二，**召回了但排序靠后**，改 rerank、增加标题/时间/权限/业务字段权重。
第三，**召回正确但模型没用**，这不是纯 RAG 问题，而是 Context Packer 或 prompt 问题，要把关键证据放到更高优先级，并强制 source_refs 绑定。

LangSmith 对 RAG eval 的说明也区分 retrieval quality 和 generation quality，例如 context precision 关注是否检索到相关文档，faithfulness 关注回答是否忠实于检索上下文。([LangChain][3])

**什么时候改路由**

当 trace 显示 **一开始任务类型判断错、Skill 选错、工具 shortlist 错、上下文源选错**，就应该改路由。

比如用户问“继续上一版基金报告”，系统却当成普通问答，没有读取 artifact 和 tool ledger；用户问“最近黄金为什么跌”，系统却只查长期记忆，没有触发 Web Search；用户问“根据上传文档总结”，系统却走外网搜索，没有走 RAG。这些都不是模型最终生成层的问题，而是 Router / Gateway 的问题。

OpenClaw 的 agent loop 把真实 run 描述为 intake → context assembly → model inference → tool execution → streaming replies → persistence，这说明路由和上下文组装在模型生成之前，前置链路错了，后面的回答自然会错。([OpenClaw][4])

**什么时候改模型**

换模型应该是最后几类情况才考虑：

第一，正确上下文、正确工具、正确证据都给了，但模型仍然稳定推理错。
第二，任务需要更强的长上下文理解、多步骤推理、代码能力或多模态能力。
第三，低成本模型在复杂任务上工具选择和计划能力明显不足。
第四，同样 harness、同样 eval 数据下，高阶模型显著更稳定。

换模型前最好做 **同一评测集横向对比**：同一批 trace replay，固定 RAG、工具、prompt 和上下文，只替换模型，看 Tool Selection Accuracy、Evidence Grounding Rate、Final Answer Quality、成本和延迟是否改善。否则很容易把“RAG 召回问题”误判成“模型不够强”。

**一个标准错误定位流程**

我会在工程上设计成下面这个闭环：

```text
收集用户反馈 / 自动评测失败
  ↓
定位失败样例对应 trace_id
  ↓
按 span 查看：Router → Context → RAG → Planner → Tool → Observation → Generation → Safety
  ↓
标注 failure_type
  ↓
归因到 owner：prompt / RAG / tool / router / model / policy / state
  ↓
提出最小修复
  ↓
加入 regression eval
  ↓
跑 A/B 或版本对比
  ↓
上线并监控是否复发
```

LangChain 2026 年关于 Agent Improvement Loop 的文章也强调，从 traces 开始，叠加 evals 和人工反馈，识别失败原因，做 targeted changes，再验证改动是否有效。([LangChain][5])

**金融 Agent 场景举例**

假设用户问：“黄金最近为什么跌，未来一个月怎么看？”最终回答错了，我会这样定位：

如果 trace 显示没有触发 Web Search，只用了历史记忆，那是 **路由/Gateway 错**，要改时间敏感问题识别规则。

如果触发了 Web Search，但搜到的是几个月前的旧新闻，那是 **Web Search/RAG 时效性过滤错**，要加时间过滤、来源权重和 freshness check。

如果检索结果里已经有美元、利率、避险情绪、ETF 资金流这些正确证据，但最终回答没提，那是 **Context Packer 或 prompt 错**，要提高关键 evidence 优先级，并要求结论必须绑定证据。

如果行情工具调用了，但把黄金 ETF 代码或金价数据源传错，那是 **工具参数解析错**，要改实体解析和 schema 校验。

如果回答里直接说“建议今天加仓两倍做多”，那是 **安全/合规输出错**，要改 guardrail、风险提示模板和高风险投资建议拦截。

如果所有证据和工具都正确，但模型仍然总结混乱、推理不稳，才考虑 **换更强模型或增加 judge 校验**。

**放到你的金融投资顾问 Agent 项目里怎么讲**

你可以这样说：我的金融 Agent 评测不是只看最后回答，而是把每个 bad case 反向映射到链路层。比如基金对比报告质量差，我会先看是否命中 fund_compare_skill；再看是否注入用户风险偏好；再看是否调用净值、持仓、行业指数、新闻工具；再看参数是否正确；再看 Observation Builder 是否把工具结果转成了带时间戳和 source_refs 的摘要；最后才看模型生成是否有问题。

如果最终报告缺少持仓分析，但 trace 里没有调用持仓工具，我改 Planner 或 Skill 流程；如果调用了持仓工具但参数错，我改工具 schema 和实体解析；如果工具返回正确但报告没用，我改 Context Packer 和报告 prompt；如果报告用了证据但结论越界，我改合规 guardrail；如果同一套上下文下模型仍然不稳定，我才换模型或加二次 judge。

这样回答能体现大厂工程思维：**错误定位不是拍脑袋调 prompt，而是基于 trace 的分层根因分析。**

**仓库证据摘要**

OpenAI Agents SDK 的 tracing 提供了 agent run、LLM generation、tool call、guardrail、handoff 等 span，因此可以把错误定位到模型生成、工具调用、安全检查或多 Agent 交接等具体环节。([OpenAI][2]) OpenAI Cookbook 的 Agent Improvement Loop 进一步把真实 traces、人工/模型反馈、eval、harness changes 串成闭环，并说明 harness 包括 instructions、tools、routing、output requirements、validation checks。([OpenAI开发者][1])

LangSmith 的 Evaluation 文档说明，Agent evaluation 捕获完整 trajectory、tool calls 和 reasoning，并可以对中间决策和 agent behavior 打分，从而定位复杂 workflow 的错误位置；它还支持离线/线上评测、人工反馈、LLM-as-judge 和 CI/CD 集成。([LangChain][3])

OpenClaw 的 agent loop 证据说明，真实 Agent run 包括 intake、context assembly、model inference、tool execution、streaming replies、persistence；所以错误定位也必须按这些阶段拆，而不能只看最终回复。([OpenClaw][4])

Hermes Agent v0.13.0 的 release 提到 durable multi-agent board、heartbeat、reclaim、zombie detection、per-task retries、hallucination recovery、Checkpoints v2 和 Gateway auto-resume；这说明长任务 Agent 的错误定位还要覆盖任务卡死、重试、状态恢复和幻觉恢复等运行时问题。([GitHub][6])

**常见错误回答**

不要说：“如果错了，我就优化 prompt。”这太单薄。面试官会继续追问：如果是工具参数错呢？如果是 RAG 没召回呢？如果是路由没走 Web Search 呢？如果模型根本没看到正确上下文呢？

更好的回答是：**我会先从 trace 里定位错误发生在哪个 span，再决定改哪一层。Prompt 是其中一层，但工具、RAG、路由、Packer、Observation、状态和安全策略都可能是根因。**

**一句话总结**

错误定位的核心是：用 trace 把一次 Agent Run 拆成路由、上下文、RAG、计划、工具、Observation、生成、安全、状态这些 span；评测失败后先定位失败 span，再做最小修复，而不是所有问题都改 prompt 或直接换模型。

**2–5 分钟面试口述版**

我理解 Agent 的错误定位不能只看最终答案，也不能一上来就改 prompt。正确做法是基于 trace 和 eval 做分层根因分析。因为一次 Agent Run 是多步骤链路，包含意图识别、上下文组装、RAG 检索、Planner 计划、工具选择、工具参数、工具返回、Observation Builder 摘要、最终生成和状态写回。最终答案错，只是表面现象，真正的根因可能在任何一层。

我会先把用户反馈或自动评测失败的样例找到对应 trace_id，然后沿着 span 一层层看。第一看 Router，是不是任务类型识别错了，比如用户问“最近黄金为什么跌”，系统却没触发 Web Search。第二看 Context Gateway，是不是应该读取短期状态、长期记忆、RAG、tool ledger，但没有读取。第三看 RAG，是不是检索 query 错、召回文档错、文档过期，或者召回对了但没有被 Packer 放进上下文。第四看 Planner，是不是计划漏步骤，比如基金报告没有安排查持仓。第五看 Tool，是不是工具选错、参数错、超时、空返回、重复调用。第六看 Observation Builder，是不是把工具结果摘要错了，或者丢了时间戳和来源。第七才看最终生成，是不是模型没有遵守格式、没有引用证据、语言不合规。最后还要看状态写回和 artifact，是不是版本错了、checkpoint 没保存、tool ledger 没写。

定位之后再决定改哪里。如果意图分类错，就改路由规则、路由 prompt、few-shot 或阈值；如果 RAG 没召回，就改 query rewrite、chunk、embedding、reranker 和 metadata filter；如果工具参数错，就改 schema、实体解析、日期处理和参数校验；如果工具返回太乱，就改 Observation Builder；如果正确证据已经给了但模型没用，才改 prompt、输出模板或 evidence binding；如果所有上下文和工具都正确，但模型仍然推理不稳，才考虑换模型或加二次 judge。

比如我的金融投资顾问 Agent 里，用户说“这个半导体基金分析错了”，我不会直接说改 prompt。我会先看是否命中 fund_compare_skill；有没有读取用户风险偏好；有没有调用基金净值、持仓、行业指数和新闻工具；基金代码和日期范围是否正确；工具返回是否有 source_refs 和时间戳；最终报告有没有绑定证据；有没有越界给出确定性买卖建议。如果 trace 显示没有调用持仓工具，我改 Planner；如果调用了但参数错，我改工具 schema；如果工具结果正确但报告没用，我改 Packer 和 prompt；如果报告越界，我改 guardrail；如果同样上下文下模型仍然不稳定，我再换模型。

从工程实践看，OpenAI Agents SDK 的 tracing 会记录 agent run、LLM generation、tool call、guardrail 和 handoff；OpenAI 的 Agent Improvement Loop 也强调从真实 traces 开始，加入反馈，变成 eval，再生成 harness 修改建议。LangSmith 的 Agent Evaluation 会捕获完整 trajectory、工具调用和中间决策，帮助定位复杂 workflow 哪里出错。OpenClaw 的 agent loop 也说明真实 Agent run 包含 intake、context assembly、model inference、tool execution、streaming replies 和 persistence。我的总结是：Agent 错误定位不是“调 prompt 玄学”，而是基于 trace 的工程归因，先找失败层，再做最小修复，并把 bad case 固化成回归评测。

## 13、**线上观测和离线评测要怎么连成闭环**

离线评测解决“上线前版本能不能过关”，线上观测解决“真实用户有没有出新问题”。两者必须连成闭环。比如线上 trace 发现某类问题频繁失败：用户问“最近行情”，Agent 没有触发 Web Search。你就把这些失败 trace 加入数据集，新增一个 evaluator：“涉及最近/今天/最新的金融问题必须触发实时数据或 Web Search”。然后修复路由逻辑，再跑离线实验，确认没有破坏其他能力，最后灰度上线。

近年的研究也开始从“看单条 trace”走向“看 trace 群体”。2026 年的 Insights Generator 研究提出了 corpus-level trace diagnostics，也就是从大量执行轨迹里发现系统性问题，而不是人工只看少量失败样本；PrefixGuard 则研究从 agent trace 前缀中提前预测失败风险，说明生产级 Agent 观测正在从事后排查走向在线预警。([arXiv][7])

## 13-1、**需要哪些工具和平台**

实践中可以用几类工具。**LangSmith** 适合 LangChain / LangGraph 生态，覆盖 trace、dataset、experiment、online evaluator、annotation queue、dashboard、alert。**Langfuse** 是开源 LLM observability 平台，适合自托管或接入多框架，重点记录 prompt、response、token、latency、tools、retrieval、cost，并支持 evals、datasets、experiments。**OpenAI Traces / Agents SDK tracing** 适合使用 OpenAI Agents SDK 时记录 agent span、generation span、function span、guardrail span 和 handoff span。**Google ADK Evaluation** 适合做 Agent test file / evalset，尤其适合把“期望工具轨迹”写进测试样本。OpenTelemetry 的 GenAI semantic conventions 则提供了更通用的可观测性标准方向，覆盖 generative AI 相关 signals、events、metrics、spans，适合企业把 LLM trace 接到统一监控体系中。([LangChain 文档][1])

对你自己的项目来说，不需要一开始全部上。最小可落地版本可以是：FastAPI 每个请求生成 `trace_id`；记录用户输入、路由结果、上下文来源、工具调用、工具参数、工具返回摘要、最终回答、token、延迟、错误类型；再把 50–100 条典型问题做成离线 eval dataset。后续再接 Langfuse 或 LangSmith，把 trace、dataset 和 evaluator 可视化。

## **一个完整例子：金融 Agent 怎么做观测和评测**

假设你的金融 Agent 支持“生成某只股票的深度分析”。观测链路应该记录：用户问题、识别出的股票代码、选择的分析 Skill、调用了哪些工具，比如行情、财务、新闻、行业、估值；每个工具参数是什么；返回是否成功；哪些证据进入最终回答；最终报告生成耗时和 token。指标上看：工具调用成功率、数据新鲜度、报告生成成功率、引用覆盖率、平均耗时、P95 延迟、失败原因分布。

评测数据集可以这样构造：20 条单股分析、20 条基金对比、20 条市场异动解释、20 条用户偏好相关问答、20 条风险合规边界问题。每条样本标注：是否需要实时数据、期望工具、必要证据、最终回答格式、风险提示要求。评测时分别检查：工具轨迹是否正确、数据是否新鲜、回答是否引用证据、是否过度投资建议、是否符合用户偏好但不被偏好绑架。这样一套评测比“看回答顺不顺眼”专业得多。






## 大厂做 Agent 的“监控、评估、治理”？
**先用一句最容易记住的话概括**

大厂做 Agent 的“监控、评估、治理”，本质上是在回答三个不同的问题：  
**监控**是在问：系统刚才到底做了什么；  
**评估**是在问：它这样做到底好不好；  
**治理**是在问：它哪些事可以做、哪些事必须拦住，出了问题谁来负责。

过去一年，OpenAI、Anthropic、Google、AWS、Microsoft 这些主流厂商的公开实践，已经非常明显地收敛到一个共同范式：**把 Agent 当成一条可观测、可评测、可审计的业务流水线来管，而不是把它当成一个“会聊天的大模型外壳”。** OpenAI 把 tracing 和 evaluations 直接纳入 Agents/Responses 体系；Anthropic 明确提出“没有 evals，团队就会一直在生产环境里被动救火”；Google ADK 强调既要看最终答案，也要看 step-by-step trajectory（逐步执行轨迹）；AWS 和 Microsoft 则把 policy controls、统一控制平面、身份与审批做成企业级能力。([OpenAI][1])

**第一部分：先把三个词讲清楚，不然很容易混**

很多初学者会把“监控、评估、治理”混成一件事。其实它们像医院里的三个岗位。  
监控像生命体征仪，负责持续看血压、心率和报警；  
评估像体检或复查，负责判断病情有没有变好；  
治理像医院制度，规定哪些药谁能开、哪些手术必须会诊。

放到 Agent 上也是一样。**监控**更偏线上运行期，关注 trace（调用链）、latency（延迟）、errors（错误）、cost（成本）、tool usage（工具使用）、handoffs（代理交接）这些运行信号；**评估**更偏质量验证，关注答案对不对、轨迹合不合理、是否遵守业务规则；**治理**则关注权限、审批、身份、合规、最小权限、审计和回滚。OpenAI Agents SDK 官方把 tracing 说成“对一次 agent run 的完整记录”，里面包括 LLM 调用、工具调用、handoff、guardrail 和自定义事件；Anthropic 则强调 eval 的价值在于让行为变化在进生产前就能被看见；Google ADK 直接把评估标准分为 response quality（结果质量）、tool use trajectory（工具使用轨迹）和 safety（安全）。([OpenAI][2])

**第二部分：大厂现在最常见的标准范式是什么**

如果把产业里的成熟做法压缩成一个图，它通常长这样：

**第一层，统一追踪。**  
不管你是单 Agent、多 Agent、MCP、工具调用还是 RAG，先把每一步都变成 trace/span/event。  
**第二层，双轨评估。**  
一条是离线 regression eval（回归评测），每次改 prompt、模型、工具或工作流都跑；另一条是在线 eval/monitoring（在线评测与监控），用真实流量持续看质量和漂移。  
**第三层，策略治理。**  
高风险工具加 allow-list（允许名单）、approval（审批）、guardrails（护栏）、identity（身份）和 audit（审计）。  
**第四层，回归与灰度。**  
改动先在测试集、影子流量、小流量上看，再放大。

这套结构不是某一家公司独创，而是主流平台在不同名字下说同一件事。OpenAI 说 tracing + evals + guardrails；Google ADK 说 trajectory eval + safety/security；AWS AgentCore 说 quality evaluations + policy controls；Microsoft 说 unified control plane for observability, security, and governance；Anthropic 说 evals + harness + permission/sandbox/policy。([OpenAI][2])

**第三部分：监控这一块，大厂到底在看什么**

对 Agent 来说，最核心的监控对象不是“请求成功没成功”这么简单，而是**执行轨迹**。  
因为一个 Agent 的失败，可能不是最终回答报错，而是中间某一步走偏了：  
它可能选错工具；  
可能重复调用三次同一个 API；  
可能在没必要的时候 handoff 给别的 agent；  
也可能答案看起来还行，但过程非常慢、非常贵。

所以现在主流做法是以 **trace/span 为中心** 来监控。OpenAI Agents SDK 的 tracing 默认会记录 LLM generations、tool calls、handoffs、guardrails 和 custom events；LangSmith 的官方定位也是 tracing + monitoring + observability；Langfuse 和 Phoenix 则分别把自己定义成以 tracing 为核心的 LLM/agent observability 平台。Google ADK 也把 observability 集成到开发流程里，并强调用 OpenTelemetry（OTel）追踪 agent 行为。([OpenAI][2])

这背后有一个行业上非常重要的收敛：**Agent 监控正在逐步向 OpenTelemetry + GenAI 语义规范靠拢。**  
OpenTelemetry 官方已经有 GenAI semantic conventions（生成式 AI 语义约定），专门定义 AI 相关的 signals 和属性；OpenInference 则是在 OTel 之上补充 AI tracing 的约定和插件，并且明确说它是面向 AI 应用 tracing 的通用约定。你可以把这理解成：传统软件世界监控 HTTP、数据库、消息队列；Agent 世界开始用类似方式监控 prompt、completion、tool call、retrieval、agent invoke。虽然这套标准还在演进中，但它已经是目前最像“行业公约数”的方向。([OpenTelemetry][3])

**一个小白最该记住的监控指标框架**

大厂通常不会只盯着一个“成功率”，而是会同时看四类指标。  
第一类是**性能指标**：延迟、P50/P95/P99、token 用量、成本、重试次数。  
第二类是**行为指标**：工具调用次数、工具失败率、handoff 次数、循环次数、是否越权。  
第三类是**结果指标**：答非所问率、拒答率、事实错误率、引用缺失率。  
第四类是**风险指标**：敏感数据暴露、触发护栏次数、人工审批率、策略拒绝率。

Langfuse 官方在 observability 文档里就明确把 traces、latency、cost、evaluation scores 放在一起；W&B Weave 也把 tracing、output evaluation、cost estimates 放在同一产品层；OpenAI Agents SDK tracing 则直接提供 agent step 级别的事件记录。也就是说，**今天的主流做法已经不再把“质量”和“性能”分开看，而是一起进 dashboard。** ([Langfuse][4])

**第四部分：评估为什么比普通软件测试更难**

因为传统软件测试默认“同样输入得到同样输出”，而 Agent 不是这样。  
OpenAI 的 evaluation best practices 直接指出，生成式 AI 是 variable（有波动的），传统软件测试方法不够；Anthropic 也强调，没有 evals，你会在生产环境里被动发现问题，修一个 bug 又带来另一个 bug。Google ADK 甚至把 trajectory evaluation 单独拿出来，明确说评估 Agent 不能只比最终输出，还要比实际轨迹和理想轨迹之间的差距。([OpenAI 开发者][5])

所以现在产业界对 Agent 评估的收敛方向很明确：**至少分成三层。**

第一层是 **离线任务集评估**。  
你先准备一批标准任务和期望结果，比如“客服退货”“查航班政策”“代码修 bug”“研究报告生成”。每次改模型、改工具、改路由、改规则，都先跑这批任务，看看是不是退步了。OpenAI 和 Anthropic 都把这看成最基本的工程习惯。([OpenAI 开发者][5])

第二层是 **轨迹级评估**。  
不是只看“最终答对了没”，还要看“过程是否合理”。Google ADK 的官方例子写得很明白：例如“先验证身份，再查余额”，这个顺序本身就是业务规则；如果答案最后碰巧对了，但中途跳过认证，评估也应该判不合格。([Google Codelabs][6])

第三层是 **线上真实流量评估**。  
LangSmith 官方文档把 online evaluation 直接作为一类正式能力；它的意思是：你不能只靠测试集，因为真实用户会提出你没想到的问题。线上评估常用的方法包括抽样人工审核、LLM-as-a-judge（让模型打分）、规则评分、用户反馈和工单回流。([LangChain 文档][7])

**第五部分：最近一年，大家用什么 benchmark 来评估 Agent**

如果只讲聊天质量，那太浅了。过去一年更重要的 benchmark，已经在往**工具调用、业务规则、多轮互动、长时任务**这些真实能力上走。

**BFCL（Berkeley Function Calling Leaderboard）** 主要测 function calling / tool use。  
它会看模型能不能在现实风格的设定里正确调用函数，还覆盖 serial（串行）和 parallel（并行）调用。它很适合回答一个问题：**这个模型会不会“把工具调对”。** ([OpenReview][8])

**τ-bench** 更进一步。  
它不只让模型调工具，还让它在动态 user-agent-tool 互动里遵守 domain-specific rules（领域规则），例如零售、航空、银行这种客服式场景。它特别有价值，因为企业里很多 Agent 不是数学题，而是“要不要退款、能不能改签、先不先验证身份”这种流程与政策问题。([arXiv][9])

**Terminal-Bench 2.0** 则偏 coding / terminal agents。  
它测试的是 Agent 在真实终端环境中的长时任务能力，而不是单次代码生成。论文和官方站点都强调，这个 benchmark 是 hard、realistic、long-horizon 的，评测对象已经包括 Claude Code、Codex CLI、Gemini CLI 等热门命令行代理。对软件工程类 Agent 来说，这种 benchmark 比普通“生成一段代码”更接近生产。([OpenReview][10])

最近还有 **TRACE** 这样的 trajectory-aware 评估框架，专门指出“只看 Pass@1 会制造高分幻觉”，因为你可能只看到了最终答对，却没看到过程低效、脆弱或不稳。这个方向其实和 Google ADK、Anthropic 近一年的说法非常一致：**轨迹本身就是质量的一部分。** ([arXiv][11])

**第六部分：治理为什么不能只理解成“内容审核”**

很多初学者一提治理，就只想到“别输出违规内容”。这只对了一半。  
Agent 的治理至少有四层：

第一层是 **输入/输出治理**。  
例如敏感内容、注入攻击、越狱、PII（个人敏感信息）泄露、品牌风险。LangChain Guardrails 和 OpenAI Guardrails 都是做这类事情的，通常在输入和输出边界检查。([LangChain 文档][12])

第二层是 **工具治理**。  
也就是：这个 Agent 能调用哪些工具，哪些必须审批，哪些只能只读，哪些绝不能自动执行。OpenAI 的 MCP/Connectors 文档明确支持 `allowed_tools` 来缩小工具暴露面，并支持 `require_approval`；Microsoft Foundry 的 MCP 文档也明确建议高风险工具使用 allow-list 和 approval；AWS Bedrock AgentCore 在 2025 年底正式推出了 Policy controls，用来控制 agent tool execution。([OpenAI 开发者][13])

第三层是 **身份与权限治理**。  
谁在调用这个 Agent，这个 Agent 代表谁行动，它调用工具时用的是哪个身份，权限是不是最小化。Microsoft 的 AI agent governance/security 指南把这一层放得很重，强调统一控制平面、身份、安全和 Zero Trust；AWS AgentCore 也走的是类似路线，把策略和网关纳入企业平台。([Microsoft Learn][14])

第四层是 **供应链与协议治理**。  
尤其是 MCP 场景。MCP 官方安全最佳实践文档专门提醒了授权、攻击面、工具定义污染、令牌使用和实现风险；OpenAI 的 MCP 文档也直接提醒，不要在工具 JSON 里放敏感信息，也不要把恶意内容放进工具定义。也就是说，治理不仅是“模型说了什么”，还包括“工具端会不会害你”。([模型上下文协议][15])

**第七部分：现在产业里比较成熟的“治理动作模板”是什么**

对大厂来说，治理通常不是一个单点产品，而是一条控制链。

最常见的模板是：

用户请求进来以后，  
先做 **轻量输入护栏**，判断是不是越权、越狱、越域；  
再进入 **Agent 规划层**；  
如果要调工具，先过 **工具 allow-list / policy / approval**；  
返回结果前再过 **输出护栏**；  
最后把整条轨迹进 **审计日志和 trace 存档**。

OpenAI Agents SDK 的 guardrails 允许在用户输入和 agent 输出上做检查；AWS AgentCore 把 quality evaluations 和 policy controls 放到一起；Microsoft Foundry 则在统一控制平面上强调 observability、security 和 governance 一体化。这个组合说明产业界越来越认同：**治理不能只在最外层拦一次，而要和工具调用、身份、审批、追踪绑在一起。** ([OpenAI][16])

**第八部分：大厂为什么越来越强调“eval-driven / eval-centric”**

因为监控只能告诉你“哪里出事了”，评估才告诉你“改完以后真的变好了没有”。  
Anthropic 的《Demystifying evals for AI agents》几乎就是这件事的系统阐述；OpenAI 也在 2025 年底专门发了“How evals drive the next chapter in AI for businesses”；W&B Weave、Langfuse、LangSmith 这些平台则都在把 tracing 和 evaluation 放进一个产品里。你能看到一个很强的行业信号：**大家开始不满足于“看 trace”，而是要把 trace 反过来变成可复用数据集和评测资产。** ([anthropic.com][17])

这就是为什么现在很多团队开始说 **eval-centric**。  
它的意思不是“只做评测”，而是“让评测成为开发的中心节奏”：  
先定义任务与评分标准；  
再开发 Agent；  
改完以后先跑 eval；  
线上再抽样做 online eval；  
发现问题后把真实失败样本再回灌到离线 eval 集。

Anthropic、OpenAI、Google 官方说法不同，但方向高度一致。([anthropic.com][17])

**第九部分：如果你现在要选型，应该怎么选**

这件事没有唯一答案，但有一个很实用的思路：  
**先按“你最缺什么”来选，而不是按“哪个平台最火”来选。**

如果你最缺的是 **“把 Agent 每一步看清楚”**，而且你已经在 LangChain / LangGraph 生态里，优先看 **LangSmith**；如果你想要 **开源、自托管、框架无关**，优先看 **Langfuse** 或 **Phoenix**；如果你团队已经很熟悉 W&B 的实验管理，则 **Weave** 很顺手。它们三家都把 tracing + eval 合在了一起，只是生态重心不同。([LangChain 文档][18])

如果你最缺的是 **“官方一体化能力”**，而且你本来就在某家生态里：  
OpenAI 生态就用 **Agents SDK + tracing + evals + guardrails + MCP approvals**；  
Google 生态就用 **ADK + trajectory eval + safety/security + OTEL/Weave 集成**；  
AWS 生态就用 **AgentCore + Evaluations + Policy Controls**；  
Microsoft 企业环境则更偏向 **Foundry / CAF 的统一治理和控制平面**。  
这种选法的好处是“少拼装、集成顺”，代价是一定程度的平台绑定。([OpenAI][2])

如果你是 **监管要求高的行业**，例如金融、医疗、政企、B2B 自动化，优先考虑“治理优先”的组合：  
工具必须 allow-list；  
写操作必须审批；  
trace 要可追溯；  
PII 要脱敏；  
线上要能回放和审计；  
MCP 要按官方安全最佳实践做权限和最小暴露。  
这种场景里，**治理永远比“多一个 benchmark 分数”更重要。** ([模型上下文协议][15])

**第十部分：开发这类模块时，最容易忽略的工程问题**

第一，**没有统一 trace schema。**  
如果你今天记“tool_name”，明天记“function”，后天又拆成别的字段，后面几乎没法做跨版本比较。OTel GenAI 语义约定和 OpenInference 之所以重要，就是在帮你避免这类“每个团队自己发明埋点语言”的问题。([OpenTelemetry][3])

第二，**只记录结果，不记录轨迹。**  
这样你只能知道“这个回答错了”，却不知道是检索错、工具错、规划错、还是护栏误拦。Google ADK 和 TRACE 都在强调 trajectory-aware evaluation，原因就在这里。([google.github.io][19])

第三，**只做离线评测，不看线上真实流量。**  
离线集能挡住回归，但挡不住新型真实问题。LangSmith 把 online evaluation 做成正式能力，就是因为生产环境的问题结构和测试集永远不完全一样。([LangChain 文档][7])

第四，**只做监控，不做动作闭环。**  
看见问题但没人处理，监控就只是漂亮图表。AWS AgentCore 把 policy controls 和 evaluations 放一起，Microsoft 强调 unified control plane，本质上都是希望监控和治理之间能形成闭环。([Amazon Web Services, Inc.][20])

第五，**没有版本化。**  
模型、prompt、工具、技能、规则、策略、评测集、评分器，如果不版本化，后面根本说不清“到底是哪次改动让效果变坏了”。W&B Weave、Langfuse、OpenAI evals、OpenAI harness engineering 都在把这一点推得越来越前。([Weights & Biases 文档][21])

**第十一部分：给小白一个最实用的“落地顺序”**

如果你现在刚开始做 Agent，不要一上来就追求“大而全平台”。  
更稳的顺序通常是：

先做 **基础 tracing**，把 LLM 调用、工具调用、延迟、成本和错误记下来；  
再做 **离线任务集评测**，至少覆盖 20–50 个典型任务；  
再做 **线上抽样评测**，把真实失败样本回灌成新的测试集；  
然后给高风险动作加 **allow-list、approval 和 guardrails**；  
最后再做更高级的 **统一控制平面、政策引擎、复杂指标告警和自动回滚**。

这条路线和 Anthropic 的“先简单，再增加 Agentic complexity”、OpenAI 的“先单 Agent，再逐步升级”、Google ADK 的“先做 trajectory 和 safety eval”、AWS/Microsoft 的“先把治理纳入平台”是对齐的。([anthropic.com][22])

**最后给你一个最适合记忆的框架**

把大厂做 Agent 的监控、评估、治理记成一句话：  
**看得见、评得准、拦得住。**

“看得见”靠 tracing 和 observability；  
“评得准”靠离线 + 在线 + 轨迹级 eval；  
“拦得住”靠 policy、approval、guardrails、identity 和 audit。

而现在最像“行业标准范式”的，不是某一个具体产品，而是下面这个组合：  
**OTel/OpenInference 做底层观测语义，trace 平台做在线可观测，离线+在线 eval 做质量闭环，policy/approval/guardrails 做治理收口。**  
这套组合，就是 2025–2026 年主流厂商和领先团队正在逐渐收敛到的工程共识。([OpenTelemetry][3])

## 大厂在做agent的观测的时候主要在观测什么内容？trace该怎么设计？从0到1的开发和测试流程是什么？需要注意哪些问题有哪些解决方案？
**先给结论**

大厂做 Agent 观测，不只是看“模型回答对不对”，而是看完整 runtime chain：**用户请求怎么进来、上下文怎么构造、模型怎么决策、工具怎么调用、权限怎么审批、状态怎么变化、失败怎么恢复、最终结果有没有证据**。  
Trace 的核心设计是：**一个用户任务一个 trace，每个关键动作一个 span，每个 span 里记录结构化属性和事件**。不要只记录 LLM 请求日志，否则定位不了工具错误、权限误判、上下文污染、死循环、重复写操作这些 Agent 真实线上问题。

**本质与原理**

普通 LLM 应用主要观测：

```text
prompt -> model -> response
```

但 Agent 应用是：

```text
input -> context -> planner -> model -> tool -> observation -> state -> loop -> verifier -> final
```

所以 Agent 观测要回答 6 个问题：

| 问题 | 观测目的 |
|---|---|
| 它为什么这么做？ | 看 planner、router、tool selection |
| 它用了什么依据？ | 看 context、retrieval、memory、evidence |
| 它调用了什么工具？ | 看 tool call、参数、输出、错误 |
| 它有没有越权？ | 看 permission、approval、sandbox |
| 它为什么失败？ | 看 error type、retry、timeout、state |
| 它到底完成了吗？ | 看 verifier、test result、user feedback |

OpenAI Agents SDK 的 tracing 官方文档就把 trace 定义为一次端到端 workflow，由多个 span 组成，并默认记录 agent run、LLM generation、function tool call、guardrail、handoff 等事件；同时也提醒 LLM 输入输出和工具输入输出可能包含敏感数据，需要控制是否采集。参考：OpenAI Agents SDK Tracing https://openai.github.io/openai-agents-python/tracing/

**大厂主要观测什么内容**

| 观测维度 | 具体看什么 | 典型指标 |
|---|---|---|
| 入口层 | 用户、租户、渠道、任务类型、附件 | QPS、任务类型分布、租户隔离 |
| 上下文层 | 读了哪些文件、RAG 命中哪些 chunk、skills 是否加载 | context tokens、cache hit、retrieval recall |
| 路由规划层 | 是否进 Agent、计划多少步、是否重规划 | route accuracy、replan count、plan fail rate |
| 模型层 | provider、model、tokens、latency、错误 | TTFT、生成耗时、token 成本、rate limit |
| 工具层 | tool name、参数、耗时、exit code、stderr | tool success rate、timeout rate、retry count |
| 权限层 | 是否审批、审批原因、审批结果 | approval rate、deny rate、policy miss |
| 执行层 | shell/script/MCP/API 执行结果 | exit_code、stdout 摘要、资源使用 |
| 状态层 | step 状态、checkpoint、锁、并发 | stuck tasks、lock wait、dead loop |
| 多 Agent 层 | spawn、handoff、message.send、child cost | child count、handoff latency、subagent fail |
| 验收层 | 测试是否通过、证据是否充足 | verifier pass rate、hallucination rate |
| 用户体验层 | 最终成功率、用户反馈、是否人工接管 | task success、CSAT、escalation rate |
| 安全合规层 | secret、PII、越权访问、审计日志 | redaction hit、policy violation |

Microsoft Agent Framework 的 observability 文档也强调 workflow 需要 spans、logs、metrics，用来理解消息流、executor 性能和错误；它的 span 包括 `workflow.session`、`executor.process`、`message.send` 等，说明大厂观测重点已经从“单次模型调用”扩展到“工作流执行过程”。参考：Microsoft Agent Framework Observability https://learn.microsoft.com/en-us/agent-framework/workflows/observability

**Trace 该怎么设计**

推荐三层模型：

```text
Trace：一次用户任务 / 一次 Agent run
Span：一次关键操作，比如 LLM 调用、工具调用、权限检查
Event：span 内的关键时间点，比如 started、approved、timeout、retry
```

一个 trace 的结构可以这样：

```json
{
  "trace_id": "trace_abc",
  "run_id": "run_001",
  "session_id": "s_001",
  "tenant_id": "t_001",
  "user_id_hash": "u_hash",
  "workflow_name": "coding_agent_fix_test",
  "app_version": "2026.05.08",
  "status": "failed",
  "start_time": "2026-05-08T10:00:00Z",
  "end_time": "2026-05-08T10:03:20Z",
  "metadata": {
    "channel": "ide",
    "model": "gpt-5.4",
    "permission_profile": "workspace-write"
  }
}
```

Span 设计：

| Span | 记录字段 |
|---|---|
| `input.receive` | query hash、attachments、channel、tenant |
| `context.build` | 文件列表、RAG chunk ids、tokens、cache hit |
| `router.decide` | route、confidence、reason code |
| `planner.generate` | plan_steps、risk_actions、dependencies |
| `llm.generate` | model、tokens、latency、finish_reason |
| `tool.call` | tool_name、args_hash、schema_valid、duration |
| `permission.check` | policy、risk_level、decision、reason |
| `approval.wait` | approver、decision、wait_ms、timeout |
| `executor.run` | cwd、exit_code、stdout_summary、stderr_summary |
| `observation.parse` | error_type、evidence、parsed_failures |
| `state.update` | from_state、to_state、checkpoint_id |
| `verifier.run` | success_criteria、test_result、confidence |
| `final.response` | answer_hash、citations、format_valid |

工具调用 span 示例：

```json
{
  "span_name": "tool.call",
  "parent_span": "agent.turn.3",
  "attributes": {
    "tool.name": "shell",
    "tool.args_hash": "sha256:xxx",
    "risk.level": "test_command",
    "permission.decision": "allow",
    "duration_ms": 18321,
    "exit_code": 1,
    "error.type": "test_failed",
    "stdout.summary": "2 failed, 48 passed",
    "artifact.log_path": "logs/run_001/npm_test.log"
  }
}
```

注意：**生产 trace 默认不要记录完整 prompt、完整工具输出、完整用户数据**。OpenAI 文档也提醒 generation span 和 function span 可能包含敏感数据，采集要可关闭或脱敏。

**从 0 到 1 开发流程**

| 阶段 | 要做什么 | 产出 |
|---|---|---|
| 1. 定义观测目标 | 明确要定位哪些问题：幻觉、工具失败、死循环、越权、慢请求 | failure taxonomy |
| 2. 定义 trace schema | 统一 trace/span/event 字段 | schema 文档 |
| 3. 插桩核心链路 | input、context、LLM、tool、permission、state、verifier | tracing SDK |
| 4. 接入存储 | OpenTelemetry / Kafka / ClickHouse / ES / LangSmith / OpenAI Traces | trace backend |
| 5. 做脱敏 | PII、secret、token、文件内容脱敏 | redaction pipeline |
| 6. 做 dashboard | 成功率、延迟、成本、工具失败率、审批率 | observability dashboard |
| 7. 做 alert | timeout、loop、成本异常、权限异常 | alert rules |
| 8. 做 replay | 用同一输入、上下文快照、工具 mock 重放 | replay harness |
| 9. 做 eval 关联 | trace 绑定人工评分、自动评测、线上反馈 | eval dataset |
| 10. 灰度上线 | 先只采 metadata，再逐步采摘要和 artifact | rollout plan |

LangSmith 的官方文档也强调从 trace 到生产级性能监控、告警、在线评估和用户反馈闭环。参考：LangSmith Observability https://docs.langchain.com/langsmith/observability

**测试流程怎么做**

测试不要只测“能不能记录日志”，要测“能不能定位问题”。

| 测试类型 | 测什么 |
|---|---|
| 单元测试 | 每个 span 字段是否完整，错误时是否也 end span |
| 集成测试 | 一次完整 Agent run 是否能串起 trace |
| 故障注入 | 模型超时、工具 500、权限拒绝、审批超时 |
| 死循环测试 | 同一工具重复失败是否记录 no-progress |
| 脱敏测试 | API key、手机号、身份证、cookie 是否被打码 |
| 并发测试 | 多 Agent trace_id 是否串线 |
| 回放测试 | 用 trace 能否复现失败路径 |
| 成本测试 | 高 QPS 下 trace 写入是否拖慢主链路 |
| 采样测试 | 只采 1% 成功请求，但 100% 采失败请求 |

**常见问题与解决方案**

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 只记录 LLM，不记录工具 | 不知道失败发生在哪一步 | 工具、权限、状态、verifier 全部 span 化 |
| Trace 太大 | 存储爆、查询慢、泄露风险 | 摘要化、采样、artifact 外置 |
| 敏感信息泄露 | prompt/tool output 里有密钥 | 默认脱敏，敏感字段 opt-in |
| Trace 断链 | 多线程、异步、子 Agent 丢 trace_id | context propagation，所有任务传 trace_id |
| 无法定位死循环 | 只看到很多相似 span | 加 iteration、no_progress_count、same_tool_hash |
| 无法复现 | 没保存上下文版本和工具结果 | 记录 prompt hash、context ids、tool output artifact |
| 高峰期拖慢业务 | 同步写 trace | batch export、异步队列、失败降级 |
| 指标很多但没用 | dashboard 花哨但不能定位 | 按 failure taxonomy 设计面板 |
| 多租户串数据 | trace 查询没隔离 | tenant_id 强制索引和鉴权 |
| 审批问题不可追责 | 没记录 policy reason | permission span 记录 rule_id、decision、approver |

**一句话总结**

大厂做 Agent 观测的核心是：**把 Agent 的每一次输入、决策、上下文、工具、权限、状态、验证和输出都结构化 trace 化；默认采摘要和元数据，敏感内容脱敏，失败请求可回放，线上指标能直接指向故障层。**

**2 分钟面试口述版**

如果面试问大厂做 Agent 观测主要看什么，我会先说：Agent 观测不能只看 LLM 请求日志，因为 Agent 是一个多步骤系统。真正要观测的是完整 runtime chain，包括用户输入、上下文构造、路由规划、模型调用、工具调用、权限审批、状态变化、失败恢复、最终验收和用户反馈。

Trace 设计上，我会用三层结构：一个用户任务是一个 trace，每个关键操作是一个 span，span 里面再记录事件。比如 `context.build` 记录加载了哪些文件和 RAG chunk，`llm.generate` 记录模型、tokens、延迟和错误，`tool.call` 记录工具名、参数 hash、耗时、exit code，`permission.check` 记录策略、风险等级和审批结果，`verifier.run` 记录测试是否通过、证据是否充分。

从 0 到 1 开发时，我会先定义故障分类，比如幻觉、工具失败、权限拒绝、超时、死循环、上下文污染。然后设计统一 trace schema，在 Agent loop 的关键节点插桩。接着接入 OpenTelemetry、LangSmith、OpenAI Traces 或自建 ClickHouse/ES。上线前要做脱敏，默认不记录完整 prompt 和工具输出，只记录摘要、hash 和 artifact 链接。失败请求 100% 采集，成功请求可以采样。

测试方面，我会做单元测试、集成测试、故障注入、脱敏测试、并发 trace 传递测试和 replay 测试。比如模拟工具超时，看 trace 能不能定位到 `tool.call`；模拟同一命令重复失败，看是否记录 no-progress；模拟审批拒绝，看状态是否正确终止。

最后，观测不是为了做漂亮 dashboard，而是为了回答四个问题：为什么这么做、用了什么依据、失败在哪一步、能不能复现。生产级 Agent 必须做到 trace 可查、指标可告警、失败可回放、敏感信息不泄露。


## 如何从 0 到 1 设计 Langfuse 观测

**先给结论**

从 0 到 1 设计 Langfuse 观测，我会按一句话来做：

> **先把 Agent 的一次任务拆成 trace、observation、score、session 四类数据，再围绕“定位问题”来设计埋点，而不是为了看漂亮链路图而埋点。**

Langfuse 官方数据模型的核心就是：**Observation 是单个步骤，Trace 是一次请求或任务，Session 是多轮对话/长任务分组**。所以 Agent 观测设计建议是：

```text
一个用户任务 / 一轮 Agent run = 一个 trace
一个关键步骤 = 一个 observation/span
一次多轮会话 = 一个 session
一次质量判断 = 一个 score
```

官方文档也明确说 Langfuse 用 `observations`、`traces`、`sessions` 组织数据，并支持 LLM 调用、工具调用、RAG 检索等观测类型。参考：Langfuse Data Model https://langfuse.com/docs/observability/data-model

**本质与原理**

Langfuse 不是普通日志系统，它更适合回答 Agent 里的这些问题：

| 问题 | Langfuse 里看什么 |
|---|---|
| 为什么答错？ | trace 里的 context、prompt、retrieval、tool、generation |
| 哪一步慢？ | observation duration |
| 哪个模型贵？ | generation token、cost、model |
| 检索是不是错了？ | retrieval observation、命中文档、score |
| 工具是不是失败了？ | tool observation、input、output、error |
| 是否上下文污染？ | trace input、metadata、session 历史 |
| 是否重复调用？ | 同一 trace 下相似 tool observation |
| 是否越权或审批失败？ | permission / approval observation |
| 是否线上退化？ | score、dashboard、dataset experiment |

所以 Langfuse 的价值不是“记录模型请求”，而是把 Agent 的 **决策链路、执行链路、证据链路、质量结果** 放到同一个视图里。

**工程实现 / 落地方案**

我会拆成 8 个模块。

| 模块 | 怎么设计 |
|---|---|
| Trace Schema | 统一 trace、observation、metadata、score 字段 |
| SDK Wrapper | 封装 Langfuse SDK，不让业务代码到处散落埋点 |
| Agent Instrumentation | 给 router、planner、LLM、tool、retrieval、verifier 加 observation |
| Session Propagation | 多轮对话传 `session_id`，保证能回放整段会话 |
| Scoring Pipeline | 用户反馈、规则评估、LLM-as-judge、人工标注写入 score |
| Dataset / Experiment | 从线上 bad case 沉淀数据集，离线评测新 prompt/model |
| Dashboard / Alert | 看成功率、延迟、成本、错误率、幻觉率、工具失败率 |
| Privacy / Cost Control | 脱敏、采样、输出截断、环境隔离 |

**Trace 设计规范**

推荐命名：

```text
trace.name = agent.run / rag.answer / coding.fix_test / customer_service.resolve
session_id = 一段会话 ID
user_id = hash 后的用户 ID
metadata = tenant_id、env、app_version、model_policy、permission_profile
tags = ["prod", "agent", "rag", "tool-use"]
```

Agent trace 结构：

```text
agent.run
  ├─ input.normalize
  ├─ router.decide
  ├─ context.build
  │   ├─ memory.retrieve
  │   ├─ rag.retrieve
  │   └─ skill.load
  ├─ planner.generate
  ├─ llm.generate
  ├─ tool.call.search
  ├─ permission.check
  ├─ executor.run
  ├─ observation.parse
  ├─ verifier.run
  └─ final.answer
```

每类 observation 记录字段：

| Observation | 必备字段 |
|---|---|
| `router.decide` | route、confidence、reason |
| `context.build` | context_tokens、source_count、cache_hit |
| `rag.retrieve` | query、doc_ids、chunk_ids、score、rerank_score |
| `skill.load` | skill_name、version、matched_reason |
| `planner.generate` | step_count、risk_actions、plan_valid |
| `llm.generate` | model、prompt_version、input_tokens、output_tokens、latency、cost |
| `tool.call` | tool_name、args_hash、success、error_type、duration |
| `permission.check` | risk_level、decision、policy_id、approval_required |
| `executor.run` | exit_code、stdout_summary、stderr_summary、timeout |
| `verifier.run` | pass、evidence_count、test_result、confidence |
| `final.answer` | format_valid、citation_count、user_visible_error |

**一个简化埋点示例**

```python
from langfuse import observe, get_client, propagate_attributes

langfuse = get_client()

@observe(name="agent.run")
def run_agent(user_query, session_id, user_id):
    with propagate_attributes(
        session_id=session_id,
        user_id=user_id,
        tags=["prod", "agent"],
        metadata={"app_version": "2026.05.08"}
    ):
        route = route_intent(user_query)

        with langfuse.start_as_current_observation(
            as_type="span",
            name="router.decide",
            input={"query": user_query},
            metadata={"route": route}
        ):
            pass

        answer = call_llm(user_query)

        return answer
```

**开发流程**

| 阶段 | 要做什么 |
|---|---|
| 1. 定义问题 | 明确要定位：幻觉、检索差、工具失败、慢、贵、越权、死循环 |
| 2. 定义 schema | 统一 trace、observation、metadata、score 命名 |
| 3. 封装 SDK | 做 `observe_llm()`、`observe_tool()`、`observe_retrieval()` |
| 4. 接入核心链路 | 先接 router、LLM、tool、retrieval、verifier |
| 5. 做脱敏 | prompt、用户数据、工具输出、密钥默认脱敏 |
| 6. 做评分 | 用户反馈、自动规则、LLM-as-judge、人工标注 |
| 7. 建 dashboard | 成功率、延迟、成本、错误率、工具失败率 |
| 8. 建 dataset | 从 bad case 一键加入数据集 |
| 9. 做实验 | 比较 prompt/model/retrieval 参数 |
| 10. 灰度上线 | dev/staging/prod 分环境，失败请求 100% 采集 |

**测试流程**

| 测试类型 | 测什么 |
|---|---|
| 单元测试 | wrapper 是否能正确创建 observation |
| 集成测试 | 一次完整 Agent run 是否能在 Langfuse 看到完整 trace |
| 异常测试 | LLM 超时、tool 失败、permission deny 是否记录 error |
| 脱敏测试 | 手机号、token、API key、cookie 是否被打码 |
| 并发测试 | 多用户 session_id、trace_id 是否串线 |
| 采样测试 | 成功请求采样，失败请求全量 |
| 成本测试 | observation 数量是否爆炸 |
| 回放测试 | 能否根据 trace 复现 bad case |
| 评分测试 | score 是否能绑定到 trace / observation / session |

**需要注意的问题与解决方案**

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 埋点太粗 | 只看到 LLM 调用，看不到工具和检索 | 按 Agent runtime chain 拆 observation |
| 埋点太细 | observation 爆炸、成本高 | 关键链路全量，内部循环采样 |
| 敏感信息泄露 | trace 里出现密钥、PII | 默认脱敏，完整内容 opt-in |
| 多轮会话断裂 | 每轮都是孤立 trace | 强制传 `session_id` |
| 无法定位幻觉 | 只记录 final answer | 记录 context、retrieval、evidence、verifier |
| 无法定位工具失败 | 没有 tool args/error | tool span 记录 args_hash、error_type、stderr_summary |
| 成本不可控 | 大量 stdout/prompt 入库 | 输出截断，完整日志放 artifact |
| 数据集没人维护 | bad case 沉淀不下来 | 低分 trace 自动进入 review queue |
| prompt 变更不可追责 | 不知道哪个 prompt 版本出问题 | metadata 记录 prompt_name、version、label |
| 线上问题难复现 | 缺上下文版本和工具结果 | 保存 doc_id、chunk_id、tool_output_hash |

Langfuse 官方也提供 evaluation、datasets、scores、experiments 等能力，用于把线上 trace 转成可评测样本，并对 prompt/model 改动做离线实验。参考：Langfuse Evaluation Concepts https://langfuse.com/docs/evaluation/core-concepts

**如何根据 Langfuse 结果排查定位**

我会按这个顺序看：

```text
1. 先看 trace outcome
   是成功、失败、超时、用户差评，还是 verifier fail？

2. 看耗时瀑布图
   慢在 LLM、retrieval、tool、rerank、还是外部 API？

3. 看 router / planner
   是否走错链路？简单问题是不是误进 Agent？

4. 看 context.build
   上下文是否过长？是否加载了错误 skill、旧 memory、无关 chunk？

5. 看 retrieval
   召回是否命中正确文档？rerank 后是否把正确证据排掉？

6. 看 llm.generate
   prompt 版本、模型、temperature、tokens 是否异常？

7. 看 tool.call
   工具是否失败？参数是否 hallucination？是否重复调用？

8. 看 permission / approval
   是否被策略拒绝？是否审批超时？是否误放行高风险动作？

9. 看 verifier
   有没有证据校验？有没有测试结果？是不是模型自称完成？

10. 看 scores
   差评、LLM-as-judge、人工标注集中在哪类任务？
```

**几个典型案例**

| Langfuse 现象 | 判断 | 解决方案 |
|---|---|---|
| `retrieval` score 低，但 LLM 正常 | 检索问题 | 调 chunk、embedding、hybrid、rerank |
| `context_tokens` 很高，答案跑偏 | 上下文污染 | context pruning、只保留 evidence |
| 同一 tool 连续调用 5 次失败 | Agent loop | 加 repeated tool guard、max steps |
| `tool.call` 参数为空或错字段 | 工具 schema / planner 问题 | schema 更严格，缺参先澄清 |
| LLM latency 飙升 | 模型或上下文过大 | prompt cache、压缩、换快模型 |
| cost 突增 | tokens 或 observation 过多 | 采样、截断、压缩 |
| 用户差评集中在某 prompt version | prompt regression | rollback prompt，跑 dataset experiment |
| verifier pass 但用户差评 | 验收标准错 | 增加业务指标和人工标注 |

**与优秀 Agent 实践的对应**

本地 OpenClaw / Hermes / cc-haha 没看到直接 Langfuse 接入证据，但它们的实践和 Langfuse 埋点点位是对应的：

| 项目 | 可映射到 Langfuse 的观测点 |
|---|---|
| Hermes | session logs、tool loop guardrails、code_execution timeout/max_tool_calls |
| OpenClaw | agent loop timeout、exec approval、plugin hooks、session status |
| cc-haha | LocalAgentTask 状态、progress events、toolUseCount、permission_request |

也就是说，Langfuse 负责“看见这些链路”，而 Agent runtime 本身要先把这些关键事件结构化出来。

**一句话总结**

从 0 到 1 设计 Langfuse 观测，核心是：**把 Agent 的每次任务建成 trace，把每个关键步骤建成 observation，把质量结果建成 score，把多轮会话建成 session，再用这些数据反推是上下文、检索、工具、模型、权限、状态还是验收出了问题。**

**2 分钟面试口述版**

如果让我从 0 到 1 设计 Langfuse 观测，我会先定义数据模型。Langfuse 里一个用户任务对应一个 trace，一个关键步骤对应一个 observation，多轮对话用 session 聚合，质量判断用 score 表示。

具体埋点上，我不会只埋 LLM 调用，而是按 Agent runtime chain 埋：入口、router、context build、RAG retrieval、skill load、planner、LLM generation、tool call、permission check、executor、observation parse、verifier 和 final answer。每个 observation 都要记录关键字段，比如 LLM 的 model、tokens、latency、cost；工具的 tool name、args hash、duration、error type；检索的 doc id、chunk id、score；权限的 risk level、decision、policy id；最终验收的 evidence 和 pass/fail。

开发流程上，我会先封装 Langfuse SDK，避免业务代码散落埋点。然后从核心链路开始接入，再加脱敏、采样、score、dataset、dashboard 和 alert。测试时要测完整 trace 是否串起来，异常时 span 是否关闭，敏感信息是否脱敏，多用户 session 是否串线，失败 case 是否能进入数据集并回放。

排查时，我会先看 trace 的最终状态和 score，再看瀑布图定位慢在哪一层。然后依次看 router 是否走错、context 是否污染、retrieval 是否召回错、LLM prompt/model 是否异常、tool 参数和错误是否正常、permission 是否误拒绝、verifier 是否真的验收。这样就能把“Agent 答错了”拆成具体问题：是检索问题、上下文问题、工具问题、模型问题、权限问题，还是验收标准问题。

最终重点是，Langfuse 不是简单日志平台，而是 Agent 的诊断系统。它要帮我们做到线上问题可定位、bad case 可沉淀、prompt/model 改动可实验、质量退化可告警。

## 如何从零到一设计一个agent的评估框架
**先给结论**

从 0 到 1 设计 Agent 评估框架，我会把它拆成一句话：

> **先定义任务集，再跑完整 Agent Harness，记录 trace，然后用多层 grader 评估最终结果、执行过程、工具调用、安全权限、成本稳定性，最后把失败样本沉淀成回归集。**

大厂收敛实践很明确：  
OpenAI 建议先用 **trace grading** 找 workflow 级问题，再沉淀成 datasets 和 eval runs；Anthropic 强调 eval-driven development，任务要有 reference solution、稳定隔离环境、transcript review；Microsoft Foundry 把 Agent eval 拆成 **system evaluation** 和 **process evaluation**，分别看最终结果和执行过程。

所以 Agent 评估不能只问：

```text
最终回答对不对？
```

而要问：

```text
任务完成了吗？
路径合理吗？
工具选对了吗？
参数对了吗？
工具结果用了吗？
有没有越权？
有没有死循环？
成本和延迟能接受吗？
失败能不能复现？
```

**本质与原理**

传统 LLM eval 主要评估：

```text
input -> output
```

Agent eval 要评估：

```text
input -> plan -> tool calls -> observation -> state updates -> final output
```

所以 Agent 评估框架必须同时覆盖两类：

| 类型 | 看什么 | 例子 |
|---|---|---|
| System Evaluation | 最终结果是否完成目标 | 代码是否修好、客服是否解决、报告是否正确 |
| Process Evaluation | 过程是否正确可靠 | 工具是否选对、参数是否正确、是否重复调用、是否越权 |

Microsoft Foundry 的 Agent Evaluators 也是这个分法：Task Completion、Task Adherence、Intent Resolution 属于系统评估；Tool Selection、Tool Input Accuracy、Tool Output Utilization、Tool Call Success 属于过程评估。参考：Microsoft Agent Evaluators https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/agent-evaluators

**整体架构**

我会设计 8 个模块：

| 模块 | 作用 |
|---|---|
| Eval Dataset | 存测试任务、期望结果、工具预期、标签、难度 |
| Eval Harness | 按生产一致的方式启动 Agent |
| Environment Manager | 创建隔离环境、mock 工具、准备 fixture |
| Trace Collector | 收集 LLM、工具、状态、权限、输出 |
| Grader System | deterministic grader、LLM judge、human review |
| Metric Aggregator | 聚合成功率、成本、延迟、工具质量 |
| Report / Dashboard | 输出对比报告和失败原因 |
| Regression Gate | CI/CD 阈值拦截，防止回归上线 |

执行链路：

```text
准备 eval dataset
 -> 启动 sandbox / fixture / mock tools
 -> 运行完整 Agent loop
 -> 记录 trace
 -> 执行 graders
 -> 聚合 metrics
 -> 生成失败分类
 -> 进入人工抽检
 -> bad case 回灌数据集
 -> CI/CD 回归门禁
```

OpenAI Agent eval 文档也强调：用 traces、graders、datasets、eval runs 改进 Agent 质量；先通过 trace grading 找 workflow 级问题，再进入可重复的 dataset/eval runs。参考：OpenAI Agent Evals https://developers.openai.com/api/docs/guides/agent-evals

**评估哪些内容和指标**

核心指标可以分成 9 类。

| 评估维度 | 指标 | 说明 |
|---|---|---|
| 任务结果 | `task_success_rate`、`pass_rate`、`partial_credit` | 最终是否完成目标 |
| 指令遵循 | `task_adherence`、`constraint_violation_rate` | 是否遵守系统规则和用户约束 |
| 意图识别 | `intent_accuracy`、`route_accuracy` | Router 是否选对链路 |
| 规划质量 | `plan_valid_rate`、`replan_count`、`step_efficiency` | 计划是否可执行、是否过度拆解 |
| 工具调用 | `tool_selection_accuracy`、`tool_input_accuracy`、`tool_success_rate` | 工具是否选对、参数是否对、调用是否成功 |
| 工具结果利用 | `tool_output_utilization` | 是否真的理解并使用工具结果 |
| RAG / 上下文 | `recall@k`、`precision@k`、`groundedness`、`citation_accuracy` | 证据是否找对、回答是否有依据 |
| 安全权限 | `unsafe_action_block_rate`、`false_allow_rate`、`false_deny_rate` | 是否误放行高风险动作 |
| 稳定性成本 | `p95_latency`、`token_cost`、`tool_calls_per_task`、`timeout_rate`、`loop_rate` | 是否稳定、快、便宜、不会死循环 |

其中最重要的是：

```text
task_success_rate + tool_input_accuracy + groundedness + safety_violation_rate + cost_per_success
```

因为一个 Agent 如果成功率高但成本爆炸，或者答案正确但靠越权工具完成，都不能上线。

**数据集怎么设计**

每条 eval case 不要只写 input，要写完整测试条件。

数据来源：

| 来源 | 用途 |
|---|---|
| 产品需求 | 覆盖核心业务流程 |
| 历史线上 bad case | 防止回归 |
| 用户反馈 | 覆盖真实分布 |
| 人工构造边界案例 | 测极端参数、缺字段、歧义 |
| 对抗样本 | 测 prompt injection、越权、敏感信息 |
| 合成数据 | 扩大覆盖，但必须抽检质量 |

Anthropic 特别强调要构建 balanced problem sets，不只测“应该搜索”的问题，也要测“不应该搜索”的问题，否则会把 Agent 优化成过度调用工具。参考：Anthropic Agent Evals https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

**每类指标怎么写测试脚本**

| 指标 | 脚本设计 |
|---|---|
| `task_success_rate` | 跑完整 Agent，检查最终 artifact、API 状态、数据库状态或参考答案 |
| `tool_selection_accuracy` | 从 trace 里提取 tool sequence，和 expected/forbidden tools 比对 |
| `tool_input_accuracy` | 校验工具参数 schema、必填字段、类型、值是否符合 reference |
| `tool_success_rate` | 统计工具 exit_code、HTTP status、timeout、exception |
| `tool_output_utilization` | LLM judge 判断最终回答是否使用了工具返回的关键信息 |
| `groundedness` | 检查回答中的 claim 是否能被 retrieved evidence 支撑 |
| `citation_accuracy` | 检查引用 doc_id/chunk_id 是否真的包含答案 |
| `plan_valid_rate` | 校验计划是否有依赖、缺参、越权、不可执行步骤 |
| `loop_rate` | 检查 repeated tool call、same args、same error、no-progress count |
| `safety_violation_rate` | 注入越权请求，看是否拒绝或审批 |
| `cost_per_success` | 总 token + tool cost / 成功任务数 |
| `latency_p95` | 统计端到端和各模块耗时 |

一个工具选择 grader 示例：

```python
def grade_tool_selection(trace, expected_tools, forbidden_tools):
    called_tools = [s["tool_name"] for s in trace["spans"] if s["type"] == "tool_call"]

    missing = set(expected_tools) - set(called_tools)
    forbidden = set(forbidden_tools) & set(called_tools)

    if forbidden:
        return {"score": 0, "reason": f"forbidden tools used: {forbidden}"}

    if missing:
        return {"score": 0.5, "reason": f"missing expected tools: {missing}"}

    return {"score": 1, "reason": "tool selection correct"}
```

工具参数 grader：

```python
def grade_tool_input(tool_call, expected_schema):
    errors = validate_json_schema(tool_call["args"], expected_schema)

    if errors:
        return {"score": 0, "reason": errors}

    return {"score": 1, "reason": "arguments valid"}
```

循环检测 grader：

```python
def grade_loop(trace):
    seen = {}
    for call in trace["tool_calls"]:
        key = (call["tool_name"], hash_args(call["args"]), call.get("error_type"))
        seen[key] = seen.get(key, 0) + 1

    repeated = [k for k, v in seen.items() if v >= 3]
    if repeated:
        return {"score": 0, "reason": "repeated same tool call"}

    return {"score": 1, "reason": "no loop detected"}
```

**测试计划怎么设计**

从轻到重分 5 层：

| 层级 | 什么时候跑 | 测什么 |
|---|---|---|
| Unit Eval | 每次提交 | 工具参数、router、schema、权限规则 |
| Golden Set Eval | PR / CI | 核心 50-200 条稳定样本 |
| Regression Eval | 每次 prompt/model/tool 改动 | 历史 bad case |
| Scenario E2E Eval | 每日/发布前 | 完整业务流程、真实 sandbox |
| Online Eval | 上线后 | 抽样生产 trace、用户反馈、漂移 |

```yaml
  loop_rate: "<= 0.01"
```

Anthropic 还强调 eval harness 必须稳定隔离：每个 trial 要从 clean environment 开始，避免缓存、旧文件、共享状态污染评估。这个点在 coding agent 里尤其重要，比如每个 case 都要新建临时 repo/worktree/container。参考：Anthropic eval harness 建议 https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

**如何根据指标判断问题**

这是面试最关键的部分。指标不是为了好看，是为了定位。

| 现象 | 可能问题 | 定位方式 | 解决方案 |
|---|---|---|---|
| `task_success_rate` 下降，`tool_success_rate` 正常 | 推理/规划/最终生成问题 | 看 planner、final answer、verifier | 改 prompt、加 verifier、补 few-shot |
| `tool_selection_accuracy` 低 | 工具描述或 router 问题 | 看选错工具的 trace | 优化工具命名、描述、分组、retriever |
| `tool_input_accuracy` 低 | 参数抽取或 schema 设计问题 | 看缺字段、类型错、幻觉参数 | 强 schema、缺参澄清、参数校验重试 |
| `tool_success_rate` 低 | 工具服务或执行环境问题 | 看 status、timeout、exception | 加 retry/backoff、mock 稳定、修工具 |
| `tool_output_utilization` 低 | 模型没读懂 observation | 看工具输出和最终回答 | 输出摘要化、结构化 observation |
| `groundedness` 低，`recall@k` 高 | 证据找到了但没用 | 看 final answer 是否忽略 evidence | 强制 citation、claim verification |
| `groundedness` 低，`recall@k` 低 | 检索问题 | 看 chunk、query rewrite、rerank | 调 chunk、hybrid、metadata filter |
| `replan_count` 高 | 初始计划质量差或工具不稳定 | 看失败 step | plan validator、工具健康检查 |
| `loop_rate` 高 | 没有 no-progress guard | 看重复 tool+args+error | max steps、same-call breaker |
| `approval_rate` 异常高 | 权限策略太细或工具风险标注错 | 看 permission span | 调权限分级、allow session |
| `false_allow_rate` 高 | 权限漏洞 | 看越权 case | denylist、policy test、人工审批 |
| `cost_per_success` 上升 | 工具过度调用或上下文膨胀 | 看 token、tool_calls | 压缩上下文、减少重试 |
| 离线高分、线上低分 | 数据集不贴近真实分布 | 对比线上 trace 标签 | 从线上 bad case 回灌 |
| LLM judge 高分、人类低分 | grader 不准 | 抽样人工复核 | 校准 rubric，拆维度评分 |

一个典型判断链：

```text
任务失败
 -> 先看 task_success
 -> 再看 process 指标
 -> 如果工具没选对：工具选择问题
 -> 如果工具选对但参数错：参数抽取/schema 问题
 -> 如果工具成功但答案错：observation 利用或生成问题
 -> 如果证据不对：RAG 问题
 -> 如果工具重复：loop/runtime 问题
 -> 如果被权限拦截：policy 或审批问题
```

**2 分钟面试口述版**

如果让我从 0 到 1 设计 Agent 评估框架，我会先说，Agent eval 不能只评最终答案，因为 Agent 是多步骤系统。它会规划、调用工具、读工具结果、更新状态、做权限判断，所以必须同时做 system evaluation 和 process evaluation。

我会先建 eval dataset。每条样本除了 input，还要有 expected outcome、expected tools、forbidden tools、reference answer、success criteria、risk level 和 tags。数据来源包括产品需求、线上 bad case、用户反馈、边界样本和对抗样本。

然后做 eval harness。它要尽量和生产一致，启动同一个 Agent loop、同一套工具 schema、同样的权限和 sandbox。每次 case 都在隔离环境里跑，避免缓存、文件残留、共享状态污染。运行时必须保存 trace，包括 planner、LLM、tool call、permission、executor、observation、verifier。

评估指标我会分几类：任务完成率、指令遵循、意图识别、规划质量、工具选择、工具参数、工具成功率、工具结果利用、RAG groundedness、安全权限、延迟、成本和死循环率。对应的 grader 有三种：确定性 grader，比如 schema 校验和单测；LLM-as-judge，比如判断最终回答是否使用了工具结果；人工评审，用来校准主观任务和 judge。

测试计划分五层：每次提交跑 unit eval；PR 跑 golden set；prompt/model/tool 改动跑 regression eval；发布前跑场景 E2E；上线后跑 online eval 和用户反馈。CI 里设置门禁，比如 task success 不能低于 85%，tool input accuracy 不能低于 95%，安全违规必须为 0，p95 延迟和 cost 要在预算内。

最后根据指标定位问题。比如工具选择低，说明工具描述或 router 有问题；工具参数低，说明 schema 或参数抽取有问题；工具成功率低，是工具服务或环境问题；检索召回高但 groundedness 低，说明模型没用证据；召回低则是 RAG 问题；成本升高但成功率不变，说明 loop 或上下文膨胀。这样评估框架就不是打分系统，而是一个持续定位、回归和改进 Agent 的工程闭环。

## 如何从0到1设计agent的治理框架
**先给结论**

Agent 治理框架不是单个“安全插件”，而是一套 **Agent Control Plane + Runtime Enforcement + Evaluation/Audit** 体系。  
大厂现在的收敛实践是：

```text
身份认证 -> 数据分级 -> 上下文治理 -> 工具治理 -> 权限审批
-> 沙箱执行 -> 输出安全 -> 记忆写回治理 -> trace审计
-> eval红队 -> 灰度发布 -> 事故回滚
```

一句话：

> **治理框架负责规定 Agent 能看什么、能想什么、能调什么工具、能写什么、什么时候必须审批、出了问题怎么追责和回滚。**

注意：**治理 governance 比 guardrail 更大**。  
Guardrail 是某个环节的安全闸门；Governance 是贯穿设计、开发、上线、运行、审计、评估、回滚的完整制度和工程系统。

**本质与原理**

Agent 比普通 LLM 应用更需要治理，因为 Agent 不只是生成文本，它会：

| Agent 能力 | 带来的治理风险 |
|---|---|
| 读文件 / RAG | 数据泄露、越权读取、上下文污染 |
| 调工具 / API | 错工具、错参数、误执行业务动作 |
| 执行脚本 / 终端 | 命令注入、删文件、依赖污染 |
| 写记忆 | 记忆污染、隐私长期保存 |
| 多 Agent 协作 | 权限扩散、上下文漂移、重复写 |
| 自动重试 | 重复下单、重复发券、重复退款 |
| 自主规划 | 幻觉计划、越权计划、高风险误执行 |

所以治理的核心目标是 5 个：

```text
1. 安全：不能越权、不能泄露、不能被注入攻击
2. 可控：高风险动作必须审批
3. 可观测：每一步能 trace
4. 可评估：上线前后能量化质量
5. 可恢复：出错能暂停、回滚、补偿
```

```text
2. 建 Tool Registry
3. 给每个工具标 risk_level、schema、timeout
4. 做 Permission Engine
5. 对 L4/L5 动作加审批
6. 接 trace/audit
```

第二阶段：上下文和输出治理。

```text
1. RAG 文档打 untrusted 标签
2. 做 prompt injection 检测
3. 做 PII/secret redaction
4. 做 groundedness verifier
5. 做 memory write policy
```

第三阶段：上线治理。

```text

2. 做 red team case
3. 做 CI eval gate
4. 做 canary release
5. 做线上监控和告警
```


**设计链路示例：退款 Agent**

用户说：

```text
帮我给订单 A123 退款
```

治理链路：

```text
1. Identity：确认用户是谁、是否有退款权限
2. Input Guardrail：识别这是金融写操作
3. Context：读取订单信息，只能读当前租户数据
4. Planner：生成退款计划
5. Plan Validator：判断 refund.create 是 L4 高风险动作
6. Permission Engine：要求人工审批
7. Approval：展示订单、金额、原因、影响
8. Executor：审批通过后调用 refund API
9. Idempotency：使用 order_id + action 生成幂等 key
10. Audit：记录审批人、工具参数、结果
11. Verifier：查询退款状态确认成功
12. Final：告诉用户已提交或失败原因
```

如果审批没通过：

```text
不执行工具，只返回“需要审批/已拒绝”
```

如果工具超时：

```text
不能盲目 retry，因为退款请求可能已经到达下游。
先查 action log / refund status，再决定补偿。
```

这就是治理和普通 tool calling 的区别。

**一句话总结**

Agent 治理框架的核心是：**把 Agent 的输入、上下文、计划、工具、权限、执行、输出、记忆、评估、审计全部策略化和可追踪化，让 Agent 不仅能做事，而且只能在被授权、可验证、可回滚的边界内做事。**

**2 分钟面试口述版**

如果让我从 0 到 1 设计 Agent 治理框架，我会先明确一点：治理不是单个安全过滤器，而是 Agent 的控制面。因为 Agent 不只是生成文本，它会读数据、调工具、执行脚本、写记忆，甚至做业务写操作，所以必须治理它能看什么、能调什么、能写什么、什么时候必须审批、出了问题怎么追责。

我会把治理框架拆成 10 个模块：身份和租户治理、Policy Center、Tool/Skill/Prompt/Model Registry、输入安全、上下文治理、Plan Validator、Tool Permission Engine、Sandbox、输出和记忆治理、Trace/Eval/Audit。

执行链路是：用户请求进来先做身份认证和租户识别，然后做输入安全检测。接着构造上下文，但 RAG 文档、网页、邮件都要标记为 untrusted，不能让检索内容覆盖系统策略。Planner 生成计划后，Plan Validator 检查是否缺参数、越权、调用高风险工具。每次工具调用都要经过 schema 校验和 Permission Engine。低风险读操作自动允许，高风险动作比如退款、发邮件、删库、执行命令必须审批，并且要有幂等 key、审计日志和回滚方案。

运行时还要有 sandbox，限制文件、网络、环境变量、CPU、内存和超时。工具输出返回后，要做 observation 清洗，避免工具结果污染上下文。最终回答前做输出安全、PII 脱敏和 groundedness 校验。记忆写回也要治理，不能随便把用户隐私或错误事实写成长记忆。

上线治理方面，我会建 eval dataset、红队样本、CI eval gate、canary 灰度、trace 监控和 rollback playbook。大厂实践也在这个方向收敛：OpenAI 有 guardrails 和 tracing，Microsoft 有 Agent Governance Toolkit，Google 有 Model Armor，AWS 把 AgentCore 拆成 runtime、gateway、identity、memory、observability，OpenClaw/Hermes 这类项目也实现了审批、tool policy、timeout 和 loop guardrails。

所以总结就是：Agent 治理的目标不是让 Agent 什么都不能做，而是让它在清晰授权、可观测、可评估、可回滚的边界内安全地做事。
