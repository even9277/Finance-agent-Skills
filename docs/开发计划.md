# Finance 智能投研助手 — 二次开发计划

> 基于现有 `Financial-MCP-Agent` + `a-share-mcp-is-just-i-need` 架构，**在不破坏任何现有功能**的前提下，扩展为：带前端交互的投研助手 + 短期/长期记忆体系 + 持仓管理模块。
>
> **版本 v1.2 新增需求**：报告下载/预览、ChatGPT 风格对话 UI（历史管理+搜索+模板问题）、可视化记忆管理（风险偏好/关注板块/期望收益直观编辑）、持仓/自选股上传与涨跌同步（预留接口）。

---

## 一、目标与约束

### 1.1 核心目标

| 目标 | 说明 |
|------|------|
| 前后端交互 | FastAPI 后端 + Vue 3 前端，提供网页操作界面 |
| 双模式切换 | **调研报告模式**（触发完整多 Agent 工作流）与**对话模式**（轻量多轮问答）可一键切换 |
| 报告下载/预览 | 投研报告支持页内 Markdown 预览、一键下载 `.md` 文件 |
| ChatGPT 风格对话 | 左侧历史会话列表（支持搜索/重命名/删除）+ 消息气泡 + 常用问题模板一键填充 |
| 短期记忆 (STM) | 单次会话内的多轮对话历史管理，超长时自动压缩，不丢关键信息 |
| 长期记忆 (LTM) | 跨会话的用户投资画像：风险偏好、关注板块/股票，支持冷启动与用户自主更新 |
| 可视化记忆管理 | 直观卡片式 UI 管理风险偏好、关注板块、期望收益，支持点选/滑动/标签操作 |
| 个性化报告 | 长期记忆在 `summary_agent` 生成报告时被注入，实现个性化投资建议 |
| 持仓管理（预留） | 支持用户上传/录入持仓与自选股，获取前日收盘涨跌，持仓同步展示 |
| 不破坏现有功能 | 现有 CLI `python src/main.py --command "..."` 继续可用，新功能以新路径引入 |

### 1.2 技术选型

| 层次 | 技术选型 | 理由 |
|------|----------|------|
| 后端框架 | **FastAPI** | 原生异步、OpenAPI 自动生成、生产级，优于 Gradio（Gradio 仅适合原型） |
| 前端框架 | **Vue 3 + TypeScript** | 生态成熟，配合 Composition API 更易维护 |
| UI 组件库 | **Shadcn-vue** (基于 Radix-vue + TailwindCSS) | 无头设计系统，高度可定制，免费开源 |
| Markdown 渲染 | **@vueuse/core + marked + highlight.js** | 报告内容以 Markdown 渲染展示 |
| HTTP 客户端 | **Axios + VueQuery (TanStack Query)** | 异步请求管理、缓存、加载状态 |
| STM 管理 | **LangGraph 原生 checkpointer + thread_id + 三段式 state** | 调研报告明确结论：STM 留在 LangGraph，不引入第二套框架；Mem0 不用于 STM |
| LTM 管理 | **Mem0 OSS (mem0ai) + PostgreSQL/pgvector** | 调研报告推荐路线，金融画像抽取+检索 |
| 向量数据库 | **PostgreSQL + pgvector 扩展** | 统一存储，与业务数据同库管理，Mem0 原生支持 |
| 对话会话存储 | **SQLite（开发）→ PostgreSQL（生产）** | 快速启动，后期无缝迁移 |
| 异步并发 | **asyncio + FastAPI BackgroundTasks** | 报告生成耗时较长，异步非阻塞 |

## 四、分阶段开发计划

### Phase 1：FastAPI 后端 + Vue 前端基础搭建（预留接口）

**目标**：前后端跑通，能触发现有分析流程并展示结果，暂无记忆功能。

#### 1.1 FastAPI 后端

**任务列表**：

- [ ] `backend/main.py`：FastAPI app 初始化，挂载路由，配置 CORS
- [ ] `backend/config.py`：使用 `pydantic-settings` 读取 `.env`
- [ ] `backend/schemas/`：定义全部 Pydantic 模型（含记忆相关的预留字段）
- [ ] `backend/db/`：SQLAlchemy 异步引擎（`asyncpg` 或 `aiosqlite`），定义以下 ORM 表：
  - `users`（user_id, display_name, created_at）
  - `sessions`（session_id, user_id, mode, created_at）
  - `messages`（id, session_id, role, content, timestamp）
  - `reports`（id, user_id, session_id, stock_code, company, content, created_at）
- [ ] `backend/routers/report.py`：`POST /api/report/generate`（异步触发完整工作流，返回 task_id），`GET /api/report/status/{task_id}`（轮询进度），`GET /api/report/{report_id}`（获取报告），`GET /api/report/history`（历史报告列表）
- [ ] `backend/routers/chat.py`：`POST /api/chat/message`（发送消息，返回 AI 回复），`GET /api/chat/sessions`，`GET /api/chat/sessions/{id}/messages`，`DELETE /api/chat/sessions/{id}`；**预留 WebSocket 端点** `WS /api/chat/stream`
- [ ] `backend/routers/memory.py`：**全部预留接口**，返回空/mock 数据，供前端联调用
- [ ] `backend/routers/user.py`：`POST /api/user/init`（冷启动，提交初始标签），`GET /api/user/profile`，`PUT /api/user/profile`
- [ ] `backend/services/agent_service.py`：将现有 `Financial-MCP-Agent/src/main.py` 的逻辑封装为可异步调用的函数，返回报告文本；**原有 CLI 入口不改动**，新封装通过 `import` 复用
- [ ] 后台任务：使用 FastAPI `BackgroundTasks` 或 `asyncio.create_task` 异步执行报告生成（避免 HTTP 超时）

**核心 API 契约**（Phase 1）：

```
POST /api/report/generate
  Body: { "command": "帮我看看茅台(600519)这只股票...", "user_id": "xxx" }
  Response: { "task_id": "uuid", "status": "pending" }

GET /api/report/status/{task_id}
  Response: { "status": "running|completed|failed", "progress": 0-100, "report_id": "uuid" }

GET /api/report/{report_id}
  Response: { "report_id": "...", "content": "# Markdown报告...", "created_at": "..." }

POST /api/chat/message
  Body: { "session_id": "...", "user_id": "...", "message": "..." }
  Response: { "reply": "...", "session_id": "..." }
```

### Phase 2：短期记忆（STM）集成

**目标**：对话模式实现真正的多轮对话，历史消息不丢，超长时自动压缩；调研报告模式的 analyst 工具输出不再全量堆积在上下文中。

> **选型结论**：STM 使用 **LangGraph 原生 checkpointer + thread_id 持久化 + running summary**，不引入任何第三方 STM 框架。Mem0 **不用于 STM**，它只负责 Phase 3 的 LTM（跨会话长期画像）。这是调研报告的明确结论：短期整段会话 history 要在 LangGraph 里单独管理，Mem0 更适合长期可检索事实。

#### 2.1 STM 三层架构设计

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：thread 级持久化（LangGraph Checkpointer）           │
│  每次 invoke 携带固定 thread_id，state 自动持久化至检查点    │
│  thread_id = f"user_{user_id}_session_{session_id}"         │
└────────────────────────┬────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│  第二层：State 内三段式上下文管理                            │
│                                                             │
│  running_summary    ← 早于滑动窗口的对话，压缩存储           │
│  messages (recent)  ← 最近 8-12 条原始消息（约 4000 tokens）│
│  recent_tool_digest ← analyst 工具输出的精炼摘要             │
│                       （只保留：最终结论+关键数值+证据ID）   │
│                       （不保留：完整新闻段落、原始财务表）   │
└────────────────────────┬────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│  第三层：原始审计层（数据库，与 STM 严格分离）               │
│  messages 表 ← 完整对话历史，is_compressed 标记             │
│  现有 logs/  ← analyst 工具原始输出、报告日志               │
│  保留周期：消息记录 7 天 TTL（按需配置）                     │
└─────────────────────────────────────────────────────────────┘
```

**关键原则**：
- LangGraph checkpointer 内的 `messages` 只保留"当前对话够用的上下文"，做过 summarize/delete 后不再充当完整聊天记录的唯一来源
- 完整历史由数据库 `messages` 表（`is_compressed=True` 标记）独立保存，用于前端"查看历史"和审计回放
- `recent_tool_digest` 解决 analyst 工具输出过长的问题：保存"结论摘要 + 关键数值 + 对应 log 文件引用 ID"，不把整段新闻/财务表继续带着跑

#### 2.2 扩展 AgentState（最小改动，5 个新字段）

### Phase 3：长期记忆（LTM）与个性化画像集成

**目标**：建立以 PostgreSQL **权威画像表**（`user_invest_profiles`）为主数据源、Mem0 OSS + pgvector 为语义检索增强层的**双轨 LTM 体系**；打通调研报告模式与对话模式，使两者共享同一套用户投资画像，在不篡改实时数据的前提下个性化报告结论与对话风格；通过 outbox 异步队列（`ltm_write_tasks`）保证 Mem0 写操作**永不阻塞**任何主链路。

**Phase 3 整体数据流**：
```
前端 UI 卡片/滑块/冷启动（显式操作，最高优先级）
   │ 立即写
   ▼
PostgreSQL: user_invest_profiles ──直接 SQL 读──▶ memory_read_node / chat_service
   │ enqueue                                        合并：结构化画像(确定性) + Mem0语义记忆(补充)
   ▼                                                写入 state["data"]["memory_context"]
ltm_write_tasks（outbox）                                    │
   │ ltm_worker 后台轮询执行（AsyncMemory）                   ▼
   ▼                                          summary_agent / 对话 LLM
Mem0 + pgvector（语义增强层）           system prompt 注入（实时数据优先，画像仅参考）

对话/报告推断出的偏好（低优先级）
   │ enqueue（source=chat_inferred / report_inferred）
   ▼
ltm_write_tasks ──worker──▶ Mem0（遵守优先级规则，不覆盖 UI/cold_start 字段）
```

#### 3.2 数据层扩展：权威画像表 + LTM outbox 队列

> **设计原则**：  
> ① 结构化主数据（风险偏好、收益目标、板块偏好等）**只存 PostgreSQL**，前端 UI 直接读写，报告/对话确定性画像也从这里读。  
> ② Mem0 pgvector 负责**语义长程记忆**（非结构化的偏好迹象、历史修正、多轮推断），不是主数据。  
> ③ 所有 Mem0 写入**通过 outbox 异步执行**，主链路立即返回，不等待向量写入。  
> ④ 来源优先级链：`ui / cold_start` > `explicit_correction` > `chat_inferred / report_inferred`；低优先级推断不覆盖高优先级字段。

**新增 DB 表**（在 `backend/db/models.py` 中定义 SQLAlchemy ORM，同步更新第六节 SQL Schema）：

```sql

CREATE TABLE user_invest_profiles (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id              UUID REFERENCES users(id) ON DELETE CASCADE UNIQUE,
    risk_level           VARCHAR(20) CHECK (risk_level IN
                           ('conservative','moderate','balanced','aggressive','speculative')),
    investment_horizon   VARCHAR(20) CHECK (investment_horizon IN
                           ('ultra_short','short','swing','long')),
    expected_return_min  NUMERIC(5,2),          -- 期望年化收益下限（%）
    expected_return_max  NUMERIC(5,2),          -- 期望年化收益上限（%）
    sectors              JSONB DEFAULT '[]',    -- 关注板块，如 ["消费/白酒","银行/金融"]
    constraints          JSONB DEFAULT '[]',    -- 约束，如 ["不碰ST","不碰科创板"]
    response_pref        VARCHAR(20) DEFAULT 'balanced'
                           CHECK (response_pref IN ('concise','balanced','detailed','risk_first')),
    updated_by           VARCHAR(20) DEFAULT 'system'
                           CHECK (updated_by IN ('user','system','llm')),
    updated_at           TIMESTAMPTZ DEFAULT NOW(),
    created_at           TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE ltm_write_tasks (
    id           BIGSERIAL PRIMARY KEY,
    user_id      UUID REFERENCES users(id) ON DELETE CASCADE,
    task_type    VARCHAR(30) CHECK (task_type IN
                   ('add_conversation','explicit_update','explicit_delete','cold_start')),
    payload      JSONB NOT NULL,        -- 序列化的 MemoryService 调用参数

    processed_at TIMESTAMPTZ
);
-- 只索引 pending 状态，减少 worker 扫描范围
CREATE INDEX idx_ltm_tasks_pending ON ltm_write_tasks(user_id, status)
    WHERE status = 'pending';
```

- [ ] `memory_service.py`：**统一服务接口层**，所有 Mem0 操作必须经过此层，禁止直接调 Mem0 SDK

  ```python
  class MemoryService:
      # ── 读取（同步性强，直接读 PostgreSQL，不等 Mem0）──
      async def get_structured_profile(user_id: str) -> dict
          # 直接 SELECT user_invest_profiles，返回结构化画像字典
          # 这是报告/对话注入的"权威主干"，网络延迟可控

      async def search_semantic(
          user_id: str, query: str,
          categories: list[str] | None = None,   # 默认：全 8 类
          sources: list[str] | None = None,       # 默认：全来源
          top_k: int = 5,
          threshold: float = 0.60,               # score < threshold 的结果丢弃
      ) -> list[dict]
          # 调用 AsyncMemory.search()，传 user_id + metadata filter（active=True）
          # categories/sources 做结果侧二次过滤（Mem0 v1.x metadata filtering）
          # 返回 [{"text": ..., "metadata": {...}, "score": ...}, ...]

      async def get_memory_context(user_id: str, query: str) -> dict
          # 合并 get_structured_profile + search_semantic 的结果
          # 返回 {"profile": {...}, "semantic_memories": [...]}
          # memory_read_node 和 chat_service 统一调用此方法
          # 若 Mem0 不可用（异常），仅返回结构化画像，semantic_memories=[]，不抛出

      # ── 用户事实通道（对话/报告推断，仅 enqueue，不直接写 Mem0）──
      async def enqueue_add_conversation(
          user_id: str, messages: list, metadata: dict
      ) -> None
          # 将参数序列化后 INSERT ltm_write_tasks（task_type=add_conversation, status=pending）
          # 立即返回；ltm_worker 异步执行实际 Mem0 写入

      # ── 显式更新通道（UI/冷启动/主动纠正，双写：权威表立即 + Mem0 异步）──
      async def update_profile_and_enqueue(
          user_id: str, field: str, value: Any, source: MemorySource
      ) -> None
          # 1. UPDATE user_invest_profiles SET {field}=value, updated_by=source, updated_at=NOW()
          # 2. INSERT ltm_write_tasks（task_type=explicit_update）→ worker 再同步到 Mem0
          # 前端 UI 响应速度不受 Mem0 网络延迟影响；权威表已立即生效

      async def enqueue_explicit_delete(user_id: str, memory_id: str) -> None
          # INSERT ltm_write_tasks（task_type=explicit_delete）

      async def cold_start(user_id: str, tags: dict) -> None
          # 1. UPSERT user_invest_profiles（批量设置，updated_by=user）
          # 2. INSERT ltm_write_tasks（task_type=cold_start）
          # tags 格式：{risk_level, horizon, expected_return_min/max, sectors, constraints}

      # ── 直接操作（供 /api/memory/items 接口、前端删除功能调用）──
      async def get_all_memories(user_id: str, page: int, page_size: int) -> dict
      async def delete_memory(memory_id: str) -> None
      async def delete_all(user_id: str) -> None
          # delete_all：清空 Mem0 全部记忆 + 重置 user_invest_profiles 为 NULL 默认值
  ```

  ```python
  # 每隔 LTM_WORKER_INTERVAL_SEC（推荐 5s）轮询 ltm_write_tasks WHERE status='pending'
  # 按 task_type 分发到 AsyncMemory：
  #   add_conversation → mem0_client.add(messages, user_id=..., metadata=...)
  #   explicit_update  → mem0_client.update(memory_id, data, metadata)
  #   explicit_delete  → mem0_client.delete(memory_id)
  #   cold_start       → mem0_client.add(冷启动事实列表, user_id=..., metadata)

  ```

```sql
-- 用户表
CREATE TABLE users (

    updated_at  TIMESTAMPTZ DEFAULT NOW()

-- 消息表（STM 原始审计层）
CREATE TABLE messages (
    id          BIGSERIAL PRIMARY KEY,
    session_id  UUID REFERENCES sessions(id) ON DELETE CASCADE,
    role        VARCHAR(20) CHECK (role IN ('user', 'assistant', 'system')),
    content     TEXT NOT NULL,
    token_count INTEGER,
    is_compressed BOOLEAN DEFAULT FALSE,  -- 已被压入 running_summary
    created_at  TIMESTAMPTZ DEFAULT NOW()

-- 报告记录表
CREATE TABLE reports (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      UUID REFERENCES users(id),
    session_id   UUID REFERENCES sessions(id),
    task_id      UUID,
    stock_code   VARCHAR(20),
    company_name VARCHAR(100),
    content      TEXT,               -- Markdown 全文
    status       VARCHAR(20) DEFAULT 'pending',
    created_at   TIMESTAMPTZ DEFAULT NOW()
);

-- 持仓表（Phase 4）
CREATE TABLE holdings (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      UUID REFERENCES users(id) ON DELETE CASCADE,
    stock_code   VARCHAR(20) NOT NULL,    -- 含 sh./sz. 前缀
    stock_name   VARCHAR(100),
    cost_price   NUMERIC(12, 4),          -- 成本价（元）

    updated_at   TIMESTAMPTZ DEFAULT NOW()

CREATE TABLE watchlist (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    stock_code   VARCHAR(20) NOT NULL,    -- 含 sh./sz. 前缀
    stock_name   VARCHAR(100),
    added_at     TIMESTAMPTZ DEFAULT NOW(),

-- 行情快照缓存表（前日收盘，每日刷新）
CREATE TABLE price_snapshots (
    stock_code   VARCHAR(20) NOT NULL,
    trade_date   DATE NOT NULL,
    close_price  NUMERIC(12, 4),
    pct_chg      NUMERIC(8, 4),           -- 涨跌幅（%）
    updated_at   TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (stock_code, trade_date)
);

-- 用户权威投资画像表（Phase 3 新增）
-- 前端卡片/滑块/标签的写入目标；报告和对话读取结构化画像的来源
-- 与 Mem0 是"双轨"关系：此表为主数据，Mem0 为语义增强层
CREATE TABLE user_invest_profiles (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id              UUID REFERENCES users(id) ON DELETE CASCADE UNIQUE,
    risk_level           VARCHAR(20) CHECK (risk_level IN
                           ('conservative','moderate','balanced','aggressive','speculative')),
    investment_horizon   VARCHAR(20) CHECK (investment_horizon IN
                           ('ultra_short','short','swing','long')),
    expected_return_min  NUMERIC(5,2),          -- 期望年化收益下限（%）
    expected_return_max  NUMERIC(5,2),          -- 期望年化收益上限（%）
    sectors              JSONB DEFAULT '[]',    -- 关注板块列表，如 ["消费/白酒","银行/金融"]
    constraints          JSONB DEFAULT '[]',    -- 约束列表，如 ["不碰ST","不碰科创板"]
    response_pref        VARCHAR(20) DEFAULT 'balanced'
                           CHECK (response_pref IN ('concise','balanced','detailed','risk_first')),
    updated_by           VARCHAR(20) DEFAULT 'system'
                           CHECK (updated_by IN ('user','system','llm')),
    updated_at           TIMESTAMPTZ DEFAULT NOW(),
    created_at           TIMESTAMPTZ DEFAULT NOW()
);

-- LTM 异步写入 outbox 队列（Phase 3 新增）

CREATE TABLE ltm_write_tasks (
    id           BIGSERIAL PRIMARY KEY,
    user_id      UUID REFERENCES users(id) ON DELETE CASCADE,

    payload      JSONB NOT NULL,        -- 序列化的 MemoryService 调用参数

    retry_count  INTEGER DEFAULT 0,
    error_msg    TEXT,                  -- 失败时写入，不影响主进程
    created_at   TIMESTAMPTZ DEFAULT NOW(),
    processed_at TIMESTAMPTZ

CREATE INDEX idx_ltm_tasks_pending ON ltm_write_tasks(user_id, status)
    WHERE status = 'pending';
```

### 7.2 STM 与 LTM 分工边界（关键）

| 维度 | STM（LangGraph 原生）| LTM 结构化层（PostgreSQL）| LTM 语义层（Mem0 + pgvector）|
|------|----------------------|--------------------------|------------------------------|
| 作用范围 | 单次会话 / 单个 thread | 跨会话、永久主数据 | 跨会话、语义增强检索 |
| 存储内容 | 最近消息 + running_summary + recent_tool_digest | 风险偏好、板块、收益目标、约束等结构化字段 | 非结构化长程偏好线索、历史修正记录 |
| 存储位置 | LangGraph checkpointer + DB messages 表（审计） | `user_invest_profiles` 表（业务 Postgres） | Mem0 OSS + pgvector（`finance_ltm` 集合）|
| 写入时机 | 每轮对话同步写入 checkpointer | UI 操作/冷启动时立即写入 | 通过 `ltm_write_tasks` outbox 异步写入 |
| 读取时机 | 每次 LangGraph invoke 自动加载 | `memory_read_node` / `chat_service` 直接 SQL 读 | `memory_read_node` / `chat_service` 语义搜索补充 |
| 压缩时机 | turn_count ≥ 10 或 token ≥ 6000 | 不压缩（字段级更新） | 不压缩（向量 ADD/UPDATE/DELETE） |
| 激活时机 | Phase 2 | Phase 3 | Phase 3 |
| 降级策略 | `ENABLE_STM=false` | LTM 结构化层不可单独关闭（与业务 DB 同库）| `ENABLE_MEMORY=false` 关闭全部 LTM 读写 |
| 主导写入来源 | 对话/报告内容 | UI 显式操作 > 冷启动 > 系统初始化 | enqueue_add_conversation（低优先级推断）|

> **三个关键原则**：  
> ① 不要让 Mem0 管 STM：Mem0 不负责 session 内消息窗口管理，STM 留在 LangGraph；  
> ② LangGraph checkpointer 内 messages 做过压缩后，不能再充当前端"完整历史"的唯一来源，完整历史在 DB `messages` 表独立保存；  
> ③ Mem0 不是产品主数据：`user_invest_profiles` 才是权威来源，Mem0 仅做语义增强；前端 UI 直写的是 PostgreSQL 权威表，Mem0 通过 outbox 异步同步。

### 7.3 异步并发原则

- FastAPI 路由全部使用 `async def`
- 报告生成（耗时 2-3 分钟）使用 `asyncio.create_task` + 任务状态表轮询，避免 HTTP 超时
- 对话单轮（约 10-20 秒）可直接 `await`，或使用 WebSocket 流式推送
- `maybe_summarize_state` 节点的压缩操作（LLM 调用）在 LangGraph 图内同步执行，但触发频率低（每 10 轮一次），不影响主流程性能
- Mem0 读写使用 `AsyncMemory`（Phase 3 起）
- Baostock 调用（同步 I/O）已通过单例登录解决并发问题，不需要额外处理
- 多个 Agent 并行分析（现有）保留，不引入额外锁

### 7.4 前端 UI 设计原则

- 主色调：深色金融风（深蓝 `#0F172A` + 金色 `#F59E0B`）
- 字体：标题使用 `Noto Serif SC`（衬线，专业感），正文使用 `Noto Sans SC`
- 布局：左侧折叠侧边栏（记忆画像）+ 主内容区（报告/对话）+ 顶部导航
- 动效：报告生成时各 Agent 卡片依次亮起（步进动画）
- 响应式：支持 1280px 以上宽屏，移动端基础可用

### 7.6 审阅与风险说明（v1.2 增补）

- **STM 双轨制**：**报告模式**的 STM 在 LangGraph 内（checkpointer + thread_id + 三段式 state）；**对话模式**的 STM 在 `chat_service.py` + DB（`sessions.running_summary` + `messages` 表）。两套实现职责不同，文档与代码注释中需明确区分，避免误用。
- **数据库**：当前第六节 schema 为 PostgreSQL。若 Phase 1 使用 SQLite 开发，需单独维护 SQLite 建表语句（如 `UUID`→`TEXT`、`gen_random_uuid()`→应用层生成、`BIGSERIAL`→`INTEGER`），或**统一采用 Docker PostgreSQL** 从 Phase 1 起避免双库差异。
- **任务与报告生命周期**：`POST /api/report/generate` 返回 `task_id` 后，建议先插入 `reports` 行（status=`pending`，task_id 关联），任务完成后更新同一条的 `content` 与 status；轮询/SSE 均以 `task_id` 查该行，避免“任务存在但无报告行”的中间态。
- **自选股双源**：LTM（Mem0）中的自选股 = 用户画像（用于个性化报告）；`watchlist` 表 = 持仓模块行情同步用，可与 LTM 同步或独立维护。前端/接口需明确数据来源与同步策略（见 Phase 4 联动描述）。

### 7.7 日志与监控（复用现有系统）

**原则**：不新增独立日志/监控体系，与现有 `Financial-MCP-Agent` 内设施复用。

| 现有设施 | 位置 | 复用方式 |
|----------|------|----------|
| **统一 Logger** | `Financial-MCP-Agent/src/utils/logging_config.py` | `backend` 及各 service 通过 `setup_logger(name, log_dir)` 获取 logger；`log_dir` 可配置为 `backend/logs` 或统一到项目根 `logs`，格式与现有（控制台 INFO、文件 DEBUG、时间/name/level/message）一致。 |
| **执行日志（按次报告）** | `Financial-MCP-Agent/src/utils/execution_logger.py` | 报告模式触发工作流前：在 `agent_service` 中调用 `initialize_execution_logger(base_log_dir)`，传入本次 `task_id` 或沿用现有 `execution_id` 目录结构；工作流内各 Agent 继续使用 `get_execution_logger()` 写入 `log_agent_start` / `log_agent_complete` / `log_llm_interaction` / `log_tool_usage`；任务结束后 `finalize_execution_logger(success, error)`。对话模式无需 ExecutionLogger，仅用 `setup_logger` 即可。 |
| **可观测（可选）** | `Financial-MCP-Agent/src/utils/langfuse_tracer.py` | 若配置 `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY`，在 `agent_service` 触发报告时 `start_trace(name, input_data, user_id=user_id, metadata={"task_id": task_id})`，现有 Agent 内已集成的 `log_agent_execution` / `log_llm_generation` / `log_tool_usage` 会自动挂到该 trace 下；无需在 backend 再实现一套追踪。 |

**实施要点**：

- Backend 与 Agent 同进程调用时，直接 `import` 上述模块即可；若未来报告任务拆到独立 worker 进程，需保证该 worker 使用相同 `log_dir` 与同一 Langfuse 配置。
- 不在本计划中引入 Prometheus/自定义 metrics；若后续需要，再在现有日志或 Langfuse 之上扩展。
