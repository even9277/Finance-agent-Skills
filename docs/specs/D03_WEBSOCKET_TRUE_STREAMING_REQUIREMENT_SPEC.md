# REQUIREMENT_SPEC.md

## 1. Task Type

Primary type: New Feature

Secondary types: Performance Optimization, Test / Evaluation Improvement, Engineering Governance, Project Packaging / Interview Demo Improvement

Classification rationale: 当前 WebSocket 对话虽然使用长连接，但用户主要在生成结束后一次性收到完整回答；D03 要把它升级为可验证的真实增量输出，同时冻结协议、失败语义、断连治理、可观测字段和允许调用真实 API 的端到端验收标准。

## 2. Requirement Restatement

D03 要实现对话模式的真实 WebSocket 流式输出：当金融 Agent 生成最终自然语言回答时，后端应在上游模型持续生成内容的过程中，将可展示的文本增量及时发送给客户端，而不是等待完整回答生成后再一次性发送，也不能为了制造“流式效果”而对完整结果进行事后切片。

用户应在前端看到回答逐步增长；流结束后，客户端展示的完整回答应与服务端确认的最终回答一致。工具调用、证据校验等前置阶段可以在没有文本增量的情况下继续执行，但连接必须保持正确状态，最终生成阶段应真实转发上游增量。

本任务同时定义最小充分的自动化测试和真实 API 端到端测试。用户已明确授权验收测试调用真实模型 API 和真实金融数据 API，但真实调用必须显式启用、限制次数和成本，不得混入默认单元测试或常规离线回归。

本任务不实现 D04 的计划预览、步骤卡片和复杂控制面板，也不实现 D05 的报告 SSE。

## 3. Problem Source

Source: 用户端到端体验反馈、前序静态审计结果、面试项目口径一致性要求。

已知现象：当前 WebSocket 路径主要在完整回答生成后发送一次结果，用户无法在模型生成期间看到持续文本，实际体验和“逐 Token/增量流式输出”的项目 Claim 不一致。

尚未提供以下基线证据：

- 当前 WebSocket 协议的完整消息示例。
- 当前前端如何解析 WebSocket 消息。
- 当前模型 Provider 是否原生支持 streaming，以及各 Provider 的 chunk 语义。
- 首包时间、总耗时、单次回答 chunk 数量和断连后的资源行为。

这些内容应在 Codebase Reconnaissance 阶段只读确认。

## 4. Current Behavior

- 客户端可以通过 WebSocket 发起对话。
- 后端能够完成现有金融 Agent 调用链并返回最终回答。
- 当前用户主要一次性收到完整回答，WebSocket 只提供了传输通道，没有形成可证明的模型增量转发链路。
- 当前是否存在消息类型、协议版本、序列号、完成帧或错误帧，需要后续代码勘察确认。
- 当前客户端断连是否能停止仍在运行的生成任务，以及是否存在后台任务泄漏，需要后续确认。
- 当前 HTTP 非流式接口是否与 WebSocket 共用同一业务服务，需要后续确认。

## 5. Expected Behavior

### 5.1 正常流式行为

对于能够生成较长回答的请求：

1. 服务端确认请求后，建立唯一 `request_id` 或 `run_id`。
2. 金融 Agent 可以继续执行原有实体解析、路由、工具调用、证据校验和回答生成链路。
3. 当上游模型产生可展示文本增量后，服务端及时向当前连接发送有序的内容增量事件。
4. 客户端按顺序追加增量，并在流尚未完成时展示不断增长的回答。
5. 服务端发送且只发送一个成功终止事件；客户端完成最终渲染。
6. 所有内容增量按顺序拼接后，应与最终确认文本语义和字符内容一致；协议元数据不应混入正文。

“真实流式”必须满足：首个非空内容增量发生在成功终止事件之前，并且对指定的长回答验收样例至少产生两个非空内容增量。仅把完整回答在服务端事后拆分成多个片段不算通过。

### 5.2 失败和断连行为

- 如果错误发生在任何内容增量之前，客户端收到一个明确的失败终止结果，不显示空白成功消息。
- 如果错误发生在部分内容已经发送之后，客户端能够识别结果为 `PARTIAL` 或等价失败状态，不把残缺回答标记为完整成功。
- 如果客户端主动取消或断开连接，服务端应停止继续向该连接发送消息，并在安全可行的边界取消或终止不再需要的模型生成任务。
- 已经发生不可回滚工具副作用时不得通过盲目重试重复执行；D03 不新增自动重放机制。
- 一个连接或会话的增量不得发送到另一个用户、会话或请求。

### 5.3 前端最小行为

- 前端能够消费 D03 的流式消息，并在同一条助手消息中增量更新正文。
- 流式过程中用户能够区分“仍在生成”“已完成”“失败/部分完成”。
- 中文、数字、Markdown 和常见金融符号在跨 chunk 边界时不得乱码、丢失或重复。
- D03 只实现增量正文的最小展示；计划预览、工具步骤卡片、证据面板和复杂控制帧展示属于 D04。

## 6. Scope

### 6.1 In Scope

- 对话 WebSocket 的真实文本增量传输。
- 明确流开始、内容增量、成功结束、失败/部分结束的可机器识别语义。
- 同一请求内的事件顺序、请求关联、终止唯一性和正文重组一致性。
- 模型 Provider 到 Agent 回答生成、WebSocket 发送和前端增量渲染之间的流式调用链。
- 最小前端适配，使用户能实际看到逐步增长的助手回答。
- 客户端取消、连接中断、上游模型异常和发送异常的受控处理。
- 记录首个增量、增量数量、完成状态和各阶段耗时等必要可观测指标。
- 离线单元/集成测试，以及显式启用的真实模型 API、真实金融数据 API 端到端测试。
- 与 D03 直接相关的协议、运行方式和验收文档更新。

### 6.2 Out of Scope

- 不实现 D04 的计划预览、步骤状态卡片、工具详情面板、证据校验面板或人工审批 UI。
- 不实现报告模式 SSE、报告任务恢复或 Redis 幂等；这些属于 D05/D06。
- 不修改金融 Skill 路由、工具选择、实体解析、记忆策略、报告工作流或回答质量 Prompt。
- 不要求模型逐个 tokenizer token 发送；Provider 合并后的自然 chunk 可以接受，但必须是真实上游生成增量。
- 不实现断线后的流式续传、历史 chunk 回放或跨实例恢复。
- 不引入新的消息队列、Kafka、Celery 或生产级多实例广播架构。
- 不改变认证、授权和用户数据边界。
- 不把真实 API 测试加入默认离线测试命令。
- 本 Requirement Definition 阶段不读取代码、不修改业务代码、不运行测试、不选择最终技术方案。

### 6.3 Unknown Scope

- 当前 WebSocket 是否发送纯文本还是结构化 JSON，以及升级后是否需要兼容旧客户端。
- HTTP 非流式接口是否需要继续返回完整回答。本 Spec 默认保持其现有行为不变。
- 当前所有模型 Provider 是否都支持原生 streaming；不支持者的降级行为需要在勘察后确认。
- 客户端是否已有“停止生成”入口。本 Spec 要求正确处理断连和取消信号，但是否新增可见按钮需在勘察后确认。
- 工具执行阶段是否需要轻量保活事件。默认不把复杂阶段事件纳入 D03，除非现有网关存在空闲超时风险。

## 7. Constraints

### 7.1 Hard Constraints

- 必须转发模型生成过程中的真实增量，不允许对完整答案进行事后切片冒充流式。
- 每个请求必须有且只有一个终止结果：成功、失败、取消或部分完成之一。
- 内容增量必须有序、不可跨请求串流；拼接后不得丢字、重字或乱码。
- 现有金融业务链路、权限、会话隔离、安全策略和工具治理不得因流式改造被绕过。
- 前端最小适配与后端协议变更必须能够在同一里程碑完成验收，不能交付一个当前客户端无法消费的协议。
- 默认单元测试和常规 CI 不得调用付费模型或生产金融数据服务。
- 真实 API E2E 必须显式启用，使用专用测试账号/额度，限制用例数、最大耗时和最大重试次数。
- API Key、Token、Cookie、Authorization Header、完整私有 Prompt 和敏感模型响应不得写入仓库、测试报告、终端或 Trace。
- 不新增数据库迁移、Redis 状态或与 D03 无关的依赖。
- 不修改 D01、D02、D04～D11 的行为合同。

### 7.2 Soft Constraints

- 优先复用现有 Provider streaming 能力、Agent 状态和 WebSocket 消息模型。
- 协议事件应稳定、类型明确、便于后续 D04 扩展，但本轮不预先实现无消费者的复杂事件。
- 服务端应尽快转发可展示增量，避免不必要的大缓冲；具体转发延迟目标在建立基线后冻结。
- 测试以证明传输正确性、真实增量和失败语义为主，不对模型答案措辞做脆弱断言。
- 实现应支持可控取消和资源清理，避免为追求首包速度牺牲安全或正确性。

## 8. Stakeholders and Impact

| Stakeholder / System | Impact |
|---|---|
| 最终用户 | 可以更早看到回答开始生成，降低等待中的不确定感。 |
| 面试评审者 | 能通过协议、Trace 和真实 E2E 证据确认系统具备真正流式能力。 |
| 前端 | 需要最小增量渲染、终止状态和错误状态处理。 |
| WebSocket API | 从一次性结果发送升级为兼容性敏感的事件流协议。 |
| Agent Runtime | 需要把最终回答生成过程暴露为增量，同时保持原有编排和最终结果。 |
| Model Provider Adapter | 需要正确承接上游 streaming、取消、异常和用量信息；具体所有权待勘察。 |
| Skills / Tools | 行为不变，但工具完成后的最终回答应能进入流式生成。 |
| Memory | 只能在符合现有完成语义时写入最终助手回答，不能把每个 chunk 当作独立消息持久化。 |
| Observability | 需要记录 TTFT、chunk 数量、总耗时、终止状态和断连原因，并保持脱敏。 |
| Maintainer | 需要同时维护离线确定性测试和少量显式启用的真实 API E2E。 |

## 9. Engineering Quality Requirements

### 9.1 Interface Documentation and Types

- WebSocket 输入、输出事件和终止状态必须使用明确的类型或 Schema，说明字段含义、顺序约束、可选性和兼容语义。
- 稳定事件类型和状态不得依赖任意字符串或无约束 `dict[str, Any]`。
- 修改的公开 Provider、Agent、服务和 WebSocket 接口应有与仓库语言一致的 Google-style docstring，说明异步迭代、取消、异常、资源释放和最终结果语义。
- 注释应解释跨 chunk Unicode 边界、部分结果、终止唯一性和取消传播等非显然约束。

### 9.2 Architecture and Module Ownership

- API/WebSocket 层负责连接生命周期、协议校验和事件发送，不应复制 Agent 业务规则。
- Agent/应用编排层负责业务执行和回答生成生命周期；Provider 适配层负责供应商特定 streaming 语义。最终文件归属由 Codebase Reconnaissance 确认。
- 前端只消费稳定协议并管理展示状态，不重新推断后端业务阶段。
- HTTP 与 WebSocket 若共享业务服务，应避免为了流式功能复制整套 Agent 调用链。
- 记忆、日志和最终回答只能消费明确的完成结果，不应将中间 chunk 当作多个业务消息。

### 9.3 Configuration, Secrets, Constants, and Prompts

- 真实 API 凭证继续通过现有安全配置入口加载，不增加硬编码凭证。
- 真实 E2E 采用显式开关或测试标记，与默认离线测试隔离；确切变量名在后续方案阶段决定。
- 可部署变化的超时、测试模型和 E2E 开关进入集中配置；事件类型、协议状态等稳定合同保留在代码中。
- D03 不修改回答 Prompt；如某 Provider 需要 streaming 参数，应由其适配边界统一处理。
- `.env.example` 只能包含安全占位符和运行说明，不能包含可用 Token。

### 9.4 Terminal Output, Logging, Tracing, and Artifacts

- 每个流式请求至少可观察：`request_id`/`run_id`、连接或会话安全标识、`stage`、`status`、`chunk_count`、首个非空增量时间、TTFT、总耗时、终止原因和 `error_code`。
- Trace 应能区分上游首 chunk、服务端首个发送事件和流完成，以证明不是完整回答事后切片。
- 日志不得逐 chunk 输出完整正文，避免日志膨胀和敏感内容泄露。
- Live E2E 生成精简、脱敏的验收 Artifact，包含测试 ID、运行时间、Provider/模型的非敏感标识、事件序列摘要、chunk 数量、TTFT、总耗时、终止状态和失败原因。
- 不默认保存完整用户输入、完整回答、Authorization Header、Cookie 或 API Key。

### 9.5 Validation, Errors, Retry, State, and Compatibility

- 非法消息、缺少必要字段、未认证连接和超限输入继续遵循现有边界校验。
- 上游 streaming 异常必须转换成明确失败或部分完成状态，不得静默结束或发送成功终止事件。
- 自动重试只允许发生在尚未向客户端发送正文且不存在工具副作用的可证明安全阶段，并受次数与总耗时限制；具体策略在后续方案阶段冻结。
- 客户端断开后，不得继续向关闭的连接写数据；应清理后台生成任务和相关资源。
- 同一请求不得发送重复终止事件；晚到 chunk 不得出现在终止事件之后。
- HTTP 非流式接口默认保持兼容；WebSocket 旧客户端兼容策略需要在勘察后明确。

## 10. Success Criteria

### 10.1 Functional Criteria

冻结以下验收场景：

| Case ID | 场景 | 预期结果 |
|---|---|---|
| D03-C01 | 模型直接生成较长金融知识回答 | 收到开始、至少两个非空内容增量、一个成功终止结果；首增量早于终止。 |
| D03-C02 | 先调用真实金融数据工具，再生成回答 | 工具链保持正确，最终回答阶段真实增量输出，不泄露内部工具载荷。 |
| D03-C03 | 中文、数字、百分号和 Markdown 跨 chunk | 客户端最终文本无乱码、丢失、重复或顺序错误。 |
| D03-C04 | 上游在首 chunk 前失败 | 客户端得到明确失败结果，不产生空白成功消息。 |
| D03-C05 | 上游在部分 chunk 后失败 | 客户端保留已展示内容并标记失败/部分完成，不标记成功。 |
| D03-C06 | 客户端生成中断开或取消 | 服务端停止发送并清理可取消任务，不产生跨连接串流。 |
| D03-C07 | 两个会话并发请求 | 每个客户端只收到自己的有序事件和最终回答。 |
| D03-C08 | 现有非流式 HTTP 对话 | 保持原有完整响应行为和响应结构。 |

### 10.2 Compatibility Criteria

- 现有认证、授权、会话隔离、金融路由、工具治理、证据校验和记忆语义保持不变。
- 前端在 D03 完成后能够正常显示增量回答，不要求等待 D04 才能使用对话功能。
- HTTP 非流式接口保持兼容。
- WebSocket 协议升级不能让当前正式客户端出现无法解析、重复消息或永不结束的状态；具体兼容方式在代码勘察后确认。
- 现有相关回归测试继续通过。

### 10.3 Reliability Criteria

- 每个请求恰好一个终止状态，终止后不再出现正文 chunk。
- D03-C01 的冻结长回答样例至少产生两个非空增量，且首增量时间早于成功终止时间。
- 增量按协议顺序重组后与客户端最终展示正文一致。
- 断连、取消和上游异常不会造成未处理异常、后台任务持续泄漏或跨会话内容污染。
- 默认离线测试可重复、无网络、无付费调用。
- Live E2E 每次验收最多运行两条真实 API 主路径；对已知瞬时网络失败最多允许一次有记录的重试，不能用无限重试掩盖缺陷。
- TTFT 和服务端转发开销必须记录基线；本 Spec 不在无基线情况下虚构硬性毫秒指标，后续根据首次稳定测量决定是否设门槛。

### 10.4 Observability Criteria

- 能从 Trace 证明：上游首个 chunk 被接收后，服务端在流完成前向客户端发送了非空增量。
- 能查看每次请求的 chunk 数量、TTFT、总耗时、成功/失败/取消/部分状态和错误类型。
- 真实 E2E 失败时能够区分认证失败、Provider 不支持 streaming、模型 API 超时、金融数据 API 失败、WebSocket 断开和客户端渲染失败。
- 日志和 Artifact 不包含凭证或不必要的完整敏感内容。

### 10.5 Testing Criteria

本任务采用四层最小充分测试，不用大量重复用例堆覆盖率：

1. **协议/重组单元测试**
   - 使用固定异步 chunk 序列，不调用网络。
   - 一组参数化测试覆盖正常顺序、中文/Markdown 边界、空 chunk 忽略、终止唯一性和终止后禁止追加。
   - 断言增量重组正文与最终正文一致。

2. **失败、取消和隔离测试**
   - 使用 Fake Provider 覆盖首 chunk 前失败、部分输出后失败、客户端取消和两个并发会话。
   - 断言失败状态、取消传播、资源清理和无跨会话串流。
   - 不为每个异常类型复制整套业务测试。

3. **离线入口集成测试**
   - 从真实 WebSocket 应用入口进入，使用可控 Fake Provider/Tool 产生多个增量。
   - 验证认证、请求关联、事件顺序、前端或客户端重组、完成语义和现有 HTTP 接口兼容。
   - 默认 CI 只运行这一层及上述离线测试。

4. **显式启用的真实 API 端到端验收**
   - `D03-LIVE-01`：在真实前后端或等价浏览器级客户端登录后，提问“请用三点解释市盈率，并给出一个简短例子”。调用真实模型 API；断言页面中的同一条助手消息在完成前至少增长两次，最终状态成功，网络事件可重组为最终展示正文。
   - `D03-LIVE-02`：提问一个需要真实行情数据的固定金融问题，调用真实金融数据 API 和真实模型 API；断言工具链成功后回答以真实增量展示，最终状态成功，协议中不暴露密钥或原始内部工具载荷。
   - Live 测试只断言协议、增量、终止状态和必要业务链路，不断言模型完整措辞，也不把波动行情值写死。
   - Live 测试必须通过专用标记或命令显式运行；缺少凭证时标记为 `SKIPPED` 并给出原因，不得伪装通过。
   - 每次验收最多两条 Live 主路径，每条默认一次，只有可识别的瞬时网络错误允许额外一次重试。
   - 保存脱敏结果摘要：测试 ID、`run_id`、时间、Provider/模型非敏感标识、chunk 数、TTFT、总耗时、终止状态和失败分类。

交付验证顺序应为：格式检查 → Lint → 类型检查 → D03 离线聚焦测试 → 相关对话回归 → 显式 Live E2E → Diff Review。实际命令由 Codebase Reconnaissance 和 Plan 阶段依据仓库现状冻结。

不要求为 D03 运行新闻训练、报告全流程、Portfolio 全流程、全仓真实 API 测试或无关浏览器回归。

## 11. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| 完整回答生成后再切片，测试却误判为流式 | Trace 同时记录上游首 chunk、服务端首发送和终止时间；验收首增量必须早于生成完成。 |
| WebSocket 协议升级破坏当前前端 | 后续勘察现有协议和解析器，后端与最小前端适配在同一里程碑验收。 |
| Provider streaming 语义不一致 | 在 Provider 边界归一化事件和错误；不在路由层散落供应商判断。 |
| chunk 过细导致渲染抖动，过粗又失去流式体验 | 先记录真实 chunk 分布和转发延迟，再在方案阶段选择最小必要缓冲策略。 |
| 客户端断连后模型继续计费或任务泄漏 | 测试取消传播和资源清理；记录取消原因和任务终止状态。 |
| 部分输出被误记为成功或写入长期记忆 | 明确 `PARTIAL/FAILED/CANCELLED` 语义，只有符合现有完成合同的结果才能作为完整回答持久化。 |
| 真实 API 测试不稳定或成本失控 | 显式启用、固定两条用例、限定超时和一次瞬时重试，默认 CI 完全离线。 |
| Live Artifact 泄露密钥或用户数据 | 只保存脱敏元数据和事件摘要，不保存认证信息和不必要的完整内容。 |
| 并发请求发生内容串流 | 用两个会话的确定性并发测试验证 request/session 关联和隔离。 |
| D03 范围膨胀成 D04 控制台开发 | 只交付正文增量及最小状态；计划、工具和证据 UI 明确留到 D04。 |

## 12. Open Questions

### Question 1

- Question: WebSocket 新事件协议是否必须兼容当前旧客户端？
- Why it matters: 这决定是否需要过渡期兼容层，还是允许前后端同版本原子升级。
- Suggested default: 保持现有正式客户端可用；若当前项目只部署单一前端，则前后端原子升级，不长期维护双协议。

### Question 2

- Question: 是否确认 D03 包含“最小前端增量渲染”，但不包含 D04 的计划、步骤、工具和证据卡片？
- Why it matters: 没有最小前端适配就无法进行用户可见的端到端验收；加入完整控制 UI 又会导致范围失控。
- Suggested default: 确认包含同一条助手消息的增量正文、生成中/完成/失败状态，其他控制面留到 D04。

### Question 3

- Question: 对当前不支持原生 streaming 的模型 Provider，是否允许保留一次性完整回答作为明确降级？
- Why it matters: 如果要求所有 Provider 强制流式，可能需要替换 Provider 或扩大适配范围。
- Suggested default: 允许显式标记的非流式降级，但默认演示 Provider 和 Live E2E Provider 必须支持真实 streaming，且不得将降级冒充流式。

### Question 4

- Question: 是否确认真实 API E2E 使用专用测试凭证和现有测试环境，而不是生产用户数据或生产账号？
- Why it matters: 真实 API 授权不等于允许泄露生产数据、无限调用或影响真实用户。
- Suggested default: 使用专用测试账号/额度和非敏感固定查询；无安全凭证时 Live 测试跳过并报告。

### Question 5

- Question: 是否需要在 D03 增加可见的“停止生成”按钮？
- Why it matters: 后端必须处理取消，但 UI 按钮会增加一个用户交互合同。
- Suggested default: 后端和客户端生命周期支持取消；若当前界面已有取消入口则接通，否则按钮作为 D04 或后续体验项，不阻塞 D03。

## 13. Handoff to Next Step

用户审核并确认本 Spec 后，下一步使用 Codebase Reconnaissance Skill 进行只读勘察，输出 D03 对应的 `CODEBASE_RECON.md`。勘察至少确认：

- WebSocket 路由、认证、消息模型和当前一次性发送的完整调用链。
- 前端 WebSocket 客户端、消息状态和渲染更新路径。
- Agent 最终回答生成节点与 Provider 适配器是否支持异步 streaming。
- 工具调用、证据校验、最终合成和记忆写回之间的顺序与完成语义。
- 当前取消、断连、异常、超时和后台任务清理行为。
- HTTP 非流式接口与 WebSocket 是否共享业务服务。
- 当前日志、Trace、Langfuse 或其他观测路径能否证明上游 chunk 和下游发送时间。
- 现有测试、WebSocket Fixtures、Fake Provider、浏览器 E2E 工具和真实 API 测试入口。
- 可用 Provider、测试环境、真实 API 凭证加载方式及防止秘密泄露的规则。
- 最小修改所有者、协议兼容风险和仍需用户确认的问题。

Codebase Reconnaissance 阶段不得修改代码、设计最终架构或运行真实 API 测试。
