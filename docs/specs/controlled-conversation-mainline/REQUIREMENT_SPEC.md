# REQUIREMENT_SPEC.md

## 1. Task Type

Primary type: Refactor

Secondary types: New Feature, Test / Evaluation Improvement, Engineering Governance, Project Packaging / Interview Demo Improvement

Classification rationale: 本任务的核心是把现有金融 Agent 对话处理能力迁移并重构为一条可控制、可验证、可观测、可回滚的唯一主链；同时需要补齐当前实现中缺失或不稳定的能力、分层测试和工程证据。

## 2. Requirement Restatement

以 `Finance-agent-Skills` 为唯一主仓库，参考 `Finance` 中已有但质量不一的历史实现，以及项目描述和统一面试口径，逐步完成受控对话主链的迁移与重构。

这里的“受控”不是让模型自由决定所有行为，而是要求每一轮对话从请求进入、上下文准备、实体和意图理解、问题改写、计划与工具治理、执行与证据校验，到最终回答和状态落库，都具有明确的输入、输出、失败语义、停止条件和观测证据。

预期结果不是一次性大重写，而是一系列可独立验收、独立 Review、独立回滚的小模块交付。每个模块在改变生产行为前，必须先锁定现有行为和目标契约；完成后必须通过相关单元、契约、集成、离线评测和完整 Compose E2E。涉及真实模型或外部服务质量的模块，还需要在安全前置条件满足时执行受保护 Live E2E。

本步骤只定义需求，不读取或修改业务代码，不决定最终目录、框架、类或函数设计，也不实施迁移。

## 3. Problem Source

Source: 用户观察、产品需求、既有基础设施计划中的代码勘察结论，以及简历/面试项目口径需要。

用户已经明确指出：

- `Finance` 保存了不同阶段实现过的功能，但部分代码冗杂、混乱或不完整，不能原样复制。
- `Finance-agent-Skills` 将作为唯一主仓库，需要按企业级工程方式继续开发。
- 当前对话链路中部分能力实现不完整，模块之间的真实差距仍需逐项核对。
- 后续开发必须小步推进，每一处都有对应测试和完整工程闭环。

目前尚未提供一组可直接复现的真实失败对话、线上 Trace 或量化基线。这些证据需要在后续只读代码勘察和需求澄清阶段补齐。

## 4. Current Behavior

以下内容来自当前已完成的基础设施规格和用户描述，尚需下一步对真实代码重新验证：

- 对话请求已有 Vue、FastAPI、聊天服务、Agent 路由/执行、数据库和 Trace 等组成部分，但核心编排职责可能集中在较大的服务或节点文件中。
- 当前实现已经能够处理部分金融查询、Skill 路由、工具调用、会话和记忆，但各阶段的状态契约、失败语义和模块所有权尚未形成统一真相源。
- `Finance` 中可能存在实体解析、路由、改写、规划、执行、证据校验、有限重规划和总结等更丰富的历史实现，但完成度、正确性和可迁移性未知。
- 当前基础设施已具备默认离线 CI、分层测试目录、离线 Compose E2E 和基础 Trace 脱敏；这些能力尚未证明业务主链各模块本身已经迁移完成。
- Planner、Executor、Verifier 等未迁移模块在现有离线评测中仍可能被条件跳过。
- 当前完整离线 E2E 通过测试装配替换聊天服务，能够验证前端代理、FastAPI、数据库和响应契约，但不能作为真实 Agent 决策质量已通过的证据。

缺少的当前行为证据：

- 真实对话入口、流式和非流式调用链的完整调用图。
- 每一阶段当前实际输入、输出、状态写入、Prompt、模型和工具依赖。
- 典型正确案例、错误案例、超时案例、歧义案例和多轮上下文案例。
- 当前路由、工具选择、证据充分性、回答可追溯性、延迟和成本基线。
- `Finance` 与 `Finance-agent-Skills` 各模块可复用逻辑、冲突口径和技术债清单。

## 5. Expected Behavior

### 5.1 正常金融对话

当用户提出信息充分、允许回答的金融问题时，系统应识别本轮目标和关键实体，选择与问题类型一致的处理路径，只执行必要且允许的模型/工具调用，并基于可识别的证据生成回答。

最终响应应保持现有前端可消费的协议，至少能关联本轮会话和运行标识；需要实时或外部数据时，应说明数据时间、来源或证据不足状态，不能把空数据、估算或过期信息伪装成确定事实。

### 5.2 普通聊天或非金融问题

当问题不需要金融工具或复杂规划时，系统不应为了“看起来像 Agent”而强制调用工具。它应进入明确的普通对话或安全兜底路径，并保持与金融分析链路一致的错误、观测和响应契约。

### 5.3 歧义、缺参和上下文不足

当标的、时间范围、比较对象、指标或用户目标不足以安全执行时，系统应在工具调用前识别缺口，并选择明确追问、保守解释或安全终止；不得猜测高风险参数后静默执行。

### 5.4 多轮对话

当用户使用“它”“刚才那个”“再比较一下”等上下文指代时，系统应只复用与当前任务相关且仍有效的会话信息。上下文冲突、过期或不足时应触发澄清，不能把历史轮次中的错误实体或旧计划无条件带入本轮。

### 5.5 工具和外部依赖失败

当模型、Tushare、MCP、数据库或其他只读工具发生超时、限流、无权限、返回空值或返回非法结构时，系统应产生稳定错误分类，按允许的有限预算重试或降级，并向用户返回诚实的部分结果或可理解失败信息；不得死循环、无限重规划、伪造证据或把失败转成成功空结果。

### 5.6 证据不足或相互冲突

当工具结果无法支持原问题、时间或主体不匹配、来源冲突，或关键字段缺失时，系统应阻止无依据结论进入最终回答。允许输出明确标记的部分结果、不确定性和补充信息需求。

### 5.7 终止与安全边界

每轮运行必须具有可判断的成功、失败、部分成功、需要澄清和安全拒绝状态，并具有最大步骤、重试/重规划次数、总耗时或其他等价终止约束。任何真实写操作、交易、持仓修改或生产数据副作用都不属于本对话主链的默认能力。

## 6. Scope

### 6.1 In Scope

- 定义并逐步迁移唯一的受控对话主链，不保留同义的新旧双轨 Runtime。
- 对现有前端聊天入口、后端 REST/流式入口、应用服务和 Agent Runtime 的真实调用关系做后续只读勘察。
- 对照 `Finance` 历史实现、`Finance-agent-Skills` 当前实现、项目描述和统一面试口径，形成逐模块 Gap 清单。
- 覆盖对话请求边界、会话/运行上下文、实体理解、意图和路径选择、问题改写、计划和工具治理、执行、证据校验、有限重试/重规划、回答合成和结果映射等业务责任。
- 为跨阶段状态建立明确且可验证的字段含义、允许状态、转换、失败和兼容要求；具体类型和文件位置在后续方案阶段决定。
- 对 Prompt、工具 Schema、Agent State、错误码、事件和评测数据建立版本化契约要求。
- 对模型、工具、MCP、数据库、记忆和可观测出口定义可替换测试边界要求；具体接口形式在后续方案阶段决定。
- 复用并完善现有 unit、contract、integration、offline eval、Compose offline E2E 和 protected live E2E 验收链路。
- 每个迁移模块先建立 characterization/regression cases，再修改实现；同一交付中更新所有内部调用方并删除被替换实现、旧导入和重复 Prompt。
- 更新与实际实现直接相关的架构、接口、Prompt、配置、日志、Trace、测试和项目讲解文档。

### 6.2 Out of Scope

- 本需求定义阶段不读取业务代码、不修改代码、不执行测试、不选择最终技术方案。
- 不一次性迁移全部模块或整体重写仓库。
- 不把 `Finance` 加入运行时依赖、`PYTHONPATH`、生产镜像或长期同步机制。
- 不建立旧 Runtime 到新 Runtime 的兼容 Adapter、转发模块、双写或永久 Feature Flag。
- 不在本主链迁移中顺带重构长期记忆、RAG、报告模式、量化交易、模型训练或无关前端页面；除非后续勘察证明它们是对话链路不可分割的直接依赖。
- 不改变鉴权、用户权限或数据库 Schema；如真实模块必须改变，应单独建立高风险规格和迁移/恢复计划。
- 不增加交易、下单、持仓修改、报告发布等生产写能力。
- 不建设 Kubernetes、微服务拆分、Redis、消息队列、OTel Collector 或正式生产 CD，除非出现经过验证的真实需求。
- 不把离线 Fake 测试结果表述为真实模型效果或生产可用性指标。
- 不承诺尚未测量的准确率、延迟、吞吐、费用或可用性数字。

### 6.3 Unknown Scope

- 第一批迁移应从跨阶段 Typed State/运行上下文开始，还是先从真实入口和编排器边界开始。Needs confirmation after reconnaissance.
- 非流式 REST 与流式 WebSocket/SSE 是否共用同一业务主链，以及当前协议能否无损统一。Needs confirmation.
- 现有短期记忆和长期记忆在本轮主链中的最小读取/写回责任。Needs confirmation.
- 对话模式与报告模式目前是否共享路由、规划、执行或证据模块。Needs confirmation.
- `Finance` 中哪些模块属于可提炼的行为证据，哪些只是实验性实现。Needs confirmation.
- 是否需要在首批模块中引入新的 Prompt 版本、公开错误码或事件字段。Needs confirmation.
- 首批 Live E2E 使用哪个真实模型、只读数据源、预算和隔离账号。Needs confirmation.

## 7. Constraints

### 7.1 Hard Constraints

- `Finance-agent-Skills` 是唯一运行仓库和最终真相源；`Finance` 只读参考。
- 迁移必须分模块、小步执行，一个里程碑只交付一个清晰责任边界。
- 每个模块必须可以独立 Review、验收和通过单个 revert 恢复上一已验证状态。
- 不得用兼容 Adapter、长期双轨、重复实现或复制整块历史代码规避直接重构。
- 不得破坏现有公共 REST、流式事件、鉴权、会话和前端消费协议，除非另行确认版本化变更方案。
- 不得在未单独批准的情况下修改数据库 Schema、持久化语义或生产配置。
- 默认测试和普通 CI 不调用付费模型、真实 Tushare/MCP/Langfuse 或生产服务。
- Live E2E 必须显式触发，具有凭证隔离、固定只读案例、费用/调用预算、超时和清理证据；生产写永久禁止。
- 所有外部输入、模型输出、工具参数和工具结果必须在边界验证；验证失败不能进入下一阶段。
- 模型、工具、重试、重规划和主链运行必须具有有限预算和明确终止条件。
- 日志、Trace、测试夹具和产物不得泄露 Token、Authorization、Cookie、连接串、个人敏感数据或完整敏感 Prompt/响应。
- 新增或修改的 Python 公共接口必须包含类型和完整中文 Google-style docstring；关键复杂逻辑添加说明意图、边界和失败语义的中文注释。
- 所有行为变化必须有风险相称的自动化测试；完整功能验收必须包含离线 Compose E2E。
- 不得通过删除断言、扩大 ignore、静默 skip、降低类型规则或把异常吞掉来让门禁通过。
- 未经用户明确授权，不执行 commit、push、创建/合并 PR、修改分支保护、release 或部署。

### 7.2 Soft Constraints

- 优先复用仓库已有且验证有效的 FastAPI、Vue、PostgreSQL、pytest/eval、Trace 和 CI 基础设施。
- 优先保持模块化单体，只有真实扩展或隔离需求出现时才引入更复杂部署形态。
- 每个模块以最小可证明的行为切片推进，避免“只搬文件、不建立契约”的伪重构。
- 面向项目维护者使用通俗中文解释关键设计、权衡、测试证据和失败原因，使项目可以用于学习和面试讲解。
- 工程质量对齐成熟开源 Agent 和后端项目，但不为了形式创建无消费者的抽象、目录、配置或指标。

## 9. Engineering Quality Requirements

### 9.1 Interface Documentation and Types

- 对话请求、响应、流式事件、跨阶段状态、计划、工具调用、证据、校验结果和最终运行结果应具有明确结构，而不是依赖未约束的核心 `dict[str, Any]`。
- 公共路由、服务、工作流/Agent 节点、工具和 Provider 边界必须声明类型，并说明业务含义、约束、返回、失败和副作用。
- 状态字段需要说明来源、是否持久化、隐私级别、允许值、生命周期和下游消费者。
- 稳定状态、错误和终止原因应使用机器可消费的枚举、Literal 或等价受控值。
- Prompt 输入输出、工具 Schema、流式事件和评测数据属于兼容敏感契约，变更必须记录版本和影响。

### 9.2 Architecture and Module Ownership

- API 层只拥有协议适配、输入校验、认证上下文和响应映射。
- 应用/工作流层拥有用例编排、事务边界、阶段协调、预算和状态转换。
- 领域/Agent 模块拥有稳定业务规则、对话决策和阶段契约。
- 基础设施/Provider 实现拥有模型、工具、MCP、数据库、记忆和外部观测 SDK 细节。
- 启动装配负责构造依赖和生命周期，不得通过模块导入副作用偷偷改变生产行为。
- 最终目录和接口形式由后续 Codebase Reconnaissance 与 Solution Tradeoff 决定，本规格不预先锁定。

### 9.3 Configuration, Secrets, Constants, and Prompts

- 部署变化配置通过单一 typed Settings 边界加载并校验，再注入消费者；不得继续在业务阶段散落读取环境变量。
- 凭证只来自环境变量或 Secret；仓库只提交无效占位的 `.env.example`。
- 稳定业务规则、状态枚举、协议和预算默认值保留在可审查代码中，不能把所有逻辑转成环境配置。
- Prompt 需要集中、可定位、可版本化，并能关联评测用例和 Trace；不得散落在路由、数据库或 Provider 代码中。
- Provider 专有请求字段只能存在于适配边界，不能污染通用对话状态和业务契约。

### 9.4 Terminal Output, Logging, Tracing, and Artifacts

- 用户结果、简洁终端进度、结构化日志、Trace/span 和大体积运行产物必须区分。
- 每轮对话至少可关联 `trace_id`、`run_id`/等价运行标识和 `session_id`；重要阶段记录稳定的 `stage`、`status`、`elapsed_ms`、`error_code`。
- 模型调用、工具调用、阶段 handoff、重试、重规划、终止、降级和失败应可在同一 Trace 中关联。
- Trace 名称保持稳定低基数；动态 ID、实体或工具参数放属性，不拼进 span 名称。
- 日志和 Trace 先脱敏再落盘或导出；可选 Langfuse/exporter 关闭或失败不能阻断业务和本地证据。
- 长 Prompt、模型原文、Verifier 诊断和工具原始载荷默认不在终端输出；确需保留时进入受控、脱敏且有生命周期的 artifact。
- 每个 E2E/评测产物应记录代码/Prompt/数据集版本、安全配置摘要、样例 ID、状态和失败原因，不能保存真实秘密。

### 9.5 Validation, Errors, Retry, State, and Compatibility

- 用户输入在 API 边界验证；模型结构化输出和工具结果在各自边界验证后才能写入核心状态。
- 异常只在增加上下文、转换抽象、清理资源或执行批准降级时捕获，不允许 `except Exception: pass`。
- 瞬时错误才允许重试，并需有最大次数、总时间预算、退避和副作用幂等保护。
- 重规划只能由明确可恢复原因触发，必须限制次数并记录原因；不可恢复错误直接终止或返回部分结果。
- 成功、失败、部分成功、需要澄清、安全拒绝和取消必须可区分，不能用空字符串或 `False` 承载全部语义。
- 对话状态转换需要明确前置条件和不变量；失败后不得留下伪成功状态、重复消息或半写入副作用。
- 已公开 REST/流式协议、会话语义和前端消费行为默认保持兼容；任何必要变更都需先建立契约测试和版本/迁移决策。

## 10. Success Criteria

### 10.1 Functional Criteria

- 给定明确金融问题，主链能够从真实应用入口完成理解、必要执行、证据检查和回答，并产生结构化终态。
- 给定无需工具的普通对话，系统不会无意义调用金融工具。
- 给定缺少实体、时间范围或关键目标的问题，系统在执行前追问、保守处理或明确终止。
- 给定多轮指代，系统只复用相关且有效上下文；冲突或不足时要求澄清。
- 给定工具超时、限流、空结果或非法结果，系统按明确错误语义降级或失败，不崩溃、不无限循环、不伪造数据。
- 给定证据与问题主体、时间或结论不匹配，系统阻止无依据结论并明确说明不足。
- 每轮运行都能到达唯一可解释终态，并受步骤、重试/重规划和耗时预算约束。
- 每完成一个迁移模块，生产主链只保留该责任的唯一实现，不残留旧导入、转发 Adapter 或重复 Prompt。

### 10.2 Compatibility Criteria

- 未经单独批准，现有 REST 路径、请求字段、响应字段、流式事件、鉴权和会话语义保持兼容。
- 未经单独批准，不改变数据库 Schema 和现有用户数据。
- 已存在的对话、记忆、报告或其他直接调用方不得因内部迁移出现未解释回归。
- 默认运行不依赖 `Finance` 目录，也不要求用户安装第二套 Runtime。

### 10.3 Reliability Criteria

- 所有外部模型和工具调用都有超时；瞬时错误重试有界且可观察。
- 主链具有明确终止条件，自动化测试可证明不会因工具失败或模型反复给出非法结果而无限执行。
- 有副作用或持久化操作在重试下不会产生重复写入；无法证明幂等时禁止自动重试。
- 外部观测出口不可用时，本地业务结果和必要 Trace 仍可产生。
- 每个里程碑能够通过单个版本回退恢复到上一已验证行为，不依赖长期保留旧实现。

当前没有可信的准确率、P95 延迟、并发、成本或可用性基线；这些指标必须先在后续勘察/评测阶段建立，不能在本规格中虚构阈值。

### 10.4 Observability Criteria

- 从 API 请求到最终响应，可以通过同一 `trace_id` 关联关键阶段、模型、工具、重试/重规划和终态。
- 每个重要阶段至少暴露 `stage`、`status`、`elapsed_ms` 和失败时的稳定 `error_code`。
- Trace 能区分正常成功、部分结果、澄清、降级、拒绝和失败，并记录触发终止的原因。
- 日志、Trace、CI artifact 和测试报告通过自动化断言证明不会输出常见凭证字段；字符串模式脱敏是否作为首批范围在勘察后确认。
- 观测数据足以回答“为什么选择这条路径、为什么调用这个工具、证据为何通过/拒绝、为何终止”，但不要求记录不可控的完整思维过程。

### 10.5 Testing Criteria

- 每个模块在实现前建立现有行为刻画、目标契约或稳定复现测试；如果某行为不能自动测试，必须记录替代证据和原因。
- 每个模块至少覆盖正常输入、空/非法输入、歧义、下游超时、非法下游结果、无证据、终止和兼容性场景中适用项。
- unit 测试验证纯规则、状态转换、校验、预算和错误映射，不访问网络。
- contract 测试锁定 API/流式事件、跨阶段状态、工具 Schema、Provider 和错误码等兼容边界。
- integration 测试使用隔离数据库和 Fake Provider，验证阶段协作、事务和失败清理。
- offline eval 使用固定、版本化、可追踪样例；区分工程正确性和模型质量指标，并记录未迁移模块的 skip 原因。
- 每个可交付模块必须运行离线 Compose E2E，从生产构建的前端/Nginx 入口经过真实 FastAPI、目标主链模块和隔离 PostgreSQL，再验证响应、错误路径、Trace 和资源清理。
- 仅独立测试 Fake Provider 不算目标主链 E2E；对应模块迁移后，Fake 必须通过真实主链公开边界被调用。
- 模型/Prompt/路由/工具质量发生变化时，在安全条件满足后执行固定小样本 protected live E2E；记录模型版本、参数、耗时、费用、结果和副作用边界。
- 默认 CI 必须保持离线并执行锁文件、Ruff、Pyright、相关分层测试、全仓回归、前端 lint/type-check/build 和 Compose E2E。
- 每个里程碑的验收报告必须记录准确命令、结果、skip、失败修复、剩余风险、Trace/产物位置和回滚方式。

## 11. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| 整条主链范围过大，导致一次改动跨越多个隐式职责 | 后续按真实调用图拆成单责任模块；一个计划只冻结一个可独立验收里程碑。 |
| `Finance` 历史代码被当作正确答案整体复制 | 只提取可观察行为、测试样例和可证明规则；每项能力重新做契约、权衡和实现审查。 |
| 新目录只搬运旧大文件，没有建立边界 | 验收必须证明模块所有权、依赖方向、公开契约和调用方已收敛，而不是仅检查文件移动。 |
| 直接重构破坏现有 REST/流式/会话兼容 | 先建立 characterization 和 contract tests；同一 PR 更新调用方，完整 E2E 验证。 |
| Fake 测试绕开真正 Agent 主链，形成“假 E2E” | 模块迁移后要求 Fake 通过与真实 Provider 相同的主链边界注入，并断言目标阶段确实执行。 |
| 模型输出不稳定使测试偶发失败 | 默认 CI 使用确定性结构化 Fake 和固定离线数据；模型质量放到小样本受保护 Live E2E。 |
| 状态字段继续无限膨胀或跨层共享可变字典 | 在后续方案中冻结阶段输入输出和字段所有者；契约测试限制非法状态转换。 |
| 重试/重规划产生循环、成本失控或重复写入 | 强制步骤、耗时、次数和费用预算；副作用需要幂等证明；Trace 覆盖每次重试原因。 |
| 证据校验过严导致有效问题被拒绝 | 同时建立正例、反例和边界样例；用离线评测观察误拒绝和误通过，阈值后续基于基线决定。 |
| 日志和 Trace 泄露用户输入或密钥 | 所有出口统一先脱敏；加入本地和 exporter payload 自动化测试。 |
| Prompt、工具 Schema 与代码版本漂移 | 把它们作为版本化契约，PR 同步更新评测和变更说明。 |
| 未定义真实服务预算导致 Live E2E 意外费用或副作用 | 使用显式开关、保护环境、固定样例、单并发、调用/费用上限、只读账号和清理检查。 |
| 为简历包装而声明未实现能力或未测指标 | 项目描述只能引用已合并实现和可复现验收证据；外部最佳实践标注为未来方向。 |

## 12. Open Questions

### Question 1

- Question: “受控对话主链”第一批是否只覆盖对话模式，不同时迁移报告模式？
- Why it matters: 两种模式如果共享入口但有不同输出和长任务语义，同时迁移会显著扩大首批风险。
- Suggested default: 首批只覆盖交互式对话模式；报告模式仅保持兼容，待真实调用图确认共享边界后另立规格。

### Question 2

- Question: 第一里程碑应先冻结跨阶段状态/终态契约，还是先重构后端入口与编排边界？
- Why it matters: 状态契约决定后续所有模块如何协作，但如果现有入口存在多个实际主链，需要先确认唯一调用路径。
- Suggested default: 先只读勘察所有入口和调用方；若存在唯一主链，则优先做最小 Typed State/运行结果契约；若入口分叉，则先统一应用编排入口。

### Question 3

- Question: 多轮对话中哪些信息允许自动继承，哪些必须重新确认？
- Why it matters: 这直接影响实体解析、问题改写、安全性和用户体验。
- Suggested default: 只继承最近且明确的标的、任务和时间范围；发生冲突、跨任务或高风险参数缺失时必须澄清。

### Question 4

- Question: 对证据充分性的最低要求是什么，例如是否必须包含来源、时间、主体匹配和关键字段？
- Why it matters: 这是 Verifier/Controller 能否阻止幻觉和错误金融结论的核心产品规则。
- Suggested default: 涉及外部事实的结论至少要求主体和时间匹配、来源可识别、关键字段非空；不满足时只能输出部分结果或明确不足。

### Question 5

- Question: 首批真实 Live E2E 可以使用哪些模型和只读金融数据源，单次预算上限是多少？
- Why it matters: 没有明确账号、只读权限和费用边界，就不能把真实链路加入验收。
- Suggested default: Codebase Reconnaissance 阶段只记录现有 Provider；在模块实现前另行确认一个模型、一个只读数据源、固定 3-5 个案例和明确调用上限。

### Question 6

- Question: 现有 REST 和流式接口是否允许增加新的可选状态/错误字段？
- Why it matters: 更完整的澄清、部分结果和失败语义可能需要前端展示，但错误增加字段也可能造成兼容问题。
- Suggested default: 首批不删除、不改名现有字段；仅在契约和前端消费者验证后增加向后兼容的可选字段。

### Question 7

- Question: 项目描述和统一面试口径的权威文档具体是哪一份，冲突时以代码事实还是表述目标为准？
- Why it matters: 迁移计划需要区分“当前已实现”“历史实现”“未来目标”，否则容易把口径当成代码事实。
- Suggested default: 运行代码和可复现测试决定当前事实；用户确认的项目描述决定目标；冲突项进入 Gap/Decision Log，不伪造已实现状态。

## 13. Handoff to Next Step

下一步必须使用 Codebase Reconnaissance Skill，对当前仓库和本规格做只读勘察，不修改代码、不选择最终方案。

勘察至少需要产出：

- 对话模式全部真实入口，包括 REST、流式、后台任务和测试装配入口。
- 从前端请求到后端路由、应用服务、Agent 节点、模型/工具、数据库、Trace 和响应的调用图。
- 当前主链每个阶段的文件、责任、输入输出、状态字段、Prompt、配置、失败和调用方。
- `Finance` 与 `Finance-agent-Skills` 在实体、路由、改写、规划、执行、证据、控制、总结等能力上的逐模块 Gap。
- 对话模式与报告模式、记忆系统和其他模块的共享边界。
- 现有 unit/contract/integration/eval/E2E/live 测试实际覆盖和绕过点。
- 现有日志、Trace、Langfuse、artifact、秘密和敏感数据处理路径。
- 第一可迁移模块的候选范围、依赖、风险和仍需用户决策的问题，但不做最终方案选择。

## Decisions Needed Before Codebase Reconnaissance

- [ ] 确认本规格名称和范围采用“受控对话主链”，首批默认不迁移报告模式。
- [ ] 指定项目描述和统一面试口径的权威文件位置；如果暂不指定，勘察阶段在工作区内定位候选文档并列出。
- [ ] 提供 3-10 个最希望主链正确处理的真实对话案例；如果暂不提供，先从现有测试、文档和历史实现提取候选案例。
- [ ] 确认是否接受“先勘察入口，再决定首个模块是 Typed State 还是应用编排入口”的默认顺序。
- [ ] Live E2E 的模型、数据源、账号和预算可以推迟到对应 Provider/模块实施前确认，不阻塞下一步只读勘察。
