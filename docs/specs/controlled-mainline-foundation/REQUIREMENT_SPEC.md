# 受控主链迁移前置基础设施：需求规格

> 状态：需求基线（待代码勘察与方案权衡补充）
> 主仓库：`Finance-agent-Skills`
> 历史实现来源：`Finance`（仅作证据与迁移候选，不作为主仓库）

## 1. 任务类型

- 主要类型：工程治理与基础设施建设。
- 次要类型：架构重构、测试与评测完善、可观测性治理、开发文档建设、历史能力迁移规划。
- 风险级别：高。原因是该工作会约束后续跨模块开发、公共接口、测试门禁、日志与追踪协议以及 GitHub 协作方式。

## 2. 用户目标复述

本阶段不是立即把 `Finance` 中的全部受控主链代码复制进主仓库，而是先为 `Finance-agent-Skills` 建立一套可以长期执行、能够被面试官审阅、也便于初学者学习的工程基线。基线建立后，再以小步里程碑逐步迁移和重写受控主链；历史实现只作为行为证据和设计输入，存在缺陷的部分不得原样照搬。

优先完成并统一以下内容：

1. 根级 `AGENTS.md`：成为后续所有 Agent 与开发者必须遵循的工程规则。
2. 代码结构与命名：明确每类代码的归属、依赖方向、允许修改的位置以及禁止堆放的位置。
3. GitHub 研发闭环：Issue、需求规格、分支、提交、Pull Request、Code Review、CI、合并、回滚与发布记录。
4. 测试与评测基础设施：单元测试、契约测试、集成测试、离线评测、真实依赖 E2E 的职责和门禁。
5. CI/CD 基线：普通 CI 稳定、离线、低成本；真实模型与真实服务测试显式触发并受保护。
6. 日志、终端输出、运行产物、OpenTelemetry/Langfuse 追踪规范：既可排障，又避免泄露密钥和敏感数据。
7. 受控主链迁移路线：每次只迁移一个可验收闭环，保留回退路径，不做一次性大搬家。

## 3. 需求来源与现有证据

### 3.1 用户观察

- 现有代码存在模块职责、目录归属和命名不够统一的问题。
- `Finance` 历史版本包含较多能力，但部分实现不完整、冗杂或实验性较强。
- 之前的局部测试不足以证明完整链路可上线，需要从后端和依赖启动开始验证真实请求闭环。
- 项目将用于简历与面试讲解，不能继续以 Demo 标准扩展。
- 用户需要所有关键决策都用通俗语言、例子和取舍讲清楚。

### 3.2 已知仓库事实（待代码勘察复核）

- 主仓库已经具备第一版离线 CI、评测 smoke、前端构建检查和根级 `AGENTS.md`。
- 默认测试不调用付费模型或生产服务；真实服务 E2E 允许人工或受保护工作流显式执行。
- 一部分受控主链评测因目标模块尚未迁移而跳过。
- `Finance` 中存在实体解析、两阶段路由、改写、Planner、Executor、Verifier、Synthesis、Tool Discovery、Controller/Replanner 等候选实现。

## 4. 当前行为与主要问题

以下内容是待勘察验证的初始问题陈述：

1. 当前 `AGENTS.md` 偏向个人项目轻量流程，与新的企业级工程目标存在冲突。
2. 当前可运行入口、历史入口和未来受控主链入口之间的所有权边界不够清晰。
3. CI 已能执行基础测试和构建，但格式化、静态检查、契约测试、容器集成测试、安全检查及产物留存规则尚未形成完整矩阵。
4. 离线评测已有入口，但跳过条件、基线更新、回归阈值和失败归因仍需统一。
5. 本地真实 E2E 的启动、测试数据、请求、日志、清理和验收报告尚未标准化。
6. 日志字段、错误码、`run_id`/`trace_id`、Langfuse span 边界、敏感字段脱敏和采样规则需要形成统一契约。
7. 目录、模块、类、函数、配置项、Feature Flag、Prompt 版本和测试文件命名需要统一。

## 5. 期望的可观察行为

完成本阶段后，新的贡献者应能够：

1. 从一个 Issue 出发，按模板明确需求、风险、验收标准和不做事项。
2. 根据目录与依赖规则准确找到应修改的模块，不把路由、业务规则、模型调用、工具实现和持久化混在同一文件。
3. 创建规范分支和提交，通过 Pull Request 获得自动检查与可审阅的变更说明。
4. 在本地通过统一命令执行格式化、Lint、类型检查、单元测试、集成测试和离线评测。
5. 对功能里程碑启动完整容器链路，发送固定测试请求，在允许的情况下调用真实模型与外部服务，并生成可追溯、可脱敏的验收报告。
6. 在普通 CI 中保证不调用付费模型和生产服务；需要真实依赖的测试只能通过显式标签和受保护入口运行。
7. 使用稳定的 `run_id`/`trace_id` 关联终端摘要、结构化日志、Langfuse trace、错误信息和测试产物。
8. 当迁移模块失败时，能关闭 Feature Flag 或回退单个里程碑，不影响现有稳定入口。

## 6. 范围

### 6.1 本轮包含

- 生成需求、代码勘察、澄清、方案权衡和可执行计划文档。
- 重新设计根级 `AGENTS.md` 的统一规则，但在计划确认前不直接替换。
- 设计目标目录、模块所有权、依赖方向与命名规范。
- 设计 GitHub Issue/PR/Review/CI/合并/发布闭环。
- 设计测试金字塔、离线评测、容器集成测试和真实 E2E 门禁。
- 设计配置、错误、日志、终端输出、Langfuse 与运行产物规范。
- 把后续实施拆成独立、可回滚、可验收的里程碑。

### 6.2 本轮不包含

- 不批量复制 `Finance` 的历史代码。
- 不在计划确认前迁移 Planner、Executor、Verifier 等业务模块。
- 不修改现有公共 API、数据库结构或持久化数据格式。
- 不建立尚无明确目标环境的生产部署平台。
- 不提交真实密钥，不在 CI 中默认调用付费模型或生产服务。
- 不为了“看起来企业级”引入没有实际用途的平台、依赖或微服务。
- 不虚构吞吐量、准确率、成本下降等简历指标。

## 7. 硬约束

1. `Finance-agent-Skills` 是唯一主仓库；`Finance` 只能作为历史参考。
2. 所有跨模块改造执行规格驱动、小步里程碑流程；一个里程碑对应一个 Issue、一个分支和一个 PR。
3. 默认 CI 必须可重复、无真实密钥、无付费模型调用、无生产服务写操作。
4. 真实 E2E 必须显式启用，并具备超时、预算、脱敏、失败清理和可审计报告。
5. 密钥、Authorization、Cookie、个人数据、私有 Prompt 和敏感模型/工具载荷不得进入代码、日志、trace、fixture 或 CI 产物。
6. 公共 Python 接口、Agent 节点、工具、配置和状态必须有类型标注及中文 Google-style docstring；注释解释意图、边界、取舍和失败语义。
7. 核心 Agent 状态不得长期依赖无约束的 `dict[str, Any]`；Prompt、工具 Schema、持久化状态和评测数据按兼容性契约管理版本。
8. 外部调用必须定义超时；只对瞬时错误做有上限重试；有副作用的调用必须考虑幂等性。
9. 每项工程规则必须说明“为什么、适用范围、执行方式、验证方法和例外审批”，不能只写口号。
10. 关键方案需要引用官方文档或成熟开源仓库作为外部证据，同时说明哪些是行业实践、哪些是本项目选择。

## 8. 相关角色

- 产品负责人/项目所有者：用户，决定功能优先级、外部服务预算和最终验收。
- 开发者：用户与编码 Agent，共同遵循 Issue、规格、测试和 PR 契约。
- 审阅者：当前以独立 Agent 审阅和项目所有者确认组成；不得伪造人工双人审批。
- 运行者：本地开发环境与 GitHub Actions；未来部署环境在目标明确后补充。
- 面试审阅者：关注架构合理性、工程证据、取舍、失败处理、测试和可观测性，而非目录数量。

## 9. 质量要求

### 9.1 正确性与可靠性

- 行为变更必须有与风险相称的自动化测试。
- 外部依赖失败时返回稳定错误码和明确失败阶段，不得伪装为空结果或成功。
- 受控主链必须有终止条件、循环上限、工具预算和降级路径。

### 9.2 可维护性

- 采用明确的分层与单向依赖；每个模块有清晰所有者和公开契约。
- 配置统一从类型化 Settings 注入，不在业务代码中散落 `os.getenv()`。
- 删除或迁移代码时必须同步处理测试、文档、配置和观测字段。

### 9.3 可观测性

- 关键阶段至少记录 `stage`、`run_id`/`trace_id`、`status`、`elapsed_ms`、核心计数、`error_code`。
- 终端只输出短摘要；详细诊断进入受控日志、trace 或运行产物。
- Langfuse 用于记录模型、Prompt、工具、Agent 节点和评测关联，但不成为业务正确性的单点依赖。

### 9.4 安全与成本

- 普通 CI 零付费模型调用。
- Live E2E 具备预算上限、并发限制、只读优先和环境隔离。
- 日志、异常、快照和测试报告必须脱敏。

### 9.5 可学习与可解释

- 重要规范附带小白可理解的正例、反例和常用命令。
- 每个里程碑记录为什么这么做、替代方案、权衡、测试证据和遗留问题，便于形成可信简历材料。

## 10. 成功标准

1. 需求规格、代码勘察、澄清决策、方案权衡和 `PLAN.md` 相互引用且不存在冲突。
2. 计划明确到每个里程碑的目标、允许修改范围、接口与配置影响、测试矩阵、观测要求、回滚方式和禁止事项。
3. 新 `AGENTS.md` 覆盖需求到合并的完整闭环，并能被实际命令和 CI 配置验证。
4. 目标目录图能为现有入口和未来受控主链标明归属、依赖方向与过渡策略。
5. 测试矩阵明确区分 unit、contract、integration、offline eval、container E2E、live E2E，并为每层定义触发方式与通过标准。
6. CI/CD 方案明确必选检查、可选检查、受保护环境、产物、失败处理和回滚；未确定生产环境时不得假装已完成生产 CD。
7. 至少选取成熟开源项目与官方文档作为工程决策依据，并在方案中记录适配本项目后的取舍。
8. 用户确认计划后，能从第一个基础设施里程碑开始实施，而不需要重新讨论整体架构。

## 11. 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 直接复制历史 v2 代码 | 把实验性耦合和缺陷带入主仓库 | 先提取行为契约和测试，再按目标分层重写或迁移 |
| 一次改动过大 | 难以 Review、定位回归和回滚 | 单里程碑、单 Issue、单 PR，Feature Flag 双轨切换 |
| “企业级”变成工具堆砌 | 增加维护成本但没有质量收益 | 每个工具必须对应明确风险、命令、门禁和退出条件 |
| Live E2E 不稳定或产生费用 | CI 波动、意外成本或数据污染 | 与普通 CI 隔离，显式触发、预算/超时/只读限制、保存脱敏报告 |
| 日志与 Langfuse 泄露敏感信息 | 安全与隐私风险 | 入口脱敏、字段白名单、默认不记录原始敏感载荷 |
| 规则与实际配置不一致 | 文档失效，团队误判 | 让规则对应可执行脚本和 CI 检查，PR 中做文档—配置一致性审查 |
| 为面试过度包装 | 技术叙述不可验证 | 只使用仓库提交、测试报告、trace 和评测结果作为证据 |

## 12. 待澄清决策与建议默认值

这些问题不阻塞只读代码勘察，但会影响最终方案和实施顺序：

1. **目标 Python 包布局**：是渐进整理现有 `Financial-MCP-Agent/src`，还是新建规范包并通过适配层迁移？建议先勘察真实导入链，再选择“渐进式旁路迁移”，避免大爆炸重构。
2. **本阶段 CD 的边界**：尚未明确云平台和生产环境。建议把 CD 定义为“可复现镜像构建 + 本地/临时环境 E2E + 受保护的手工发布入口”，生产部署留到环境确定后。
3. **个人项目的 Code Review**：建议采用“独立 Agent 审阅 + 作者修复 + 项目所有者确认 + 必选 CI”，不伪造第二位人工 Reviewer。
4. **质量工具组合**：格式化、Lint、类型检查、安全扫描应优先复用少量成熟工具；具体选择在代码勘察和方案权衡后确定。
5. **真实 E2E 数据权限**：建议默认只读、固定小数据集、单请求预算和显式环境变量开关；任何写生产数据的测试继续禁止。
6. **Langfuse 内容边界**：建议默认记录结构化元数据、耗时、token/cost、Prompt 版本和脱敏摘要；原始请求/响应按环境和数据分类显式开启。
7. **兼容策略**：建议所有受控主链模块先通过 Feature Flag 接入，成功验证后再逐步替换旧入口。

## 13. 交接给代码勘察阶段

代码勘察必须回答：

- 当前唯一真实请求入口和完整调用链是什么？
- 目录、依赖、配置、日志、Langfuse、Docker、测试与 CI 当前分别由谁负责？
- 哪些规则已有可执行实现，哪些只存在于文档，哪些完全缺失？
- `Finance` 历史模块中哪些可复用行为或测试，哪些结构不得迁移？
- 哪些改动可以成为第一个独立、可回滚的基础设施里程碑？

在代码勘察完成前，不冻结最终目录方案，不修改业务实现，不迁移受控主链模块。
