# D09 澄清结论

## 1. 澄清依据

本文件只冻结 D09“实体解析受控模型兜底”的实现决策，不修改任何面试材料。决策依据为：

- 用户明确授权：受保护真实 API 测试允许且必须，需模拟真实使用；迁移调用方后删除旧路径，不保留长期双轨；D09 按推荐方案开发。
- `REQUIREMENT_SPEC.md` 与 `CODEBASE_RECON.md`。
- 面试材料中已经形成的口径：实体解析先于路由；规则、目录、别名和模糊匹配优先；模型只作受控兜底；结果必须回查权威目录；歧义进入澄清；报告与对话复用共享底座；短期记忆只保存已确认实体。
- 当前代码事实：公开对话使用静态同步 Resolver，报告使用独立 LLM-only Resolver；旧兼容函数和历史 CLI 还复制了解析规则。

以下问题均已通过用户授权、现有口径和保守工程默认消解，不再阻塞方案设计。

## 2. 已消解问题、原因与采用方案

### Q1：模型兜底可以直接生成并采用股票代码吗？

- **为什么要问**：当前报告 Resolver 会让模型按常识填写代码，存在幻觉代码、名称与代码不一致以及不可审计风险。
- **候选方案**：
  1. 直接信任模型，成本最低但风险最高。
  2. 模型只提出候选，目录回查后才可形成 canonical entity。
  3. 完全不用模型，只扩充静态别名；无法覆盖长尾口语表达。
- **采用方案**：方案 2。模型不是权威源；候选必须经过共享 Catalog Adapter 的代码格式、实体类型和名称—代码一致性校验。回查失败不得伪装成功。

### Q2：权威目录使用什么来源，目录不可用时怎么办？

- **为什么要问**：仅靠十余条静态目录无法覆盖真实使用，但每轮全量拉取外部目录会增加延迟、额度和故障面。
- **候选方案**：
  1. 只用静态目录。
  2. 每轮加载完整 Tushare 目录。
  3. 本地稳定目录优先，长尾候选按代码通过 Tushare 点查校验，并允许短 TTL 缓存。
- **采用方案**：方案 3。离线测试使用确定性 Catalog；生产复用既有 Tushare Client，不增加依赖。外部目录不可用时，已被本地目录确认的实体仍可用；长尾候选返回稳定的 unavailable/clarification 语义，不降级为“相信模型”。

### Q3：何时允许调用模型？

- **为什么要问**：没有硬门禁会导致常见实体也付费、显式错误代码被模型“脑补修正”，并使结果不稳定。
- **采用方案**：严格按“显式合法代码/精确名称/别名/确定性模糊匹配 → 模型兜底”执行。显式但无效的证券代码、已发现多候选且无法收敛、继承冲突等情况不调用模型，直接失败或澄清。

### Q4：模型输出失败后允许怎样修复？

- **为什么要问**：无上限重试会放大成本和延迟；宽松截取 JSON 会掩盖协议错误。
- **候选方案**：无限/通用重试、零修复、一次受控语法修复。
- **采用方案**：最多一次 syntax repair。两次模型调用共用一个逻辑预算；严格 schema 校验后仍失败即停止。语义校验失败不再次问模型，避免把幻觉变成循环。

### Q5：模型超时、限额或协议异常时，产品如何表现？

- **为什么要问**：当前报告路径吞掉所有异常并返回空值，无法区分未识别、外部服务故障和模型协议错误。
- **采用方案**：领域层返回稳定 failure code；对话进入可恢复澄清/降级，报告在四个分析 Agent 启动前明确失败。日志和 Trace 只记录路径、调用次数、修复次数、错误码和耗时，不记录完整用户输入、模型原文或凭证。

### Q6：报告和对话是否保持各自 Resolver？

- **为什么要问**：两条相反实现正是当前口径与代码的主要 Gap。
- **采用方案**：只保留一个共享 Resolver 内核和一个 canonical entity 合同；对话与报告只保留薄场景 Adapter。报告 Adapter 可继续暴露既有 `resolve_stock()` 调用形状，但不保留旧 LLM-only 决策逻辑。

### Q7：如何处理现有同步签名和旧调用方？

- **为什么要问**：模型和目录均为 I/O，继续同步接口会阻塞事件循环；长期保留 sync/async 双实现又违反用户要求。
- **采用方案**：共享 Resolver 改为 async，逐个迁移公开对话、报告和仍在生产调用图中的工具入口；迁移完成后删除无调用的 `agent_service.extract_stock_info()`。历史 `skill_executor_node` 不重新接回公开主链；若其模块测试仍要求可导入，只迁移到统一 Adapter，不保留私有解析策略。

### Q8：历史独立 CLI 中的本地正则解析器怎么办？

- **为什么要问**：它复制了第三套规则，但不是当前 FastAPI 产品入口；盲删可能破坏开发演示。
- **采用方案**：把 CLI 调用迁移到共享报告 Adapter 后删除内嵌解析函数。若依赖路径无法在不引入新的反向依赖下闭合，则该里程碑停止并记录阻塞，不以兼容副本收尾。

### Q9：报告未识别或歧义时是否允许四个 Agent 继续运行？

- **为什么要问**：当前代码只记录 `DEGRADED` 后继续，可能浪费四路模型调用并生成错误对象的报告。
- **候选方案**：继续运行并让下游猜测、静默返回空、入口前失败。
- **采用方案**：入口前失败。只有目录确认的单一股票实体才能进入报告 Agent fan-out；歧义和未确认实体不会启动下游 Agent。

### Q10：哪些实体类型进入本轮？

- **为什么要问**：对话合同包含 stock/fund/index/sector，而报告只接受 stock。
- **采用方案**：共享合同继续覆盖四类；报告 Adapter 显式收窄为 stock。首期动态目录至少完整支持 A 股股票，基金/指数/板块保留现有确定性目录并通过同一扩展接口接入；不为未验证的外部目录能力伪造覆盖。

### Q11：受保护真实 API 测试如何做到既真实又可重复？

- **为什么要问**：普通测试不能产生费用或依赖凭证，但用户要求模拟真实使用并验证兜底路径。
- **采用方案**：新增显式 marker 与环境门禁，从真实产品工作流入口提交一个不在本地静态目录中的稳定 A 股公司自然语言查询；真实调用 OpenAI-compatible 模型和 Tushare 目录，断言 `resolver_path=model_fallback`、目录确认的 canonical code、模型调用预算以及最终可恢复/成功语义。缺少凭证时是受保护测试的环境失败或显式 skip，不影响默认离线套件；正式验收必须在已授权环境实际执行，不以 skip 代替通过。

### Q12：历史 93.9% / 4.4% / 90.7% 是否是本轮门禁？

- **为什么要问**：仓库中没有能独立复现这些数字的完整原始数据集和运行制品。
- **采用方案**：不伪造历史结果。新增可版本化 eval 样例与 runner，报告本次真实样本数、分路径指标和结果；历史百分比作为 P2 证据补全，不阻塞 D09 功能验收。

## 3. 配置与兼容性边界

- 复用现有 OpenAI-compatible、Tushare、Pydantic 和缓存能力，不新增生产依赖。
- 新配置统一进入 `backend.config.Settings` 与安全 `.env.example`；业务代码不新增散落 `os.getenv()`，不提交真实凭证。
- 不修改数据库 schema、鉴权、前端公共协议、Skill 模块、记忆归属或报告正文格式。
- canonical symbol 由共享领域层统一；报告 Adapter 负责转换为既有下游需要的代码格式。
- 不保留 feature flag 下的旧 Resolver，也不建立 shadow 双写或长期回退路径；回滚依赖 Git 提交/PR，而不是代码内双轨。
