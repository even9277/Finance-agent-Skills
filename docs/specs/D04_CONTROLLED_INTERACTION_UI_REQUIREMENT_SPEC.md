# D04 受控交互与执行状态 UI 需求规格

## 1. Task Type

- Primary: New Feature
- Secondary: Test / Evaluation, Engineering Governance, Interview Demo Alignment

## 2. Requirement Restatement

在 D03 已落地的 `chat-stream-v2` 真流式协议之上，为对话模式补齐受控交互与执行过程展示。用户除最终回答外，还应看到经过后端权威状态投影后的计划预览、步骤状态、工具调用摘要和证据校验摘要；前端不得自行猜测执行状态，也不得暴露原始 Prompt、完整工具参数、工具原始结果或内部异常。

本任务同时建立可重复验证的功能测试、协议测试、前端状态测试和显式开关保护的真实 API 端到端测试，使代码实现、运行效果与金融 Agent 项目面试文档中的“可观测、可解释、可控”口径一致。

## 3. Problem Source

### 3.1 User Requirement

用户要求从 D04 开始逐项补齐此前识别的 Gap，并在开发前先确定验收标准和测试标准。D04 的范围是：

- 最终文本之外展示计划预览、步骤状态、工具调用和证据校验。
- 增加控制帧及对应执行状态 UI。
- 允许使用真实 API 完成端到端验证。
- 经过完整 Spec Coding、测试、代码审核、提交、推送、PR 和合并流程。

### 3.2 Interview-document Claims

项目文档将对话前端描述为 Agent 运行过程的产品化可观测界面，而不只是文本聊天框。文档中的关键 Claim 包括：

- WebSocket 消费 `plan_preview`、`step_status`、`verification_summary`、`trace_summary`、`skill_confirm` 等控制事件。
- `chatStore` 保存当前计划、步骤执行状态和证据校验摘要。
- 页面可展示路由摘要、计划卡片、工具调用和验证结果。
- 计划预览来自校验通过的计划，而不是 Planner 未校验草稿。
- 步骤状态至少覆盖 `planned`、`running`、`succeeded`、`failed`、`replanned`、`skipped`。
- 重规划后应标识被替换步骤、补充新步骤，并给出适合用户阅读的原因。
- 证据校验面向用户表达“证据是否充分、结论等级和缺失维度”，而不是泄露内部证据载荷。

### 3.3 Existing Verified Baseline

D03 已建立并验证 `chat-stream-v2` 的文本流式传输、类型化信封、`request_id` / `session_id` / `sequence`、终态和取消语义。D04 必须在该契约上增量扩展，不能退回无类型消息，也不能另建一套平行流式协议。

当前代码是否已经部分产生或消费上述控制事件、事件字段是否与文档一致、组件和状态归属是否正确，尚未在本任务中完成代码级核查，必须在 Codebase Recon 阶段形成证据。

## 4. Current Behavior

当前已知行为：

- 对话文本可以通过 D03 协议流式展示。
- D03 已验证同一请求内的有序序列、单一终态和取消传播。
- 既有 Skills 确认、记忆命令、上下文更新和压缩事件属于兼容性边界，D04 不得破坏。

当前待核查行为：

- 后端是否在真实工作流中产生计划、步骤、工具和证据校验事件。
- 事件是在权威节点完成后产生，还是由前端或旁路逻辑推断。
- 前端类型、解析器、Store 和组件是否已有部分实现，是否存在重复状态源。
- 刷新、断线、取消、异常、重规划和并行步骤下的状态是否一致。
- 当前 UI 是否只显示最终文本，或已有不可用/未接线的执行状态组件。

## 5. Expected Behavior

### 5.1 Normal Controlled-execution Flow

一个需要多步骤工具执行的请求，应按以下可观察顺序推进：

1. 后端完成意图识别、规划和计划校验。
2. 仅将校验通过且已经脱敏的计划投影为 `plan_preview` 控制帧。
3. 每个步骤从 `planned` 进入实际运行状态；前端依据后端事件更新，不自行推断。
4. 发生工具调用时展示工具名称、所属步骤、运行状态、耗时和安全参数摘要；不展示完整参数与原始返回值。
5. 工具或步骤结束后，展示 `succeeded`、`failed`、`skipped` 等权威状态及安全错误摘要。
6. 证据校验完成后展示证据充分性、结论等级和缺失维度摘要。
7. 最终答案继续按 D03 文本增量流式展示，并以 D03 单一终态结束。

### 5.2 Plan Preview Contract

计划预览至少包含：

- 稳定的计划标识与版本。
- 步骤稳定标识、顺序、用户可读标题或目的。
- 必需或可选标记。
- 当前状态。
- 经过白名单投影的参数摘要；禁止透传原始参数 JSON。

只有校验通过的计划可以向客户端发出。前端不得把模型草稿、Chain-of-Thought 或内部 Prompt 当作计划展示。

### 5.3 Step and Tool Status Contract

步骤状态至少支持：

- `planned`
- `running`
- `succeeded`
- `failed`
- `replanned`
- `skipped`

工具调用摘要至少支持：

- 稳定调用标识、关联步骤标识和安全工具显示名。
- `started`、`succeeded`、`failed` 状态。
- 完成时可展示毫秒级耗时。
- 可选的安全参数摘要、结果摘要或稳定错误码。

如果实际工作流没有独立的工具事件源，应从工具执行器或统一观测边界产生事件，不允许前端从文本内容解析或猜测。

### 5.4 Evidence Verification Contract

证据摘要至少表达：

- `sufficient`、`partial`、`insufficient` 中的一种充分性状态。
- 可供用户理解的结论等级或置信提示。
- 已覆盖与缺失的证据维度摘要。
- 当结果不充分时，对最终答案限制或降级的简短说明。

证据摘要必须来自实际 Evidence Verifier 或等价权威校验阶段，不能由 UI 根据工具成功数量推算。

### 5.5 Replan Behavior

发生重规划时：

- 计划版本递增。
- 被替换但未执行的旧步骤标为 `replanned` 或 `skipped`。
- 新增步骤拥有新的稳定标识并按新顺序显示。
- 展示经过脱敏、适合用户理解的重规划原因。
- 已成功步骤的历史状态不得被覆盖或伪装成未执行。

### 5.6 Failure, Partial, Clarification and Cancellation

- 单个工具失败但工作流可降级时，步骤和工具显示失败，最终任务可进入 `PARTIAL`，且证据摘要说明限制。
- 不可恢复失败必须显示稳定错误状态，D03 终态保持唯一。
- 需要 Skills 确认或业务澄清时，既有确认事件继续可用；计划与步骤 UI 不得越过确认点提前显示为运行。
- 用户取消后，正在运行的步骤和工具进入取消或跳过语义；若现有协议没有独立 `cancelled` 枚举，可由请求终态表达取消、未完成步骤表达 `skipped`，但不得显示成功。
- 无需工具的静态回答或澄清请求不强制生成虚假计划卡片。

### 5.7 Frontend Ownership

- `api` / protocol layer owns TypeScript public frame contracts and strict parsing.
- chat composable/hook owns WebSocket side effects and frame dispatch.
- chat store owns current request的计划、步骤、工具、验证和生命周期状态；不得让多个组件各自维护冲突副本。
- presentation components只负责渲染和用户动作，不解析协议、不推断业务状态。
- page/view layer只负责组合聊天文本和受控交互组件。

## 6. Scope

### 6.1 In Scope

- 扩展 `chat-stream-v2` 类型化控制帧，承载计划、步骤、工具和证据摘要。
- 在后端真实执行链的权威节点产生安全、可追踪的控制事件。
- 完善前端协议类型、严格解析、状态归一化和生命周期清理。
- 新增或接线计划预览、步骤状态、工具调用和证据校验 UI。
- 显示当前请求的加载、完成、部分完成、失败和取消状态。
- 若 D03 的取消动作已有完整后端契约但前端缺少入口，则增加“停止生成”按钮。
- 单元、组件、协议、集成、浏览器和显式保护的真实 API E2E 测试。
- 更新与实际契约直接相关的开发文档和安全示例。
- 独立 Issue、分支、提交、PR、自审、CI 修复和合并。

### 6.2 Out of Scope

- D05 报告模式 SSE 与轮询回退。
- D06 Redis 幂等键、状态快照、断线恢复和重复提交治理。
- 原始 Trace 浏览器、完整 Prompt、思维链或模型内部推理展示。
- 完整工具参数、原始工具返回、数据库记录或内部堆栈展示。
- 修改工具选择策略、Skills 路由策略、记忆写入策略或报告生成业务规则。
- 新增数据库迁移、生产消息总线、多实例事件广播或跨设备历史重放。
- 改造认证、授权和现有会话身份模型。
- 为展示效果伪造计划、工具调用、证据或性能指标。

### 6.3 Unknown Until Recon / Clarification

- 现有控制帧的确切名称、载荷结构及是否已有可复用事件。
- 工具调用适合独立 `tool_status` 帧，还是作为步骤状态的类型化子结构。
- 计划和执行卡片只保留当前请求，还是随聊天历史在当前页面生命周期内保留。
- 重规划在当前代码是否存在真实触发路径；若无，应以协议/模拟集成测试验证而不伪造生产业务。
- 取消是否已有 `cancelled` 细粒度状态，还是沿用 D03 请求终态与 `skipped` 步骤组合。

## 7. Constraints

### 7.1 Hard Constraints

- 保持 D03 `chat-stream-v2` 的序列、终态、取消和错误契约兼容。
- 控制事件必须来自后端权威执行阶段；前端只做投影和渲染。
- `plan_preview` 只能来自已通过校验的计划。
- 所有面向客户端的内容必须经过显式安全投影或白名单序列化。
- 禁止输出密钥、令牌、认证头、Cookie、完整用户隐私数据、原始 Prompt、思维链、完整工具参数/结果和内部异常堆栈。
- 默认测试不得调用付费模型或生产服务；真实调用必须有显式环境开关、超时和数量上限。
- 不改动 D04 范围外的 Skills、记忆、报告、认证和持久化行为。
- 不提交真实 `.env`、凭据、运行日志或含敏感载荷的测试产物。
- 不引入与现有技术栈不一致的新生产依赖，除非 Recon 和方案权衡证明必要。

### 7.2 Compatibility Constraints

- 旧客户端遇到未知新增控制帧时不得导致服务端失败。
- 新客户端必须继续处理既有文本、错误、终态、Skills 确认、记忆和上下文事件。
- 缺少可选控制帧时，最终文本聊天仍能正常工作。
- 并发请求和多会话状态不能串线；所有控制帧继续携带可关联的请求与会话标识。

### 7.3 Financial Correctness Constraints

- 工具状态不能在工具实际成功前显示成功。
- 证据充分性不能由前端或“工具调用数量”推断。
- 部分证据、过期数据或工具失败必须在摘要和最终回答限制中保持一致。
- 展示层不得把过程状态包装为投资建议确定性结论。

## 8. Stakeholders and Consumers

- End user: 需要理解 Agent 正在做什么、为什么等待以及结论受哪些证据限制。
- Interviewer / reviewer: 需要从代码和运行效果验证“受控、可观测、可解释”不是只存在于文档。
- Frontend: 消费稳定、类型化、脱敏的流式控制契约。
- Backend workflow: 在权威状态转换点发布事件。
- Tool and evidence layers: 提供真实执行状态与验证结论，不承担 UI 拼装。
- QA / evaluator: 使用确定性测试和有限真实调用验证事件顺序、状态一致性和视觉行为。
- Operations: 通过 `request_id` / `session_id` / `run_id` 和稳定错误码定位问题，同时不记录敏感载荷。

## 9. Engineering Quality Requirements

### 9.1 Architecture and Ownership

- 后端协议模型、事件投影、工作流事件发布和传输适配必须职责分离。
- 前端协议类型、Socket 副作用、状态管理和展示组件必须职责分离。
- 不允许在路由或页面组件中堆叠规划、证据判断或工具业务规则。
- 使用现有模块和模式；避免另建重复的状态机或第二套事件总线。

### 9.2 Types and Documentation

- 所有新增公共 Python/TypeScript 接口必须显式类型化。
- Python 公共类、函数、路由、服务和工作流节点按仓库语言规范补齐 Google-style docstring。
- 非显然状态转换、脱敏、安全边界和兼容逻辑使用简短意图注释。
- 协议字段说明业务语义、允许值、隐私级别和失败语义。

### 9.3 Configuration and Secrets

- 新增运行配置必须进入统一 Settings 或前端统一配置入口，不得散落读取环境变量。
- 如真实 E2E 需要模型或 Tushare 凭据，只读取本地环境变量，日志和断言不得回显凭据。
- 仓库只提交安全的示例配置说明，不提交可用密钥。

### 9.4 Observability

- 重要事件保留 `stage`、`request_id` / `run_id`、`session_id`、`sequence`、`status`、`elapsed_ms`（适用时）、稳定错误码。
- 服务端日志记录事件类型和状态，不记录完整计划参数、工具载荷或模型内容。
- 前端调试信息默认不向普通用户暴露内部堆栈和敏感对象。

### 9.5 Validation and Failure Semantics

- 服务端在发帧前校验事件模型并执行安全投影。
- 客户端严格解析已知事件；畸形事件必须隔离并产生可诊断错误，不能污染 Store。
- 重复、乱序或过期事件的行为必须确定且可测试。
- 不可恢复错误使用稳定错误码；可降级失败使用 `PARTIAL` 或等价明确状态，不能静默转为空成功。

## 10. Acceptance and Test Standard

### 10.1 Functional Acceptance Cases

#### D04-C01 Normal Multi-step Execution

- 输入一个真实需要检索与分析的金融问题。
- UI 在工具执行前或开始时展示已校验计划。
- 每一步按实际执行更新状态。
- 工具调用卡片显示安全摘要和结果状态。
- Evidence Verifier 完成后显示证据摘要。
- 最终文本继续流式输出并正常结束。

#### D04-C02 Parallel or Out-of-order Step Updates

- 对存在并行或交错事件的测试流，Store 按稳定步骤 ID 更新对应项。
- 不因数组位置或到达顺序更新错误步骤。
- 重复帧不产生重复卡片或错误回退。

#### D04-C03 Tool Failure and Partial Result

- 工具失败显示失败状态和安全错误摘要。
- 若工作流继续，任务状态明确为部分完成或受限完成。
- 证据摘要和最终回答均体现限制，不显示虚假成功。

#### D04-C04 Replan

- 新计划版本替换当前活动计划。
- 旧成功步骤保留，新步骤加入，被替换步骤标识清楚。
- 展示安全的重规划原因。

#### D04-C05 No-tool / Static / Clarification Path

- 不需要工具时不生成伪计划、伪工具或伪验证卡片。
- 需要 Skills 确认或业务澄清时，既有交互仍可完成。

#### D04-C06 Cancellation

- 用户可在流式运行中触发已有取消能力。
- UI 立即停止等待状态，并最终与服务端取消终态一致。
- 未完成步骤不显示成功，Socket 与后台任务无泄漏。

#### D04-C07 Concurrent Sessions

- 两个会话或请求的计划、步骤、工具和证据状态互不串线。
- 迟到旧事件不能覆盖新请求状态。

#### D04-C08 Existing Control-frame Compatibility

- Skills 确认、记忆命令、上下文更新、压缩、文本、错误和终态事件仍按原契约工作。

### 10.2 Automated Test Pyramid

- Backend unit tests: 事件模型校验、安全投影、状态枚举、错误码、敏感字段过滤。
- Backend workflow/integration tests: 计划通过校验后才发帧；步骤/工具/验证事件顺序；失败、重规划、取消和单一终态。
- Protocol tests: `chat-stream-v2` 新旧帧兼容、序列关联、畸形/重复/乱序处理。
- Frontend store tests: 多请求隔离、状态转换、重复帧幂等、迟到事件保护、终态清理。
- Frontend component tests: 计划、步骤、工具、证据、失败、部分完成、取消和无控制帧降级渲染。
- Browser E2E: 从用户发送消息到计划/步骤/工具/验证/最终文本的可见行为，并验证停止生成入口（如适用）。

### 10.3 Real API E2E

真实调用测试必须：

- 通过显式环境开关启用，默认测试套件跳过。
- 使用真实模型和真实 Tushare 数据源，但只执行固定、无写副作用的金融查询。
- 最多覆盖两个路径：一个正常多步骤成功路径，一个受限/失败或无需工具路径。
- 设置单次和总测试超时、调用次数上限，并记录脱敏的请求关联信息。
- 断言真实控制事件存在、顺序合法、状态与最终回答一致；不得只断言 HTTP 200 或页面有文本。
- 如果外部服务因配额、网络或认证不可用而跳过/失败，必须给出明确原因，不能伪造通过。

### 10.4 Browser Acceptance

- 在实际启动的前后端页面执行至少一个固定问题。
- 验证桌面常用宽度下卡片层级、状态颜色/文本、滚动和最终回答不互相遮挡。
- 验证窄屏不产生关键内容不可达或横向溢出。
- 验证错误摘要可读且不含内部堆栈、完整参数或密钥。

### 10.5 Regression Gates

合并前至少执行：

- 后端格式/静态检查（按仓库既有命令）。
- 后端相关测试与完整回归测试。
- 前端 lint、类型检查、单元/组件测试和生产构建。
- D03 WebSocket 流式与取消回归。
- 显式保护的 D04 真实 API E2E。
- 浏览器手工/自动验收。
- `git diff --check` 和最终变更范围审查。

若仓库已有与本次变更无关的基线失败，必须给出准确命令、证据和剩余风险；不得把新增失败归因于历史债务。

### 10.6 Success Criteria

- D04-C01 至 D04-C08 均有自动化证据或明确的运行验收记录。
- 用户可以在真实页面看到计划、步骤、工具和证据摘要，而不只是最终文本。
- 所有展示状态来自真实后端事件，与实际执行和最终答案一致。
- 默认测试确定、离线、可重复；真实测试显式保护且实际运行通过。
- 无敏感数据泄露，无 D03 及既有 Skills/记忆/上下文事件回归。
- PR CI 全绿并完成自审后合并到目标主分支。

## 11. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| 文档 Claim 与现有代码事件不一致 | 形成表面 UI，无法证明真实链路 | Recon 阶段从工作流权威节点到组件逐段取证，再冻结方案 |
| 前端自行推断步骤/证据状态 | 展示与真实执行不一致 | 后端发布权威类型事件，前端仅归一化和渲染 |
| 透传计划、工具或错误原始载荷 | 泄密、隐私与安全风险 | 白名单投影、模型校验、日志脱敏和负向测试 |
| 新事件破坏 D03 顺序或单一终态 | 重复结束、乱序或 UI 卡死 | 复用 v2 信封与 sequence，增加协议回归测试 |
| 并行与重规划导致状态覆盖 | 错误步骤或历史丢失 | 使用稳定 ID、计划版本和确定性 reducer |
| UI 信息过载 | 用户难以理解重点 | 默认摘要，按层级展示；不引入原始调试面板 |
| 真实 API 测试不稳定或昂贵 | CI 波动、成本失控 | 默认跳过、固定查询、最多两条、严格超时与调用预算 |
| 后端缺少真实重规划事件 | 为通过验收而伪造生产能力 | 生产只接真实事件；协议/状态机用确定性夹具验证，并记录能力边界 |

## 12. Open Questions and Proposed Defaults

1. 工具状态使用独立控制帧还是嵌入步骤帧？
   - Proposed default: 若现有后端已有工具级生命周期事件，使用独立 `tool_status`；否则在统一事件投影层增加独立帧，避免步骤模型承载工具详情。
2. 控制卡片是否持久化到跨刷新历史？
   - Proposed default: D04 仅保证当前页面生命周期和当前会话内展示；跨刷新恢复归入 D06 状态快照与重连恢复。
3. 是否包含“停止生成”按钮？
   - Proposed default: 包含。D03 已建立取消契约，D04 将其产品化为可见控制入口，但不新增暂停、恢复或重放。
4. 是否增加 `cancelled` 步骤枚举？
   - Proposed default: 优先复用现有协议；若现有状态模型支持无破坏扩展，则增加 `cancelled`，否则请求以取消终态结束、未完成步骤标为 `skipped`。
5. 重规划没有真实业务触发样例时如何验收？
   - Proposed default: 生产代码只绑定真实 replan 输出；用确定性工作流夹具覆盖协议与 UI，不为演示强行改变规划策略。
6. 是否展示完整 trace？
   - Proposed default: 不展示。仅显示面向用户的阶段摘要；原始 trace 和内部诊断继续留在受控日志/观测系统。
7. 是否为新增事件建立新协议版本？
   - Proposed default: 保持 `chat-stream-v2`，以向后兼容的可选类型化控制帧扩展；只有 Recon 发现破坏性字段冲突时才升级版本。

上述默认值将在 Recon 与方案权衡中用代码证据验证；如果不存在会改变产品语义或持久化边界的冲突，可按默认值继续，不额外阻塞开发。
